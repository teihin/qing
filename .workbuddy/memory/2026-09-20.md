## 修复「牌型提示」界面点击穿透（未提交）

- 现象：游戏内打开「牌型提示」后，点击界面会穿到后面的座位/操作区，界面自身不关。
- 根因：`牌型提示` 是 `panelGameView` 的子节点（根下第 21 个，全屏 750×1334，Widget 四边对齐），
  但节点上**没有任何触摸监听**（无 Button、无 BlockInputEvents、脚本也没注册），
  于是触摸命中直接落到下层 `UserInfo` 里的座位按钮 —— 那个 listener 会 swallow 掉这次触摸，
  连 `panelGameView.node` 的 `ON_POINT_DOWN`（TOUCH_END）都收不到，所以界面也不关。
- 机制（查 Creator 2.4.13 引擎源码确认）：触摸候选 listener 按**场景图 z-order 排序**派发
  （`CCEventManager._sortEventListenersOfSceneGraphPriorityDes`，降序、active 的在前），
  **与注册先后无关**。节点只要注册了任一 touch 监听就会进入候选并被 `swallowTouches` 吞掉，
  不会再传给下层。节点 `_onPostActivated(true)` 会 `eventManager.resumeTarget`，所以
  active=false 时注册的监听在激活后照常生效。
- 改法（`assets/scripts/UI/panelGameView.ts` `onLoad`，仿既有「奖池面板」写法）：
  给 `牌型提示` 注册 `TOUCH_END` → `active = false`。一次改动同时解决穿透 + 点击任意位置关闭。
  未动 prefab（纯交互逻辑，不需要 Creator 重新导入）。语法自检 0 诊断。
- 同类隐患（未处理，待主人决定）：`系统设置`/`牌局回顾`/`实时战绩`/`带入窗口` 也是全屏遮罩但只靠

## 修 Android Studio「Cannot create directory …/.gradle/8.9/fileHashes」

- 现象：AS 里 Gradle sync 失败，报 `Cannot create directory '/Volumes/SSD/qing/build/jsb-link/
  frameworks/runtime-src/proj.android-studio/.gradle/8.9/fileHashes'`。
  AS 日志 `~/Library/Logs/Google/AndroidStudio2024.3/idea.log` 14:02:16 实锤同一句。
- 根因：该工程的 `.gradle` 是**软链接** → `/private/tmp/qing-android-gradle-project-cache`。
  `/private/tmp` 会被 macOS 在**重启时清空**（当天 uptime 仅 5h50m），目标一没，软链接悬空，
  之后任何 mkdir 都失败。**每次重启必然复发**，不是偶发。
- 这套 hack 的出处：`gradlew` 第 164-168 行早前加的 `set -- --project-cache-dir /private/tmp/…`
  （注释写"项目在 exFAT 卷上"，但 `/Volumes/SSD` 现挂载为 **hfs**，注释已过时）。
  **AS 不走 gradlew**，它直接用 `<projectDir>/.gradle`，所以两边本是同一路径、一起挂。
- 根治：缓存位置换成持久目录 `/Users/yy/Library/Caches/qing-android-gradle-project-cache`；
  `rm .gradle` 后重新 `ln -s` 指过去，**同时**把 `gradlew` 的 `--project-cache-dir` 改成
  `"$HOME/Library/Caches/…"`，否则 AS 与命令行会分裂成两份缓存。`bash -n gradlew` 通过；
  `.idea/`、`tools/`、`*.command` 均无旧路径残留。AS 里点一次 Sync 即生效。
- 注意：`build/jsb-link/…` 整条路径**不被 git 跟踪**（`git ls-files` 返回空），改这里零 git 影响。
- 顺带发现（未处理）：同目录有两个 7/23 的 JVM 堆转储 `java_pid26794.hprof`(553MB)、
  `java_pid50462.hprof`(574MB)，合计约 1.1GB 占空间。

## 修 AS `:qing:packageRelease` 失败（真因：Gradle daemon 堆 512m 打爆 OOM）

- 现象：`.gradle` 悬空软链接修好后，AS 里 release 构建仍失败 ——
  `Execution failed for task ':qing:packageRelease'.` →
  `A failure occurred while executing ...PackageAndroidArtifact$IncrementalSplitterRunnable`。
- **真因不是代码/资源，是 daemon 堆不够**：daemon 用 Gradle 默认 `-Xmx512m`，release 打包
  （R8 + shrinkResources + 两个 ABI 的 APK 打包）把它撑爆。AGP 把 OOM 包成了那句看不出所以然的
  `IncrementalSplitterRunnable`。
- **铁证**：daemon 带 `-XX:+HeapDumpOnOutOfMemoryError`，OOM 时在**工程目录**落堆转储。故障当场多出
  `java_pid88442.hprof`（620MB，**14:07**，与失败同一分钟；88442 正是 AS 那个 daemon）。另有 7/23 的
  26794 / 50462 两份，且 `daemon-50462.out.log` 里 7/23 就记着**同样**的 packageRelease +
  IncrementalSplitterRunnable 失败 —— **反复发作的老毛病，不是新问题**。
- 判坑手法（可复用）：daemon 日志里**找不到** OOM 报错行（异常转发给客户端了），
  但 `<工程目录>/java_pid<daemonPid>.hprof` 的时间戳与失败时刻对齐即可定案；hprof 只在
  `+HeapDumpOnOutOfMemoryError` 下产生。
- 修法：`proj.android-studio/gradle.properties` 把注释掉的 jvmargs 换成生效的
  `org.gradle.jvmargs=-Xmx4096m -XX:MaxMetaspaceSize=1024m -XX:+HeapDumpOnOutOfMemoryError -Dfile.encoding=UTF-8`
  （本机 16GB 内存）。验证：新 daemon 日志出现 `Starting build in new daemon [memory: 4 GiB]`。
- 排查中两条被证伪的线索（记下避免重踩）：① 曾疑心 AS 的 JBR 21 与 CLI 的 Corretto 19 有差异 ——
  实测两边都能成功打包，**不是 JDK 问题**；② `buildDir` 被重定向到
  `$TMPDIR/qing-android-gradle/<name>`（根 `build.gradle` 第 24 行），该目录同样会被系统清理，
  但 Gradle 会自行重建，不致命。
- 沙箱副作用：在沙箱里跑 `--rerun` 复现时，ndk-build 的 `rm` 被拒（`Operation not permitted`），
  导致 NDK obj 目录被清空 —— **下次 AS 构建会重新编译原生库，耗时较长**，属预期。
- 遗留：三个 hprof 共约 **1.75GB** 未删（等主人确认）。

## 核实「后续会不会复发」——发现真正的复发口子

- **结论**：重启引起的（fileHashes 悬空软链接）**不会**复发；OOM **不会**复发，
  **除非在 Cocos Creator 里重新构建原生 Android 工程**。
- **口子在这**：`proj.android-studio` 是 Creator 生成的，模板位于
  `/Applications/Cocos/Creator/2.4.13/.../cocos2d-x/templates/js-template-link/frameworks/runtime-src/proj.android-studio/`。
  逐项核对过该模板是**干净原版**：`gradlew` 无 `--project-cache-dir`（0 命中）、
  `app/build.gradle` 无 `cleanReleaseAppleDouble`（0 命中）、`gradle.properties` 里那行 jvmargs
  **是注释掉的** —— **OOM 的根子就在这行**。
  → 一旦重新构建原生工程：4G 堆配置、`.gradle` 软链接、`gradlew`/两个 `build.gradle` 的 hack **全部被覆盖**，
  **OOM 原样复发**。（附带一点好转：模板无软链接，所以重建后不会再报 fileHashes 悬空 —— 缓存落回
  `<projectDir>/.gradle`，且盘已是 HFS 不是 exFAT。）
- 另两个口径：`build-templates/` 里只有 `web-mobile/splash.png`，**没有 Android 模板**；
  四个 `.command` 脚本只做热更生成/上传，**不重建原生工程** → 主人日常流程短期碰不到这个口子。
- **持久化办法**：镜像到 `build-templates/<构建输出目录名>/`。命名约定由既有文件佐证：
  `build-templates/web-mobile/splash.png` ↔ 输出目录 `build/web-mobile`，故原生 link 构建应放
  `build-templates/jsb-link/frameworks/runtime-src/proj.android-studio/`。**软链接无法靠模板复制**。
- 残余风险（已告知）：第三方「清缓存」工具若清掉 `~/Library/Caches`，软链接目标会被删 → fileHashes 报错复发。
