## 客服站线上宕机 24 天：pid 复用误判 + 无存活看门狗

- 现象：`http://154.37.155.17/chattool/` 全站 502，裸 IP 根仍 404 → Caddy 活着，后端 8893 进程没了。
- 时间线：`logs/chattool.log` 最后一条 **9-27 00:50:50**（正常 INFO，无 panic），机器 **9-28 23:06 重启**，`/var/log/cron` 里 9-28 23:06:26 确有 `CROND[1104]` 执行 `@reboot start.sh`，但服务没起来。
- 根因：`start.sh` 用「pid 文件 + `kill -0`」判断存活。重启后 `run/supervisor.pid` 里是重启前的 **1134**，该号被系统启动期其它进程复用（同机 audio=1119、xuanmanager=1157，正好夹住 1134），`kill -0` 返回成功 → 误判「已在运行」→ `exit 0`，之后再无任何拉起机制。
- 修复：① `start.sh` 存活判断改为校验 `/proc/<pid>/cmdline` 含 `supervise.sh`，并加「守护存活但健康检查不过则整体重启」分支；② `install-cron.sh` 增 `* * * * * start.sh` 存活性看门狗（日志过滤掉「已在运行」写 `logs/watchdog.log`）。
- 已上线实测：伪造 pid 文件指向 caddy(1014) → 新逻辑正确拉起（pid 8052）；`kill -9` 整个守护 → cron 22:36:01 自动恢复（pid 8151）。验收：首页 200 / 入口 JS 200 text/javascript 241924B / `/agent` 200 / health ok。
- 备份在服务器 `start.sh.bak-pidfix-20261021-223516`、`install-cron.sh.bak-20261021-223516`。本地两个脚本已改，**未提交**。
- 排坑注意：这台机器**没有 `ss` 命令**，`ss | grep 端口` 一律回 "NOT LISTENING"，会误判 MySQL 挂了。查端口用 `</dev/tcp/127.0.0.1/PORT` 或 `ps aux`。另 `pkill -9 -f ".../chattool"` 会匹配到 ssh 自己的 `bash -c` 命令行把会话杀掉（exit 255），用 `ps -C chattool` 取 pid。
