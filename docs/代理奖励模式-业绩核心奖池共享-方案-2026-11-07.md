# 代理奖励新模式（业绩 / 核心 / 奖池共享）需求分析与实施方案

日期：2026-11-07　基线：`/Volumes/SSD/qing`　范围：仅分析出方案，未改任何代码。
需求来源：代理方提交的十条需求（取消收返，改为业绩奖励 + 核心奖励 + 奖池共享）。

---

## 一、结论先说

1. **后台侧 90% 能做，而且大部分数据已经在手边**：代理整条线今日/总输赢、总贡献、代理上下级树、业绩毛/下发/净点数、发金币通道、审计、权限，XuanManager 全都有现成实现，不需要重造。
2. **真正做不了的两件事都在游戏端**：① 停掉旧的"收返"（代理红利按局返点）必须改 KBE 服务端，后台只能看不能停；② 玩家金币流水显示【补发】由旧发钱服务的工单前缀决定，后台改不了文字。
3. **第三个卡点是业绩覆盖面，而且是硬卡点**：他说的"3 万 / 60 人"只是举例，实际参与方应当是系统里**全部代理与盟主**（数量以现有代理列表为准，几十到几百都有可能）。但现有业绩报表只统计 `client_prop='True'` 的账号。**2026-11-07 实测**：全库 64 个账号、代理候选 16 人、已开通业绩 27 个（比代理还多 11 个，含普通玩家），而代理名单里只有 9 人开通 —— 名单与报表两边对不齐，后台按现状连"全员点名"都做不到。**必须服务端加全量口径，这是业绩奖励能上线的前置条件，不是可选项。**
4. **需求里"业绩点数"有歧义**，两种解法差一个量级的工作量，必须业务先拍板（见第八节第 1 问）。我推荐按现有奖池业绩的"净业绩"当点数，因为它的上下级扣减算法服务端已经实现了，直接能用。

## 四、方案设计

### 4.1 菜单位置

`游戏管理 → 业绩核心共享`（`/game/agent-rewards`），模块 id 57（56 已被代理贡献管理占用），迁移文件从 `047_agent_rewards.sql` 起。

三个 tab 共用一个"代理名单"，但各自的每日计划与发放批次独立：

```
业绩核心共享
├── 业绩奖励      （自动算点数 → 人工调 → 一键发）
├── 核心奖励      （人工填）
└── 奖池共享      （看线输赢 → 人工填）
```

页面顶部固定显示：**日期 / 计划发放总额 / 已分配 / 剩余**。剩余 ≠ 0 时"一键发放"禁用（需求③要求总额不少不多）。

### 4.2 数据表（全部建在自有 `mgr_` 库，游戏库仍只读）

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `mgr_agent_reward_member` | 三个 tab 共用的代理名单 | `agent_id`、`name`、`role`（老板/盟主/合伙人/总裁/代理）、`level`、`source`（auto/manual）、`include`（是否参与本期）、`status`、`created_by`，唯一键 `agent_id` |
| `mgr_agent_reward_sub_account` | 主子账号绑定 | `agent_id`、`sub_guuid`、`note`、`status`，唯一键 `(agent_id, sub_guuid)` |
| `mgr_agent_reward_plan` | 每日每类的计划 | `reward_date`、`kind`（performance/core/pool）、`planned_total`、`status`（draft/confirmed/paying/paid/partial/failed）、`operator` |
| `mgr_agent_reward_item` | 每个代理当天的分配明细 | `plan_id`、`agent_id`、`kind`、`gross_points`（毛，分）、`granted_points`（下发）、`net_points`（净）、`auto_amount`、`final_amount`、`adjust_reason`、`snapshot_json` |
| `mgr_agent_reward_payout` | 实际发钱流水（一个收款账号一行） | `item_id`、`payee_guuid`、`payee_type`（main/sub）、`amount`、`work_order`、`status`、`ret_code`、`cash_water_id`、`paid_at` |

要点：

- `mgr_agent_reward_item` 落**发放当时的快照**（毛/下发/净/输赢/贡献），事后服务端数据变了也不影响对账。
- `mgr_agent_reward_payout` 上建唯一索引 `(work_order)`，防重复发；`(item_id, payee_guuid)` 唯一，防子账号重复加。
- 三类奖励同一天同一代理可以各发一次，唯一键要带 `kind`，不能只按 `agent_id + date`。

### 4.2.1 名单口径（60 人只是举例，按全员来设计）

需求方明确"3 万 / 60 人"只是示例，60 应该就是系统里所有代理和盟主。所以名单不能做成"手工一个个加"，得按全量同步：

- **来源**：`GET /api/game/agents` 的候选口径已经覆盖老板（`sm_role LIKE '%老板%'`）、盟主（`sm_bigAgentID` 自指）、合伙人（`sm_supperAgentID` 自指）、总裁（`sm_chiefAgentID` 自指）、`sm_level > 0` 的普通代理。直接复用，不要另写一套 SQL。
- **翻页**：该接口每页上限 100，服务端内部循环拉到 `total` 为止；不要指望一次请求拿全。
- **去重**：`agentSelectSQL` 关联 `third_marketing_info` 会出现同一账号多行，必须按 `sm_guuid` 合并；否则一个多身份的账号会在名单里出现两三次，**分摊时重复发钱**。
- **一人多身份**：优先按 `role` 归一类（老板 > 总裁 > 合伙人 > 盟主 > 代理），同时保留 `level`，供"核心奖励看规模"用；绝不允许拆成多行。
- **同步策略**：每天首次打开页面时自动同步一次（新增的进名单、脱离代理的标 `status=inactive` 但**不物理删除**，保住历史账）。手工增删只作为例外修补。
- **规模**：名单几百人时，表格必须分页 + 支持按 ID/昵称/身份筛选；分摊与发放在后端按批次处理，不要一次渲染几百个输入框。
- **是否含 BOSS 与无俱乐部代理**：要业务定。BOSS 通常自己也拿一份；无俱乐部的代理拿不到线输赢数据（见 4.7），但业绩点数仍可能有。

### 4.2.2 排除与名单增删（业务明确要求）

需求原话是"可以通过 ID 添加或删除"，且"设置排除就要把这些人删除出去"。含义要落成两条明确规则，否则会跟每日自动同步打架：

**规则一：排除 = 从本期名单移除，但保留历史账**

- 排除后：该代理不出现在本栏的发放列表里、不参与分摊、不能被打款。
- 但 `mgr_agent_reward_item` 的历史记录一条不动（已发过的是既成事实），只把名单状态置为 `excluded`。
- 已排除的人若当天已经有 `paid` 记录 → **拒绝排除**，提示"已发放，先作废批次再排除"，防止账实不符。

**规则二：排除要能压住自动同步**

这是最容易踩的坑：如果只是把行删掉，第二天全量同步又会把人加回来。所以排除必须是**独立的一张抑制表**，而不是删行：

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `mgr_agent_reward_exclude` | 排除名单，同步时跳过 | `agent_id`、`kind`（performance/core/pool/all）、`reason`（必填）、`operator`、`created_at`，唯一键 `(agent_id, kind)` |

- 自动同步时：命中排除表的账号**不写入名单**；手工"恢复"就删掉这条排除记录，下次同步自然回来。
- **按栏独立**：三种奖励的参与人本来就可能不同（比如某人只拿核心不拿业绩），所以 `kind` 要支持分栏排除，另外留 `all` 表示"任何人任何奖都不发"（离职、封号、跑路代理用这个）。
- 排除必须填原因、进审计，页面上有"已排除"折叠区可查可恢复，不能是黑盒。

**规则三：手工添加的人不能被同步清掉**

- 名单里 `source=manual` 的行，即使已不在代理候选 SQL 结果里，也保留不删（业务可能就是要给某个已降级的老代理发钱）。
- 同步只做两件事：补新出现的代理、把已脱离代理体系且非 manual 的标 `inactive`。**永远不物理删除。**

**页面交互**：名单行右侧提供「排除」按钮 → 弹窗填原因 → 确认后该行从当前列表消失，顶部提示"已排除 N 人，可在已排除列表恢复"。批量勾选支持批量排除。

### 4.3 业绩奖励算法（需求第三条）

**取数**：调用 `异步_查询_奖池业绩_结算报表`（date = 当天或昨天），拿 `proxy_performance`（净点数）作为分母基础。**不做任何二次扣减**——上下级扣除是服务端的活，后台再减一次就变成重复扣。

**分摊**：

```
Σ 点数 = Σ proxy_performance（只算净点数 > 0 的代理）
每人金额 = floor(计划总额 × 本人点数 / Σ点数)
尾差 = 计划总额 − Σ每人金额
按小数余数从大到小补 1 金币，余数相同按点数降序、再按 agent_id 升序
```

补尾差必须**可复现**（同一天同样的输入永远得到同样的结果），方便客服对账和事后复核。

**人工调整**：允许改 `final_amount`，但保存与发放两个时点都要校验 `Σ final_amount == planned_total`。前端实时显示"还差 N / 超了 N"，差额不为 0 不允许确认。

**关键限制（全员参与时这是唯一阻塞点）**：现有报表只返回 `client_prop='True'` 的账号。2026-11-07 实测开通 27 个（含 18 个非代理账号），而 16 个代理里只有 9 个在报表中，另外 7 个点数取不到。三条路：

1. **服务端给报表加 `all_agents=1` 参数**（推荐）：业绩按代理链全员计算，`client_prop` 只保留"控制客户端入口显示"的作用。后台一次取全，改动最小。
2. **后台批量开通 `client_prop`**：能立刻让全量代理进报表，但会带来两个副作用 —— ① 每个代理客户端都会冒出"业绩比例 / 业绩下发"入口，而新模式是平台统一发放，不需要代理自助申请返款，等于多暴露一个界面；② 上级的点数会被自动扣走，若业务只想让平台掌握分配额，代理端看到的就是一堆变动数字。**除非确认客户端入口可以接受，否则不建议。**
3. **服务端新增一个专用命令**（如 `异步_查询_代理_业绩点数`）：只返回 `agent_id + 毛点 + 下发 + 净点`，不碰客户端任何显示。改动比方案 1 稍大，但最干净。

**点数 0 的人怎么处理（已定：不保底）**：业务确认**按真实点数来，不做保底**。因此：

- 参与者 = `净点数 > 0` 的代理；点数为 0 的人金额就是 0，不占分母（点数是 0，本来也不影响分母），表格里保留一行并标注"0 点 · 不参与"。
- **金额为 0 的人不产生发放流水、不调发钱接口**。否则几百个 0 元 exchange 既刷屏又留下无意义工单，对账时还得一条条排除。
- 页面不出现"保底/人均"之类按钮，避免客服误用；如果以后要做保底，那是新增规则，不是配置项。

### 4.4 核心奖励、奖池共享（需求第四、五条）

- **核心奖励**：纯人工。表格预填上次金额（"相对固定"的要求），客服改数字，总额校验同上。建议加"沿用上次"按钮，省得每天重填几十上百行。
- **奖池共享**：每行显示 `team_raw.today_score`（整条线今日输赢，单位积分）和 `total_score`、`total_contrib_fen`（÷100 为元），客服按输赢手动填。表格可按今日输赢排序，方便判断。
- 两类都支持"批量按比例预填"（按输赢或按上次金额分摊总额），客服再微调——比纯手填几十行现实得多，需求没提但实际必需。
- 三类奖励共用同一套排除规则：被排除的代理在三栏里都不出现（分栏排除只影响对应栏）；金额填 0 的行不落发放流水。

### 4.5 主账号 / 子账号（需求第七条）

- 名单行内提供"绑定子账号"：输入 guuid → 校验存在 → 保存。
- 分配金额时，该代理出现"主账号 / 子账号 1 / 子账号 2"三个输入框，默认全给主账号。
- 校验：`Σ(主 + 各子) == 该代理 final_amount`，不等不让确认。
- 发放时：一个收款账号一笔 exchange，**各自独立 work_order**（`JL` + 日期 + 类型 + 代理 + 序号），避免旧服务按工单去重时把第二笔吞掉。
- 账本按"代理"汇总、按"收款账号"明细，两个口径都出：汇总时只算代理一次（防重复统计），明细里主/子分开显示（需求第十一条）。

### 4.6 发放流程与状态机

```
草稿(draft) → 已确认(confirmed) → 发放中(paying) → 已发放(paid)
                                      ↓
                                部分成功(partial) → 重试 / 作废
```

- **确认**：锁快照（写 `snapshot_json`），校验总额、名单完整性、子账号合计。确认后不允许再改金额，要改先作废重来。
- **发放**：串行逐笔调 exchange（同一时间只跑一个批次，进程内加锁），每笔写回读余额核对（现有加减分已这么做）。单笔失败不中断，记录 `ret_code` 和错误，最后汇总成 partial。
- **重试**：重试前必须先用 `work_order` 查 `third_cash_info` / `usr_cash_water` 判断是否已到账，确认未到账才补发。**不要盲目重发**——旧服务的幂等性没有文档保证。
- **作废**：只允许对未发放或完全失败的行作废，作废留审计。

### 4.7 代理数据查看（需求第八条）

在名单行点"查看线数据"→ 弹窗复用代理贡献管理页的树：上级链（到 BOSS）+ 当前节点 + 逐层下级，每行带今日/总输赢、总贡献、人数。底部给三个大字：**今日输赢 / 总输赢 / 总贡献**，客服扫一眼就能判断该给多少。

数据来源直接调 `异步_查询_代理_展示数据`（team_raw），不用切 Boss 号。

**限制**：这些数据是**俱乐部口径**（`club_member_score_info`），必须传 `club_id`。代理若不属于任何俱乐部、或线里成员分散在多个俱乐部，取到的是"该俱乐部内这条线"，不是全局。这一点需求方大概率没意识到，方案里要让客服看到"数据范围：俱乐部 XXX"，并在无俱乐部时明确显示"无俱乐部数据"，不能显示 0。

### 4.8 记账与对账（需求第十一条）

- 发放成功的每一笔落 `mgr_agent_reward_payout`，天然可按日期、类型、代理、收款账号查询。
- **账单页**：选起止日期（默认近 10 天，支持 15 天/整月快捷）→ 按代理汇总三类金额与合计 → 顶部显示平台期间总发放。行内可展开看到每日明细和主/子账号明细。
- **导出 CSV**：两个视图 —— ① 按代理汇总（对账给代理看）；② 按发放流水（财务核账用，含 work_order，可与游戏流水 `usr_cash_water` 逐笔勾对）。
- **结算周期**：不引入"结算"概念，只做区间查询与导出。需求说"每 10 天/15 天/一个月结算一次"，本质是拉一段账单，不需要新状态。
- 账本**只增不改**：金额调整只体现在 item 的 `auto_amount / final_amount / adjust_reason`，不覆盖历史。

### 4.9 权限与审计（需求没提，必须有）

| 权限码 | 作用 | 建议角色 |
| --- | --- | --- |
| `game.agent_reward.view` | 查看名单、数据、账本 | 客服 |
| `game.agent_reward.edit` | 设总额、填/调金额、管名单 | 客服主管 |
| `game.agent_reward.pay` | 一键发放 | 财务（与 edit 分离） |
| `game.agent_reward.configure` | 奖池业绩授权、名单自动同步开关 | 超管 |

所有写操作进 `mgr_audit_log`，发放额外记录批次号与逐笔结果。

## 五、必须游戏/服务端配合的四件事

| # | 事项 | 为什么后台做不了 | 建议改法 |
| --- | --- | --- | --- |
| G1 | **停掉收返**（代理红利按局返点） | 红利是服务端每局结算时写 `usr_income_info` 并加 `sm_hongli`，后台只读 | 服务端关掉返点结算分支；或加全局开关便于回滚 |
| G2 | **业绩全量覆盖**（业绩奖励的硬前置） | 报表只统计 `client_prop='True'`（实测 27 个，含非代理），代理名单只覆盖 9/16 人 | 优先给报表加 `all_agents=1`，业绩按代理链全员算，`client_prop` 只管客户端入口；或新增只读命令返回全员点数 |
| G3 | **流水显示【补发】** | 类型由旧发钱服务按 `work_order` 前缀映射（BF/JL/TK/CZ/HB），没有"补发" | 旧服务加前缀（如 `BFBF`/`JB`）→ 写 `option_type='补发'`；这比改 KBE 轻 |
| G4 | **跨俱乐部线路统计**（可选） | `club_member_score_info` 是俱乐部口径 | 若一老板多俱乐部需合并，服务端加"按老板聚合"口径；否则接受当前口径并明确标注 |

G1 是这套方案的**成本前提**：如果服务端不停返点，后台再发三份奖励，代理拿的是"旧返点 + 新奖励"，利润只会更低。**这条不落地，整个需求没意义。**

## 六、需求没写、我建议一定补上的

1. **幂等**：同一天同一代理同一类型只能有一个有效分配；一个收款账号只能有一笔成功流水（唯一索引 + 工单号）。
2. **发放前二次确认**：显示"本次将发放 X 人 / 共 Y 金币 / 涉及 Z 个子账号"，防止误点。
3. **单人上限**：单代理单日 ≤ 某个阈值（可配置），超阈值需超管二次确认——防内部人一次刷走大量金币。
4. **不给"负数/零"发放**：净点数为 0 的代理仍可留在名单（记录用），但默认不分配。
5. **奖池共享与输赢的符号**：输赢是代理线整体口径，正数是玩家整体输（平台赚）还是赢，要先跟业务对齐文案，别让客服看反了。
6. **调整原因必填**：任何手动改动的金额都要留一句原因，否则对账时说不清。
7. **发放时间窗**：建议固定"次日发放前一日"，避免当天数据还在变时按错误点数分钱（尤其业绩点数依赖服务端内存态）。
8. **名单自动同步**：手工按 ID 加容易漏人。建议每天早上按代理列表自动补全名单，手工只做增删例外。
9. **停发开关**：某个代理异常（被封、跑路）能一键从名单停发，不影响其他人。
10. **历史收返数据保留只读**：切除旧模式后，红利流水页不要删，留作对比和客诉核查。
11. **旧红利余额处置**：取消收返后代理红利账户里的历史余额是否清零、能否提取，必须业务先定，否则会有一波提现纠纷。
12. **预算看板**：每天三类奖励实发合计 + 当月累计，和平台当日抽水做对比，让老板能看到成本率有没有真降下来。这条最能验证"提高利润"的目的有没有达成。

## 七、分期落地建议

| 阶段 | 内容 | 前置 |
| --- | --- | --- |
| P1（打地基） | 名单（全量自动同步 + 去重）、账本、权限、审计、代理线数据弹窗、账本查询与导出 | 无，可先做 |
| P2（核心 + 奖池共享） | 两个手动 tab 全流程：设总额 → 填 → 校验 → 发放 → 记账 | 需 G3（流水显示补发）确认，否则流水显示"奖励/补分" |
| P3（业绩奖励） | 报表取数 + 全员分摊 + 尾差 + 调整 | **必须 G2 完成**，否则只有已授权代理能参与，全员名单形同虚设 |
| P4（收返下线） | 关闭旧返点，观察成本与代理反应 | 需 G1，且旧红利余额处置方案已定 |

P2 可以先用 P1 的账本跑起来，业绩那一栏先只读展示"毛/下发/净"，让客服熟悉口径，等 G2 好了再开放自动分摊。

## 八、需要业务方拍板的五件事

1. **"业绩点数"到底是什么？**
   - A：就是现有奖池业绩的净业绩金额（分）—— 服务端已有、上下级扣减已实现，**推荐**。
   - B：一个长期固定的份额（上级 2 点、下级 1.8 点），跟当天流水无关 —— 需要另建配置体系，且要服务端改业绩归属计算，工作量大得多。
2. **参与范围到底覆盖谁**：老板 / 盟主 / 合伙人 / 总裁 / 普通代理是否全进名单？BOSS 自己拿不拿一份？（"不保底、按真实点数"已确认，不用再问）
3. **排除的适用范围**：分栏独立排除（推荐，我按这个设计）还是全局一排除就三种奖都不发？被封号、离职、跑路的代理是否统一走 `all`？
4. **奖池共享的"输赢"看谁**：整条线（含下级）还是只看自己 + 直属？现在 `team_raw` 是整条线。
5. **旧收返什么时候停、历史红利余额怎么处理**（见 G1 与建议 11）。

## 九、风险

- **R1 口径重复**：如果服务端已经给某代理发了返点，后台又按"业绩"发一份，等于双份成本。上线前必须核对"业绩点数"里有没有已经包含返点过的部分。
- **R2 数据跨源对不上**：业绩（提留分）、输赢（积分）、贡献（分）三种单位混在一张表，前端口径写错就会让客服按错误数字发钱。方案里每个字段都要带单位标注。
- **R3 当天数据不稳**：业绩报表的链判定依赖服务端内存中已加载的代理，当天取数可能少算。建议业绩默认按"次日发前一日"，且发放前刷新一次重新取数比对，差异超阈值则拦截。
- **R4 俱乐部口径（已实测证实）**：16 个代理里只有 4 个有线数据，12 个为空（含拥有 8 个下级的 BOSS 648425）。"奖池共享"对这 12 人没有任何判断依据。要么服务端补"按老板/全站聚合"口径（G4），要么明确奖池共享只对 4 个人发。
- **R5 批量发放的半途失败**：几十上百人发到一半挂了，容易重复补发。必须靠工单号回查 + 状态机，不允许"拍脑袋重发"。
- **R6 一人多身份重复发**：全量名单里同一账号可能既是老板又是盟主（`agentSelectSQL` 关联注册表还会出多行）。名单必须按 `sm_guuid` 去重，分摊与发放在 `agent_id` 上做唯一约束，否则一个人发两次以上。
- **R7 发放接口压力**：全员名单意味着一天可能几百笔 exchange 串行调用。单笔 6 秒超时，最坏情况整批十几分钟。必须做成后台任务 + 进度条 + 可中断续发，不能挂在一次 HTTP 请求里。
- **R8 金额放大**：参与人数从"报表里的 9 个"扩到 16 个代理全量后，同样的计划总额被摊薄，单个代理到手金额会明显低于以前的"净÷2"。上线前要跟代理沟通预期，否则会集体反弹。
- **R9 先发后排除**：客服先发完再想把某人排除，会造成"名单里没有他、账上有他"。规则上已禁止对已发放行排除，但仍要提供"当日已发放名单"视图，避免客服以为没发。
- **R10 排除被同步覆盖**：若实现时把"排除"做成删行而不是独立的抑制表，第二天自动同步会把人全部加回来，等于白做。这是本需求最容易写错的一处。
