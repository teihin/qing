# 「强制同步带入钻石」后台按俱乐部/联盟开关 —— 方案

- 日期：2026-11-25
- 状态：**仅方案，未改任何代码**
- 关联现状：`docs/memory/handoffs/2026-11-10-club-seat-stone-ratio.md`、`docs/暗抽开关-后台按联盟或俱乐部授权-方案-2026-11-12.md`

## 1. 需求

后台对**指定俱乐部**或**指定联盟**提供「强制同步带入钻石」开关（默认关闭）。
打开后：该俱乐部创建房间规则时，「同步带入钻石」自动打开且用户不能关闭。

## 2. 结论（推荐）

**存储直接复用游戏库哈希表 `kbedm.usr_hash_info`，与「暗抽_俱乐部_<clubId>」完全同构：**

| 项 | 取值 |
| --- | --- |
| hash_key | `强制入座扣钻_俱乐部_<clubId>` |
| hash_content | `"1"` / `"0"` |
| 缺行 / 空 / 非法 | **按关闭处理**（满足"后台默认关闭"） |
| 联盟开关 | 写联盟总群主俱乐部（`kbedm.club_union_info.club_guuid`）的同一个 key |
| 权限 | 沿用 54（俱乐部）/ 55（联盟）模块，新增两个 code |

理由（按重要性排序）：

1. **零新增协议、零新增游戏服命令**。客户端已有 `ConfigManager.GetOneHashKey()` + `查询_哈希_信息`，`UserHashInfo` 推送通道现成，暗抽已经跑通同一条路。
2. **后台不用碰游戏业务表**。`usr_hash_info` 后台可直接读写（`club_dark_setting.go` 已有成熟的「快照 → 写 → 回读校验 → 失败按 id 恢复」实现，MyISAM 无事务）。
3. **客户端打开弹窗时就能拿到状态**，不需要等 `ClubPlayList` 推送带新字段，旧规则列表也不受影响。
4. 联盟/俱乐部两套入口可共用一套读写函数，后台改造量 ≈ 复制暗抽那份（约 400 行）。

不采用「后台新建 `mgr_club_seat_stone_force` 表」的原因：服务端要新增加载/缓存/失效逻辑，客户端要么新增推送字段要么新增查询命令，等于把暗抽已经解决过的问题重做一遍；收益只是"表更像后台的东西"，不划算。

## 3. 存储层

### 3.1 数据形态

```sql
-- 示例（无需 DDL，usr_hash_info 已存在）
INSERT INTO kbedm.usr_hash_info (hash_key, hash_content)
VALUES ('强制入座扣钻_俱乐部_820084', '1');
```

- 客户端只读**自己当前俱乐部**的 key（`resolveRoomClubId(account)` 得到的那一个），不需要知道联盟 ID。
- 入盟俱乐部的玩法由联盟总群主俱乐部配置（与暗抽同一业务约定），所以联盟开关写 owner club key 即可被客户端读到；后台俱乐部页对已入盟俱乐部拒绝单独开关，提示去联盟页操作。
- 值语义统一为 `1` 开 / `0` 关；解析时兼容 `true/on/开`，其余一律关闭。

### 3.2 开关与现有比例的关系

「是否扣钻」由比例 `usr_hash_info['俱乐部积分对应钻石输赢比']` 决定：比例 `0` 时即使强制开启也不扣钻石。
后台弹窗必须显示当前比例；比例为 0 时红字提示"当前兑换比例为 0，强制开启不会实际扣钻"，但**不阻止保存**（避免运营被卡住，比例可能在另一页配置）。

## 4. 生效链路（三层，缺一层就能被绕过）

| 层 | 位置 | 行为 |
| --- | --- | --- |
| ① 客户端 UI | `panelGameSettings.ts` 创建规则弹窗 | 读到 `1` → `createSeatStone = true`；开关显示为"开"且置灰不可点；说明文案改为"运营已为该俱乐部强制开启，不可关闭" |
| ② 服务端创建规则 | 游戏服 `创建_俱乐部_玩法` | 读到 `1` → 忽略客户端传值，直接把 `入座扣钻` 写入 `club_room_play_info.special_rule`（改包也绕不过去） |
| ③ 服务端建房 | 游戏服 `BuildClubPlayRoomSetting` | 读到 `1` → 无论规则里有没有，都把 `入座扣钻` 追加进房间 `special_rule` |

第 ③ 层是关键：**存量规则也能生效**。`BuildClubPlayRoomSetting` 本来就是"按规则拼房间模板"，在这一步兜底，老规则新开的房间立刻带钻，不需要运营逐条删了重建。已有房间不追溯（房间模板在开房时固化），关房重开即生效。

> 服务端代码不在本仓库。上述 ②③ 的落点按 `docs/memory/handoffs/2026-11-10-club-seat-stone-ratio.md` 记录的 `club_room_play_info.special_rule` + `BuildClubPlayRoomSetting` 推导，需游戏服确认读取方式（按需读库还是启动缓存）。

## 5. 后台改造清单（XuanManager）

### 5.1 迁移 `server/migrations/076_club_seat_stone_force.sql`

  (54, 'game.club.seat_stone_force', '强制带入钻石', 'seat_stone_force',

  (55, 'game.union.seat_stone_force', '强制带入钻石', 'seat_stone_force',

### 5.2 后端 `server/internal/api/club_seat_stone_force.go`（新增）

- 复用 `club_dark_setting.go` 中的 `loadHashSettingRows` / `restoreHashSettingRows` / `writeClub*`，把前缀参数化（或新增 `writeHashSetting(ctx, key, enabled)` 通用函数，暗抽改为调用它，行为不变）。
- 端点：
  - `PUT /api/game/clubs/{clubId}/seat-stone-force`
  - `PUT /api/game/unions/{unionId}/seat-stone-force`
- 请求体与暗抽一致：`{enabled, expectedEnabled, note, confirm}`；防空转、防并发覆盖（`expectedEnabled` 不符返 409）、原因 2–120 字、`confirm=true`。
- 审计：`game.club.seat_stone_force.update` / `game.union.seat_stone_force.update`。
- 响应：`{scope, targetId, ownerClubId?, enabled, verified, message}`。
- 列表/详情补字段 `seatStoneForceEnabled`：批量读 `kbedm.usr_hash_info`，一次 `IN (...)`，与 `readClubDarkSettings` 同写法。

### 5.3 前端

- `web/src/components/SeatStoneForceModal.tsx`（新增，结构照 `DarkSettingModal.tsx`）：标题「俱乐部/联盟「X」的强制带入钻石」、当前状态 → 保存后、原因必填、确认勾选。
- 弹窗内新增一行展示「当前兑换比例 1 积分 = X 钻」；为 0 时红字警告。比例取 `/api/configuration/club-seat-stone-ratio` 现有读接口。
- 俱乐部详情/联盟详情页在「暗抽设置」旁加「强制带入钻石」按钮，列表加一列状态徽标；已入盟俱乐部按暗抽同样规则禁用并提示去联盟页。
- 文案明确写清：**开关只影响之后创建/开出的房间；已开着的房间需关房重开；关闭开关不会摘掉已有规则里的「入座扣钻」**。

## 6. 客户端改造清单（本仓库）

`assets/scripts/UI/panelGameSettings.ts`：

- 新增常量 `SEAT_STONE_FORCE_HASH_PREFIX = "强制入座扣钻_俱乐部_"`、`SEAT_STONE_FORCE_CONTEXT_PREFIX = "强制带入钻石_"`、超时 5 秒。
- 新增字段 `seatStoneForced: boolean`、`seatStoneForceClubId/Context/PendingAt`。
- `openCreateDialog()` 里与 `requestDarkState(true)` 并排调用 `requestSeatStoneForce(true)`（两个 key 两次查询，互不影响）。
- `onUserHashInfo` 里增加分支：key/context 命中强制 key → `applySeatStoneForced(value)`；`onUserHashError` / 超时按"未强制"处理（失败放行，服务端仍会兜底，不会漏扣）。
- `applySeatStoneForced(on)`：`on` 时 `createSeatStone = true`，并把节点开关设为不可交互（`cc.Button.interactable = false`、`opacity = 110`），说明文案替换为强制提示；`off` 时恢复原状与比例文案。
- `toggleCreateSeatStone()` 入口直接 `if (this.seatStoneForced) { setCreateHint("该俱乐部已强制带入钻石，不可关闭"); return; }`。
- `submitCreate()` 保留现有逻辑即可，但改为 `if (this.createSeatStone || this.seatStoneForced)` 传 `special_rule`，防止状态未到位的窗口期漏传。
- `refreshSeatStoneRow()` 文案优先级：强制 > 比例正常 > 比例 0 红字。

退出/切俱乐部：与暗抽一致，`clubId` 变化时先回到"未强制"，避免 A 俱乐部状态带到 B。

## 7. 上线顺序

1. **游戏服**：读开关 → `创建_俱乐部_玩法` 强制写入 → `BuildClubPlayRoomSetting` 兜底 → 重启/加载。
2. **后台**：076 迁移 → 后端二进制 → 前端静态包（按 `xuanmanager-timezone-and-deploy` 流程发布正式 8891）。
3. **客户端**：Creator 导入 → 构建/热更。

客户端先上、后台没开关时，读不到 key 一律按关闭，行为与现在完全一致，无兼容风险。

## 8. 验证清单

1. 测试服写入 `强制入座扣钻_俱乐部_<测试club>` = `1`，用该俱乐部群主账号打开「游戏设置 → 创建规则」：开关自动为开、点不动、有强制文案。
2. 提交创建，查 `club_room_play_info.special_rule` 含 `入座扣钻`。
3. 删改客户端传值（不带 special_rule）后重试：服务端仍写入 `入座扣钻`。
4. 用一条**没带** `入座扣钻` 的存量规则等自动补房：新房 `roomSetting.special_rule` 含 `入座扣钻`，带入窗口出现「钻石余额」行。
5. 后台关闭开关 → 客户端重开弹窗恢复可切换；已建规则与新开房间是否仍带钻，按第 ③ 层口径确认（建议保持带钻，避免中途改口径）。
6. 联盟：联盟页开关写 owner club key，跨俱乐部验证客户端读取；后台俱乐部页对入盟俱乐部正确拒绝。

## 9. 风险与待决

- **比例 0**：强制打开但不扣钻，需弹窗提示；是否要"比例为 0 时不允许开启"需运营拍板（建议允许 + 警告）。
- **联盟归属**：客户端只读自己 clubId 的 key，若群主账号持多个俱乐部、且创建规则时选中的不是 owner club，则 UI 不会显示强制。彻底解法是 `ClubPlayList` 下发 `seat_stone_forced` 字段（服务端按 club+union 算好），可作为二期。
- **缓存时效**：若游戏服对 `usr_hash_info` 是启动加载缓存，后台改完需重启才生效 —— 暗抽上线时就留了这个未决点，本次需先按暗抽的现网验证结论确认；客户端侧每次打开弹窗都补拉，不受影响。
- **不可逆**：后台关闭开关后，已有规则里的 `入座扣钻` 不会被自动摘除（与暗抽一致），弹窗文案必须写清，避免运营误判。
- **审计与误操作**：沿用"原因必填 + 确认勾选 + 状态冲突 409"，强制开关影响真金白银，不能做成一键静默切换。
