# 代理奖励：联盟独立发放账户设计与当前发放修复方案

日期：2026-11-09　范围：XuanManager 代理奖励（业绩 / 核心 / 奖池共享）　状态：设计稿，未改代码

## 0.0 已确认口径（2026-11-09）

| 决策 | 结论 |
| --- | --- |
| 资金来源 | **平台预算注资联盟账户**：平台先给每个联盟发放账户注资，发放从账户扣，联盟只做分账 |
| 账户粒度 | **每个联盟一个**；未入盟的独立俱乐部单独绑平台账户或俱乐部账户 |
| 落地节奏 | **先修 bug，再做账户**：阶段 0 先让现有发放可信，账户方案随后实施 |
| 500 万上限 | **预检阻止 + 待发重试**：发放前拦住并写明原因，不产生 0 元假流水；余额降下来后可重试 |

## 0. 结论摘要

1. **当前发放确实执行了，不是“完全没发”。** 线上 `mgr_agent_reward_payout`、`kbedm.third_cash_info`、`kbedm.usr_cash_water` 三张表能对上：大多数收款账号已加金币并写了“补分”流水。
2. **两类真实失败导致“显示成功但没到账”：**
   - **500 万金币上限**：旧发钱通道对 `sm_gold` 已到 5,000,000 的账号直接加 0，但仍返回 `ret_code=512`、`third_cash_info.status=完成`，只写一条 `add_money=0` 的补分流水。后台回读发现差额会标 `mismatch`，但前端提示和计划状态没有把它算进“异常”。
   - **重复发放判定过粗**：重新分摊后金额从 100 改成 125，发放时按“收款账号已发过”整笔跳过，`paid=0 / skipped=1`，而计划状态仍可能落 `paid`，页面提示“发放完成：0 笔”，也没有新的发放流水。
3. **“平台直接印金币”是事实。** 现有发放只调用旧 exchange 正向加金币，没有资金来源账户、没有出账流水，跨联盟无法分账。
4. **建议分三段走（已确认）：**
   - 阶段 0（先做）：修上限预检、重复发放、状态与提示、账单和联盟标签。
   - 阶段 1（不等游戏服）：**每个联盟一个专用金币账户，平台预算注资**；发放从联盟账户出账，后台建联盟资金账本。
   - 阶段 2（需 KBE 排期）：游戏服新增“联盟奖励资金账户 + 原子发放命令”，取消普通账号 500 万上限，这是终态。
5. **资金口径已定**：平台预算注资联盟账户；联盟不承担成本，只做分账；平台通过注资和账户余额控制发行总量。

## 3. 设计目标与原则

1. **每个联盟（大联盟）有独立发放资金账户**；未入盟的独立俱乐部可单独绑账户或走平台账户。
2. 发放时**先从对应账户出账，再给收款账号入账**；账户余额、出账流水、入账流水、计划/代理/日期/类型都能单独统计。
3. **成功必须有余额回读证据**；没有证据只能标“待核/异常”，不得显示成功。
4. **游戏服是资金权威**；后台只做编排、账本和对账，不直接改游戏库表。
5. **幂等、可恢复**：任何一步失败都能定位到工单，允许补发或退回，不产生双发。
6. **不改收款方式**：代理主账号/子账号仍是最终收款人；联盟账户只是出资方。

### 4.1 方案对比（已选 B，A/C 保留作备选）

| | A. 联盟额度池 `union_quota` | B. 联盟独立金币账户（已选） | C. 联盟红利 `owner_bonus` |
| --- | --- | --- | --- |

### 4.2 三类奖励的资金归属

已确认：三类奖励都从**联盟账户**出，平台预算注资。奖池共享暂不直接扣奖池池，避免同一笔钱被“奖池”和“联盟账户”重复计账；如果后续要改成奖池直扣，再把奖池共享切到 `fund_source=jackpot`，联盟账户只做分配统计。

| 奖励类型 | 默认出资方 | 说明 |
| --- | --- | --- |
| 业绩奖励 | 联盟账户 | 平台预算注资，联盟只做分配 |
| 核心奖励 | 联盟账户 | 同上 |
| 奖池共享 | 联盟账户（暂） | 后续可选：改为奖池池直扣，需新增奖池发放命令 |

### 4.3 已确认的实施路线

- **阶段 0（现在）**：不改资金模型，只修 P0/P1，让现有发放可信。
- **阶段 1（1 周内，不改 KBE）**：每个联盟一个专用金币账户（普通游戏账号），平台预算通过 exchange 注资；发放先从联盟账户出账，再给收款账号入账；后台建 `mgr_reward_fund_*` 账本和按联盟报表。受普通账号 500 万上限约束，预算分批注资。
- **阶段 2（KBE 排期）**：游戏服新增联盟奖励资金账户和原子发放命令，取消 500 万上限、支持专用流水类型；后台账本不变，只换出账适配器。

mgr_reward_fund_ledger (
  id,
  account_id,

### 5.3 发放明细扩展

`mgr_agent_reward_payout` 增加：

- `union_id`、`club_id`：归属，用于分联盟统计（子账号跟随代理的联盟，不跟随子账号自身）。
- `fund_account_id`、`fund_source`：这笔钱从哪个账户出。
- `debit_order`、`debit_status`：出账工单与状态。
- `block_reason`：上限、余额不足、账号不存在等阻止原因。

### 5.4 计划扩展

`mgr_agent_reward_plan` 增加 `fund_owner_type`、`fund_owner_id`，允许一个计划按联盟拆成多个发放批次；或保持一计划多联盟，在发放时按 `union_id` 分组。

## 6. 发放流程（阶段 1：联盟专用金币账户）

```
1. 预检（不调用游戏）
   - 计划总额 = 明细合计
   - 每个收款账号存在、未被禁用
   - 收款账号当前金币 + 本次金额 ≤ 通道上限（默认 5,000,000）
   - 代理/子账号本次应付金额 > 0
   - 按 union_id/club_id 归集，检查对应联盟账户余额
   - 检查是否已发过、已发金额与本次金额是否一致
2. 锁定资金账户（后台互斥 + 账户级锁）
3. 出账：从联盟账户扣减本次该联盟的发放合计
   - 阶段 1：对联盟专用账号调用 exchange 负数，回读余额确认减少
   - 阶段 2：KBE 原子扣减/转账
   - 写 mgr_reward_fund_ledger(out, pending)
4. 入账：逐收款账号加金币
   - 工单唯一：BF + 日期 + 联盟码 + 类型 + 序号
   - 写 payout(pending)，再调用 exchange
   - 读回余额，增加额 = 本次金额才置 paid
5. 结算
   - 全部入账成功：ledger(out) = done，计划 paid
   - 部分失败：未入账部分退回联盟账户（正向补偿），计划 partial
   - 出账成功但进程中断：恢复任务按 ledger/payout 状态继续入账或退回
6. 对账
   - 联盟账户：期初 + 注资 - 发放 = 期末
   - 游戏侧：third_cash_info / usr_cash_water 逐笔核对
```

### 6.1 幂等与补差

- 出账、入账各自唯一工单；`mgr_agent_reward_payout.uk_order` 防重复入账。
- **已发金额比较**：同一计划同一收款账号，本次金额 = 已发金额 → 跳过并明确提示；本次 > 已发 → 只对差额生成新工单（补差），或要求新建批次；本次 < 已发 → 拒绝并提示“已发金额大于当前分配”。
- 任何“跳过”都要写入账单/返回结果，不能静默。

### 6.2 500 万上限策略

- 预检阶段直接阻止，不调用 exchange，避免产生 0 元假流水。
- 失败原因写明：“账号金币 5,000,000，已到旧发钱通道上限；请让账号先消耗金币、改发子账号或联系游戏服提额。”
- 支持“待发”状态：账号余额降到上限以下后可重试；重试沿用同一计划/工单规则，不双发。
- 根治要游戏服确认 500 万是配置还是硬编码；如果是配置，提高到业务可接受值；如果是硬编码，需要 KBE/旧服务改动。

### 阶段 0：发放可信化（建议立即）

## 9. 风险与未验证

1. **500 万上限来源未拿到源码**：从“4 个账号卡在 5,000,000、请求 2431 落 0 元补分”推断是旧发钱通道截断，需游戏服确认是配置项还是硬编码。联盟专用账号同样受此限制。
2. **阶段 1 两步非原子**：出账成功、入账中断时依赖补偿和恢复任务；旧 exchange 虽有 `work_order`，幂等性没有文档保证，必须写后回读并按工单核对，不允许盲目重发。
3. **专用账号管理**：联盟账户是普通游戏账号，需要注册、保管密码、限制登录；会出现在玩家列表/交易查询里，运营口径要提前约定。
4. **平台预算仍是发行**：平台注资那一步仍然在发行金币，只是把发行集中到“注资”并可按联盟审计；需要注资审批和单联盟预算上限，否则账目清楚了但总量仍可能失控。
5. **奖池共享暂不扣奖池**：当前方案从联盟账户出，奖池池本身不减少，奖池账与实际发放仍不完全闭合；要闭合需阶段 2 的奖池扣减命令。
6. **流水文案**：玩家侧仍会显示“补分”而不是“联盟奖励”，除非旧服务/KBE 增加前缀映射。
7. 本文所有线上数据为 2026-11-09 只读查询结果；未做任何发放、扣款或配置变更。
