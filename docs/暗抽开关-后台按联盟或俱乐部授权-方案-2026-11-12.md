# 暗抽开关（后台按联盟/俱乐部授权）改造方案

> 日期：2026-11-12  
> 状态：方案评审，未改代码  
> 范围：游戏客户端大厅「开房 → 游戏设置」、游戏服（KBE）、XuanManager 运营后台
>
> **2026-11-12 补充**：用户提出用 `usr_hash_info` 的 `暗抽_俱乐部_<id>` 键替代 DDL/新命令。评估见 §10。结论：可行，建议先做最小验证；客户端用现有 `查询_哈希_信息`（`ConfigManager.GetOneHashKey`）读，后台直接读写 `usr_hash_info`（`设置_哈希_信息` 也是 Account 命令，`/hall/command` 调不到）。若 KBE 接受在既有创建/结算逻辑里读同一个键，优先采用 Hash 方案，§4 的 DDL 和新命令可省略。若 KBE 完全不能改，则 Hash 只能做界面隐藏，不能作为权限/收益开关。

## 1. 需求拆解

1. 默认关闭：所有俱乐部/联盟的「开房 → 游戏设置 → 创建规则」里的暗抽整项默认不显示。
2. 平台后台授权：运营在 XuanManager 的「俱乐部管理」或「联盟管理」里，对指定俱乐部或联盟勾选开启暗抽。
3. 只有被授权的俱乐部/联盟，客户端才显示暗抽设置。
4. 服务端必须是最终权限方：客户端隐藏不能代替服务端拒绝；关闭状态下旧客户端即使提交非 0 暗抽，也不能生效。
5. 关闭状态不能出现“界面看不到、结算仍在扣”的暗抽。

## 3. 推荐总体设计

新增一个“暗抽总开关”，按俱乐部和联盟各存一份，服务端计算某个俱乐部当前是否可用暗抽。

```text
俱乐部开关（club_guuid_info.dark_enabled）
联盟开关（club_union_info.dark_enabled）
        │
        └─ 某个俱乐部当前是否可用 = 本俱乐部开关 || 所属联盟开关（OR，待确认）
```

推荐 OR 语义：

- 未入盟的俱乐部：只受本俱乐部开关控制。
- 已入盟的俱乐部：联盟开关打开时全部成员俱乐部跟随打开；某个成员俱乐部也可单独打开自己的开关。
- 开房玩法仍只允许联盟总群主俱乐部/独立俱乐部群主配置，沿用现有权限，不因开关改变。

数据下发只走一个既有通道：`ClubPlayList` 增加顶层 `dark_enabled`。客户端打开游戏设置时本来就会请求/接收这个推送，不需要新增客户端查询命令。

服务端同时做两层强制：

1. `创建_俱乐部_玩法`：开关关闭时，`dark_percent` 必须为 0；非 0 直接拒绝。
2. 结算/房间生效路径：开关关闭时，实际暗抽按 0 处理，不能只靠界面隐藏。

## 4. 游戏服（KBE）改造

### 4.1 存储

推荐在游戏库加两列，由游戏服命令维护：

```sql
ALTER TABLE kbedm.club_guuid_info
  ADD COLUMN dark_enabled TINYINT(1) NOT NULL DEFAULT 0;

ALTER TABLE kbedm.club_union_info
  ADD COLUMN dark_enabled TINYINT(1) NOT NULL DEFAULT 0;
```

默认 0，保证上线后所有俱乐部/联盟默认隐藏。

> 备选：不改业务表，使用 `kbedm.usr_hash_info` 的按实体键（如 `俱乐部暗抽开关:<club_id>`、`联盟暗抽开关:<union_id>`）。优点是零 DDL；缺点是游戏服仍要新增读取/缓存路径，且后台列表聚合不如列直观。除非游戏服明确不愿改表，否则推荐上面的列方案。

### 4.2 新增后台命令

建议新增两个仅后台/boss 可调的命令。XuanManager 的 `/hall/command` 调用方按 boss 处理，与 `设置_俱乐部_代理_红利暗抽` 同级。

**设置**

```json
{
  "header": "设置_俱乐部_暗抽开关",
  "scope": "club",
  "target_id": "820084",
  "enabled": 1,
  "context": "xuan:club-dark:820084"
}
```

- `scope`：`club` / `union`
- `target_id`：俱乐部 ID 或联盟 ID
- `enabled`：`0/1`
- 成功：最终 `onHallCommand` 回 `0x200`，`result` 返回 `{scope, target_id, enabled}`。
- 失败：`0x301` + `俱乐部不存在` / `联盟不存在` / `权限不足` / `参数错误`。
- 命令内部要同时更新数据库和内存中的 `Hall.clubs` / `Hall.club_unions`，保证不重启即生效。

**查询（用于后台回读）**

```json
{
  "header": "查询_俱乐部_暗抽开关",
  "scope": "club",
  "target_id": "820084",
  "context": "xuan:club-dark:read:820084"
}
```

返回 `{scope, target_id, enabled}`。如果游戏服已有等价的俱乐部/联盟详情查询能带回该字段，也可以不新增查询命令，由后台读库回读。

### 4.3 `ClubPlayList` 增加开关字段

在现有推送顶层增加：

```json
{
  "ClubPlayList": [ ... ],
  "club_id": "820084",
  "dark_enabled": 1,
  "context": "ctx_play_01"
}
```

- `dark_enabled`：该 `club_id` 当前有效值（俱乐部 OR 联盟）。
- `club_id`：建议一并下发，客户端可以用它校验推送是否对应当前俱乐部；不加也能靠现有 `rulesClubId` 兜底。
- 玩法数组字段不变；`dark_percent` 仍返回存储值，客户端在开关关闭时自行隐藏。
- 只在有权限的查询/创建/删除回包里下发，不向普通成员暴露。

### 4.4 `创建_俱乐部_玩法` 增加校验

- 取当前俱乐部的有效 `dark_enabled`。
- `dark_enabled=0` 且 `dark_percent != 0`：返回 `0x301`，错误文案建议 `暗抽未开启`。
- `dark_enabled=0` 且 `dark_percent=0`：允许创建。
- `dark_enabled=1`：保持现有 `0~water_rate` 校验。

旧客户端仍会显示暗抽输入框；关闭状态下旧客户端提交非 0 会收到明确错误，不会静默扣钱。

### 4.5 关闭状态下的生效口径（关键）

必须明确“关闭”是停止生效，而不只是隐藏界面。推荐：

- 已有玩法配置里的 `dark_percent` 保留原值，不删除。
- 开关关闭期间，房间默认暗抽和代理覆盖暗抽在结算/生效路径上一律按 0 处理。
- 重新开启后，原有配置恢复生效。
- 后台关闭弹窗明确提示：“关闭后该联盟/俱乐部所有暗抽立即停止生效，重新开启后恢复原有配置。”

如果产品希望关闭时永久清零，需要在后台增加“同时清零现有规则”的二次确认，并由游戏服批量把该俱乐部/联盟下 `dark_percent` 写 0；不建议默认这样做。

### 4.6 代理暗扣（成员设置）是否同受总开关控制

这是本方案最大的口径点。当前客户端还有一处暗抽入口：俱乐部成员列表 → 玩家信息 → 成员设置 →「暗扣」，走 `设置_俱乐部_代理_暗抽`，见 `assets/scripts/UI/ClubManagementView.ts:1230-1282`。

如果本开关定位为“暗抽总开关”，则服务端还需要：

- `设置_俱乐部_代理_暗抽` 在开关关闭时返回 `暗抽未开启`。
- 结算时的代理覆盖值在开关关闭时按 0 处理，否则会出现“开房页看不到暗抽、成员暗扣仍在扣”的情况。
- `查询_俱乐部_信息` 或成员列表回包增加 `dark_enabled`，客户端据此隐藏成员设置里的「暗扣」行。

如果本开关只控制开房页的“房间默认暗抽”，则成员设置的暗扣保持独立；但这种情况下界面隐藏了默认值，代理覆盖仍可能生效，不建议。

## 6. 游戏客户端改造

### 6.1 状态与数据

`panelGameSettings.ts` 增加：

- `private darkEnabled: boolean = false;`
- `onClubPlayList` 解析 `dark_enabled`（兼容 `0/1`、`"0"/"1"`、`true/false`），缺省 false。
- 收到推送后：
  - 更新 `darkEnabled`
  - 如果创建规则弹窗正开着，调用 `refreshCreateDialog()` 同步显隐
  - 重新 `renderRules()` 处理规则行
- 如果推送带 `club_id`，与 `rulesClubId` 不一致时忽略；旧服务端不带 `club_id` 时保持现有判断。

### 6.2 创建规则弹窗

- `openCreateDialog()`：`createDark` 固定从 0 开始；按 `darkEnabled` 决定是否显示暗抽区。
- `refreshCreateDialog()`：调用统一的 `syncDarkSection()`。
- `syncDarkSection()`：
  - 开关关闭：把第 2.1 节列出的 12 个节点 `active=false`，`createDark=0`，跳过暗抽数值/快捷 Chip 刷新。
  - 开关打开：恢复节点显示和原布局。
  - 防重复调用，避免每次刷新重复位移。
- `onButtonClick()`：`darkEnabled=false` 时，`暗抽加/暗抽减/暗抽快捷_*` 直接忽略。
- `submitCreate()`：`dark_percent: this.darkEnabled ? this.createDark : 0`。
- 默认值：首次进入、尚未收到推送时按关闭处理，避免先闪一下再隐藏；收到推送后再决定是否显示。

### 6.3 规则列表与删除弹窗

- `fillRuleRow()`：
  - `darkEnabled=false`：隐藏 `row.getChildByName("暗抽")`；抽水 Chip 可移到中间，避免右侧留空。
  - `darkEnabled=true`：恢复暗抽 Chip 和「暗抽 X% · 仅创建者」。
- `showDeleteDialog()`：
  - `darkEnabled=false`：摘要只拼「抽水 X% · N 个房间」。
  - `darkEnabled=true`：保持原文案。

### 6.4 关闭后的布局收紧

当前创建规则弹窗是 702×1080 的固定面板，暗抽区大约占 y=-36 到 -188：

- 暗抽标题/说明/右侧：y=-36
- 加减/数值：y=-88
- 快捷 Chip：y=-150
- 提示：y=-188
- 下方：同步带入钻石行 -238、自动信息 -318、创建提示 -372、房费提示 -410、按钮 -480

只隐藏节点会留下约 200px 空洞，不建议。推荐两种做法，二选一：

1. **整体收紧（推荐）**：关闭时把下方节点整体上移约 172px，同时把顶部组下移约 86px，内容重新居中；面板保持 1080。需要在 Creator 里按 1334/1624 两档核对无压叠。
2. **缩小面板**：关闭时把面板高度从 1080 调到约 900，所有内容重新居中；需要同步更新面板 Widget 和九宫格尺寸，风险略高。

最终坐标以 Creator 实际效果为准；代码只负责按开关设置预设坐标，不在运行时批量创建节点或改 SpriteFrame。

### 6.5 成员设置暗扣（待确认）

如果第 4.6 节决定“总开关同时管代理暗扣”，客户端还需要：

- `查询_俱乐部_信息` 或成员列表回包增加 `dark_enabled`。
- `panelMain.ts:382-399` 构造 `ClubManagementView` 上下文时带上该字段。
- `ClubManagementView.syncDarkRow()` 在开关关闭时隐藏「暗扣」行，见 `ClubManagementView.ts:1268-1282`。
- `设置_俱乐部_代理_暗抽` 服务端拒绝关闭状态下的设置。

## 7. 发布顺序与验证

## 10. 备选方案评估：Hash 键（用户 2026-11-12 提出）

### 10.1 结论

**可行，而且比 §4 的 DDL + 新命令方案轻**：把开关做成 `usr_hash_info` 的普通配置。客户端用现有 `查询_哈希_信息`（`ConfigManager.GetOneHashKey`）读；后台直接读写 `usr_hash_info`（`设置_哈希_信息` 是 Account 命令，后台 `/hall/command` 调不到）。不新增 KBE 接口、不改表、不改 `ClubPlayList`。

> 上一版 §10.4 误写成了 `获取_大厅_配置数据` / `设置_大厅_配置数据`；那是大厅配置命令，不是哈希读取。以本节为准。

但它只解决“存、读、显示”。要满足“服务器权威”，KBE 仍必须在**既有** `创建_俱乐部_玩法`（以及需要时的结算路径）里读同一个键。否则只是界面开关：旧客户端或改过的客户端仍能创建暗抽规则，关闭状态也可能继续扣钱。

所以先确认“不用 KBE 加接口”的范围：

- 指“不新增命令、不改表”：这个方案满足。
- 指“KBE 一行都不改”：不满足，只能做界面隐藏，不能作为权限/收益开关。

### 10.2 建议键设计

```text
暗抽_俱乐部_<clubId>   = "1" / "0"
暗抽_联盟_<unionId>    = "1" / "0"   （可选，见 10.3）
```

- 缺失、空串、`"0"`、非 `1` 一律按关闭处理。
- 不建议用 `暗抽_<id>`：俱乐部 ID 和联盟 ID 都是 6 位数字时可能撞键，必须带类型前缀。
- 值统一写字符串 `"1"` / `"0"`；客户端兼容 `1`、`"1"`、`true`、`"True"`，后台回读也按同一套归一化。
- `usr_hash_info.hash_key` **没有唯一索引**（见 `俱乐部实时房奖池-客户端与后台接口文档.md` §5.5），可能出现同 key 多行：
  - 读取取最新 `id` 的一行；
  - 写入更新同 key 的所有行（或先清重复再写）；
  - 上线前跑一次 `暗抽_%` 去重自检。

### 10.3 联盟怎么处理

两种做法，按开关范围选：

**A. 只控制开房页的房间默认暗抽（推荐先做）**

- 客户端只读 `暗抽_俱乐部_<当前 clubId>`，不需要知道联盟 ID。
- 联盟页开启时，写联盟总群主俱乐部的键：`club_union_info.club_guuid`（后台列表已有 `ownerClubId`）。
- V2 本来就只有联盟总群主俱乐部能配置玩法，所以“联盟开关”落到 owner 俱乐部键上语义成立。
- 风险：联盟总群主换俱乐部时，旧键要清、新键要补；后台联盟设置里要提示或做迁移。

**B. 联盟开关要覆盖成员俱乐部的代理暗扣（可选）**

- 增加 `暗抽_联盟_<unionId>`；客户端先拿 `union_id`（可复用 `查询_俱乐部_信息`），再同时查俱乐部键和联盟键，任一为 1 就显示。
- KBE 的 `创建_俱乐部_玩法` / 结算 / `设置_俱乐部_代理_暗抽` 要同时检查两个键。
- 好处：联盟统一控制所有成员俱乐部，不受 owner 俱乐部变更影响；代价是客户端多一次查询、KBE 多一处键拼接。

### 10.4 读写通道

**客户端读：`查询_哈希_信息`**

客户端应走已有的哈希接口，而不是大厅配置命令：

```ts
// ConfigManager.GetOneHashKey 内部发：
// {"header":"查询_哈希_信息","key":"暗抽_俱乐部_820084","context":"暗抽开关_820084"}
ConfigManager.getInstance().GetOneHashKey("暗抽_俱乐部_820084", "暗抽开关_820084");
```

- `GetOneHashKey` 走 `reqAccountCommand`，见 `assets/scripts/logic/ConfigManager.ts:288-293`。
- 结果不在同步回包里，服务端另推：

```json
{"UserHashInfo":{"key":"暗抽_俱乐部_820084","context":"暗抽开关_820084","content":"1"}}
```

- 查不到行时推：

```json
{"UserHashError":{"context":"暗抽开关_820084"}}
```

- `panelGameSettings` 应注册 `UserHashInfo` 和 `UserHashError`，按 key/context 匹配；或在 `ConfigManager.OnUserHashInfo` 里对未知 key 统一 fire 一个事件（推荐，避免每个面板重复解析），见 `ConfigManager.ts:299-337`。
- `content` 是原始字符串：`"1"` = 显示；`"0"` / 空 / 缺行 = 隐藏。不需要 base64 解码；如果后台写入时做了编码，客户端再兼容。
- 每次打开创建规则弹窗重新拉一次即可，保证后台刚改能生效；本 panel 会话内可缓存，按 clubId 区分。
- 缺键走 `UserHashError`，必须按“关闭”处理，不能弹错误提示。

**后台写：直接写 `usr_hash_info`**

`设置_哈希_信息` 也是 Account 命令，后台 HTTP `/hall/command` **调不到**；后台只能直接读写 `kbedm.usr_hash_info`，或走已有管理页。参考现有实现：

- `XuanManager/server/internal/api/stone_consume_price.go`（消费钻石价格）
- `XuanManager/server/internal/api/club_seat_stone_ratio.go`（入场比例）
- `XuanManager/server/internal/api/promotion_download_url.go`（下载 url）

流程按这些页的既有模式：读前值 → 写 → 回读 → 失败恢复 → 审计。

- 同 key 多行：`hash_key` 没有唯一索引，先 `SELECT id, hash_content ... ORDER BY id`；更新同 key 的所有行或插入一行；读取取最新 `id`；上线前去重。
- 写后回读 DB 确认值；**游戏服侧 `查询_哈希_信息` 是否立即看到新键必须实测**（见 10.7）。
- 如果实测发现“运行时新建的 key 必须重启 baseapp 才可见”，改用单 key JSON 列表方案（见 10.7 第 2 条），不要给每个俱乐部在运行时新建 key。

**后台列表展示**

- 不需要每行调游戏服；直接只读 `kbedm.usr_hash_info`，按当前页的 ID 批量查：

```sql
SELECT hash_key, hash_content
FROM kbedm.usr_hash_info
WHERE hash_key IN ('暗抽_俱乐部_820084', ...)
ORDER BY id DESC;
```

- 同 key 多行取最新 `id`；列表显示 `开启/关闭`，联盟页显示 owner 俱乐部键（或联盟键，取决于 10.3 选型）。
- 列表读库只用于展示；写入后的权威确认以 DB 回读为准，客户端可见性以游戏服 `查询_哈希_信息` 为准。

### 10.5 KBE 需要的最小改动

这不是新增接口，而是既有命令/逻辑里的读取判断：

1. `创建_俱乐部_玩法`：读 `暗抽_俱乐部_<club_id>`（如果采用 10.3-B，再读 `暗抽_联盟_<union_id>`）；关闭时 `dark_percent != 0` 返回 `0x301`，文案 `暗抽未开启`。
2. 结算/生效路径：关闭时暗抽按 0；如果玩法配置在创建房间时快照，要明确“只影响新房”还是“即时停止”。要即时停止，就在结算时读当前键。
3. 代理暗扣（如果纳入总开关）：`设置_俱乐部_代理_暗抽` 关闭时拒绝；结算忽略代理覆盖。
4. 读取失败/键缺失按关闭处理，不能按开启兜底。

| 项 | DDL + 新命令方案（§4-§6） | Hash 方案 |
| --- | --- | --- |
| 游戏库表结构 | 加两列 | 不加列 |
| KBE 新命令 | 设置/查询两个命令 | 不加命令 |

### 10.7 风险清单

1. **KBE 不改就只是 UI 开关**：不能满足“关闭后不能再设/不能再扣”。
2. **运行时新建 key 的可见性**：`查询_哈希_信息` 是按需读库，还是读 baseapp 启动时加载的哈希缓存？如果是后者，后台新插入的 `暗抽_俱乐部_<id>` 可能重启后才可见。`消费钻石价格` 已知有约 10 秒缓存，但那是价目表服务自己的缓存，不能直接推断所有 key。
   - 先按 10.8 实测。
   - 若必须重启才可见，改用**单 key JSON 列表**：部署时预建一行 `暗抽开关`（空 JSON），后台只更新这一行的内容，客户端读同一个 key 判断 clubId 是否在列表里。这样 key 在启动时已存在，避免运行期新建 key 的缓存问题。
3. **键是约定不是 schema**：拼错、大小写、值格式、重复行都会造成“后台开了但前端不显示”；必须统一常量、后台回读、上线自检。
4. **`usr_hash_info` 是 MyISAM、无唯一索引**：并发写/历史重复要处理，不能假设只有一行。
5. **联盟语义偏弱**：owner 俱乐部键在换 owner 时需要迁移；要覆盖成员俱乐部就得加联盟键并让客户端查 `union_id`。
6. **后台不能调 `设置_哈希_信息`**：只能直接写 `usr_hash_info`；要注意缓存、并发、写失败恢复和审计，不能依赖游戏服命令的即时回读。
7. **客户端事件串扰**：`UserHashInfo` 有多个监听者（`ConfigManager`、`panelMain`、`panelHongli`、`panelManager`、`panelQianBao`、`panelPaihangbang`、`panelGivePad`）。目前它们都按 `context` 分支，未知 context 不处理；新增 `暗抽开关_<clubId>` context 后仍要逐个确认，不能假设所有监听者都只处理自己的 key。
8. **`UserHashError` 必须按关闭处理**：缺 key 是正常状态，不能弹“查询失败”。
9. **默认关闭的发布风险**：和 §7.1 一样，发版前要盘点现有 `dark_percent > 0` 的俱乐部/联盟，先写键再发客户端。

### 10.8 建议的验证顺序（不改业务代码）

1. 在测试服 `usr_hash_info` 插入三条测试数据：
   - `暗抽_俱乐部_<测试club>` = `"1"`
   - `暗抽_俱乐部_<另一个club>` = `"0"`
   - 不插入第三条，用于验证缺行。
2. 用目标俱乐部群主账号在客户端调用 `ConfigManager.GetOneHashKey`（可临时在面板里加一行调试，或用现有调试入口），确认：
   - `"1"` 收到 `UserHashInfo.content = "1"`；
   - `"0"` 收到 `"0"`；
   - 缺行收到 `UserHashError`；
   - 修改 value 后客户端重新查询是否能立即看到（不重启 baseapp）。
3. 如果第 2 步发现新 key 必须重启才可见，改用单 key JSON 列表方案并重新验证。
4. 确认 KBE 的 `创建_俱乐部_玩法` 能读到同一个键（服务端本地调试或日志）。
5. 三项都通过后，按 Hash 方案实施；任何一项不通过，退回 §4 的 DDL + 命令方案。

### 10.9 推荐

- **P0**：先按 10.8 做最小验证。通过后采用 Hash 方案：客户端用 `ConfigManager.GetOneHashKey`（`查询_哈希_信息`）读 `暗抽_俱乐部_<clubId>`；后台直接读写 `usr_hash_info`；联盟页写 owner 俱乐部键，客户端只读俱乐部键。
- **P0 备选**：如果实测发现运行期新建 key 必须重启才可见，改用预建的单 key `暗抽开关` + JSON 列表，客户端读同一 key 判断自己的 clubId 是否在列表里。
- **P1**：如果产品要求联盟开关同时控制成员俱乐部（含代理暗扣），再加 `暗抽_联盟_<unionId>` 并让客户端/KBE 同时检查两个键。
- **不建议**：KBE 完全不动、只靠客户端隐藏。这样后台的“关闭”挡不住旧客户端或改客户端，收益口径不可控。
