# 谷歌验证（TOTP 两步验证）接入方案

- 日期：2026-11-12
- 范围：XuanManager 运营后台登录、ChatTool 客服系统登录
- 状态：**方案待评审，未改任何代码 / 数据库 / Prefab**
- 结论：两套系统结构高度相似（Go 标准库 + MySQL `webcm` + HttpOnly Cookie + DB 会话 + 单点登录），可以按同一套设计分别落地；建议先做「基础设施 + 自愿绑定」，跑稳后再打开强制开关。

---

## 1. 目标与边界

### 要做的

1. 账号密码通过后，再校验 6 位动态口令（Google Authenticator / Microsoft Authenticator / 1Password 等标准 TOTP，RFC 6238）。
2. 已登录用户可自助绑定、解绑、重新生成恢复码。
3. 管理员可查看绑定状态、重置他人绑定。
4. 提供一次性恢复码，防止手机丢失后彻底锁死。
5. 支持灰度：默认不强制，可切换为「未绑定禁止登录」。

### 不做的（本期）

- 短信 / 邮箱验证码、硬件密钥（WebAuthn）、设备信任（记住本机 30 天）。
- 高风险操作的二次口令确认（如重置他人密码、提现），可作为第二阶段。
- 统一两套系统的账号体系（目前 `mgr_user` 与 `chat_agent` 完全独立）。

### 2.3 对方案的直接影响

1. **不能在密码通过时立刻下发 Cookie**：必须插入一个"待验证"阶段，否则 2FA 形同虚设。
2. **密码通过时也不能踢掉旧会话**：若在待验证阶段就 `DELETE` 旧会话，攻击者只要知道密码就能把正常用户踢下线。旧会话必须在 TOTP 通过后才被替换。
3. **两端都限制未知 JSON 字段**：不要往原登录请求里加 `totpCode`，改用独立的校验接口，避免老前端多传字段直接 400。
4. **两端都是 HttpOnly Cookie + DB 会话**，不需要引入 JWT、Redis 或新框架。
5. **两端都跑在纯 HTTP 上**（`154.37.155.17`）：TOTP 只能防密码泄露/撞库，防不了链路窃听；HTTPS 需要单独立项。

## 3. 总体设计

### 3.1 登录改为两阶段（核心）

```
[1] POST /auth/login  账号 + 密码
      ├─ 密码错 / 锁定            → 401（与现在一致）
      ├─ 未开启 2FA               → 200 + Set-Cookie（与现在完全一致）
      └─ 已开启 2FA               → 200 { totpRequired:true, challengeToken, expiresIn:300 }
                                    不下发 Cookie、不建会话、不动旧会话

[2] POST /auth/login/totp  challengeToken + code（或恢复码）
      ├─ 失败                     → 401，本次 challenge 尝试次数 +1
      ├─ 尝试超限 / 过期 / 已用    → 401 CHALLENGE_EXPIRED，回到第 1 步
      └─ 成功                     → 复用现有"建会话"逻辑 + Set-Cookie → 登录完成
```

**挑战态（challenge）设计**

- 服务端生成 32 字节随机 token，**只把 SHA-256 落库**，明文只出现在响应体，前端放内存（不写 localStorage）。
- 有效期 5 分钟，一次性消费；同一账号产生新挑战时，旧挑战全部作废。
- 每次挑战最多 5 次尝试，超限即销毁，并要求重新输入密码。
- 挑战失败同时累加账号的登录失败计数（沿用现有 5 次 / 15 分钟锁定规则），防止 6 位码被暴力枚举。
- 落库而不是放进程内 map：两端都是单实例，但会话本来就是 DB 权威模型，重启不丢、易排查。

**TOTP 参数**

- RFC 6238，HMAC-SHA1，30 秒步长，6 位数字，允许前后各 1 个步长（±30s）。
- 防重放：记录该账号最近一次通过的步长，拒绝 `step <= lastStep` 的重复码。
- 密钥：20 字节随机 → Base32（32 字符），生成 `otpauth://totp/...` 供扫码。
- 服务端时间必须 NTP 同步；前端提示"手机时间不准会导致验证失败"。

### 3.2 绑定 / 解绑 / 恢复

**绑定（已登录状态下）**

1. 点击「安全设置 → 开启谷歌验证」，先输入一次登录密码。
2. 服务端生成密钥，返回 `otpauth://` URI + 明文密钥（仅此时返回一次），并落库为"未确认"。
3. 页面展示二维码（前端本地生成）+ 手动密钥文本。
4. 用户输入 6 位码 → `confirm` 接口校验通过后置为已启用。
5. 同时生成 **10 个一次性恢复码**，只展示这一次，可复制/下载；库里只存 SHA-256。

**解绑**

- 需要「登录密码 + 当前动态码」双因素确认。
- 解绑后清空密钥、删除恢复码、写审计；可选择同时踢掉其他会话。

### 3.2.1 验证丢失后的恢复（三层兜底）

**第一层：恢复码（用户自助，不依赖管理员）**

- 绑定成功时生成 10 个 10 位 Base32 恢复码（去掉易混淆的 `0/O/1/I`），**只展示一次**，必须勾选「我已保存」才能继续，可复制/下载。
- 库里只存 SHA-256，管理员也看不到；每个码一次性，用后写 `used_at`。
- 登录第二步点「使用恢复码」，输入时忽略大小写和空格；输错同样计入挑战尝试次数和账号失败计数。
- 恢复码也能当「当前动态码」使用：关闭验证、重新绑定、重新生成恢复码时都接受恢复码，**否则手机丢了、人还登录着，关闭验证会卡死**。
- 重绑成功后：旧密钥、旧恢复码全部作废，重新发 10 个新码。
- 剩余数量在安全设置页可见；用完后可用「密码 + 当前动态码/恢复码」重新生成一批（旧码全部作废）。

**第二层：管理员重置（用户手机和恢复码都丢了）**

- XuanManager：有 `user.reset_totp` 权限的管理员在「用户管理」页点「重置二次验证」。
- ChatTool：客服主管在「团队」弹窗里重置普通客服；主管之间不互相重置，避免互相顶掉第二因子。
- 重置动作：
  1. 必须填写原因（审计留痕），二次确认；
  2. 清空 `totp_secret` / `totp_enabled` / `totp_last_step`，删除该用户的全部恢复码；
  3. 踢掉该账号所有现有会话（含单点登录里的那一条）；
  4. 写审计：操作人、目标账号、时间、IP、原因；
  5. **若已打开强制开关，同时生成一个 10 分钟有效的一次性绑定令牌**，否则用户重置完仍然登录不了。用户凭「账号 + 密码 + 令牌」进入绑定页。
- 管理员全程看不到旧密钥，也不需要旧动态码。

**第三层：根账号 / 最后一名主管（运维兜底）**

- 不开放公开接口，只在服务器本机执行维护命令（推荐）或文档化 SQL（见 §7.3）。
- 命令行为：给指定账号发一次性绑定令牌并打印，强制开关保持开启；若选择直接清空绑定，必须同时临时关闭强制或重启服务。
- 前置条件：只有能 SSH 登录服务器的人可执行；执行前后核对审计日志，确认没有异常重置；操作写入变更记录。
- 建议至少保留两名主管/超管，且各自保存恢复码，避免同时走到这一步。

**恢复场景矩阵**

| 场景 | 用户手上有什么 | 恢复路径 |
|---|---|---|
| 换手机 / 重装验证器，人还登录着 | 有效会话 + 恢复码 | 安全设置 → 用恢复码重新绑定 |
| 手机丢失，当前未登录 | 恢复码 | 登录第二步用恢复码 → 登录后立刻重绑 |
| 手机 + 恢复码都丢了 | 无 | 联系管理员重置 → 用一次性绑定令牌重绑 |
| 管理员本人丢失，且无恢复码 | 无 | 上一级管理员重置；根账号 / 最后一名主管走运维 |
| 怀疑账号被盗、被人恶意重置 | — | 查审计 → 封禁会话 → 强制重绑 + 改密 |

**明确不做的找回方式**

- 不提供邮件 / 短信「找回验证器」：系统没有邮件短信基础设施，且会新增账号接管面。
- 不允许管理员查看、导出或代为输入 secret。
- 不允许无审计、无原因的自助重置。
- 不把运维兜底 SQL 做成 HTTP 接口。

### 3.3 强制策略（建议分三步）

| 阶段 | 行为 | 目的 |
|---|---|---|
| P1 基础设施上线 | 2FA 能力可用，但**默认不强制**，用户自愿绑定 | 不影响现有登录，零风险 |
| P2 绑定窗口（1 周） | 在用户管理/团队列表显示「已绑定 / 未绑定」；运维催办 | 让多数人先绑好 |
| P3 打开强制开关 | 未绑定账号登录直接拒绝（`TOTP_SETUP_REQUIRED`），不再签发会话 | 真正形成第二因子 |

**强制后未绑定账号怎么处理（关键安全决策）**

- 推荐（严格）：强制后不允许"密码对了就自助绑定"，否则密码泄露时攻击者可以自己绑一个验证器，等于没有 2FA。未绑定账号由管理员「发起绑定」，系统生成 10 分钟有效的一次性绑定令牌，本人凭「账号 + 密码 + 令牌」进入绑定页。
- 备选（简单）：强制后仍允许密码通过后自助绑定，只适合内部完全可信的小团队。
- 强制开关用环境变量控制，回滚只需改 env + 重启，不动数据库：XuanManager `XUAN_TOTP_ENFORCE=off|all`，ChatTool `CHAT_TOTP_ENFORCE=off|all`（后续可扩成按角色）。

### 3.4 其它安全细节

- **密钥加密落库**：不要明文存 `totp_secret`。XuanManager 直接复用 `SealCredential`；ChatTool 目前没有加密工具，需新增一个约 40 行的 AES-GCM 封装（`internal/security/seal.go`），密钥来自新环境变量 `CHAT_TOTP_KEY`（缺省从 `CHAT_PLAYER_LINK_KEY` 派生，零配置也能跑）。
- **加密密钥必须备份**：密钥一换，所有已绑定用户都要重新绑定；这一条要写进部署说明。
- **二维码本地生成**：两端 CSP 都是 `script-src 'self'`，不能引 CDN。前端加 `qrcode` npm 依赖自绘到 canvas/data-URL；同时始终显示手动密钥，防止扫码失败。
- **审计**：绑定、解绑、重置、恢复码使用、校验失败全部写现有审计表（XuanManager `mgr_audit_log`、ChatTool `chat_audit_log`），命名建议 `auth.totp.*` / `agent.totp.*`。
- **不记录敏感值**：审计只记动作和结果，绝不落明文密钥、动态码、恢复码。
- **响应不泄露**：除「未确认」状态返回一次密钥外，任何接口都不再返回 secret；列表只返回 `totpEnabled` 布尔值。

```sql
  ADD COLUMN totp_last_step BIGINT NOT NULL DEFAULT 0 AFTER totp_confirmed_at;

CREATE TABLE IF NOT EXISTS chat_agent_recovery_code (...同结构，agent_id...);
CREATE TABLE IF NOT EXISTS chat_agent_login_challenge (...同结构，agent_id...);
```

无需新增权限位：主管/本人两条路径即可覆盖。

### 4.3 向后兼容

- 新列全部可空或有默认值，旧二进制忽略新列，**可以先发迁移再发代码**。
- 老前端 + 新后端：未绑定用户响应结构不变，完全兼容；已绑定用户会被要求二步验证，因此**前端必须先于"打开强制/完成绑定"发布**。

## 7. 上线顺序、灰度与回滚

### 7.1 顺序

1. **数据库迁移**：先单独执行新迁移（新列可空，旧代码不受影响）。
2. **后端**：发布含 2FA 能力但 `ENFORCE=off` 的二进制，登录行为与现在完全一致。
3. **前端**：发布两步登录 + 安全设置 + 管理侧入口。
4. **P2 绑定窗口**：通知用户绑定，管理员看未绑定名单。
5. **P3 强制**：改 env 打开开关并重启；先小范围（如只用超管账号验证一晚）再全员。
6. **HTTPS（建议同期）**：当前两端都是纯 HTTP 且 `CookieSecure=false`，2FA 的收益会被链路窃听抵消。

### 7.2 回滚

- 首选：把 `*_TOTP_ENFORCE` 改回 `off` 并重启，所有人恢复"密码即可登录"。
- 次选：回退二进制到上一版；新列和新表不影响旧代码，无需回滚数据库。
- 单个用户被锁：管理员重置该用户绑定；根账号/最后一名主管走运维脚本。

### 7.3 运维脚本（根账号兜底）

优先提供本机维护命令（读取同样的环境变量连库），行为是「重置绑定 + 打印一次性绑定令牌」，强制开关不用关：

```bash
# XuanManager（示例，实际子命令名以实现为准）
./xuanmanager reset-totp --username admin999
# ChatTool
./chattool reset-totp --username <主管账号>
```

命令必须只在本机执行、打印审计信息、令牌 10 分钟有效且一次性；不监听 HTTP。
若没有该命令，退化为在两套系统的部署说明里执行下面这段文档化 SQL（执行前需临时关闭强制开关，执行后重启并重新打开）：

```sql
-- XuanManager 根账号 / 最后一名超管
UPDATE mgr_user SET totp_enabled=0, totp_secret=NULL, totp_confirmed_at=NULL, totp_last_step=0
WHERE username='admin999';
DELETE FROM mgr_user_recovery_code WHERE user_id=(SELECT id FROM mgr_user WHERE username='admin999');

-- ChatTool 最后一名主管
UPDATE chat_agent SET totp_enabled=0, totp_secret=NULL, totp_confirmed_at=NULL, totp_last_step=0
WHERE username='<主管账号>';
```

执行后必须记录在运维变更单里；不要把这段做成公开接口。

## 8. 测试清单

**单元测试**

- RFC 6238 官方测试向量（SHA-1）全部通过。
- 同一动态码第二次提交被拒（防重放）。
- ±30s / ±60s / 超窗口的边界。
- 恢复码只能用一次；重新生成后旧码失效。

**接口测试**

- 密码错、锁定、挑战过期、挑战超 5 次、恢复码错误、绑定未确认时登录。
- 已绑定用户在两台设备同时登录：第一台停在验证码页时，第二台完成登录 → 第一台挑战应失效（新挑战作废旧挑战），且最终只保留一个会话。
- 登录失败计数与账号锁定的联动。
- `reset_totp` 权限校验、根账号不可被他人重置。
- 解锁后旧会话清理（强制开关打开时）。

**前端验收**

- 手机扫码能被 Google Authenticator / Microsoft Authenticator 正常识别。
- 断网、刷新、返回上一步、恢复码登录、关闭验证、复制恢复码。
- 1334 / 1624 两档画布下登录页与安全弹窗不压叠（项目 UI 约束）。

**上线验收**

- 打开强制后，未绑定账号被拒绝且提示明确。
- 关闭强制后立即恢复原登录。
- 审计日志能看到绑定/解绑/失败记录，且不含明文密钥或验证码。

## 11. 实施状态（2026-11-12，仅 XuanManager）

### 已实现

- 登录两阶段、挑战落库、5 分钟有效、5 次尝试、失败计入账号锁定。
- TOTP RFC 6238（SHA-1 / 30 秒 / 6 位 / ±30 秒），密钥 AES-256-GCM 加密落库，`totp_last_step` 防重放。
- 自助绑定/确认、关闭、重新生成恢复码；恢复码 10 个、一次性、只存 SHA-256，也可用于关闭/重绑。
- 顶栏「安全」弹窗（二维码本地生成，零依赖 `qrcode-generator`）、登录页二步与倒计时。
- 管理员「重置二次验证」：`user.reset_totp` 权限，清空绑定/恢复码、踢会话、写审计；根账号与超管不可重置。
- 迁移 `057_totp.sql`；`go build/test/vet`、`npm lint/build` 通过。

### 与本文方案的差异

1. **本轮未实现强制开关**（`XUAN_TOTP_ENFORCE`）与「管理员一次性绑定令牌」。原因是强制后未绑定账号会被锁死，需要先确认 §3.3 的严格模式；当前默认行为与升级前一致，先完成自愿绑定。
2. 二维码库用 `qrcode-generator`（零运行时依赖）而不是 `qrcode`，减少 node_modules 体积与漏洞面。
3. 因未做强制，管理员重置不生成绑定令牌，只清空绑定并要求用户重新登录后自助绑定。
4. ChatTool 客服系统本轮未动，沿用同一设计另开迁移 `014`。
