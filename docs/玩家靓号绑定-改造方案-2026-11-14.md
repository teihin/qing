# 玩家靓号绑定 — 我方改造方案（XuanManager + 客户端）

> 依据：`服务器文档整理/玩家靓号绑定-后台接口文档.md`（2026-11-14 最新版，KBE 侧已实现、未建表、未部署、未重启）
> 范围：本仓库内可改的部分（XuanManager 后台、Cocos 客户端）；KBE 服务端只列交付/确认项，不在本仓库实现。
> 本文只给方案，不改代码。

## 1. 结论摘要

1. **后台是零实现**：XuanManager 目前没有任何靓号相关表、命令代理、页面或权限，需要新增一整个「靓号管理」模块。
2. **玩家管理必须改**：列表、详情、搜索都要能显示/命中 `真实ID(靓号)`，否则运营拿到靓号后无法在后台找到人。
3. **邀请码侧基本自动生效**：客户端和后台展示的 `invite_code` 本身就是 6 位码，服务端把码换成靓号后，现有展示链路不用改。
4. **客户端大概率不用新增页面/入口**，但**不能直接认定零改动**：文档没有写明「个人ID靓号」在客户端用哪个字段下发。必须先抓包确认（见 §4），再决定是“零改动”还是“改约 10 处展示点”。
5. **一个流程缺口**：邀请码靓号要求账号已是该俱乐部在职代理，但 XuanManager 目前**没有** `设置_俱乐部_代理` 的入口。需要补入口，或明确要求运营先在游戏内设代理。
6. **ChatTool/客服站是否要改，取决于 §4 的字段结论**：如果服务端把客户端可见的 `guuid` 全局替换成靓号，直聊票据、成员目录、头像查询都会拿靓号去查真实账号，必须适配。

## 2. 文档要点（只列与我方相关的）

| 项 | 内容 |
| --- | --- |
| 命令 | 4 条：`异步_添加_靓号`、`异步_查询_靓号_池`、`异步_绑定_靓号`、`异步_解绑_靓号` |
| 号池 | `usr_pretty_no_info`，6 位数字，跨 `uid`/`invite` 全局唯一 |
| 状态 | `init` 可绑 / `used` 已绑 / `disabled` 停用且**永不回收** |
| 入池 | 个人ID 从 `usr_guuid_info` 删行锁定；邀请码把 `club_invite_code_info.status` 置 `reserved`。**不可逆** |
| 绑定 | 个人ID 不限身份；邀请码必须是在职代理（或创建者），且 `club_id` 必填 |
| 解绑 | 号码转 `disabled`，不回收；邀请码解绑时若仍是有效代理会补随机码 |
| 后台展示 | 文档建议 LEFT JOIN `usr_pretty_no_info` 得到 `user_id_display`，**不要改 `user_id` 本身** |
| 后台调接口 | 必须传真实 `user_id`，服务端不对后台通道做靓号反解 |
| 分页 | KBE `page` 从 0 开始，后台页面从 1 开始，需要换算 |

## 4. 必须先和服务端确认的契约（决定客户端改不改）

文档写了“客户端不需要改协议，只是值可能变成靓号”，但**没有说明个人ID靓号通过哪个字段下发**。开工前先做一次联调抓包，用已绑定个人ID靓号的账号登录，看下面 3 个位置的值：

1. 登录后 `Account.guuid`（客户端 `GameDataManager.getAccount().guuid`）是真实 ID 还是靓号；
2. 房间 seat 的 `user_guuid` / `id` 是哪一个；
3. 俱乐部成员列表行里的 `user_id` / `guuid` 是哪一个。

据此二选一：

### 方案 A（推荐，风险低）：真实 ID 不动，新增纯展示字段

- 服务端保留 `guuid`、`user_id`、`agent_id` 等身份字段为真实 ID，另下发 `pretty_no`（或 `display_id`）只用于展示。
- 客户端只在上述 §3.2 的展示点优先取 `pretty_no`，所有命令、头像、缓存、比较仍用真实 ID。
- 老客户端忽略新字段，向后兼容；ChatTool、客服站、推广站完全不受影响。
- 代价：服务端要加字段（属于协议新增，不破坏旧字段），与文档“字段不变”的表述不同，需要服务端确认能接受。

### 方案 B（文档隐含做法）：客户端通道全局把 ID 值换成靓号

- 服务端对所有下发 ID 做替换、对所有入站命令做反解，客户端展示代码零改动。
- 必须同步确认/适配：
  - 客户端本地缓存键：`directChatToken:<guuid>`、`lastRoomClub:<guuid>`（`DirectChatManager.ts:537/771`）；
  - 直聊票据由 KB 登录服签发，ChatTool 的 `game_directory.go`、`hosting*.go` 都用 `sm_guuid = ?` 查真实账号，需要把靓号反解成真实 `sm_guuid`，否则查不到人/余额/头像；
  - 客服站头像查询 `ChatTool/server/internal/api/avatars.go:58` 同上；
  - 任何用“ID 相等”做判断的客户端逻辑（自己/他人、行归属）必须保证两边同时是靓号或同时是真实 ID。

> 建议：优先争取方案 A。若服务端已按 B 实现，则本项目要追加 ChatTool 反解适配，不能只改后台。

## 5. XuanManager 后端改造清单

### 5.1 新增 `pretty_numbers.go`（命令代理 + 号池查询）

建议路由（均走后台鉴权）：

两类靓号是两个独立入口，`{kind}` 只能是 `uid`（账号ID靓号）或 `invite`（俱乐部邀请码靓号），类型由路由决定、请求体改不了：

| 方法/路径 | 用途 | 对应 KBE |
| --- | --- | --- |
| `GET /api/game/pretty-numbers/{kind}` | 本类号池分页列表（status/keyword） | `异步_查询_靓号_池` |
| `GET /api/game/pretty-numbers/{kind}/candidates` | 本类入池前候选号查询 | 直连 kbedm 只读 |
| `POST /api/game/pretty-numbers/{kind}` | 号码入池 | `异步_添加_靓号` |
| `POST /api/game/pretty-numbers/{kind}/{prettyNo}/bind` | 绑定：`uid` 传 `userId`；`invite` 只传 `invite_code`，游戏服自行定位代理与俱乐部 | `异步_绑定_靓号` |
| `POST /api/game/pretty-numbers/{kind}/{prettyNo}/unbind` | 解绑（**2026-11-15 已关闭**，接口一律返回“解绑已关闭”，页面无入口） | `异步_解绑_靓号` |

实现要点：

- 参数校验：`kind ∈ {uid, invite}`；`prettyNo` 必须 `^\d{6}$`；`userId` 必须是真实 ID（`^\d+$`，不走靓号回填）；`kind=invite` 时 `clubId` 必填。
- 调 KBE 时 `op_name` 取当前后台登录账号，`context` 用 `pretty-YYYYMMDD-序号`；`page` 做 1→0 换算，`count` 上限 100。
- 回包：`ret_code=512` 解析 `ret_result`（字符串二次 `JSON.parse`）；`769` 把 `{"error":...}` 原样返回给前端；网络/解码失败返回 502 并写审计。
- 写操作加进程内互斥锁，防止双击重复绑定/入池。
- 审计动作：`game.pretty_no.add` / `game.pretty_no.bind` / `game.pretty_no.unbind`，记录 kind、prettyNo、目标 userId、clubId、remark、context、前后状态、成功/失败文案。
- 不要自己做“靓号映射查询”接口：玩家列表直接 JOIN。
- 候选号查询：
  - `uid`：`kbedm.usr_guuid_info` 中 `account_id = 0`；
  - `invite`：`kbedm.club_invite_code_info` 中 `status = 'init'`；
  - 统一 `NOT EXISTS` 排除已在 `usr_pretty_no_info` 的号码；
  - 前端只传结构化条件（`mode=prefix|suffix|contains` + 1–6 位数字），后端拼参数化 `LIKE`；**不要**接收原始 SQL/通配符，避免注入和全表扫失控；单次上限 50–100 条。

### 5.2 玩家列表/详情显示与搜索（`players.go` + `types.ts`）

- 主查询增加：
  ```sql
  LEFT JOIN kbedm.usr_pretty_no_info p
         ON p.user_guuid = a.sm_guuid
        AND p.kind = 'uid'
        AND p.status = 'used'
  ```
- `playerItem` 新增 `PrettyNo string \`json:"prettyNo,omitempty"\``，`user_id`/`playerId` 保持真实 ID 不变。
- 搜索：
  - `playerId` 精确筛选继续匹配真实 ID；
  - 新增 `prettyNo` 精确筛选（或让 `keyword` 同时 LIKE `p.pretty_no`），保证运营直接粘贴 888888 能搜到人；
  - 关联账号弹窗（`relations.go`）的 `PlayerRelationItem` 也带 `prettyNo`，避免同一玩家在两个页面显示不一致。
- 前端渲染统一为 `真实ID(靓号)`，所有操作仍传 `player.playerId`。

### 5.3 权限与模块（新增迁移 `064_pretty_numbers.sql`）

- 只保留一个模块挂在「游戏管理」下（`parent_id = 20`）：`code = game.pretty_numbers`，`route = /game/pretty-numbers`，名称「靓号管理」；进入后页内用两个页签切换账号ID / 俱乐部邀请码（`065` 曾拆成两个模块，`066` 已回归单菜单并把按类型权限挂回本模块）。
- 权限按类型各一套（互不串用）：
  - `game.pretty_no.uid.view` / `game.pretty_no.uid.manage`
  - `game.pretty_no.invite.view` / `game.pretty_no.invite.manage`
- 历史：064 建的合并入口 `game.pretty_numbers` 与 `game.pretty_no.view|manage` 由 065 停用并隐藏，原授权角色按类型继承。
- 授权方式照 `058/061`：按 code 关联授权，不写死 module/permission 自增 ID；默认授予总管理员角色，并给持有 `game.player.view` 的角色补 view、持有 `game.player.balance_adjust` 的角色补 manage（按实际运营角色调整）。
- 玩家列表新增的靓号展示不单独设权限，跟随 `game.player.view`。

### 5.4 「设置代理」入口（流程缺口）

邀请码靓号要求目标账号是该俱乐部在职代理，但 XuanManager 没有 `设置_俱乐部_代理` 接口。建议二选一：

- **推荐**：在靓号绑定弹窗内提供「先设为代理」的快捷操作，后端代理调用 `设置_俱乐部_代理`（`club_id` + `user_id` + `percent`），成功后再绑定；需要先验证 boss 账号调用该命令的权限是否被服务端放行。
- **保守**：不新增命令，前端明确提示“请先到游戏内将玩家设为该俱乐部代理”，绑定失败时回显服务端错误文案。

### 5.5 暂不做

- 不在交易记录、房间战绩、上下分流水、自动化等历史列表上批量 JOIN 靓号。这些表存的是历史真实 ID，全量改造收益低、回归面大；第一阶段只做「玩家管理 + 靓号管理 + 俱乐部成员树（可选）」。
- 不做批量入池/Excel 导入。入池不可逆（会从原号池删行），先按单号操作跑稳，再评估批量。

## 6. XuanManager 前端改造清单

### 6.1 新增页面 `PrettyNumbersPage.tsx`

- 顶部筛选：类型（全部/个人ID/邀请码）、状态（init/used/disabled）、关键字（号码/账号ID/昵称）。
- 列表列：靓号、类型、状态、绑定账号（昵称 + 真实 ID）、归属俱乐部（仅邀请码）、绑定时间、操作人、备注、操作。
- 状态徽标：可绑 / 已绑定 / 已停用；停用号码说明“不回收”。
- 操作：
  - **入池**：选类型 → 候选号搜索（前缀/包含/后缀 + 数字）或手输 6 位 → 备注 → 二次确认（明确“入池后该号码不再作为普通号发出，且不可逆”）。
  - **绑定**：玩家搜索选择（支持真实 ID/昵称/靓号）→ 邀请码类型额外选俱乐部 → 备注 → 确认；错误文案原样展示。
  - **解绑**：展示当前绑定人 → 二次确认（“号码停用且永不回收”）；邀请码类型提示“若仍是有效代理会补一个随机码”。
- 行内提供「查看玩家」入口，跳转 `#/game/players?playerId=<真实ID>`。
- 分页与后台其他页面一致；后端已完成 1→0 换算，前端不感知。

### 6.2 玩家管理页 `PlayersPage.tsx`

- 列表「玩家」列 ID 改为 `真实ID(靓号)`；详情页标题行同样处理。
- 搜索区增加「靓号」精确输入，或把占位文案改成“玩家ID/靓号/登录账号/昵称”并让 keyword 命中。
- 关联账号弹窗、发放钻石/重置密码弹窗的玩家标识也带靓号，方便核对；操作参数不变。
- 不要改 `player.playerId` 的语义，所有接口路径继续用它。

### 6.3 俱乐部页（可选，建议一并做）

- 成员树已显示邀请码，靓号自动生效。
- 如需成员个人 ID 也显示靓号，在 `clubs.go` 的成员树查询里补 `usr_pretty_no_info` JOIN，前端按 `ID：真实(靓号)` 渲染；不改变节点定位键。

### 6.4 路由

- `App.tsx` 只有 `/game/pretty-numbers` 一个分支，进入条件是 `game.pretty_no.uid.view || game.pretty_no.invite.view`；页面内页签按各自权限渲染，只有一类权限时不显示页签。`session.modules` 白名单由迁移自动提供。

## 7. 客户端改造（按 §4 结论执行）

### 方案 A（推荐）

- 新增一个统一的展示取值方法，例如 `GetDisplayPlayerId(entity)`：优先 `pretty_no`，回退真实 ID；只在 §3.2 的展示点使用。
- 所有网络参数、缓存键、头像 key、ID 相等判断继续用真实 ID。
- 房间 seat、直聊、客服、推广站不动。
- 预计改动 10 处左右的纯展示代码，无协议破坏。

### 方案 B（服务端全局替换）

- 客户端展示代码零改动，但必须完成：
  - 直聊票据/目录/头像链路对靓号的反解（ChatTool 代码改动）；
  - 本地缓存键切换的兼容（旧键可丢弃，不致命）；
  - 全量检查“用 ID 做相等/查表”的位置，确保服务端替换口径一致。
- 如果服务端只替换大厅回包、不替换登录 `guuid`，则会出现“我的ID仍是真实 ID、别人列表显示靓号”的不一致，必须让服务端明确范围。

### 邀请码侧

- 客户端无需改动：展示、复制、推广二维码、入会输入都只认服务端返回的 `invite_code`。

## 8. KBE 服务端交付/确认项（非本仓库）

1. 按方案 §12 建 `usr_pretty_no_info` 表（含唯一索引），执行顺序在后台部署之前。
2. 部署 4 条命令并重启；确认登录实体、房间 seat、俱乐部成员/代理回包中个人ID的下发字段（§4）。
3. 确认客户端入站反解范围：至少覆盖上下分、赠送、设代理、查链路、加成员、玩家选择器里手输 ID 等所有 `user_id/guuid` 入参；后台通道不反解。
4. 确认绑定/解绑后在线玩家的刷新方式：文档只提到推 `ClubAgentInfo`，但该结构没有个人ID字段；若采用方案 A，需要新增展示字段并随账号信息/相关列表下发。
5. 确认 `设置_俱乐部_代理` 对 boss 账号放行，否则邀请码靓号无法从后台完成。
6. 确认 `usr_pretty_no_info` 对 XuanManager 只读库账号可见（通常 `kbedm.*` SELECT 已覆盖）。

## 9. 部署顺序与回滚

1. KBE：建表 → 部署命令 → 重启 → 用一个测试号跑通入池/绑定/解绑。
2. XuanManager 后端：交叉编译 → 传二进制 → 启动自动执行 064 迁移 → 回读 `mgr_module` / `mgr_permission`。
3. XuanManager 前端：构建替换静态目录 → 校验 hash → 菜单出现「靓号管理」。
4. 客户端：仅方案 A 需要构建/热更；方案 B 验证后可不发版。
5. 回滚：后台前端/二进制可回退；**号码入池不可回滚**（原号池行已删），首次上线先用 2–3 个测试号验证。

## 11. 风险与边界

| 风险 | 说明 | 处理 |
| --- | --- | --- |
| 个人ID 下发字段未定义 | 文档只说“值可能变成靓号”，客户端展示点全靠猜 | 开工前抓包定 A/B（§4） |
| 全局替换 guuid | 直聊/客服/头像/本地缓存会被靓号打断 | 优先方案 A；若 B 则先改 ChatTool |
| 入池不可逆 | 删 `usr_guuid_info` 行、占邀请码 | 二次确认；先小批量；不提供批量导入 |
| 解绑不回收 | 客户退号后号码永久停用 | 运营话术和页面文案写清楚 |
| 取消代理使靓号失效 | 重新设代理给随机码，需再绑一次 | 俱乐部页/靓号页提示 |
| 分页口径 | KBE 0 起、后台 1 起 | 后端统一换算，前端不感知 |
| 权限 ID 漂移 | 迁移写死自增 ID 易撞号 | 全部按 code 关联授权 |
| 历史流水 | 交易/战绩等仍显示真实 ID | 本期明确不改，避免大面积回归 |
