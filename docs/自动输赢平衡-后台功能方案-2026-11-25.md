## 1. 结论

在 XuanManager 新增**独立模块「自动输赢平衡」**，路由 `/game/auto-balance`，挂在「游戏管理」（`parent_id=20`）下，`sort_order=72`（紧跟「玩家控制」70）。

**不塞进现有「玩家控制」页**，理由三条：

1. 命令族完全不同：玩家控制走 `异步_设置/停止/查询_胜率目标`（单玩家）；本模块走 8 条 `*_自动平衡_*` / `*_伙牌成员` 命令（老板级全局策略）。
2. 权限对象不同：玩家控制是"给某个玩家设一个目标"，本模块是"改全局策略 + 维护反伙牌名单"，两者不该共用一个权限位。
3. 数据来源不同：候选来自房间内存快照、名单来自 `usr_partner_team_member`，与 `opt_target_ctrl` 的目标列表没有交集。

页面本身分三个 Tab（配置 / 候选 / 名单），够用，不需要二级菜单。

后台到游戏服全部走现有 `callGameCommand`（`GET {GameAdminURL}/hall/command`），**不直连 kbedm 写库**，不改客户端、不改协议、不碰 `usr_hash_info`（配置由游戏服自己落库）。

## 2. 模块与权限

新增迁移 `server/migrations/075_auto_balance.sql`（编号接当前 074）。

### 2.1 模块

```sql
INSERT INTO mgr_module (id, parent_id, code, name, route, icon, sort_order, visible, status)
VALUES (<MAX(id)+1 实测值>, 20, 'game.auto_balance', '自动输赢平衡', '/game/auto-balance', 'balance', 72, 1, 'enabled')
ON DUPLICATE KEY UPDATE name = VALUES(name), route = VALUES(route), icon = VALUES(icon),
  sort_order = VALUES(sort_order), visible = VALUES(visible), status = VALUES(status)
```

> 模块 id **必须先在目标库查 `SELECT MAX(id) FROM mgr_module`** 再写死进迁移。历史上有过 57/5801 撞号覆盖「游戏接口日志」名称的事故，硬编码旧号会把别人的模块改名。

前端 `web/src/components/Layout.tsx` 的 `iconText` 补一行 `balance: "衡"`。

### 2.2 权限（4 个）

| code | 名称 | 说明 |
| --- | --- | --- |
| `game.auto_balance.view` | 查看自动输赢平衡 | 读配置、候选、名单 |
| `game.auto_balance.config` | 修改平衡配置 | 改总开关 / `mode` / 阈值 / 限额（**高危**） |
| `game.auto_balance.execute` | 执行平衡下发 | `run` / `run_guuids` / `stop_all` |
| `game.auto_balance.team` | 维护伙牌名单 | 加人、移除、从分组导入 |

`config` 与 `execute` **拆开**：能看候选的人不一定能切 `auto`，能执行单次下发的人不一定能改阈值。

角色继承按现有惯例（`INSERT IGNORE ... SELECT`）：`view` ← `game.player_optimization.view`；`config` / `execute` ← `game.player_optimization.update`；`team` ← `game.player_optimization.update`；最后给 `role_id=1`（super_admin）全量。

### 2.3 鉴权链路

游戏服侧 8 条命令统一校验：`game_mode='club'` + 平台 boss（`opt_target_ctrl.IsBossOnly`）。后台调 8890 的账号固定是 `Hall.boss[0]`，天然通过。

- 平台版（`main` 分支那套，`game_mode != 'club'`）会全部返回「俱乐部功能未启用」——本模块只对俱乐部版环境有意义，页面要能原样显示这句错误，不要吞。
- 后台自己的权限（上面 4 个）与游戏服 boss 名单是两层，**不互相替代**。

## 3. 后端设计

新增 `server/internal/api/auto_balance.go`，路由注册在 `server.go` 现有 `player-optimization` 那组之后。

| 方法 | 后台路由 | 上游命令 | 权限 |
| --- | --- | --- | --- |
| GET | `/api/game/auto-balance/config` | `查询_自动平衡_配置` | view |
| PUT | `/api/game/auto-balance/config` | `设置_自动平衡_配置` | config |
| GET | `/api/game/auto-balance/candidates?roomId&limit` | `查询_自动平衡_候选` | view |
| POST | `/api/game/auto-balance/execute` | `执行_自动平衡` | execute |
| GET | `/api/game/auto-balance/teams?teamName&guuid` | `异步_查询_伙牌名单` | view |
| POST | `/api/game/auto-balance/teams/members` | `异步_设置_伙牌成员` | team |
| DELETE | `/api/game/auto-balance/teams/members` | `异步_移除_伙牌成员` | team |
| POST | `/api/game/auto-balance/teams/import` | `异步_导入_伙牌名单` | team |
| GET | `/api/game/auto-balance/groups` | 分组下拉（见 R2） | team |

共用约定：

- **`ret_result` 是 JSON 字符串，要二次解析**（现有 `decodeGameObject` 已能做）；`ret_code != 512` 统一走 `describeGameFailure`。
- 所有写操作（PUT 配置、POST/DELETE 名单、导入、执行）**必须写 `mgr_audit_log`**：操作人、动作、参数、上游 `context`、返回的 `ok/failed/stopped`。沿用 `player_optimization.go` 里 `requestAudit` 那套写法，`context` 用 `gameOperationContext("auto-balance-…")` 生成，便于日志对账。
- 配置是**全量 / patch 二选一**：前端"改一个字段就保存"用 `patch`，"表单整体提交"用 `cfg`。返回后用响应里的 `cfg` 覆盖页面状态（服务端会 clamp，前端不要自己算合法值）。
- 执行接口 body 收敛成 `{action, guuids, remark}`，`action` 只允许 `run` / `run_guuids` / `stop_all`，其余直接 400。
- 写操作串行化：沿用 `winTargetWriteMu` 模式加一把 `autoBalanceWriteMu`，避免两次"一键全停"并发打穿。

## 4. 前端设计

新增 `web/src/pages/AutoBalancePage.tsx`，`App.tsx` 加一行路由：`route === "/game/auto-balance" && can("game.auto_balance.view")`。

页面结构（`PageHeader` + Tab 条 + 内容区），不做二级菜单。

### Tab 1 配置与总览

- 顶部状态条：`enabled` 徽标、`mode`（observe / advice / auto，auto 用红色）、`last_tick`（空串显示"尚未运行"）。
- 指标卡 4 个：今日已下发（`today.set_count`）、进行中（`today.active`）、名单（`team.teams` 团队 / `team.members` 人）、最近 Tick。
- 配置表单分组卡片：
  - 总开关与模式（`enabled` / `mode` / `room_play_mode` / `require_club_mode`）
  - 保护规则（`protect.*`，7 个数值）
  - 压制规则（`suppress.*`，含 `suppress.mode`）
  - 限额（`limits.*`，4 个）
  - 保护排除 `protect_exclude_guuids`（多行 guuid）
  - 按底皮覆盖 `by_dipi`（表格：底皮 → 字段 → 值；空表即 `{}`）
- 保存：只提交改动字段（`patch`），成功后用返回 `cfg` 刷新；失败原样显示游戏服文案。
- **切 `mode=auto` 或 `enabled=true` 时弹二次确认**，正文列明「开启后游戏服会在满足阈值时自动干预发牌」，并要求勾选确认框。

### Tab 2 候选 / 建议

- 工具栏：房间号筛选（`roomId`，0=全部）、`limit`（默认 100）、动作筛选（全部 / protect / suppress / **仅命中** / 已有目标）、「立即跑一次 Tick」、右侧红色「一键全停」。
- 表格列：玩家（`guuid` + `nick`）、房间、本周期净输赢（红赢绿输，按项目惯例）、局数、在座时长、今日累计、团队、命中、动作、目标分、概率、已有目标、冷却剩余、操作。
- 展示口径必须照文档：
  - `today_net === null` → 显示「未开启」，**不能当 0**；
  - `hit=0` 的行仍展示（观察用），置灰；
  - `cooldown_left > 0` 显示「冷却 12:34」，执行按钮禁用；
  - `has_target=1` 显示「已有目标」，执行按钮禁用。
- 「执行」单行 → `run_guuids`；勾选多行 → 批量 `run_guuids`（逗号拼接）。`observe` 模式下这两个按钮**置灰并提示「observe 模式不下发」**，不调到服务端再报错。
- 执行结果按 `ok[]` / `failed[]` 分栏展示，`failed` 里的 `error` 原样展示（例如「当前已不满足规则（period_net=1200）」）。
- 无推送 → 30 秒轮询一次；Tab 切走时停轮询（复用 `useQueryRefresh`）。

### Tab 3 伙牌名单

- 左侧团队列表（`team_name` + `member_count` + `update_date`），右侧选中团队的成员表（`guuid` / `name` / `club_id` / `today_net` / `today_rounds` / `status` / `remark` / `operator` / 时间）。
- 「＋ 添加成员」弹窗：团队名（可新建）+ 批量 guuid（textarea，逗号/换行）+ 备注（≤250 字）。返回 `ok` / `failed` / `stopped` 三段展示——`stopped` 要显式提示「已停掉这些玩家的保护目标」，因为运营可能会意外停掉正在生效的补偿。
- 移除：单条移除 / 整队移除（`guuids` 留空），二次确认，提示是软删（`status='deleted'`）且**重新导入不会复活**。
- 「从分组导入」弹窗：分组多选（`group_ids`）+ 前缀（默认 `导入-`）+ 先 `dry_run=1` 出预估（"将导入 N 人 / M 个团队"）→ 确认后正式导入，展示 `teams / members / affected / stopped`。
- 页面顶部常驻提示：`today_net` / `today_rounds` 最多滞后一个结算周期（约 30 分钟）；名单改动下一 Tick（≤60 秒）生效。
