## 一、功能说明

俱乐部实时房（`settle_mode=realtime` 且 `roomClubID != '0'`）的奖池改成**按联盟/俱乐部独立**：

| 维度 | 改动前 | 改动后 |
| --- | --- | --- |
| 奖池归属 | 全服一份（所有俱乐部共用） | **联盟一个池 / 未入盟俱乐部各自一个池** |
| 进池时机 | 每局，只从「本局最大赢家」收 | **30 分钟个人结算时，所有净赢超线的赢家都收** |
| 派奖 | 每局，按牌型比例 | **不变**（牌型是每局的产物） |
| 提留去向 | 按 `one_reward_bili` 分代理（现配置为 0，实际无人拿） | **归奖池归属方**：联盟总群主 / 独立俱乐部创建者 |

**支持**：

- 客户端查本池的中奖历史与最大中奖（`查询_奖池_记录`，按池隔离）；
- 客户端看到本池的奖池余额（`PlayerList` / `GamePlayerListInfo` 里的 `reward_pool` / `total_reward_money`）；
- 后台按池查/改奖池余额（SQL，见 §五）；
- 后台按底皮**开关提留**（`reward_modify` 设 0 = 该底皮不提留，见 §5.6）；
- **联盟总群主 / 独立俱乐部创建者按池调参**（提留额 + 赔付比例，见 §十）；
- 联盟总群主查联盟红利（含奖池提留）、独立俱乐部创建者查俱乐部红利（含奖池提留）。

**不支持**：

- **奖池余额**不提供查询/设置命令，后台走 SQL（见 §五）；
- 池参数（提留额 / 比例）**新增了两条命令**（见 §十），这是唯一的新增命令；
- 全服维度的提留额仍用全局配置（见 §5.6），与池级配置互不影响；
- 不提供奖池提留与其他联盟收入的分离报表（二者共用 `remark5='unionroot'`，见 §六 与 §八 限制 5）。

**适用与不适用**：

| 场景 | 是否走独立池 |
| --- | --- |
| `settle_mode=realtime` + 俱乐部房 | **是**（本文档描述的行为） |
| `settle_mode=realtime` + 大厅房（`roomClubID='0'`） | 否，仍走全服 `Hall.rewards` |
| `settle_mode=fixed`（任意房型） | 否，行为与改动前**完全一致** |
| `先进传销扯旋` / `副本扯旋` | 否，本次未纳入 |

## 二、通用协议（所有接口共用）

### 2.1 两条命令通道

| 通道 | 客户端→服务器 | 服务器→客户端 | 本文档用到的命令 |
| --- | --- | --- | --- |
| 大厅命令通道 | `reqHallCommand(param, context)` | `onHallCommand(ret_code, result)` | `查询_奖池_记录` |
| 账号命令通道 | `reqAccountCommand(param, context)` | `onAccountCommand(ret_code, result)` | （本功能不需要） |

### 2.2 请求格式

- `param`：**JSON 字符串**，必须含 `"header"` 字段（命令名），其余字段为参数；
- `context`：字符串，新版本格式 `"p@<任意上下文串>"`（@ 后内容原样回传，用于请求-响应配对）。

```json
// param 示例
{"header": "查询_奖池_记录", "score_type": "底皮1/3"}
```

### 2.3 响应格式

回调第二个参数 `result` 是 JSON 字符串。本功能涉及的 `查询_奖池_记录` 返回报文**即推送报文本身**（见 §三），
不再额外套一层 `{"context","result"}` 包裹——这是该命令的既有行为，本次未改。

> ⚠️ **异常路径**：命令名写错 / param 非法 JSON / 服务端内部异常时，`ret_code = 0x301`，
> `result` 可能为空或只有 `{"context":"<ctx>"}`。**客户端请先判空再解析**。

`ret_code`（`scripts/common/GlobalConst.py`）：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `GC_OK` | `0x200`（512） | 成功 |
| `GC_FAILED` | `0x301`（769） | 失败（命令不存在、参数错误等） |
| `GC_UNKOWN` | `0x500`（1280） | 服务端本次不返回，等后续消息（`查询_奖池_记录` 走这个，结果通过 `onMessage` 推送） |

## 三、接口 1：查询奖池中奖历史（客户端，按池隔离）

查询当前所在奖池的最大中奖与最近中奖记录。**俱乐部实时房按本池返回**；其他场景（大厅房 / fixed / 不在房间）回落到原全服数据，行为与改动前一致。

- **命令名**：`查询_奖池_记录`
- **通道**：大厅命令通道（`reqHallCommand` / `onHallCommand`）
- **实现**：`scripts/base/Hall.py` `_actGetRewardPoolRec`
- **权限**：任何登录账号

### 3.1 请求参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | `查询_奖池_记录` |
| `score_type` | string | 是 | 底皮全名，如 `底皮1/3`、`底皮5/10`（见下方取值表） |
| `context` | string | 否 | 操作号，原样带回 |

`score_type` 合法取值（必须与房间底皮一致，写错返回空数组）：

```
底皮0.1/0.3  底皮0.2/0.5  底皮1/3  底皮2/5  底皮5/10
底皮10/20    底皮20/40    底皮50/100  底皮100/200
```

### 3.2 请求示例

```json
{"header": "查询_奖池_记录", "score_type": "底皮1/3"}
```

### 3.3 返回

推送 router：`RewardPoolRec`（点对点，只发给请求者，走 `onMessage`）

```json
{
  "RewardPoolRec": {
    "max_winner": ["玩家昵称", "天皇", 5, "2026-11-04"],
    "history_list": [
      ["玩家C", "朵皇", 1, "2026-11-04"],
      ["玩家B", "朵朵", 1, "2026-11-04"],
      ["玩家A", "天皇", 5, "2026-11-04"]
    ]
  },
  "context": "p@xxx"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `max_winner` | array | 该底皮历史最大中奖，元素为 `[昵称, 牌型, 中奖金额, 日期]`；无记录时为 `[]` |
| `history_list` | array | 最近中奖记录，**最新在前**，最多 10 条；元素格式同上 |
| 元素第 3 项 | int | 中奖金额，**单位：元** |
| 元素第 2 项 | string | 牌型名：`天皇` / `地皇` / `朵皇` / `朵朵` / `丁二皇` |

### 3.4 数据源（重要，影响客户端展示）

| 场景 | `max_winner` / `history_list` 来源 |
| --- | --- |
| 俱乐部实时房（房间有所属俱乐部且 `settle_mode=realtime`） | **本池**（联盟池或该俱乐部池），只含本池玩家的中奖记录 |
| 大厅房 / `fixed` / 不在房间 / 热更前老房间 | 全服 `reward_max_winner` / `reward_history_list`（原逻辑，与改动前完全一致） |

> 判定方式：服务端按**调用者当前所在房间**反查奖池键。反查不出来一律回落全服数据，**不会报错**。

> 客户端无需感知池的概念，直接按原格式渲染即可；若需在界面上区分「本俱乐部奖池」，可自行加标题文案。

### 3.5 注意事项

- `history_list` 是**最新在前**（服务端已倒序），客户端不要再次反转；
- 单池最多保留最近 **10 条**，超出丢最旧；
- 该接口**不落库**历史，记录只存在 `usr_hash_info`（见 §五），重启不丢；
- 中奖金额是**派奖当时的元数**，不是玩家实际到账（会被后续 5% 抽水与 2.5% 分成分摊，见 §六 限制 3）。

## 四、接口 2：奖池余额展示（客户端，推送字段）

奖池余额通过房间推送下发，**不是独立命令**。俱乐部实时房显示本池数据，其它场景与改动前一致。

### 4.1 `total_reward_money`（奖池总额）

出现位置（两处字段同名同义）：`PlayerList` 推送（房间内玩家状态变化时）与 `GamePlayerListInfo` 推送（客户端调 `获取_游戏内玩家_信息_命令`）。
两者的数据来源是同一个方法 `Game.GetPlayerListMessage()`，口径一致。

| 场景 | 取值 |
| --- | --- |
| 俱乐部实时房 | **本池全部底皮合计**（元） |
| 其他 | 全服 `Hall.rewards` 全部底皮合计（元，原口径） |

> 单位：**元**（整数，已 `// 100`）。客户端按原样式展示即可，无需改动解析逻辑。

### 4.2 `reward_pool`（牌桌奖池）

出现位置：`PlayerList` 与 `GamePlayerListInfo` 两个推送的**顶层** `reward_pool` 字段（与 `player_xi_money` / `boss_xi_money` 并列）。

| 场景 | 取值 |
| --- | --- |
| 俱乐部实时房 | **本池本底皮余额**（元）—— 即玩家「这一把能中的那一池」 |
| 其他 | `game_reward_money - game_prize_money`（房间生命周期累计差，原逻辑） |

> ⚠️ **两个字段口径不同，是有意为之**：`total_reward_money` 是**全部底皮合计**（历史行为），
> `reward_pool` 是**本底皮**（摆在牌桌上方，若用合计会严重误导玩家）。客户端不要假设二者相等。

> **池级开关关闭时两字段均返回 `0`**（见 §10.8）；重新开启后恢复真实值。

> 单位：**元**（整数）。

## 五、接口 3：后台按池查询/设置奖池（SQL）

**本次不新增后台 HTTP 命令。** 俱乐部奖池存在 `usr_hash_info`，一池一条记录，后台直接 SQL 查改。

> 全服的 `异步_获取_奖池_数据` / `异步_设置_奖池_数据` **未改动**，仍只操作 `Hall.rewards`，
> **不会**影响俱乐部池。别混用。
>
> **按底皮开关提留**不需要 SQL，走 `设置_大厅_配置数据` 改 `reward_modify` 即可，见 §5.6。

### 5.1 存储结构

| hash_key | hash_content（JSON） | 说明 |
| --- | --- | --- |
| `club_reward\|<pool_key>` | `{"底皮1/3": 100, "底皮2/5": 200}` | 本池各底皮余额，**单位：分** |
| `club_reward_history\|<pool_key>` | `{"history": {...}, "max_winner": {...}}` | 本池中奖历史与最大中奖 |

`<pool_key>` 的取值规则：

| 房间所属俱乐部 | pool_key | 示例 |
| --- | --- | --- |
| 已加入联盟（`club_guuid_info.union_id` 非空） | `union_id` | `916139` |
| 未加入联盟的独立俱乐部 | `club-<club_guuid>` | `club-329617` |

### 5.2 查询所有池

```sql
SELECT hash_key, hash_content FROM usr_hash_info WHERE hash_key LIKE 'club_reward|%';
```

### 5.3 查询单个池

```sql
SELECT hash_key, hash_content FROM usr_hash_info WHERE hash_key = 'club_reward|916139';
```

### 5.4 给某个池注资（运营手动）

> ⚠️ **改库后必须重启 baseapp**，否则内存里的旧值会在下一次写入时把库覆盖回去。

```sql
-- 1) 先看现值，确认当前 JSON 结构
SELECT hash_content FROM usr_hash_info WHERE hash_key = 'club_reward|916139';

-- 2) 写好目标值后整体更新（保持 JSON 合法，单位：分）
UPDATE usr_hash_info
SET hash_content = '{"底皮1/3": 11000, "底皮2/5": 0, "底皮5/10": 0, "底皮10/20": 0, "底皮20/40": 0, "底皮50/100": 0}'
WHERE hash_key = 'club_reward|916139';
```

> `UPDATE` 影响行数为 0 说明该池还没有记录，用 `INSERT INTO usr_hash_info (hash_key, hash_content) VALUES (...)` 新建。
> 新建后同样需重启才生效。

### 5.5 上线前一次性去重（部署顺序第 1 步）

`usr_hash_info.hash_key` **没有唯一索引**，历史上可能出现同 key 多行。上线前跑一次：

```sql
-- 可重复执行；新库为空时是空操作
DELETE h1 FROM usr_hash_info h1
JOIN usr_hash_info h2
  ON h1.hash_key = h2.hash_key AND h1.id < h2.id
WHERE h1.hash_key LIKE 'club_reward%';
```

### 5.6 奖池开关：按底皮关闭提留（`reward_modify`）

> 这是**奖池提留的唯一开关**，无需新增接口，走与 `reward_card_bili` 完全相同的配置机制。

#### 5.6.1 配置项

| 项 | 值 |
| --- | --- |
| 键名 | `reward_modify`（`d_halls.datas[1]`） |
| 类型 | dict，key 为底皮全名 |
| 值 | **整数，单位：元**，从本次奖池贡献中优先截留给归属方的金额 |
| 默认值 | `{'底皮0.1/0.3':0, '底皮0.2/0.5':0, '底皮1/3':2, '底皮2/5':3, '底皮5/10':5, '底皮10/20':10, '底皮20/40':20, '底皮50/100':0}` |

**键顺序（`param_value` 必须按此顺序填 8 个整数）**：

```
底皮0.1/0.3, 底皮0.2/0.5, 底皮1/3, 底皮2/5, 底皮5/10, 底皮10/20, 底皮20/40, 底皮50/100
```

#### 5.6.2 读 / 写

```bash
# 读
GET /hall/command?header=获取_大厅_配置数据&param={"param_name":"reward_modify","context":"admin-get"}
# 返回 param_value 形如 "0,0,2,3,5,10,20,0"（只有值，顺序即上表）

# 写（必须 8 个整数）
GET /hall/command?header=设置_大厅_配置数据&param={"param_name":"reward_modify","param_value":"0,0,2,3,5,10,20,0","context":"admin-set"}
```

通道与权限同 `reward_card_bili`：HTTP 大厅命令，要求 `account.level >= 99`，见 `doc/奖池开奖牌型与比例-后台接口文档.md` §二。

#### 5.6.3 `0` 的语义：该底皮不提留

以底皮 1/3（`reward_money=3` 筹码 = 3 元）为例，一次触发：

| `reward_modify` | 玩家被扣 | 进奖池 | 归属方提留 | 说明 |
| --- | --- | --- | --- | --- |
| **0** | 3 元 | **300 分（全额）** | **0 分** | **该底皮不提留** |
| 1 | 3 元 | 200 分 | 100 分 | |
| 2（线上当前） | 3 元 | 100 分 | 200 分 | |
| 3 或更大 | 3 元 | 300 分 | 0 分 | ⚠️ **见 5.6.4** |

**关键**：设 `0` **不会**让玩家少扣钱，只是这 3 元**全部进奖池**、归属方一分不拿。
玩家被扣的金额由 `reward_money`（硬编码在 `pm_bipai_chuanxiaoxuan.py`，**后台改不了**）决定。

三种诉求对应的设置：

| 诉求 | 设置 |
| --- | --- |
| 关闭某底皮的**派奖** | `reward_card_bili` 对应牌型设 0（见 §六）；或全局关 `reward_on` |
| 关闭某底皮的**提留**（钱全留奖池给玩家中） | `reward_modify` 该位设 `0` |
| 让归属方**多拿** | 调大该位，但必须**严格小于**贡献额，见 5.6.4 |

#### 5.6.4 ⚠️ 两个必须知道的边界

**① 提留必须「严格小于」贡献额，否则语义反转**

代码判定是 `reward_yuan > one_modify`（严格大于）：

| 场景（底皮1/3，贡献 3 元） | 实际结果 |
| --- | --- |
| `reward_modify = 2` | 提留 2 元、进池 1 元，✅ 符合预期 |
| `reward_modify = 3`（= 贡献额） | **提留 0、进池 3 元**，❌ 与「全给创建者」直觉相反 |
| `reward_modify = 4`（> 贡献额） | **提留 0、进池 3 元**，❌ 同上 |

> 该判定沿用 fixed 既有语义（贡献额不足提留时取 0，避免负数），**本次未改**——改它会动到 fixed 线上行为。
> **运营配置时请确保每一位都严格小于对应底皮的贡献额**（见下表）。

**② 各底皮的贡献额对照（`reward_money`，硬编码在代码里）**

| 底皮 | `reward_low`（触发线，筹码） | `reward_money`（贡献额，筹码） | 建议提留上限 |
| --- | --- | --- | --- |
| 底皮0.1/0.3 | 9999（不开奖池） | 0 | 只能填 0 |
| 底皮0.2/0.5 | 50 | 10 | < 1（10 筹码 = 1 元） |
| 底皮1/3 | 29 | 3 | **< 3** |
| 底皮2/5 | 49 | 5 | **< 5** |
| 底皮5/10 | 99 | 10 | **< 10** |
| 底皮10/20 | 199 | 20 | **< 20** |
| 底皮20/40 | 399 | 40 | **< 40** |
| 底皮50/100 | 500 | 100 | **< 100** |

> 换算规则（`ChipToGold`）：底皮 0.1/0.2 时 **10 筹码 = 1 元**，其余底皮 **1 筹码 = 1 元**。
> 提留额单位是**元**，与贡献额比较前先换算成元，所以 0.2 档的实际上限是 1 元而不是 10。

**③ 后台写负数会被兜住（2026-11-04 修复）**

`_actSetHallDatas` 的 dict 分支只做 `int()` 不校验范围，历史可以写入负数。
现已在读取处加 clamp：`max(0, int(...))`，写负数等效于 0（不提留），**不会把奖池凭空撑大**。

#### 5.6.5 生效范围与持久化

| 项 | 说明 |
| --- | --- |
| 生效时机 | 改内存，**下一次触发进池即生效**，无需重启 |
| 持久化 | ❌ **不持久化**。编辑 `d_halls.py` 触发 `tools.auto_reload()` 或服务重启会**回落文件值** |
| 结论 | **后台调参 + 运维同步改 `d_halls.py`，两件事都要做** |
| 影响范围 | 只影响进池时的提留；**不影响**玩家被扣的 `reward_money`、**不影响**派奖比例 |
| 房型差异 | 俱乐部实时房 → 提留归归属方（本文档）；fixed / 大厅房 → 仍按 `one_reward_bili` 分平台代理链 |

## 七、错误与排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `查询_奖池_记录` 返回 `max_winner=[]` 且 `history_list=[]` | `score_type` 与房间底皮不一致；或本池确实还没有人中奖 | 核对底皮全名；新池从 0 开始，初期无记录正常 |
| 客户端看到的是别家俱乐部的中奖记录 | 房间未走实时模式（`settle_mode=fixed`）；或玩家已离开房间 | 确认 `settle_mode=realtime``；离开房间后回落全服数据属预期 |
| `reward_pool` 一直是 0 | 本池本底皮余额为 0（新池 / 已派空） | 运营按 §5.4 注资，或等待赢家进池 |
| 牌桌显示「奖池不足不派奖」 | 池子不足 1 元 | 按设计**不派奖、不发公告、不写历史**；注资或等待进池 |
| 联盟总群主查不到提留 | 该俱乐部未入盟（走 §6.2 创建者通道）；或代理树未加载 | 确认 `union_id`；查服务端 ERROR 日志 `奖池提留未入账` |
| 改库后池子没变 | 只改了库没重启 | **必须重启 baseapp**（内存是权威副本） |

## 十、接口 5：俱乐部奖池参数（按池独立配置，2026-11-04 新增）

> 本节为**新增命令**，与 §五 的全局配置（`获取/设置_大厅_配置数据`）**完全解耦**。
> 全局配置继续服务 fixed / 大厅房 / BOSS 控号 / 后台补发；本节命令只影响**指定池**的 realtime 俱乐部房。

### 10.1 背景

奖池余额已按联盟/俱乐部独立，但提留额与赔付比例原来是**全服一份**。本节把这两个参数也下沉到池维度。

| 配置 | 存储位置 | 粒度 |
| --- | --- | --- |
| 奖池余额 | `club_reward\|<pool_key>` | 按池 |
| 中奖历史 | `club_reward_history\|<pool_key>` | 按池 |
| **提留额 / 赔付比例** | **`club_reward_cfg\|<pool_key>`** | **按池（本节）** |


#### 10.1.1 五档牌型对照（只能配比例，不能改牌型规则）

赔付比例按**牌型名**取值，一共 5 档，**判定顺序即优先级（从高到低）**：

| 顺序 | 牌型 | 组成 | 出厂默认比例 |
| --- | --- | --- | --- |
| 1 | `天皇` | 丁二红 + 天对 | 20 |
| 2 | `地皇` | 丁二红 + 地对 | 10 |
| 3 | `朵皇` | 丁二红 + 人对/和对/中三对/下腰对/四滥 | 10 |
| 4 | `朵朵` | 对子 + 对子（不含丁二红） | 2 |
| 5 | `丁二皇` | 丁二红 + 杂牌 | 2 |

> 牌型定义来源：`doc/奖池开奖牌型与比例方案.md` §2。

**三条必须知道的约束**：

| # | 约束 | 说明 |
| --- | --- | --- |
| 1 | **只能配这 5 个 key 的比例** | 牌型判定规则（哪些牌算天皇）**写死在服务端**，不可按池修改。本接口改的是「赔多少」，不是「什么牌算赢」 |
| 2 | **未知 key 静默忽略** | 传 `{"天黄": 50}`（错字）**不会报错也不会写入**，接口仍返回成功。请严格使用上表 5 个名称 |
| 3 | **比例为 0 = 该档关闭** | 玩家击中该牌型**不派奖、不公告、不写历史** |

### 10.2 权限模型

| 身份 | 可管的池 | 判定 |
| --- | --- | --- |
| **联盟总群主** | 该联盟池（`union_id`） | `club_union_info.owner_guuid == 自己` |
| **独立俱乐部创建者** | 该俱乐部池（`club-<guuid>`） | `club.proxy.guuid == 自己` 且该俱乐部**未入盟** |
| 已入盟的俱乐部创建者 | **无**（池归联盟） | 拒绝 |
| `level >= 99` | 任意池（可传 `pool_key`） | 运维代配 |

> **联盟优先**：同一人既是总群主又是独立俱乐部创建者时，按联盟池处理。
> **参数可省略**：服务端按身份自动推断 `pool_key`，避免越权。

### 10.3 接口 5.1：获取配置

- **命令名**：`获取_俱乐部_奖池_配置`
- **通道**：大厅命令通道（`reqHallCommand` / `onHallCommand`）
- **权限**：见 §10.2

#### 请求

```json
{"header":"获取_俱乐部_奖池_配置"}
```

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | `获取_俱乐部_奖池_配置` |
| `pool_key` | string | 否 | 仅 `level >= 99` 生效；普通用户传了也按身份推断 |

#### 返回

**所有键都会返回，未配置的补 0**，客户端可直接渲染，无需判空：

```json
{
  "context": "p@xxx",
  "result": {
    "pool_key": "916139",
    "reward_modify": {
      "底皮0.1/0.3": 0, "底皮0.2/0.5": 0, "底皮1/3": 2,
      "底皮2/5": 3, "底皮5/10": 5, "底皮10/20": 10,
      "底皮20/40": 20, "底皮50/100": 0
    },
    "reward_card_bili": {
      "天皇": 20, "地皇": 10, "朵皇": 10,
      "朵朵": 2, "丁二皇": 2
    }
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `pool_key` | 实际操作的池：联盟为 `union_id`，独立俱乐部为 `club-<guuid>` |
| `reward_modify` | 8 个底皮的提留额，**单位：元**，0 = 不提留 |
| `reward_card_bili` | 5 档牌型的赔付比例，**整数百分比**，0 = 该档不派奖 |

#### 失败

`ret_code = 0x301`，`result` 为 `{"error":"你无权管理该奖池"}`。

### 10.4 接口 5.2：设置配置（批量下发）

- **命令名**：`设置_俱乐部_奖池_配置`
- **通道**：大厅命令通道
- **权限**：见 §10.2

#### 请求

```json
{
  "header": "设置_俱乐部_奖池_配置",
  "reward_modify": {"底皮1/3": 2, "底皮2/5": 3},
  "reward_card_bili": {"天皇": 20, "地皇": 10}
}
```

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | `设置_俱乐部_奖池_配置` |
| `reward_modify` | object | 否* | `{底皮: 元}`，**部分更新**：只改传入的键 |
| `reward_card_bili` | object | 否* | `{牌型: %}`，**部分更新**：只改传入的键 |
| `reward_on` | bool | 否* | 池级总开关，见 §10.8 |
| `pool_key` | string | 否 | 仅 `level >= 99` 生效 |

> \* **三个字段（`reward_on` / `reward_modify` / `reward_card_bili`）至少传一个**，否则返回 `0x301`。
> **批量下发**：一次调用可同时传全部 8 个底皮 + 5 个牌型，客户端无需逐项提交。
>
> ⚠️ `reward_card_bili` 里**只能出现 §10.1.1 那 5 个牌型名**。写错名字会被**静默忽略**，
> 接口仍返回 `0x200`，但那个键不会写入——**请回读校验**。

#### 取值规则

| 字段 | 合法范围 | 越界处理 |
| --- | --- | --- |
| `reward_modify` | 整数 >= 0 | 负数 / 非法 → 按 0 |
| `reward_card_bili` | 整数 0~100 | 超 100 → 100；负数 / 非法 → 0 |

#### 返回

与获取接口**格式相同**（返回写入后的完整配置，补 0 后），便于客户端直接刷新界面。

### 10.5 ⚠️ 默认 0 语义（重要）

**未配置的池 = 不提留 + 不派奖。**

| 情况 | 提留 | 派奖 |
| --- | --- | --- |
| `club_reward_cfg\|<pool_key>` 不存在 | 0 | **0（完全不派奖）** |
| 存在但缺某个底皮 / 牌型 | 0 | 0 |

> **上线影响**：新命令上线后，所有池默认「**开关关闭** + 不派奖 + 不提留」。
> 玩家击中天皇会看到「奖池不足不派奖」。**需池主先用 `设置_俱乐部_奖池_配置` 打开开关并配置参数**（见 §10.8）。

对比：全局配置（`d_halls`）在缺键时会回落到默认档位（天皇 20% 等），**池级配置不会**——这是刻意的，避免新池在未配置时白派奖。

### 10.6 持久化与生效

| 项 | 说明 |
| --- | --- |
| 存储 | `usr_hash_info` 的 `club_reward_cfg\|<pool_key>`，一池一条 |
| 持久化 | ✅ **持久**，重启不丢（与全局 `d_halls` 配置不同） |
| 生效时机 | 改内存，**下一次进池 / 派奖即生效**，无需重启 |
| 审计 | 每次设置写一条 `usr_attr_info`（`attr_name='club_reward_cfg\|<pool_key>'`，`remark='设置奖池配置'`） |

### 10.7 与全局配置的关系

| 配置项 | 作用域 | 影响房型 |
| --- | --- | --- |
| `d_halls.reward_modify` / `reward_card_bili` | 全服 | fixed、大厅房、BOSS 控号、后台补发 |
| `club_reward_cfg\|<pool_key>` | 单池 | **仅**该池的 realtime 俱乐部房 |

> 两者**互不影响**。改全局配置不会影响已配置的俱乐部池，反之亦然。

### 10.8 池级总开关 reward_on（2026-11-04 追加）

> **由池主自己控制本池是否启用奖池功能**，不影响其它池、不影响大厅房 / fixed。

#### 10.8.1 语义

| 项 | 说明 |
| --- | --- |
| 字段 | `reward_on`（bool，与 `reward_modify` / `reward_card_bili` 同级） |
| **默认** | **`false`（关闭）** —— 新池未配置时**不参与奖池** |
| 判定 | **只认严格 JSON 布尔** `true`；字符串或数字一律视为关闭 |
| 权限 | 与 §10.2 一致（联盟总群主 / 独立俱乐部创建者；`level>=99` 可带 `pool_key` 代配） |

#### 10.8.2 关闭后的行为

| 项 | 关闭后 |
| --- | --- |
| 赢家进池扣钱 | **不扣**（`reward_money` 不从玩家身上收） |
| 归属方提留 | **不入账**（`owner_bonus` / `agent bonus` 不增加） |
| 牌型中奖 | **不派奖、不公告、不写历史** |
| 池子余额 | **冻结保留**（不清零；重新打开后继续使用） |
| **客户端奖池展示** | `reward_pool` / `total_reward_money` **返回 0**（避免"有池子却不给中"的误解）；余额数据本身不动 |
| 有效手数 `validated_count` | **正常累计**（活动统计不受影响） |
| 其它池 | **不受影响** |
| 大厅房 / fixed | **不受影响** |

> 与全局开关的关系：池开关关闭则本池停止；`d_halls.reward_on` 关闭则**所有房型**都停止（含大厅房）。两者是逻辑与的关系。

#### 10.8.3 读取

返回体新增 `reward_on` 字段（与 `reward_modify` / `reward_card_bili` 并列）：

```json
{
  "context": "p@xxx",
  "result": {
    "pool_key": "916139",
    "reward_on": false,
    "reward_modify": {...},
    "reward_card_bili": {...}
  }
}
```

> **关闭时房间推送的奖池字段会变成 0**：`PlayerList.reward_pool` 与 `total_reward_money` 均返回 `0`，
> 避免玩家看到"有池子却不给中"。**余额数据本身不动**，重新开启后立刻恢复显示。
> 池主侧查询（`获取_俱乐部_奖池_配置`）仍返回真实余额与 `reward_on` 状态，供管理界面使用。

#### 10.8.4 设置

```json
{"header": "设置_俱乐部_奖池_配置", "reward_on": true}
```

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `reward_on` | bool | 可选。不传 = 不改原值 |

**三个字段（`reward_on` / `reward_modify` / `reward_card_bili`）都可选，至少传一个**；未传的保持原值。

**失败**：

| 情况 | ret_code | result |
| --- | --- | --- |
| 三个字段都没传 | 0x301 | `{"error":"reward_on / reward_modify / reward_card_bili 至少传一个"}` |
| `reward_on` 传了非布尔 | 0x301 | `{"error":"reward_on 必须是布尔值"}` |
| 无权管理该池 | 0x301 | `{"error":"你无权管理该奖池"}` |

#### 10.8.5 典型配置流程

```json
// 1) 开启奖池 + 配置参数（一次下发）
{"header": "设置_俱乐部_奖池_配置",
 "reward_on": true,
 "reward_modify": {"底皮1/3": 2, "底皮2/5": 3},
 "reward_card_bili": {"天皇": 20, "地皇": 10}}

// 2) 暂停本池（参数保留，随时可恢复）
{"header": "设置_俱乐部_奖池_配置", "reward_on": false}
```

### 10.9 设置赔率的完整示例

> 赔率就是 `reward_card_bili`（5 档牌型各赔百分之几）。
> 池主**不需要传 `pool_key`**——服务端按身份自动定位自己的池。

#### 10.9.1 联盟：总群主设置本联盟的赔率

**身份**：该联盟的 `owner_guuid`（联盟总群主）

```json
// 请求
{
  "header": "设置_俱乐部_奖池_配置",
  "reward_card_bili": {
    "天皇": 30,
    "地皇": 15,
    "朵皇": 10,
    "朵朵": 5,
    "丁二皇": 0
  }
}
```

```json
// 返回（0x200）
{
  "context": "p@xxx",
  "result": {
    "pool_key": "916139",
    "reward_on": false,
    "reward_card_bili": {
      "天皇": 30, "地皇": 15, "朵皇": 10,
      "朵朵": 5, "丁二皇": 0
    },
    "reward_modify": {...}
  }
}
```

> `pool_key` 是 `916139`（联盟 ID），说明写的是**联盟池**。
> `reward_on` 为 `false` 表示池还没开启——**只配赔率不会派奖，还要开开关**（§10.8）。

#### 10.9.2 独立俱乐部：创建者设置本俱乐部的赔率

**身份**：该俱乐部的 `proxy.guuid`（创建者），且俱乐部**未入盟**

```json
// 请求（格式与联盟完全一样，不用区分）
{
  "header": "设置_俱乐部_奖池_配置",
  "reward_card_bili": {"天皇": 50, "地皇": 20}
}
```

```json
// 返回
{
  "result": {
    "pool_key": "club-329617",
    "reward_card_bili": {
      "天皇": 50, "地皇": 20, "朵皇": 0,
      "朵朵": 0, "丁二皇": 0
    }
  }
}
```

> `pool_key` 是 `club-329617`，说明写的是**独立俱乐部池**。
> 只传了 2 档，**其余 3 档保持原值**（部分更新）；若原本未配置，则为 0。

#### 10.9.3 一次配好（赔率 + 开关 + 提留）

推荐的实际用法——**三步并一步**：

```json
{
  "header": "设置_俱乐部_奖池_配置",
  "reward_on": true,
  "reward_modify": {"底皮1/3": 2, "底皮2/5": 3},
  "reward_card_bili": {"天皇": 20, "地皇": 10,
                          "朵皇": 10, "朵朵": 2, "丁二皇": 2}
}
```

#### 10.9.4 读取当前赔率

```json
{"header": "获取_俱乐部_奖池_配置"}
```

返回里 `reward_card_bili` 就是当前 5 档赔率；**未配置的档补 0**，客户端可直接渲染表格。

#### 10.9.5 运维代配（`level>=99`）

指定 `pool_key` 即可改任意池：

```json
{
  "header": "设置_俱乐部_奖池_配置",
  "pool_key": "916139",
  "reward_card_bili": {"天皇": 20}
}
```

> 池必须真实存在（联盟在 `club_unions`、俱乐部在 `clubs`），否则返回 0x301「奖池不存在」。

#### 10.9.6 常见错误

| 现象 | 原因 |
| --- | --- |
| 返回 0x200 但赔率没变 | 牌型名写错（如 `天黄`），被静默忽略。**请回读校验** |
| 返回 0x200 但玩家仍不中奖 | `reward_on` 还是 `false`，池没开启（§10.8） |
| 返回 0x301「你无权管理该奖池」 | 入盟俱乐部的创建者无权改（池归联盟）；或身份不匹配（§10.2） |
| 返回 0x301「reward_on 必须是布尔值」 | 传了字符串 "true"，要传 JSON 布尔 `true` |
| 返回 0x301「至少传一个」 | `reward_on` / `reward_modify` / `reward_card_bili` 都没传 |

### 10.10 客户端入口：游戏设置 → 奖池设置（2026-11-04）

- 页面 `assets/resources/UI/panelGameSettings.prefab`，脚本 `assets/scripts/UI/panelGameSettings.ts`。大厅「游戏设置」仅**联盟总群主**或**未入盟俱乐部创建者**可见，与 §10.2 一致。
- 数据源：`获取_俱乐部_奖池_配置` / `设置_俱乐部_奖池_配置`，不使用 §5.6 的全局配置。打开面板发一次获取（不带 `pool_key`，服务端按身份推断），底部显示池键（联盟 `union_id` / 独立俱乐部 `club-<guuid>`）。
- 界面：卡片顶部「奖池总开关」对应 `reward_on`；下方是 5 档「牌型比例」列表。第 5 档服务端键 `丁二皇`，界面显示「单独丁儿皇」，字典下发/解析用服务端键。
- **底皮提留不在客户端展示**（2026-11-04 按产品要求移除）：局内设置只保留总开关与牌型比例；`reward_modify` 仍由后台/接口维护，池级回包里的该字段客户端忽略。
- 总开关：默认关闭；关闭时牌型列表置灰且不可编辑（值保留），底部提示「池未开启：不进池、不派奖」；点下方控件会提示「请先打开奖池总开关」。开启/关闭只下发 `{"reward_on": <bool>}`，响应整表回填。
- 保存：每次改动只下发 `reward_card_bili` 整表，部分更新；响应带回整表（含 `reward_on`），客户端直接回填并提示，无需再回读。牌型名必须严格用 §10.1.1 的 5 个键，写错会被静默忽略。
- 默认 0：未配置的池回包全 0；开启后若比例仍为 0，底部提示「该池未配置时不派奖」。开关关闭写 0；重新打开恢复上次非 0 值，无历史值时用出厂默认档 20/10/10/2/2。
- 失败：`0x301` 优先显示回包 `error`（如「你无权管理该奖池」「reward_on 必须是布尔值」）。
