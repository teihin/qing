## 0. 前提与角色

| 项 | 说明 |
|---|---|
| 账号形态 | 代打号是**真实账号**，像真人一样登录、入房、下注、出牌 |
| 服务端职责 | 只负责「资格（谁能配）、槽位（配到哪手）、回执（配没配到）」 |
| 客户端职责 | 打牌策略、节奏、下注金额、是否申请配牌 |
| 生效时机 | 配牌申请必须在**发牌前**登记；发牌后再登记只对下一局生效 |

## 1. 一局的生命周期

```
① 等待开局（房内）
      ↓  客户端判断「本局还能不能申请配牌」（§4.1）
② 申请配牌（发牌前）
      ↓  服务端开局并发牌
③ 发牌_结束_消息（读 all_start_player_name = 本局参局名单、pai_number = 本次开第几张）
      ↓
④ 持有_手牌_消息（读 now_pai = 配牌后的最终手牌）
      ↓  此时可拉一次 查询_房间_游戏_信息，缓存 next_order 与全桌 take_pai
⑤ 决策（下注 / 看牌 / 敲牌 / 弃牌，沿用现有协议）
      ↓  用 state + 决策_倒计时_消息 判断是否轮到我（§4.3）
⑥ 结算（结算_信息_消息 → 结算_结束_消息）
      ↓  客户端重置状态、读 room_round
⑦ 下一局（room_round + 1），回到 ②
```

> 顺序要点：`next_order` 必须在 **③④ 之后**读。**发牌完成前**读到的 `next_order` 可能随后被替换，属正常现象。

## 2. 命令清单

### 2.1 配牌命令（当前即可用）

> **范围说明**：本文只覆盖「配牌申请 + 结果解析 + 局间衔接 + 下一局预知」。出牌/下注/看牌等链路沿用现有真人协议（`玩家_看牌_命令` / `玩家_翻牌_命令` / `玩家_切牌_命令` / `玩家_预定_命令` 等），代打改造**不改变**这些命令的语义，本文不展开。

#### `执行检查_命令` —— 申请配牌（`click` 模式）

```json
{
  "header": "执行检查_命令",
  "click_count": 1
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `click_count` | int | 见 §2.3 的 `click` 语义；缺省为 `1` |

调用后，该账号的配牌申请会被登记，并按「发牌前登记本局生效」的规则参与本局/下一局的配牌。

**门禁**：是否生效取决于服务端的账号配置（属服务端配置项，本文不涉及）；未开通的账号调用后静默无效果。

#### `关闭检查_命令` —— 取消申请

```json
{ "header": "关闭检查_命令" }
```

**现状风险**：该命令在服务端是**房间级**清零，等于同时取消全房其他人的申请。改造后只清本人，届时按本说明的语义调用即可。

#### `执行安全_命令` —— 申请指定牌型（`must` 模式）

```json
{
  "header": "执行安全_命令",
  "style": "TH"
}
```

| `style` | 牌型 |
|---|---|
| `TH` | 天杠 |
| `DH` | 地杠 |
| `DD` | 地打 |

**语义**：本局由该玩家「独占指定牌型」，其余配牌全部不执行（与现状一致）。

**门禁**：账号已开通（服务端配置）+ 当前底皮未开启奖池关牌（该状态可从 `RoomGameInfo.reward_nopai_on` 读到）。

### 2.2 `查询_房间_游戏_信息` —— 牌局感知（`next_order` 的唯一来源）

这是**现有老接口**，不是新增接口，但它是代打客户端拿到「下一局整副牌 + 全桌手牌」的唯一通道，必须纳入调用链。

```json
{
  "header": "查询_房间_游戏_信息",
  "room_id": 12345,
  "context": "任意回带串"
}
```

| 项 | 内容 |
|---|---|
| 通道 | 大厅命令（与其它 `header` 类命令同一入口） |
| 参数 | `room_id` 必填；`context` 原样回带 |
| 门禁 | 账号需在服务端开通该权限（配置项，本文不涉及）；未开通时返回 `GC_FAILED` 且**不推送任何数据** |
| 房间要求 | `room_id` 必须是已开局的 `Custom`（主力房）房间 |
| 返回值 | 恒为 `GC_OK, '{}'` —— **返回值没有数据** |
| 数据下发 | 服务端另推一条消息 `RoomGameInfo`，字段见 §3.6 |
| 频率 | 每局一次即可（`next_order` 发牌后整局不变）；建议在收到 `持有_手牌_消息` 时拉一次并缓存到本局结束 |

> **别踩这个坑**：客户端只等命令返回值会永远拿到空 `{}`，必须同时监听 `RoomGameInfo` 消息。

### 2.3 `click` 语义（核心）

| `click` | 语义 | 被占时 | 越界时 |
|---|---|---|---|
| `0` | 不参加配牌（但仍可被选为交换对象） | — | — |
| `1~8` | **软模式**：在局玩家中第 N 好 | 邻近扩散（同距离**更差**优先） | 钳到最差 |
| `11~18` | **严格模式**：固定 8 组中第 N 组（`N = click - 10`） | **放弃** | 放弃 |
| `98` | 大牌最大（`maxmax`） | 池空放弃 | — |
| `99` | 小牌最大（`maxmin`） | 池空放弃 | — |
| `9` / `10` / `19~97` | **非法**，服务端返回 `invalid_click` | — | — |

**选择建议**：

| 诉求 | 用哪个 |
|---|---|
| 想要最好的一手 | `1` |
| 想要最差的一手 | `8`（4 人房等价 `4`） |
| 必须精确拿到全组第 N | `11~18`（被占就失败，不降级） |
| 想要大牌最多的 | `98` |
| 想要小牌最多的 | `99` |

> 「严格第 1」≠「软模式第 1」：4 人房里 `click=11` 可能拿到虚拟组（本局无人认领的牌），其牌值可能优于 `click=1`。

### 2.4 `next_order` —— 下一局牌组（**本次补充，必读**）

#### 2.4.1 它是什么

服务端每次开局洗牌时，会同时准备好**下一局要发的整副牌**，随 `RoomGameInfo` 一并下发。

**契约**：`next_order` 恒等于「下一局要发的那整副牌，已洗好、未发出」，发牌完成后在一局之内不变。

#### 2.4.2 数据格式（**是字符串，不是数组**）

```json
"next_order": "['0,3,1', '2,7,1', '3,11,1', '1,2,1', '4,1,1', ...]"
```

| 项 | 说明 |
|---|---|
| 外层 | **JSON 字符串**，内容是类 Python 字面量（单引号），不是合法 JSON 数组 |
| 元素 | `"花色,点数,份号"` 三段字符串 |
| 长度 | **32**（方块 7 + 梅花 8 + 红桃 8 + 黑块 8 + 鬼 1） |
| 花色 | `0` 方块 / `1` 梅花 / `2` 红桃 / `3` 黑块 / `4` 鬼 |
| 点数 | `1~13` |
| 份号 | 同花色同点数的第几张；每种至多 1 张，故恒为 `1`，可忽略 |

**解析建议**：

```python
import ast
raw = body["next_order"]                                     # "['0,3,1', ...]"
pairs = [s.split(",")[:2] for s in ast.literal_eval(raw)]    # [['0','3'], ['2','7'], ...]
```

非 Python 客户端按结构切分：去掉首尾 `[` `]`，以 `', '` 分割元素，去引号后再以 `,` 切三段。

#### 2.4.3 映射到「下一局我的手牌」

发牌顺序（客户端可直接依赖的规则）：**从庄家本人开始，按座位号升序绕圈，跳过未准备/已起立的玩家；每人每轮 1 张，共 4 轮**。因此：

```
N     = 下一局参局人数
order = [庄家, 庄家下家, ..., 绕一圈]        # 座位号升序、跳过不在局者
idx   = order.index(我的座位号)
下一局我的第 i 张牌 = next_order[i * N + idx]      # i = 0,1,2,3
```

- `N` 是**下一局**的参局人数。只能用本局 `发牌_结束_消息.all_start_player_name` 的长度（或 `RoomGameInfo` 玩家条目数）近似——阵容未变时两者相等。
- 下一局庄家：本局庄家若下一局仍准备则**连庄**，否则顺延给下一个在局玩家。阵容不变时，**下一局的发牌顺序与本局完全相同**，可直接复用本局的 `order`。
- 8 人房 `N=8` 时 32 张刚好发完；`N<8` 时只发前 `4N` 张，其余牌不会进入任何人的手牌。

#### 2.4.4 用途

| 用途 | 做法 |
|---|---|
| 提前定配牌策略 | 算出下一局原始手牌 → 判断值不值得花 `click` 配额、用 `1` 还是 `98/99` |
| 校验配牌是否生效（**当前唯一可行的回执手段**，§4.2） | 比对「预期原始手牌」与 `now_pai` |
| 判断 `执行安全_命令` 是否划算 | 下一局若本来就能拿到天杠/地杠，就没必要用 `must` 独占 |

#### 2.4.5 限制（必须知道，否则会误判）

| # | 限制 | 说明 |
|---|---|---|
| 1 | 只是**原始发牌** | 下一局若有人配牌（`vip` 先挑 / `check` 排队 / `must` 造牌 / 让路者压牌），实际手牌与预测不同。反过来，这正是判断「配牌是否生效」的依据 |
| 2 | 依赖 `N` 与座位顺序 | 下一局有人坐下/起立/离桌 → `N` 与 `order` 变化，**整张映射表平移**，预测全部作废 |
| 3 | 依赖庄家 | 庄家不准备时顺延到下一个在局玩家，`order` 起点随之改变 |
| 4 | 读取时机 | 必须在**发牌完成之后**读；发牌完成前读到的值可能被替换 |
| 5 | 权限 | 读取该接口需服务端开通（配置项，本文不涉及）；未开通的号拿不到 `next_order`，只能走 §4.2 的「事后判断」 |
| 6 | 房间类型 | 只有 `Custom`（主力房）会返回数据 |

## 3. 需要解析的服务端消息

所有游戏内消息都通过 `onMessage('状态鸡', body)` 下发，`body.msg` 是二级消息名。**同一条消息会向房内每个玩家各发一份**，正文按收件人裁剪——解析时必须用 `player_name` 与自己的 guuid 比对，否则会读到别人的（被遮蔽的）数据。

### 3.1 `持有_手牌_消息`（发牌 / 亮牌 / 扯牌时下发）

```json
{
  "msg": "持有_手牌_消息",
  "state": "东家_决策_第一次_下注_状态",
  "event": "获取_全量_状态_事件",
  "player_number": "2",
  "player_name": "10086",
  "room_id": "xxx",
  "room_round": "12",
  "action_number": "8",
  "player_over_type": "正",
  "first_deal_name": "10010",
  "is_qiang_over": "False",
  "is_shuffled": "False",
  "player_setting": "...",
  "is_chepai": "False",
  "now_pai": [[0, 5], [2, 11], [1, 3], [4, 1]],
  "now_pai_count": 4
}
```

| 字段 | 客户端用途 |
|---|---|
| `room_round` | **局号**（字符串），用于判断是否为当前局、是否进入下一局 |
| `player_name` | 与自己的 `guuid` 比对，判断是否自己的手牌 |
| `now_pai` | 自己：4 张真实手牌（`[花色, 点数]`）；他人：前 2 张为 `[0,0]`，第 3、4 张为真实牌面（见下方说明） |
| `now_pai_count` | 手牌张数（判断是否已补到 4 张；`<4` 表示三花补牌进行中） |
| `is_chepai` | 是否已扯牌（扯牌后 `now_pai` 表示已扯出的牌） |
| `player_over_type` | `正` / `弃` / `荒` / `喜` / `花`，判断自己是否还能继续 |
| `state` | 当前状态名，配合 `决策_倒计时_消息` 判断是否轮到我 |
| `first_deal_name` | **本局庄家**（此前未列）。算 `next_order` → 手牌映射的起点，必需 |
| `is_shuffled` | 是否已切牌 |
| `is_qiang_over` / `player_setting` | 抢庄结果、玩家设置串（一般无需处理） |

**关键**：`now_pai` 是**配牌后的最终结果**。客户端不需要自己推算配牌，直接读这里即可。

> **说明（旧版写的是「别人的手牌全部遮蔽」）**：他人的 `now_pai` 实际为「前 2 张 `[0,0]` + 第 3、4 张真实牌面」——后两张按规则本就是明牌。这对代打很关键：不查接口也能看到全桌明牌。

### 3.2 `发牌_结束_消息`（**新增说明**）

每名玩家「开牌」后下发（一局内可能多条：开第 1-2 张 / 第 3 张 / 第 4 张），只发给该玩家。

```json
{
  "msg": "发牌_结束_消息",
  "state": "...", "event": "...",
  "player_number": "2", "player_name": "10086",
  "room_id": "xxx", "room_round": "12", "action_number": "3",
  "is_qiang_over": "False",
  "qiepai_status": "...",
  "all_start_player_name": ["10086", "10010", "10023", "10007"],
  "pai_number": [0, 1]
}
```

| 字段 | 用途 |
|---|---|
| `all_start_player_name` | **本局实际参局玩家名单**。这是 `next_order` 映射里 `N` 与阵容的最早可靠来源 |
| `pai_number` | 本次开的是第几张（`[0,1]` / `[2]` / `[3]`） |
| `qiepai_status` / `is_qiang_over` | 切牌、抢庄状态 |

### 3.3 `决策_倒计时_消息`（**新增说明**）

每次有玩家进入决策态时**广播**给全房：

```json
{
  "msg": "决策_倒计时_消息",
  "state": "旁家_决策_第一次_敲牌_状态",
  "event": "决策_超时_事件",
  "player_number": "3",
  "player_name": "10010",
  "countdown": 12
}
```

| 字段 | 用途 |
|---|---|
| `player_name` / `player_number` | **当前该谁决策**（与自己的 guuid 比对即「是否轮到我」） |
| `state` | 该玩家所处的决策态 |
| `countdown` | 剩余秒数（缓存有效期的现成依据） |

### 3.4 `结算_信息_消息`（每局结束，按人下发）

```json
{
  "msg": "结算_信息_消息",
  "state": "庄家_结算_状态", "event": "玩家_结算_事件",
  "player_number": "2", "player_name": "10086",
  "is_he": "False",
  "is_win": "True",
  "take_pai": [[0, 5], [2, 11], [1, 3], [4, 1]],
  "turn_pai": "...",
  "no_used_pai": [[0, 5], [2, 11]],
  "game_over_type": "正",
  "is_poker_win": "大大小小",
  "table_times": "1",
  "round_score": "12,0,0,12"
}
```

| 字段 | 说明 |
|---|---|
| `is_win` | 本局是否赢（以界面显示分数为正判赢，不是按正负分差） |
| `take_pai` | 本局最终的 4 张牌 |
| `turn_pai` | 翻牌 / 牌型串 |
| `no_used_pai` | 结算展示的剩余前 2 张（仅展示） |
| `game_over_type` | `正` / `弃` / `荒` / `赔` |
| `is_poker_win` | 上下两门的大小比较（如 `大大小小`） |
| `table_times` | 桌上累计倍数 |
| `round_score` | 四段：`本局分,芒分,喜分,合计` |
| `is_he` | 是否和局 |

> **注意**：该消息**不含 `room_round`、不含 `is_vip`**；且它按「每个玩家一条」下发，**只有关于自己的那条（或公开下发的）才有上表明细**，其余条目只有 `"round_score": "0"`。

### 3.5 `结算_结束_消息`（每局一条，带局号）

```json
{
  "msg": "结算_结束_消息",
  "state": "庄家_结算_状态", "event": "玩家_结算_事件",
  "player_number": "2", "player_name": "10086",
  "room_id": "xxx", "room_round": "12", "action_number": "9",
  "is_win": "True",
  "game_over_type": "正",
  "player_over_type": "正",
  "is_exit": "False"
}
```

| 用途 |
|---|
| **判断本局结束、取局号**（`room_round`）的首选消息 |
| `is_exit` 判断自己是否被踢/离桌 |

### 3.6 `RoomGameInfo`（`查询_房间_游戏_信息` 的响应消息）

```json
{
  "RoomGameInfo": [
    {
      "number": "1",
      "is_zhuang": "True",
      "guuid": "10086",
      "name": "昵称",
      "take_pai": [[0, 5], [2, 11], [1, 3], [4, 1]],
      "ched_pai": [],
      "player_over_type": "正",
      "is_vip": "False",
      "is_one_robot": "False",
      "is_action": "True",
      "bei_shu": 2,
      "optimize_rate": "0",
      "optimize_count": 0,
      "reward_nopai_on": "0-0",
      "gps": "...",
      "xiazhu_score": "2",

      "round_score": "0"
    }
  ],
  "next_order": "['0,3,1', '2,7,1', ...]",
```

**玩家条目字段**：

| 字段 | 客户端用途 | 备注 |
|---|---|---|
| `number` | 座位号 | 与 `next_order` 映射、发牌顺序相关 |
| `is_zhuang` | 是否本局庄家 | 等价于 `first_deal_name`，可交叉校验 |
| `guuid` / `name` | 账号 / 昵称 | 与本地 guuid 比对 |
| `take_pai` | **全桌 4 张手牌**（含已弃牌者） | 比 `持有_手牌_消息` 的遮蔽更完整 |
| `ched_pai` | 扯出的牌 | 与 `is_chepai` 对应 |
| `player_over_type` | 正/弃/荒/喜/花 | 判断谁还在局 |
| `is_vip` | 是否 optimize 中标 | 该字段在服务端带账号过滤，**被过滤的账号恒为 `False`**，不要单凭它判断是否中标 |
| `is_action` | 该玩家是否处于决策态 | 「是否轮到我」的辅助信号 |
| `bei_shu` / `xiazhu_score` | 总倍数 / 本轮下注 | 下注策略 |
| `optimize_rate` / `optimize_count` | 优化概率 / 剩余次数 | 特定账号查看他人时显示 `999`（服务端口径） |
| `reward_nopai_on` | 奖池关牌状态 `全局-本底皮` | `执行安全_命令` 的门禁依据 |
| `total_score` / `round_score` | 房间累计 / 本局分 | 战绩 |
| `round_count` | 局号（每个条目同值重复） | 与 `room_round` 对照，防跨局 |
| `gps` | GPS 串 | 一般无需处理 |

**顶层字段**：

| 字段 | 说明 |
|---|---|
| `next_order` | **下一局整副牌**（字符串，见 §2.4.2） |
| `game_end_time` | 房间剩余时间（秒） |
| `all_man_score` | 全房按分数降序的分数表 |
| `all_visitor` | 访客情报串（需服务端开通，否则为空） |
| `context` | 原样回带 |

### 3.7 局号与阶段对照

| 需要的信息 | 从哪拿 |
|---|---|
| 局号 `room_round` | `持有_手牌_消息` / `发牌_结束_消息` / `结算_结束_消息` / `RoomGameInfo.round_count` |
| 本局是否已发牌 | 是否收到本局 `持有_手牌_消息` |
| 本局参局名单 | `发牌_结束_消息.all_start_player_name` |
| 本局庄家 | `持有_手牌_消息.first_deal_name` / `RoomGameInfo.is_zhuang` |
| 当前状态名 | `持有_手牌_消息.state` / `决策_倒计时_消息.state` |
| 是否轮到我 / 剩余时间 | `决策_倒计时_消息.player_name` + `countdown` |
| 配牌是否生效 | `now_pai` 与 §2.4.3 的预测比对（§4.2） |

## 4. 关键判定逻辑

### 4.1 什么时候可以申请配牌？

```
条件：尚未发牌（还没收到本局的 持有_手牌_消息）
    且 当前 room_round 与你上次申请的 round 不同（避免重复申请同一局）
```

建议在**每局结算后**立即为下一局申请：

```python
def on_settle(msg):
    if int(msg.room_round) != my_last_apply_round:   # 服务端下发的是字符串
        apply_pair(click=1)                          # 为下一局申请
        my_last_apply_round = int(msg.room_round)
```

> 现状服务端**不记录局号**（配套方案 §13.1 第 3 条）：发牌后登记的申请不保证作用于本局，也不保证作用于下一局，只能靠「发牌前登记」这条时序纪律。

### 4.2 怎么判断配牌是否生效？

服务端目前没有「配牌回执」接口，用下方两条路判断：

| 方式 | 做法 | 可靠性 |
|---|---|---|
| **推荐**：对比 `next_order` 预测 | 用 §2.4.3 算出「不配牌时应拿到的 4 张」，与 `持有_手牌_消息.now_pai` 比对：完全一致 → 本局没对你配牌；不一致 → 发生了配牌/换牌 | 高（能判断「变没变」） |
| 辅助：对比 `RoomGameInfo` | `take_pai` 全桌牌值 + `is_vip` + `optimize_rate`：自己的牌变好、同时有人变差，才是「你中标」 | 中 |

**边界**：`now_pai` 变了只能说明「牌被动了」，无法区分「你中标拿到好牌」与「你被别人换走」。要区分必须结合「牌值变好/变差」与 `is_vip`（注意部分账号的 `is_vip` 恒为 `False`，见 §3.6）。

### 4.3 怎么判断轮到我？

| 方式 | 说明 |
|---|---|
| **推荐**：`决策_倒计时_消息` | `player_name == 自己` 且 `state` 含「决策」→ 轮到我；`countdown` 即剩余秒数 |
| 兜底：`state` 字符串 | `持有_手牌_消息.state` 含「决策」；**不要只匹配前缀** `东家_决策_` / `旁家_决策_`，搓牌阶段的状态名形如 `搓牌_等待_旁家_决_策_...`（历史命名，把「决策」拆成了「决_策」），前缀匹配会漏 |

### 4.4 怎么判断进入下一局？

`room_round` 递增（字符串，需转 int 比较）。可靠时点是 `结算_结束_消息`：

```python
if int(msg.room_round) > my_round:
    my_round = int(msg.room_round)
    reset_round_state()
```

## 5. 完整流程（伪代码）

```python
class DaidaClient:
    def __init__(self):
        self.my_round = 0
        self.applied_round = -1
        self.next_order = []        # 下一局整副牌（已解析为 [[花色,点数], ...]）
        self.start_players = []     # 本局参局名单
        self.banker = None          # 本局庄家
        self.is_vip = False

    # ── ① 入房后 ──
    def on_enter_room(self):
        self.query_room_game_info()     # 拉一次牌局感知（含 next_order）

    # ── ② 每局开始前申请（结算后立即申请下一局）──
    def on_settle(self, msg):
        rnd = int(msg.room_round)       # 服务端下发的是字符串
        if rnd != self.applied_round:
            self.apply_pair(self.pick_click())   # 用 next_order 预测来选 click
            self.applied_round = rnd

    def apply_pair(self, click):
        send({"header": "执行检查_命令", "click_count": click})

    # ── ③ 发牌：先拿名单，再拿手牌 ──
    def on_fapai_over(self, msg):
        self.start_players = msg.all_start_player_name

    def on_hold_pai(self, msg):
        if msg.player_name != self.guuid:
            return
        self.my_round = int(msg.room_round)   # 注意：服务端下发的是字符串
        self.banker = msg.first_deal_name
        self.hands = msg.now_pai              # 最终手牌，含配牌结果

        # 本局发牌完成后拉一次，缓存「下一局整副牌」
        self.query_room_game_info()

        # 判定本局是否被配牌（无回执接口，用预测比对）
        expect = self.predict_hand(self.next_order, self.banker, self.start_players)
        self.was_paired = (expect is not None and expect != self.hands)

    # ── ④ 决策 ──
    def on_countdown(self, msg):
        if msg.player_name != self.guuid:
            return                            # 不是我
        if "决策" not in msg.state:
            return                            # 非决策态
        self.game_action(self.hands, msg.state, msg.countdown)

    # ── ⑤ 下一局预测（详见 §2.4.3）──
    def predict_hand(self, next_order, banker, players):
        n = len(players)
        if n == 0 or len(next_order) < 4 * n:
            return None
        order = rotate_from(banker, players)   # 从庄家起、按座位号升序绕圈
        idx = order.index(self.seat)
        return [next_order[i * n + idx] for i in range(4)]

    # ── ⑥ 策略 ──
    def pick_click(self):
        # 由客户端策略决定：下注 / 看牌 / 切牌 / 弃牌、以及是否值得配牌
        return self.strategy.choose_click(self.hands, self.next_order)
```

## 6. 错误与重试

| 现象 | 原因 | 处理 |
|---|---|---|
| `执行检查_命令` 无任何效果 | 账号未开通 | 客户端侧无法补救，需服务端配置 |
| `查询_房间_游戏_信息` 返回 `GC_FAILED`，且无 `RoomGameInfo` | 账号未开通 / `room_id` 不存在 / 该房不是 `Custom` | 换号或走 §4.2 的事后判断；不要重试刷屏 |
| 只等命令返回值，永远拿到 `{}` | 数据走的是 `RoomGameInfo` 推送 | 补监听 `RoomGameInfo`（§2.2） |
| `next_order` 为 `""` 或项数不足 `4N` | 早于发牌完成读取 / 房间未开局 | 收到 `持有_手牌_消息` 后再拉一次 |
| `next_order` 与实际手牌整体错位 | 下一局阵容或庄家变化 | 重算 `order`；算不出来就放弃预测 |
| `决策_倒计时_消息` 不带局号 | 该消息没有 `room_round` 字段 | 以 `持有_手牌_消息.room_round` 为当前局基准 |
| 手牌 `now_pai_count < 4` | 三花补牌进行中 | 等待后续 `持有_手牌_消息` |
| `is_vip=true` 但没拿到预期牌 | 配牌被 `vip` 抢占（多 vip 场景） | 以 `now_pai` 实际牌面为准 |
| 部分账号 `is_vip` 永远 `False` | 服务端对该字段有账号过滤 | 不要用 `is_vip` 判断是否中标 |

## 7. 调用约束（客户端须遵守）

| # | 约束 | 原因 |
|---|---|---|
| 1 | **申请必须在发牌前** | 发牌后登记只对下一局生效（且无局号保证） |
| 2 | **每局只申请一次** | 重复申请会被累计，多出来的申请不产生额外效果 |
| 3 | **`click` 只能用 `1~8` / `11~18` / `98` / `99`** | `9`、`10`、`19~97` 返回 `invalid_click` |
| 4 | **配牌结果以 `now_pai` 为准** | 服务端可能因槽位冲突降级 |
| 5 | **出牌沿用现有真人协议** | 代打不改变出牌链路 |
| 6 | **`must` 局独占** | 一旦有人申请指定牌型，本局其余配牌全部不执行 |
| 7 | **`next_order` 只是原始牌序** | 不含配牌结果，也不含「下一局阵容变化」 |
| 8 | **`next_order` 在发牌完成后读、每局一次** | 发牌完成前该字段可能被替换 |
| 9 | **`is_vip` 只表示 optimize 中标** | 不等于「配牌成功」；部分账号恒 `False` |

## 8. 一局最小调用序列

```
入房
  → 查询_房间_游戏_信息（拿 RoomGameInfo / next_order）
  → （结算后）执行检查_命令 click=1
  → 发牌_结束_消息（all_start_player_name）
  → 持有_手牌_消息（读 now_pai / first_deal_name / room_round）
  → 查询_房间_游戏_信息（缓存下一局 next_order、全桌 take_pai）
  → 决策_倒计时_消息（player_name == 我）→ 出牌命令 × N
  → 结算_信息_消息 → 结算_结束_消息（读 room_round）
  → 回到第 2 步
```

## 9. 当前可用性

| 能力 | 状态 |
|---|---|
| `执行检查_命令` / `关闭检查_命令` / `执行安全_命令` | ✅ 现有 |
| `查询_房间_游戏_信息` → `RoomGameInfo`（含 `next_order` + 全桌 `take_pai`） | ✅ 现有（仅 `Custom` 房 + 需服务端开通） |
| 解析 `持有_手牌_消息` / `发牌_结束_消息` / `决策_倒计时_消息` / 结算两条 | ✅ 现有 |
| 单机器人申请生效 | ✅ 现有（多机器人会互相覆盖，需改造） |
| 多机器人同时申请 | ⏳ 需服务端改造（见配套方案） |
| 配牌回执（精确到你中了哪一手） | ⏳ 无接口；当前只能用 `next_order` 预测 + `now_pai` 比对间接判断 |

**结论**：单机器人代打当前协议即可跑通；多机器人同房需等待配牌改造上线。精确的「配牌回执」目前没有接口，用 `next_order` 预测配合 `now_pai`/`take_pai` 比对是唯一可行手段。
