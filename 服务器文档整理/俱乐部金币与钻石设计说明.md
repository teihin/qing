# 俱乐部金币与钻石设计说明

> **2026-11-03 变更（额度与抽水已变）**：代理不再有独立额度账户，带入/结算改扣俱乐部的 `union_quota`（总群主授信）；抽水分成**不再回补额度**，改为按 `percent` 逐层累加到代理红利（`club_agent_info.bonus`，分），可整元提取成俱乐部积分。兑换钻石仍扣群主 `stone` 池，与联盟额度无关。本文档中涉及「额度授信 / 额度回补 / 抽水回补」的段落仅作历史参考，最新接口见 `doc/俱乐部俱乐部联盟模式V2方案-客户端接口文档.md`。

> **文档定位**：本文件收纳"俱乐部金币 / 玩家金币 / 钻石（stone）"相关的**全部服务端设计**，后续同类需求（含但不限于兑换、消费、限额、活动汇率、对账）在本文件**追加章节**，不再另建零散文档。
> **配置文档配套**：《俱乐部金币与钻石-客户端接口文档.md》（客户端对接用）。
> **状态**：v1 金币兑换钻石、v1.1 Hall 消费命令支持钻石、v1.2 牌桌消费与加时支持钻石、v1.3 客户端查询接口、**v1.4 俱乐部钱包与额度体系（§11）**。v1~v1.3 已部署测试服（DB 加列已执行）；v1.4 已改代码、**未部署**。

---

## 1. 背景与目标

1. **v1 兑换**：客户端大厅新增「兑换钻石」弹窗（档位 100 / 200 / 500 / 1000 / 2000 / 5000 / 10000 / 20000 钻，底部文案"兑换 100 钻石需消耗 1 金币"，即 **1 金币 = 100 钻石**）。目标：服务端提供**金币 → 钻石**兑换能力，复用现有货币通道，**不新增命令、不改 Account.def 协议、不改数据库表结构**。
2. **v1.1 消费**：现有玩家消费接口 `玩家_消费_命令`（示例 `{"consume_type":"看数据","money":50}`）只支持扣金币；本次**新增支持扣钻石**，同样复用现有扣减与记账函数，不新增命令。

## 2. 名词与数据模型

| 名称 | 服务端字段 / 表 | 说明 |
| --- | --- | --- |
| 金币（玩家金币） | `Account.gold`（整数，元）+ `Account.gold2`（分） | 玩家主货币；转账、红利提取、房间带入都用它 |
| 俱乐部金币（俱乐部积分） | `Account.club_gold`（JSON，按 `club_id` 存）；俱乐部侧 `Club.number_count` 等 | 按俱乐部隔离的积分，不是玩家钱包 |
| 钻石 | `Account.stone` | 房卡/兑换货币；分享奖励、消费等走它 |
| 消耗流水 | `usr_consume_info`（`date,time,user_name,user_guuid,option_type,money_number,money_type,total_money`） | `decStoneNumber` 自动写；`money_type` = `gold` / `stone`；`option_type VARCHAR(50)` |
| 金币消费流水 | `usr_cash_water`（`option_type,old_money,new_money,add_money,remark1..5`） | 金币消费/充值类流水，金额口径是**元/分**（`玩家_消费_命令` 现用它） |
| 兑换/转账流水 | `usr_exchange_info`（`date,user_name,user_guuid,target_guuid,type,stone_number,target_name`） | 客户端「记录」页数据源（`reqGetExchangeInfo`，排除 `提取红利`） |

要点：**钻石只有玩家维度**（`Account.stone`），没有"俱乐部钻石"；"俱乐部"相关的是**俱乐部金币**（见 §4.2）。**v1.4 变更**：俱乐部金币已升级为"俱乐部钱包 + 代理额度"双账户，可兑换钻石，见 §11。

## 3. 现有实现盘点（复用基础）

### 3.1 统一实现：`Account.reqExChange2(target_guuid, money_value, money_type)`

- 定义于 `scripts/base/Account.py`（约 2823-2900 行），在 `scripts/entity_defs/Account.def`（约 1224-1229 行）以 `<Exposed/>` 暴露，**客户端可直接调用（无密码）**；与"有密码"的 Hall 命令并行，见 §3.5。
- `target_guuid == self.guuid`（自己给自己）→ **货币兑换分支**；目标为他人 → 转账分支。
- `money_type` 约定：`"<币种>,<俱乐部ID|非俱乐部>"`，例如 `"gold,非俱乐部"`（逆向的 `"stone,..."` 已禁止，见 §4.3）。
  - 拆分方式：`club_money_type = money_type.split(',')[0]`、`club_id = money_type.split(',')[1]`（研发约束：必须带逗号，服务端不做容错）。

### 3.2 兑换分支现状：只实现了 `stone → gold`

```text
stone_to_gold = d_halls.config["account"].get("stone_to_gold", 0)
gold_to_stone = d_halls.config["account"].get("gold_to_stone", 0)
两者都为 0 → onExChange(EC_FAILED)

if stone_to_gold > 0 and 币种 == 'stone' and self.stone >= money_value:
    club_id == '非俱乐部' → decStoneNumber(-money_value * stone_to_gold, isGold=True)   # 加玩家金币
    否则                   → decClubGoldNumber(club_id, -money_value * stone_to_gold)   # 加俱乐部金币
    decStoneNumber(money_value, isGold=False)                                          # 扣钻石
    onExChange(EC_OK)

否则 → onExChange(EC_FAILED)
```

- **`gold_to_stone` 配置代码已在读，但没有实现分支**，`gold → stone` 会直接落到 `EC_FAILED`；仓库 `scripts/data/d_halls.py` 里也还没有这个键（默认 0）。
- 兑换流水处留有 TODO（原实现未写 `usr_exchange_info`）。
- **2026-10-26 起 `stone → gold` 已禁止**：原实现整段注释保留、不可达，详见 §4.3。

### 3.3 记账函数：`Account.decStoneNumber(stoneNumber, isGold=False, optionType='未知')`

`scripts/base/Account.py` 约 1307-1343 行：

- 语义：**正数=扣、负数=加、0 夹底**；`isGold=True` 操作 `gold`，否则操作 `stone`；
- 内部 `writeToDB()` + `updateProperty()`（属性同步客户端）+ 写 `usr_consume_info`；
- **`level >= 99`（boss）不扣不加**（只打 DEBUG）；
- 扣减与写流水**不是事务**：先改内存+落库，再异步 insert 流水；insert 失败会出现"扣了没流水"（见 §7）。

### 3.4 回调与返回码

`onExChange(INT32)`（`Account.def` 约 642-644 行），`scripts/common/GlobalConst.py`：`EC_OK=0x200`、`EC_FAILED=0x301`、`EC_NO_MONEY=0x302`、`EC_NO_PWD=0x307`、`EC_PWD_ERR=0x308`。

### 3.5 两条客户端入口（并行，客户端自选）

**2026-10-26 定案**：允许客户端二选一——**方式 A（有密码）**或**方式 B（无密码）**，两者共用同一套兑换实现与业务校验，差别只在"外层风控"。

| | 方式 A（有密码） | 方式 B（无密码） |
| --- | --- | --- |
| 入口 | Hall 命令 `调用_方法_Exchange2` → `Account._actCallExchange2`（约 4525-4612 行） | Account 直连 `reqExChange2(target_guuid, money_value, money_type)` |
| 密码 | 需要 `user_pwd`（MD5 比对 `userPWD2`） | 无 |
| 单笔限额 | `exchange2_limit_num`（线上 50000）/ `exchange2_low_num`（线上 1） | 无 |
| 客户端版本 | 低于 `limit_version` 直接失败 | 无 |
| 交易黑名单 | `usr_hash_info` 的 `<guuid>_交易黑名单` | 无 |
| boss 开关 | `level==99` 时看 `boss_exchange2_on` | 无（仍受 `decStoneNumber` 的 boss 空转影响） |
| 同步响应 | `0x200/0x301` 空壳 `result`（部分失败分支也返回 `0x200`） | 无 |

方式 A 的校验顺序：版本 → boss 开关 → 密码 → 金额 → 单笔上下限 → 币种余额 → 交易黑名单 → `reqExChange2`；任一步失败都会 `onExChange` 给出原因（`EC_FAILED` / `EC_NO_MONEY` / `EC_NO_PWD` / `EC_PWD_ERR`）。

两种方式共同的业务校验（写在 `reqExChange2` 里，改这里两条通道同时生效）：`money_value > 0`、币种必须 `gold`、目标必须 `非俱乐部`、`gold_to_stone > 0`、`self.gold >= money_value`、钻石逆向兑换禁止。

> **回包口径**：兑换成败一律以 `onExChange` 为准；方式 A 的同步响应只是"命令已受理"，不能据此提示成功。

### 3.6 消费命令现状：`Hall._actPlayerConsumeCmd`

`scripts/base/Hall.py`（约 7904-7942 行），Hall 命令 `玩家_消费_命令`（注册于约 10712 行）：

- 参数：`consume_type`（业务类型字符串）、`money`（**单位分**）、`context`；`money < 0` → `GC_FAILED`；
- 扣减：`big_money = gold*100 + gold2 - money`，**不足时把 `gold`/`gold2` 直接置 0 并继续**（不报错）；
- 流水：手写 `usr_cash_water`（`option_type='消费'`、`remark4=consume_type`、`remark5='用%s角-余%s分'`）；
- 固定返回 `GC_OK`（`result='{}'`）。

另：`pm_bipai_chuanxiaoxuan_game.py` / `pm_bipai_chuanxiaoxuan_b_game.py` / `pm_bipai_fubenxuan_game.py` 里也有同名 header 的处理，但那是**房间命令通道**且分支前已有 `return`（不可达），**本次不动**。

## 4. v1 设计：金币兑换钻石

### 4.1 规则

| 项 | 规则 |
| --- | --- |
| 方向 | **只做单向：金币 → 钻石**；钻石（房卡）→ 金币**禁止**（§4.3） |
| 汇率 | 配置 `gold_to_stone`（每 1 金币兑换的钻石数），**设 100**（1 金 = 100 钻）；`0` = 功能关闭 |
| 金额语义 | `money_value` = **消耗的金币数量**（客户端按汇率把钻石档位换算成金币后传入；服务端只做乘法，不做除法取整） |
| 校验 | `money_value > 0`；`gold_to_stone > 0`；币种必须 `gold`、目标必须 `非俱乐部`；`level < 99`（boss 拒绝） |
| 配置生效 | `reqExChange2` 每次兑换前执行 `tools.auto_reload()`，改 `d_halls` 汇率**热生效**（A/B 两条入口一致，无需重启） |
| 目标限制 | v1 仅 `club_id == '非俱乐部'`（扣玩家金币）；**v1.4 起支持 `"gold,<club_id>"` 扣俱乐部钱包**（见 §11.8） |
| 余额校验 | `self.gold >= money_value`，否则 `EC_NO_MONEY` |
| 执行 | `decStoneNumber(money_value, isGold=True, optionType='玩家兑换')` 扣金币 → `decStoneNumber(-money_value * gold_to_stone, isGold=False, optionType='玩家兑换')` 加钻石 |
| 流水 | 写 `usr_exchange_info`：`type='金币兑换钻石'`、`stone_number=money_value * gold_to_stone`、`target_guuid=self.guuid` |
| 成功回调 | `onExChange(EC_OK)` |

档位对照（`gold_to_stone=100`）：100 钻 = 1 金、200 = 2、500 = 5、1000 = 10、2000 = 20、5000 = 50、10000 = 100、20000 = 200（客户端传的是左侧换算后的**金币数**）。

### 4.2 关键取舍

1. **传金币数而不是钻石数**（2026-10-26 确认）：服务端只做乘法，不引入除法取整，避免"少扣多给"或"扣了不给"的边界问题；换算责任在客户端，汇率仍由服务端配置（改汇率时客户端档位文案同步）。
2. **俱乐部金币不能换钻石（v1.4 已作废）**：v1 时俱乐部金币是纯积分、不可换钻；v1.4 起改为「俱乐部钱包 + 代理额度」双账户，兑换会同时扣玩家积分与代理额度，模型见 §11，原结论不再适用。
3. **限额只在方式 A 生效**：走 `调用_方法_Exchange2` 时自动受 `exchange2_limit_num=50000` / `exchange2_low_num=1` 约束；方式 B（直连）不校验限额，靠客户端界面档位（最大 200 金）与余额自然约束。频控/每日上限本期不做，需要时在 §8 追加。

### 4.3 加固（同一处代码）

1. **禁止钻石（房卡）逆向兑换金币**（2026-10-26 确认）：`money_type` 币种为 `stone` 一律 `EC_FAILED`；原 `stone → gold` 实现**整段注释保留、不可达**。这同时消除了原分支"传负数会金币和钻石同时增加"的漏洞——该漏洞只存在于逆向分支，禁止后不再可达。
2. **金额正数校验**：新分支要求 `money_value > 0`，负数/零直接拒绝，不做任何货币变动。
3. **`money_type` 必须带逗号**：研发约束（固定 `"gold,非俱乐部"`），服务端按现有 `split(',')` 解析，**不做容错兜底**（客户端传错由客户端保证，不在服务端加分支）。

### 4.4 明确不做

- **钻石（房卡）→ 金币**：设计禁止，不是待办（经济模型不允许逆向）。
- **boss（`level >= 99`）不能兑换**：`decStoneNumber` 对 boss 不扣不加，若放行会"回成功 + 写流水但货币不变"，2026-10-26 起兑换分支直接返回 `EC_FAILED`（不写流水、不动货币）。
- 小数金币（`gold2`，分）不参与兑换，本设计只支持**整金币**。
- 不新增协议字段、不新增 Hall 命令、不改表（**v1.4 已突破**：新增 3 个额度 Hall 命令 + `club_agent_info.quota` 一列，仍不改 `Account.def`，见 §11）。

## 5. v1.1 / v1.2 设计：消费与加时支持钻石

### 5.1 需求与口径（2026-10-26 确认）

现状见 §3.6：只能扣金币（`money` 单位=分），余额不足"清零继续"。本次新增钻石消费，确认的口径：

| # | 口径 |
| --- | --- |
| 1 | 新增可选参数 `money_type`，**缺省 `gold`**（老客户端不传 = 金币，行为完全不变）；`money_type="stone"` 时 `money` 表示**钻石个数** |
| 2 | 钻石不足**沿用金币的"清零继续"**：扣到 0 就停，仍返回 `GC_OK`（与现有金币行为一致） |
| 3 | 钻石消费流水**只写 `usr_consume_info`**（复用 `decStoneNumber` 自动写，`money_type='stone'`），不写 `usr_cash_water`（该表是金币元/分口径，写钻石会污染统计） |
| 4 | boss/运营账号（`level>=99`）**沿用 `decStoneNumber`（不扣不记）**，仍返回成功 |

### 5.2 参数契约

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | 固定 `"玩家_消费_命令"` |
| `consume_type` | string | 是 | 业务类型（如 `看数据`），写入流水；**服务端截断到 20 字**（`option_type` 为 `VARCHAR(50)`） |
| `money` | int | 是 | **金币消费 = 分**（50 = 0.5 元）；**钻石消费 = 钻石个数**（20 = 20 钻）；必须 ≥ 0 |
| `money_type` | string | 否 | 白名单：不传 / `gold` / 空串 = 金币；`stone` = 钻石；**其它值一律失败**（见 5.4） |
| `context` | string | 否 | 透传 |

> ⚠️ 同一参数 `money` 在两种币种下**单位不同**，这是联调最容易出错的点，客户端传参处必须显式区分。

### 5.3 处理流程

```text
money < 0                                → GC_FAILED（原逻辑，不变）
money_type = json.get('money_type', 'gold')
money_type 不在 ('', 'gold', 'stone') 中  → GC_FAILED（白名单，防拼错静默扣金币）
if money_type == 'stone':
    if money == 0                        → GC_OK（不记账，避免 0 消费脏流水）
    if money > player_consume_max        → GC_FAILED（缺省 100000）
    old_stone = account.stone
    decStoneNumber(money, isGold=False, optionType='消费-%s' % consume_type[:20])   # 扣钻 + 写 usr_consume_info 台账
    add_stone = account.stone - old_stone                                            # 实际扣减额（余额不足会夹 0）
    if add_stone != 0:                                                               # boss 空转/零余额不写，避免 0 金额脏流水
        写一条 usr_cash_water（money_type='stone'、option_type='消费'、remark4=consume_type、remark5='用X钻-余Y钻'）
    → GC_OK
# 金币：走原有逻辑，逐字不变（big_money 计算 + usr_cash_water + GC_OK）
```

### 5.4 评审后补的三条加固（2026-10-26）

1. **`money_type` 白名单**（必须）：若只判断 `== 'stone'`、其余都当金币，客户端把 `money_type` 拼错（`"STONE"`、`"钻石"`）或误用兑换接口的 `"gold,非俱乐部"` 时，会**静默按金币扣钱**（且 `money` 被当"分"）。改为白名单三态后，未知值直接失败。
2. **单次金额上限**（必须）：`money` 无上限时，改包客户端可传极大值——`decStoneNumber` 只扣到 0（无资金损失），但 `usr_consume_info.money_number` 记的是**请求值**，`INT(11)` 超限时 insert 报错，而扣减已落库 → "扣了没流水"。新增配置 `player_consume_max`（`d_halls.config["account"]`，**代码缺省 100000**，线上不配也有保护），超限返回 `GC_FAILED`。
3. **`consume_type` 截断 20 字**（必须）：`option_type = '消费-%s' % consume_type`，`option_type` 为 `VARCHAR(50)`；客户端传超长/异常字符串可能导致截断或 insert 失败（同样"扣了没流水"）。统一截断到 20 字，`option_type` 最长 23 字，安全。

### 5.5 流水与报表口径

| 币种 | 展示用表（客户端查询） | 台账表（后台对账） |
| --- | --- | --- |
| 金币 | `usr_cash_water`（`money_type='gold'`）：`option_type='消费'`、`remark4=consume_type`、`add_money=-money`（分）、`remark5='用%s角-余%s分'` | —（金币不走 `decStoneNumber` 时不产生台账行） |
| 钻石 | `usr_cash_water`（`money_type='stone'`）：牌桌消费/加时由牌桌直接写；**Hall 钻石消费按"实际扣减额"补写一条** | `usr_consume_info`：`decStoneNumber` 自动写，`option_type='消费-<consume_type>'`、`money_number=-请求值`、`total_money=扣后余额` |

**口径约定（2026-10-26）**：
- **消费统计/对账以 `usr_cash_water` 为准**（金币 `money_type='gold'`、钻石 `money_type='stone'`），因为它是客户端展示源且记录实际扣减额；
- `usr_consume_info` 是 `decStoneNumber` 的扣费台账（含兑换、赠送、开房等非消费动作），**不能**直接当"消费统计"用；同一笔 Hall 钻石消费在两表各有一行，按表统计会重复计数；
- Hall 钻石消费写 `usr_cash_water` 时 `old/new/add_money` 记的是**钻石个数**（实际扣减额），靠 `money_type` 与金币行区分；报表 SQL 必须带 `money_type` 条件。

运营/对账查询示例：

```sql
-- 金币消费
select date,time,user_guuid,user_name,remark4,add_money
from usr_cash_water where money_type='gold' and option_type='消费' order by id desc limit 50;

-- 钻石消费（推荐口径：实际扣减额）
select date,time,user_guuid,user_name,option_type,remark4,add_money,new_money
from usr_cash_water where money_type='stone' order by id desc limit 50;

-- 钻石扣费台账（含兑换/赠送等，非消费统计用）
select date,time,user_guuid,user_name,option_type,money_number,total_money
from usr_consume_info where money_type='stone' order by id desc limit 50;
```

> 客户端展示：金币消费走 `查询_玩家_现金流水`，钻石消费走新增的 `查询_玩家_钻石流水`（见 §5.11）；两表都不走「记录」页的 `usr_exchange_info`（那是兑换/转账）。

### 5.6 边界与已知问题

- **账实不平（已接受）**：钻石不足时实际扣光，但流水记请求值（如持 10 传 50 → 流水 -50、余额 0）；与金币路径一致，对账时以 `total_money` 复核。
- **`money=0`**：钻石路径直接 `GC_OK` 且不记账；金币路径保持原行为（会写一条 0 消费流水）。
- **boss**：`decStoneNumber` 对 `level>=99` 不扣不加，但接口仍回 `GC_OK`；测试须用普通账号。
- **无幂等/频控**：连点会连扣（金币路径同样），界面防抖即可，服务端不加。
- **消费无退款通道**：算错价格只能后台补，属既有机制。
- **房间内同名 header**：不在本次范围（见 §3.6）。

- 不新增命令、不改 `Account.def`。

## 9. 部署与验收

部署（沿用项目规范）：本地 `py_compile` → 拉线上文件 diff 核对（只允许出现本次差异）→ 备份 `/root/backup_*` → 上传 → 校验 MD5/LF/`root:root 644` → 远端 `py_compile` → 清 `__pycache__` 对应 pyc → 用户手动重启（screen 会话 `kbe`）。**`d_halls.py` 禁止覆盖**（线上有服务器特有配置），只能原地加行。

当前部署状态：v1（兑换）已上传 `Account.py` + 线上已原地加 `"gold_to_stone": 100`；v1.1（消费）与 v1.3（查询接口）同在 `Hall.py`（`player_consume_max` 走代码缺省）；v1.2（牌桌）已上传 `pm_bipai_chuanxiaoxuan_game.py` 并已在线上执行 `usr_cash_water` 加列 DDL。全部**同一次重启后生效**。

**v1 兑换冒烟（A/B 各一遍，只看 `onExChange`）**

1. 正常兑换（A）：`调用_方法_Exchange2` + `target_guuid=自己, money_value=5, money_type='gold,非俱乐部'`（=500 钻）→ `onExChange(0x200)`，钻石 +500、金币 −5，`usr_exchange_info` 一条 `金币兑换钻石`；
2. 正常兑换（B）：`reqExChange2` 同上参数 → 行为一致；
3. 余额不足 → `EC_NO_MONEY(0x302)`，货币不变；
4. 负数/零 `money_value` → 失败，货币不变；
5. **逆向必须失败**：`money_type='stone,非俱乐部'` → `0x301`，金币和钻石都不变；
6. 传俱乐部 ID → `0x301`，俱乐部积分不变；
7. `gold_to_stone=0` → `0x301`；
8. 密码链路（仅 A）：空密码 `0x307`、错密码 `0x308`；
9. 版本链路（仅 A）：低版本 `0x301` + "当前版本失效…"；
10. boss 兑换 → `0x301`，不写 `usr_exchange_info`；
11. 汇率热更新：改 `gold_to_stone` 后不重启再兑换，按新汇率（A/B 都验）。

**v1.1 消费冒烟**

1. 金币消费（不传 `money_type`）：`money=50` → 金币扣 0.5 元（`gold2` 参与）、`usr_cash_water` 一条（行为与改动前一致）；
2. 钻石消费：`money_type='stone', money=20` → 钻石 −20、`usr_consume_info` 一条（`option_type='消费-看数据'`、`money_number=-20`、`total_money=扣后余额`）；
3. 钻石不足：持 10 传 50 → 扣到 0、回 `GC_OK`、流水记 -50（已接受）；
4. 未知 `money_type`（`"STONE"`、`"gold,非俱乐部"`）→ `GC_FAILED`，金币与钻石都不变；
5. 超上限：`money=200000` → `GC_FAILED`；
6. 超长 `consume_type`（>20 字）→ `option_type` 被截断，insert 成功；
7. `money=0`：钻石路径回 `GC_OK` 且不写流水；金币路径保持原行为；

## 11. 俱乐部钱包与额度体系（2026-10-31，v1.4）

> 完整方案与评审记录见 `doc/俱乐部积分与额度方案.md`；面向客户的说明见 `doc/俱乐部积分与额度说明（通俗版）.md`。本节只记录与金币/钻石体系直接相关的部分。

### 11.1 两层结构：积分是筹码，额度是钱

| | 玩家积分 `Account.club_gold` | 代理额度 `club_agent_info.quota` |
| --- | --- | --- |
| 本质 | 玩家在本俱乐部的**游戏筹码**，平台对玩家的负债 | 代理在平台的**资金结算账户**，玩家输赢由代理承担 |
| 单位 | 整数**元** | 整数**分**（客户端 ÷100 展示） |
| 变动时机 | 上分、下分、带入、结算、兑换 | **只有带入、结算、兑换**（另加抽水逐层回补） |
| 归属 | 玩家（`{club_id: 金额}` JSON） | 代理（每俱乐部每账号一份） |

带入与结算对两个池子是**同增同减**的，因此：

```
Σ玩家积分(元) − Σ代理额度(分)/100 = 常数 + Σ(上分 − 下分) − Σ(代理抽水分成)/100
```

只有上分/下分会改变差值；带入、结算、兑换在数学上不可能造成偏差。停服核账时等式不平 → 一定是积分加减或抽水回补的记录缺了。

### 11.2 数据模型

| 字段 | 说明 |
| --- | --- |
| `Account.club_gold` | 复用，`{club_id: 整数元}`，`BASE_AND_CLIENT` + `Persistent`，**不改 def** |
| `club_agent_info.quota` | 新增，`BIGINT(20) NULL DEFAULT NULL`，单位分。**三态**：`NULL`＝还没被上级授信；`0`＝已授信但暂无可用额度；`>0`＝可用额度 |
| 是否代理（`is_agent`） | **不落列**。加载代理树时用子查询算：`club_invite_code_info` 里有 `status='used'` 的码即为代理（创建者天然是代理）。与 `PushClubAgentInfo` 的 `is_agent` 同口径，**不能用 `percent` 判**（代理可把比例设为 0） |

`NULL` 与 `0` 的区别是业务语义，不能合并：授信 0 元也必须把 `NULL` 写成 `0`，否则这个人永远无法成为出资方。

### 11.3 三个对称动作

```text
【找代理】agent = 沿玩家 upper 链向上，第一个"是代理且已被授信"的节点；
         不限层级；整条链都没有 → 群主（创建者视为已授信，额度从 0 起）

带入 X（元）：
    need = X * 100
    if quota[agent] - need < 0 → 失败，提示"该俱乐部额度不足"
    玩家积分 -= X；quota[agent] -= need
    p.settle_agent_id = agent          # 周期锁定

结算 S（元，负分按 0）：
    玩家积分 += S
    quota[p.settle_agent_id] += S * 100      # agent 缺失兜底群主
    清空 settle_agent_id

兑换钻石 N（元）：
    need = N * 100
    if quota[agent] - need < 0 → 失败，返回 EC_NO_MONEY
    玩家积分 -= N；quota[agent] -= need
    Account.stone += N * gold_to_stone
```

**周期锁定**：`settle_agent_id` 在**新周期首次带入**（`init_money <= 0`）时确定，周期内补分沿用同一个；结算后清空。避免中途取消代理/改上级导致账错位。

**审批带入（余额 + 管理员追加）**：额度按「余额 + 追加」的**总额**校验（`Player.CheckTakeInQuota`），不足整笔拒绝；够则余额部分由 `addClubGold` 扣、追加部分由 `Player.OccupyApproveQuota` 单独占额度。追加部分本就没有俱乐部积分可扣，若不单独占额度，结算时会按全额回补，代理凭空多钱。

### 11.4 抽水回补（逐层）【2026-11-03 已改：不再回补额度，改为按 percent 累加代理 bonus】

抽水 5% 中代理份 50%（即赢利的 2.5%）按代理链 `percent` 逐级分配，**每一层各自回补自己的额度**：

```text
total = int(one_water_money * 100)          # 分
逐层： give = 该层按 percent 应得
      AddAgentQuota(该层 guuid, give, '额度抽水回补')
```

平台拿走的那 50% **不回额度**，所以额度池每局净减少约 2.5% × 赢家赢利 —— 这是模型内生特性，代理需持续补充额度。

> 注意：抽水回补按 `p.enter_club_id`（**入口俱乐部**）的代理链分配，而带入扣的是**钱包俱乐部**的额度。联盟房跨俱乐部时两者不是同一棵树，属已确认口径（钱随钱包、抽水随分账）；`club_member_score_info` 的 `score` 记钱包、`contrib_fen` 记入口。

### 11.5 授信（先代理、后授信）

- **前提一：必须是代理**。普通成员没有额度账户，授信命令直接拒绝（"对方还不是代理，请先把他设为代理"）。
- **前提二：由直属上级授信**。只能给自己的直属下级授信，从自己额度里划出（上级 `−N`、下级 `+N`），总量守恒。
- **授信方自己也必须已被授信**（创建者除外，视为已授信）。
- **授信金额可以是 0**：0 不划钱，但把下级从 `NULL` 写成 `0`，此后他可以继续往下授信。
- **负数 = 收回**：`quota_fen < 0` 时从直属下级收回（下级 −N、自己 +N）；下级余额不够则整笔拒绝，不做部分收回。
- **平台注资**：后台 / boss 直接加额度，立即生效（顺带完成授信）。
- **取消代理**：先把余额退回直属上级，再把 `quota` 置回 `NULL`。

### 11.6 上下分权限

| 身份 | 可操作范围 | 上分来源 |
| --- | --- | --- |
| 群主（创建者） | 俱乐部内所有代理与玩家 | 扣本人额度（带入时） |
| 任意层级代理（**已被授信**） | 自己整棵子树 | 扣本人额度（带入时） |
| 代理但**未被授信** / 普通成员 | 自己整棵子树 | 本人 `club_gold`（赠送） |
| 其他人 | 无 | — |

**上分/下分本身不动额度**，额度不足只在带入/兑换时报错。

`club_history_info.opt_type` 新增：

## 12. 平台直接给玩家加减钻石（2026-11-09，v1.6）

### 12.1 需求与边界

后台/运营需要给**指定玩家**直接发钻石（活动奖励、客诉补偿、误扣纠正），此前只有三条间接通道，都不满足：

| 既有通道 | 为什么不行 |
| --- | --- |
| `增加_俱乐部_钻石` | 加的是**群主钻石池**（`club_agent_info.stone`），玩家还要拿积分兑换才能到手 |
| `reqExChange2` 金币→钻石 | 玩家自己花金币换，运营无法凭空发 |
| `玩家_消费_命令` | 只扣不加（`money` 必须 ≥ 0） |

因此新增一条独立 Hall 命令，**只加/减 `Account.stone`，不碰俱乐部池与额度**。

### 12.2 命令契约：`异步_增加_玩家_钻石`

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_增加_玩家_钻石' \
  --data-urlencode 'param={"guuid":"864747","stone_number":100,"context":"admin-20261109-0001"}'
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `guuid` | string | 是 | 目标玩家 ID（`tbl_Account.sm_guuid`） |
| `stone_number` | int | 是 | **正数加、负数扣**，0 拒绝；单次绝对值 ≤ `player_stone_add_max`（缺省 1000000） |
| `context` | string | 否 | 操作号，写 `usr_cash_water.remark4`（截断 100 字） |

成功：`ret_code=0x200`，`ret_result={"guuid":"864747","add":100,"stone":110}`（`add` 是实际变动，`stone` 是变动后余额）。

失败返回 `ret_code=0x100` + `{"error": "..."}`：

| 场景 | error |
| --- | --- |
| 调用者不在 `d_users.config["account"]["boss"]` | `无权限` |
| 缺 `guuid` / `stone_number=0` | `缺少玩家ID` / `钻石数量不能为 0` |
| 超单次上限 | `单次钻石数量不能超过 N` |
| `sm_guuid` 查不到 | `玩家不存在` |
| 目标 `level >= 99` | `目标账号为运营账号，钻石不生效` |
| 扣减超过余额 | `钻石不足，无法扣减` |

### 12.3 为什么不改造 `reqExChange2` / `reqExChange3` / `reqExChange`

三个方法在 `Account.def` 里都是 **`<Exposed/>`**，客户端可直连：

1. 加"充值/发钻"分支等于把造币能力暴露到客户端，只能靠 `level>=99` 区分，boss 账号一旦被登录即可无限自刷，且日志无法区分后台调用与客户端调用；
2. `reqExChange2` 的分支已绑定 `type='金币兑换钻石'`、`usr_exchange_info` 等对账口径，掺入"平台发放"会污染现有流水语义；
3. `reqExChange3` 的 `网站充值` 走 `_closeAccountExchange`，币种由 `gold_mode` 决定，改动会牵连现有充值链路。

**结论：保持三个 Exposed 接口原样，新增 Hall 命令。** 只有 `map_hall_command_func` 里的命令能通过 `/hall/command` 或客户端 `reqHallCommand` 进来，而本命令第一行就校验 boss。

### 12.4 实现与记账

`Hall._actAddPlayerStone`（`scripts/base/Hall.py`，紧跟 `_actAddClubStone` 之后）：

1. boss 校验 → 参数校验 → `tools.auto_reload()`（上限热生效）；
2. `select id from tbl_Account where sm_guuid=?` 取 dbID，再 `createEntityFromDBID("Account", dbID)`：
   在线玩家拿到内存实体（改完即时同步客户端），离线玩家临时加载（`wasActive=False`，实体永生不销毁，与 `异步_设置_玩家_属性` 一致）；
3. `level >= 99` 直接拒绝——`decStoneNumber` 对 boss 不扣不加，放行会"返回成功但余额没变"；
4. 负数扣减先比余额，不足直接拒绝——`decStoneNumber` 会把负余额夹到 0 仍算成功；
5. 复用 `decStoneNumber(-stone_number, isGold=False, optionType='平台授钻')`：写 `usr_consume_info`（`money_type='stone'`、`money_number` 带符号）+ `writeToDB`；
6. 用实际差值双写 `usr_cash_water`（`money_type='stone'`、`option_type='平台授钻'`、`remark1=操作人`、`remark5='变动N钻-余M钻'`），保证玩家端 `查询_玩家_钻石流水` 能看到这笔。

### 12.5 部署与验收

- 改动文件：`scripts/base/Hall.py`（新增函数 + 注册一行）、`scripts/data/d_halls.py`（新增 `player_stone_add_max`，**线上只能原地加行，禁止覆盖**）；无 DDL，`Account.def` 不变；
- 冒烟：
  1. boss 调 `guuid=在线玩家, stone_number=100` → `0x200`、`add=100`，客户端余额即时 +100，`查询_玩家_钻石流水` 出现 `平台授钻 +100`；
  2. 同一玩家 `stone_number=-5` → 余额 −5，流水 `-5`；
  3. 普通玩家账号调本命令 → `无权限`，余额不变；
  4. 目标为 boss 账号 → `目标账号为运营账号，钻石不生效`；
  5. 目标余额 10 传 `-50` → `钻石不足，无法扣减`，余额仍 10、无流水；
  6. 传 `0` / 超上限 / 不存在的 `guuid` → 对应 error，均不改余额；
  7. 离线玩家加钻 → 成功；再次登录余额已变（`decStoneNumber` 内已 `writeToDB`）。

### 12.6 已知风险

- `/hall/command`（`MinHTTPServer2.py`，`0.0.0.0:8890`）**本身无鉴权**，与 `增加_俱乐部_钻石`、`增加_联盟_额度` 现状相同：任何能访问该端口的人都能发钻。必须保证 8890 只在内网/本机可达（安全组不放行）；后续若要对公网暴露后台，需要先加签名或 IP 白名单。
- 本命令不做每日/累计上限，不做二次确认；单次上限只防误输入，运营大额发放靠操作纪律与流水追溯（`usr_cash_water` + `usr_consume_info` 双份记录）。
