# 俱乐部积分与额度方案：客户端改造实施方案

> 依据文档：`服务器文档整理/俱乐部积分与额度方案-客户端接口文档.md`
>
> 目标：给后续执行模型使用的客户端实施方案。本阶段只整理方案，不修改 TypeScript、Prefab、Scene、图片或服务端代码。
>
> 适用项目：Cocos Creator 2.4.13，客户端工程 `/Volumes/SSD/qing`。
>
> 文档状态：方案稿。接口、权限和提示文案以服务端最终部署版本为准。

---

## 1. 改造目标

本次改造的核心不是把界面上的“金币”统一替换成另一个名称，而是把俱乐部场景中的资金体系、权限体系和请求链路重新对齐。

服务端的新方案把俱乐部内资金拆成三类：

| 名称 | 服务端字段/来源 | 客户端单位 | 主要用途 | 是否等同于大厅金币 |
|---|---|---:|---|---|
| 俱乐部积分 | `club_gold` | 1 积分 | 俱乐部成员之间的赠送、上分、兑换 | 否 |
| 俱乐部额度 | `quota_fen` | 分，1 元 = 100 分 | 代理向下级代理/成员授信，以及上分额度判断 | 否 |
| 平台钻石 | `Account.stone` | 钻石 | 房间消费、延时、俱乐部内明确要求钻石的功能 | 否 |

当前客户端仍有大量 `Account.gold`、`money_type: "gold"`、`gold,非俱乐部` 和“金币余额不足”逻辑。这些逻辑不能整体替换：大厅和非俱乐部场景仍使用平台金币；只有进入俱乐部玩法或俱乐部管理链路时，才切换到俱乐部积分/额度规则。

本方案需要解决以下问题：

1. 俱乐部模式的判定、俱乐部 ID 来源和请求上下文必须统一，避免把大厅选中的俱乐部误当作正在进行的俱乐部房间。
2. 带入、兑换、赠送、上分、额度查询和额度授信必须使用正确的资金类型、单位和权限。
3. 旧的金币余额显示、金币不足提示、金币转账接口和邀请码费用判断，必须按场景拆分保留或替换。
4. 服务端返回的“金币不足”和“额度不足”必须保留差异，不能全部显示成同一句提示。
5. 俱乐部余额刷新、异步请求、失败回滚和重连恢复必须明确，不允许只改静态显示。

## 2. 执行边界与必须遵守的规则

### 2.1 本方案的执行边界

后续模型按照本文件执行时，应按以下顺序工作：

1. 先确认服务端新接口已部署，确认返回字段和错误码与接口文档一致。
2. 再进行客户端接口封装和场景改造。
3. 最后修改正式 Prefab/Scene 和必要的文案资源，并进行 Creator、网页预览、构建、真机和真实账号验证。

本方案当前只做分析和任务拆分，不包含代码修改、Prefab 修改、资源替换、构建、上传、提交或发布。

### 2.2 资金安全规则

- 客户端展示和按钮权限只是交互层；俱乐部积分、额度、支付/兑换、授信和成员权限仍以服务端为准。
- 不能用 `Account.gold` 推断 `club_gold`，也不能用客户端保存的额度决定是否允许上分。
- 不能将 `quota_fen` 当作积分显示；额度的单位是分，积分显示通常是整数元。
- 所有金额输入都要在发送请求前明确单位，并在请求日志中记录字段名、数值和单位。
- 请求失败时不能提前扣减客户端余额；只有收到服务端成功结果后才更新本地展示。
- 发生切换俱乐部、退出房间、重连或重新登录时，必须清空或重建旧俱乐部的余额缓存。

### 2.3 场景分界

建议把所有资金相关入口归类为四种场景：

| 场景 | 判定依据 | 使用资金 | 典型入口 |
|---|---|---|---|
| 大厅/普通房间 | `game_mode !== "club"` | 平台金币或平台钻石 | 大厅钱包、普通金币兑换、普通邀请 |
| 俱乐部房间 | `game_mode === "club"` | 俱乐部积分、俱乐部额度；房间消费按接口指定使用钻石 | 带入、结算、俱乐部兑换、房间消耗 |
| 俱乐部管理 | 进入俱乐部管理页且有有效 `clubId` | 俱乐部积分、俱乐部额度 | 成员列表、赠送、上分、授信 |
| 服务端/Boss 操作 | 客户端不可见 | 俱乐部额度 | 平台注入额度 |

不要使用“`clubId` 非空”作为唯一的俱乐部模式判据。当前 `RoomClubContext` 在大厅也可能返回已选择的俱乐部 ID，用于显示角色或打开管理页；这不代表当前房间是俱乐部房间。

## 3. 当前客户端问题审计

以下是实施前应确认的现状和改造原因。后续模型应以当前分支文件为准重新定位行号，不能机械依赖本表的历史行号。

### 3.1 游戏房间和带入

`assets/scripts/UI/panelGameView.ts` 当前带入逻辑已经向 `坐下_事件` 传递 `money`、`ready`、`type` 和 `club_id`，但带入金额显示和余额校验仍以 `Account.gold` 为主，失败时也使用通用“带入金币不足”文案。

需要区分：

- 普通房间：继续走原平台金币逻辑。
- 俱乐部房间：`money` 表示俱乐部积分；不足时提示“俱乐部金币不足！”；如果服务端返回额度不足，则提示“该俱乐部额度不足”。
- 服务端返回 `GC_FAILED` 或 `PromptInfo` 时，应优先使用协议中的明确错误信息，避免客户端覆盖成通用文案。

### 3.2 兑换面板

`assets/scripts/UI/panelExchangeStone.ts` 当前用 `account.gold` 判断余额，并发送 `money_type: "gold,非俱乐部"`。这条链路只能继续服务普通兑换；俱乐部兑换必须发送新的 `money_type: "gold,<club_id>"`，其中 `<club_id>` 为当前有效俱乐部 ID，`money_value` 为俱乐部积分。

俱乐部兑换前需要考虑三类服务端校验：

- 请求者是否仍属于该俱乐部；
- 请求者是否有足够俱乐部积分；
- 请求者是否为最近被授信的代理，且当前额度条件满足。

失败时不能先扣积分或钻石。错误码 `0x302` 应映射为额度不足提示，其他错误要保留服务端消息或统一错误映射。

### 3.3 俱乐部管理

`ClubManagementApi.ts` 当前已有成员的 `clubGold` 显示和积分调整动作，但 action map 主要覆盖 `修改_俱乐部_成员_积分`，没有完整的额度查询、额度授信和成员上分/赠送区分。

`ClubManagementView.ts` 当前角色判断大致为 owner/manager/agent 三层，但“能否看成员”“能否调整积分”“能否授信”“能否上分”不能继续共用一个布尔值。新规则要求按角色和数据状态分别判断。

### 3.4 主界面、钱包、邀请和房间消费

- `panelMain.ts` 顶部或主界面的 `Account.gold` 是平台金币显示，不能因为俱乐部方案而全局替换。
- `panelGivePad.ts` 当前是平台金币转账链路；不能直接当作俱乐部积分赠送面板复用，除非补齐俱乐部上下文、权限、单位和接口。
- `RoomInviteManager.ts` 当前邀请码费用判断使用平台金币；若新接口规定俱乐部邀请改用俱乐部积分，需要按 `game_mode` 和邀请来源分支，否则保留普通房间逻辑。
- `ConfigManager.BuildConsumeStoneParam` 已明确构造 `money_type: "stone"` 的消耗参数。新方案没有要求把钻石消耗改成积分；应先做回归审计，再决定是否增加俱乐部上下文字段。

## 4. 推荐的统一数据与上下文设计

### 4.1 统一的俱乐部运行上下文

建议在现有 `RoomClubContext.ts` 基础上补充一个只读的上下文服务，名称可由执行模型按项目规范决定，例如 `ClubRuntimeContext` 或 `ClubCurrencyService`。不要在每个面板中各自拼接俱乐部 ID。

上下文至少包含：

```ts
interface ClubRuntimeContext {
  isClubMode: boolean;          // 仅由当前房间/游戏模式决定
  clubId: string;               // 当前房间或当前管理页的有效俱乐部 ID
  clubName?: string;
  role?: "owner" | "manager" | "agent" | "member";
  clubGold?: number;            // 俱乐部积分，单位：积分
  quotaFen?: number;            // 俱乐部额度，单位：分
  quotaDisplay?: number;        // 仅用于展示的额度值，不能作为请求依据
  isGranted?: boolean;          // 代理是否被授信，必须保留未返回/false/true 三态
  lastUpdatedAt?: number;
}
```

建议提供以下能力：

- `getCurrentRoomClubId()`：只从当前房间上下文取值。
- `getManagementClubId()`：从当前管理页或用户选择的管理俱乐部取值。
- `isClubMode()`：只判断游戏模式，不由 `clubId` 非空推断。
- `getClubCurrencySnapshot(clubId)`：读取经过接口刷新后的积分/额度快照。
- `invalidateClubCurrency(clubId)`：切换俱乐部、退出房间、登出时清理。
- `refreshClubCurrency(clubId, reason)`：成功操作、重连、进入页面后按原因刷新。

### 4.2 单位对象和格式化

建议在客户端内部把单位写进函数名或类型名，降低误传风险：

```ts
type ClubGold = number;       // 整数积分
type QuotaFen = number;       // 整数分
type PlatformGold = number;   // 大厅/普通玩法平台金币
type Stone = number;          // 平台钻石
```

至少提供以下转换和格式化规则：

- `formatClubGold(value)`：显示俱乐部积分，不加“额度”字样。
- `formatQuotaFen(value)`：按产品确认的格式显示额度，内部值仍保留分。
- `yuanToQuotaFen(yuan)`：仅用于明确输入为元时转换为分。
- `quotaFenToDisplay(fen)`：只用于展示，禁止把展示值反向当接口参数。
- 所有金额输入先校验为有限数、非负整数；不允许 NaN、Infinity、负数和小数积分。

### 4.3 请求结果和刷新策略

统一约定：

1. 发起请求前只读取本地快照用于预填充和提示，不能用本地值替代服务端校验。
2. 成功回调中更新操作涉及的本地字段，并立即刷新成员/额度数据。
3. 失败回调中不修改余额；显示明确错误；必要时执行一次重新查询以修复旧缓存。
4. 进入俱乐部管理页、进入俱乐部房间、重新连接成功后重新查询，不复用其他俱乐部快照。
5. 同一俱乐部的重复查询需要防止旧请求覆盖新结果，建议用请求序号或时间戳丢弃过期响应。

## 5. 分阶段改造方案

以下阶段按依赖关系排列。执行模型应每完成一个阶段就进行对应检查，不要一次性修改全部面板后再猜测问题来源。

### 阶段 0：服务端契约和错误码确认

**目标：** 在改客户端前确认接口文档对应的服务端版本已经可用。

**执行内容：**

1. 对照 `服务器文档整理/俱乐部积分与额度方案-客户端接口文档.md` 核对以下接口：
   - `坐下_事件`；
   - `查询_俱乐部_额度`；
   - `授信_俱乐部_额度`；
   - `增加_俱乐部_额度`（仅服务端/Boss，不做客户端入口）；
   - `查询_俱乐部_成员`；
   - `AllPlayerGold` 或当前总积分查询；
   - 俱乐部积分调整/赠送/上分相关接口；
   - `reqExChange2` 对 `money_type: "gold,<club_id>"` 的支持。
2. 确认服务端返回字段的实际类型，尤其是 `club_gold`、`quota_fen`、`is_agent`、`is_granted`、`PromptInfo` 和错误码。
3. 确认普通金币兑换 `gold,非俱乐部` 仍然可用，避免改造后大厅功能被误切到俱乐部接口。
4. 准备最小测试数据：俱乐部盟主、已授信代理、未授信代理、普通成员、没有俱乐部数据的用户，以及额度为 0 的代理。
5. 记录服务端版本、环境、测试俱乐部 ID 和返回样例。不要把账号密码、token 或私钥写入代码、文档或提交。

**通过标准：** 能用真实或测试账号区分积分不足、额度不足、非成员、未授信、权限不足和参数错误；若服务端未部署，暂停后续联调，只可继续做静态封装和 UI 预研。

### 阶段 1：统一俱乐部模式和 clubId 来源

**目标：** 解决大厅、管理页、俱乐部房间混用上下文的问题。

**涉及文件：**

- `assets/scripts/logic/RoomClubContext.ts`；
- `assets/scripts/UI/panelGameView.ts`；
- `assets/scripts/UI/panelExchangeStone.ts`；
- `assets/scripts/UI/ClubManagementApi.ts`；
- `assets/scripts/UI/ClubManagementView.ts`；
- 其他直接读取 `clubId`、`game_mode` 的入口。

**执行要求：**

1. 在房间相关代码中，使用当前房间的 `game_mode` 作为俱乐部模式开关。
2. 在房间请求中，俱乐部模式下 `club_id` 必须来自当前房间上下文；若缺失，阻止请求并显示“当前俱乐部信息已失效，请重新进入房间”。
3. 在俱乐部管理页，`clubId` 来自当前管理对象或选中的管理俱乐部；不能因为没有进入房间而判定为普通模式。
4. 在大厅兑换页，只有用户明确进入俱乐部兑换入口并选择有效俱乐部时，才使用 `gold,<club_id>`；普通兑换仍使用 `gold,非俱乐部`。
5. 页面销毁、退出房间、切换俱乐部和登录用户变化时，清理旧的俱乐部上下文。
6. 给所有资金请求增加开发期可控日志：`scene`、`game_mode`、`clubId`、`money_type`、金额和单位；生产环境不得打印敏感凭据。

**验收：**

- 大厅选中俱乐部但未进入俱乐部房间时，普通房间不会错误使用俱乐部积分。
- 俱乐部房间没有 clubId 时不会发送空 clubId 请求。
- 从俱乐部 A 切换到俱乐部 B 后，A 的积分和额度不会显示在 B 页面。

### 阶段 2：改造俱乐部房间带入和结算刷新

**目标：** 让俱乐部房间的带入金额、余额、失败提示和结算后的数据刷新符合新规则。

**重点文件：** `assets/scripts/UI/panelGameView.ts`。

**带入逻辑：**

1. 打开座位/带入面板时，俱乐部模式显示 `club_gold`，普通模式显示 `Account.gold`。
2. 带入输入值统一按“俱乐部积分”处理；在俱乐部模式下禁止把输入值传给平台金币字段。
3. 发送 `坐下_事件` 时保留现有必要参数，但校验 `club_id`、`money`、`ready`、`type` 的来源和单位。
4. 客户端本地余额不足只能作为提前提示，不能代替服务端校验；服务端仍是最终裁决。
5. `GC_FAILED`、`PromptInfo` 和命令失败回调中，按错误类型显示：
   - 俱乐部积分不足：`俱乐部金币不足！`；
   - 俱乐部额度不足：`该俱乐部额度不足`；
   - 俱乐部失效/非成员：提示重新进入或联系俱乐部管理者；
   - 普通房间金币不足：沿用普通金币文案。
6. 不要让后续的通用“带入失败，请重新选择座位！”覆盖已经明确的错误文案。

**结算和恢复：**

- 结算消息中若没有推送俱乐部额度，不要从结算结果推算额度。
- 结算完成、返回大厅、重连成功和重新进入房间时，重新查询俱乐部积分/额度。
- 避免用旧的 `Account.gold` 更新俱乐部余额。
- 如果服务端没有提供实时积分推送，使用接口查询结果作为唯一刷新来源，并避免短时间重复请求。

### 阶段 3：改造兑换入口

**目标：** 支持俱乐部积分兑换，同时保持普通兑换完全可用。

**重点文件：** `assets/scripts/UI/panelExchangeStone.ts`、调用它的房间/大厅入口，以及对应 API 封装。

**建议实现：**

1. 给兑换面板增加明确的兑换上下文：`hall`、`club` 或使用项目现有枚举。
2. 普通上下文：余额读取 `Account.gold`，请求使用原 `gold,非俱乐部`。
3. 俱乐部上下文：余额读取指定俱乐部的 `club_gold`，请求使用 `gold,<club_id>`，金额字段为俱乐部积分。
4. 俱乐部上下文没有有效 clubId 时，不展示可提交状态；提示用户重新选择/进入俱乐部。
5. 额度不是积分余额。兑换面板展示积分时不要把 `quota_fen` 直接显示为可兑换余额。
6. 兑换请求发送后锁定重复提交，成功后刷新积分、钻石和必要的俱乐部成员状态，失败后解锁但不扣本地余额。
7. 处理 `0x302`：显示额度不足，并允许用户回到额度/联系代理提示；不要显示成“金币不足”。
8. 处理服务端返回的“最近授信代理”限制、非成员、积分不足和参数错误。

**验收用例：**

| 用例 | 预期请求 | 预期结果 |
|---|---|---|
| 大厅兑换 | `gold,非俱乐部` | 读取平台金币，原流程成功 |
| 俱乐部成员兑换 | `gold,<club_id>` | 读取俱乐部积分，成功后积分减少/钻石增加 |
| clubId 为空 | 不发送请求 | 明确提示上下文失效 |
| 积分不足 | `gold,<club_id>` | 服务端拒绝，本地余额不变 |
| 额度不足 | `gold,<club_id>` | 显示额度不足，本地余额不变 |

### 阶段 4：拆分俱乐部成员的赠送、上分和积分调整

**目标：** 使按钮、接口和权限对应同一业务含义，消除“赠送”和“上分”共用金币调整逻辑的问题。

**业务定义：**

| 操作 | 资金来源 | 接收方 | 是否扣授信额度 | 主要权限判断 |
|---|---|---|---|---|
| 赠送 | 操作者自己的俱乐部积分 | 下级成员/代理 | 否，扣自己的积分 | 操作者有足够积分且满足关系/权限 |
| 上分 | 俱乐部授信额度 | 下级成员/代理 | 是，扣操作者可用额度 | 盟主或被授信代理按服务端规则 |
| 积分调整 | 按服务端定义 | 指定成员 | 由服务端决定 | 管理角色，不能只靠客户端放行 |

新方案要求在产品文案和接口参数中明确“上分（扣额度）”与“赠送（扣自己的积分）”。如果服务端当前还只提供一个“修改积分”接口，应先确认后端是否已经能区分两种来源；不能只在客户端把同一个动作改名。

**涉及文件：**

- `assets/scripts/UI/ClubManagementApi.ts`；
- `assets/scripts/UI/ClubManagementView.ts`；
- `assets/scripts/UI/panelMain.ts`；
- `assets/scripts/UI/panelGivePad.ts`；
- 新增的额度/上分面板（若产品确认需要独立页面）。

**执行要求：**

1. API action map 中分别定义查询成员、积分赠送、上分/额度操作、额度查询和额度授信动作；不要把所有动作映射到 `修改_俱乐部_成员_积分`。
2. 每个请求定义清楚：`clubId`、目标成员 ID、金额、金额单位、动作类型、备注/来源（如协议支持）。
3. 成员列表显示 `club_gold` 时，使用统一的积分格式化函数。
4. 操作按钮根据角色、目标成员关系和额度/积分状态显示，但最终权限以服务端为准。
5. 成功后刷新目标成员行、操作者的积分/额度和总积分；失败不修改行数据。
6. 处理目标成员离线、被移出俱乐部、关系变化、重复提交和请求超时。
7. 旧 `panelGivePad` 若继续用于大厅平台金币转账，要保留其普通模式语义；俱乐部赠送应使用独立上下文，不能仅传一个 `isClub` 布尔值就复用。

### 阶段 5：增加额度查询和额度授信

**目标：** 在成员管理中展示正确的额度状态，并支持符合条件的代理向直接下级授信。

**额度查询接口：** `查询_俱乐部_额度`，客户端异步调用服务端 `GetClubQuota`。接口文档明确：

- `quota_fen` 是额度计算值，单位是分；
- 额度显示值与可用额度不能混为一谈；
- `is_agent` 表示角色或代理身份；
- `is_granted` 需要保留未返回、false、true 的差异；
- 查询失败时不能用 0 伪造成功结果。

**页面建议：**

1. 成员行或成员详情中展示“俱乐部积分”和“俱乐部额度”两个独立字段。
2. 对普通成员不显示代理专属授信按钮；对未授信代理显示状态和不可操作原因。
3. 对有权限的操作者显示“授信/调整额度”，金额输入明确单位。
4. 当额度为 0 时仍允许展示授信状态；0 不是“没有数据”。
5. `is_granted` 缺失时显示“状态未知/待查询”，不能当作 false 直接允许或禁止关键操作。

**授信规则：**

- `授信_俱乐部_额度` 只允许对直接下级代理执行，不能对任意成员或跨层级代理执行。
- `quota_fen >= 0`，包括 0，具体是清零、撤销还是有效额度由服务端定义。
- 响应没有完整上下文时，客户端应保留发起请求时的 `clubId`、目标成员 ID 和请求序号，避免把返回结果写到另一行或另一个俱乐部。
- 授信成功后刷新当前操作者、目标代理和列表中的授信状态；不要只修改目标行的一个数字。
- 授信失败时不修改本地额度，并显示权限、关系、余额或参数错误。

**角色/权限矩阵建议：**

| 角色/状态 | 看积分 | 看额度 | 赠送积分 | 上分 | 授信额度 | 调整积分 |
|---|---:|---:|---:|---:|---:|---:|
| 盟主 | 是 | 是 | 按服务端 | 按服务端 | 是，直接下级代理 | 按服务端 |
| 已授信代理 | 按服务端 | 是/受限 | 按服务端 | 仅自己额度范围 | 仅按服务端关系 | 通常否，需确认 |
| 未授信代理 | 是/受限 | 显示状态 | 按服务端 | 否或额度为 0 | 否 | 通常否 |
| 普通成员 | 是/受限 | 否或无额度 | 按产品规则 | 否 | 否 | 否 |

此表只是客户端显示和入口建议，最终允许与否必须由服务端返回决定。执行时先核对服务端的 owner/manager/agent/member 角色定义，避免用当前 `manager()`、`canManageAgent()`、`approver()` 的旧逻辑直接套用。

### 阶段 6：成员积分和总积分读取

**目标：** 统一成员列表、个人详情、总览和兑换后的积分来源。

接口文档要求：

- 成员积分从 `查询_俱乐部_成员` 的 `club_gold` 读取；
- 总积分从 `AllPlayerGold.total_club_gold` 读取；
- `club_gold = -99` 表示没有该俱乐部数据，应单独处理。

**执行要求：**

1. 继续保留字段兼容解析，但最终进入业务模型时统一为 `clubGold`，不把缺失值默认为 0。
2. `-99` 显示“暂无俱乐部积分数据”或按产品确认处理，不能显示成真实的负积分，也不能直接参与扣款校验。
3. 总积分和成员行积分在不同接口返回时，显示上要说明刷新时刻或以最新成功响应为准，避免用户误以为两者实时强一致。
4. 成功完成赠送、上分、兑换、结算后，刷新受影响成员和总积分；失败不覆盖旧的有效值。
5. 退出俱乐部或切换俱乐部时，清除 `clubGold` 旧数据，防止跨俱乐部残留。

### 阶段 7：邀请码、房间入口和其他金币引用审计

**目标：** 找出隐蔽的 `Account.gold` 使用，避免普通金币和俱乐部积分在非显式入口中混用。

执行模型应全局搜索并逐项归类以下关键词：

```text
Account.gold
Account.gold2
money_type
gold,非俱乐部
金币不足
带入
邀请
club_gold
quota_fen
```

重点审计：

1. `RoomInviteManager.ts` 的邀请码费用、邀请筛选和“当前金币不足”文案：确认邀请发生在普通房间还是俱乐部房间；如果服务端仍按平台金币收费则保留，否则增加俱乐部分支。
2. `panelMain.ts` 的大厅金币、钱包和赠送入口：默认保持平台金币，不要因页面位于俱乐部 UI 就自动改成俱乐部积分。
3. 俱乐部成员列表中的“玩家设置赠送金币”：明确实际调用的是平台转账还是俱乐部积分赠送；如果文案和接口含义不一致，先改业务入口和接口再改文字。
4. `panelGameView.ts` 的延时和房间消耗：当前参数构造器使用 `stone`，需核对新服务端是否仍要求钻石；没有明确新协议前不要改成 `club_gold`。
5. 其他面板、弹窗、快捷按钮和断线重连回调：确认重新进入页面时取的是当前俱乐部数据。

**审计输出格式建议：**

| 文件/函数 | 当前资金 | 当前场景 | 服务端期望 | 改造动作 | 验证方式 |
|---|---|---|---|---|---|
| `panelGameView` 带入 | `Account.gold` | 房间 | club 模式用 `club_gold` | 增加模式分支 | 房间请求日志/真实账号 |
| `panelExchangeStone` | `Account.gold` | 大厅/俱乐部 | 按上下文选择 money_type | 拆分兑换上下文 | 两种兑换各一遍 |
| `panelMain` 钱包 | `Account.gold` | 大厅 | 平台金币 | 保留 | 大厅回归 |
| `RoomInviteManager` | `Account.gold` | 邀请 | 待确认 | 按协议分支 | 邀请成功/余额不足 |

### 阶段 8：房间钻石消耗和原有功能回归

**目标：** 保证俱乐部积分方案不会破坏已经存在的钻石消耗链路。

重点检查：

- `ConfigManager.BuildConsumeStoneParam` 是否仍发送 `money_type: "stone"`；
- 房间延时、房间消费、俱乐部相关消费是否由新协议明确改成积分；
- `Account.stone` 的余额显示、成功扣除和失败恢复；
- 俱乐部房间和普通房间的消耗回调是否都能正确刷新；
- 服务端返回的错误是否被通用金币提示覆盖。

本阶段优先做协议回归。如果接口文档没有明确要求改变钻石消耗，不要把钻石替换成俱乐部积分，也不要为了统一命名而改动现有 `stone` 参数。

## 6. UI、Prefab 和文案改造要求

### 6.1 文案必须表达资金类型

建议使用以下固定概念，最终文案由产品确认：

| 业务状态 | 建议文案 |
|---|---|
| 俱乐部积分余额 | 俱乐部积分 |
| 俱乐部额度 | 俱乐部额度 |
| 额度单位说明 | 额度单位：分 |
| 俱乐部积分不足 | 俱乐部金币不足！ |
| 额度不足 | 该俱乐部额度不足 |
| 非俱乐部成员 | 你不属于该俱乐部 |
| 俱乐部上下文失效 | 当前俱乐部信息已失效，请重新进入 |
| 额度状态未返回 | 额度状态查询中/暂不可用 |
| 无俱乐部积分数据 | 暂无该俱乐部积分数据 |

避免在同一俱乐部页面同时使用“金币”“积分”“额度”指向同一个字段。旧文案可以保留在普通大厅场景，但应通过上下文选择。

### 6.2 Prefab/Scene 修改原则

后续若需要正式 UI 调整：

1. 先确认效果稿或产品文案，再改正式 Prefab/Scene；不要只在运行脚本中动态创建完整 UI。
2. 保留原有节点名、事件绑定、动态数据节点和 `.meta`/UUID 关系。
3. 额度和积分是两个独立的数据节点；不要通过同一个 Label 在不同时间切换造成用户误解，除非设计明确要求。
4. 长屏页面固定顶部/底部，中间区域按现有设计伸缩或滚动；金额输入和按钮不能被安全区遮挡。
5. 新增图标/文字资源按正式资源流程导入，确认 Creator 已刷新后再做预览。
6. 运行时只负责填充数据和处理交互，不批量创建美术节点、不覆盖正式 SpriteFrame/颜色。

### 6.3 空态、加载态和失败态

每个新接口页面至少需要：

- 首次加载态：不能把 0 显示成已加载的余额；
- 空成员态：区分“没有成员”和“查询失败”；
- 额度查询中：按钮禁用或显示加载状态；
- 服务端失败：保留旧的有效数据并显示失败原因；
- 切换俱乐部：旧俱乐部数据清空或明确显示正在切换；
- 重复点击：请求进行中禁止重复提交；
- 超时/断线：允许重试，不能静默扣本地余额。

## 8. 错误处理和兼容策略

### 8.1 服务端错误优先级

错误显示建议按以下优先级处理：

1. 服务端明确的结构化错误码和错误消息；
2. 业务模块的错误码映射；
3. 当前场景的通用失败文案；
4. 全局兜底文案。

如果 `PromptInfo` 已经明确说明“俱乐部金币不足”或“该俱乐部额度不足”，不能在后续通用回调中替换成“带入失败”。

### 8.2 兼容旧服务端

接口文档说明新服务端代码可能尚未全部部署。客户端需要明确兼容策略，不能静默猜测：

- 若新接口不存在，页面显示“当前版本暂不支持额度功能”或项目确认的维护提示；
- 若返回字段缺失，保留可识别的“未知”，不要把未知当 0；
- 若旧服务端只支持 `gold,非俱乐部`，俱乐部兑换入口应禁用并记录接口不支持，而不是把俱乐部积分发送到旧接口；
- 若某个动作的接口契约未确认，先隐藏入口或仅展示只读状态，不能通过旧“修改积分”接口冒险实现；
- 兼容代码要有明确的版本/能力判断，不能通过捕获所有异常后回退到平台金币。

### 8.3 防止重复和乱序

以下请求必须有防重复和乱序处理：

- 俱乐部兑换；
- 赠送/上分；
- 额度授信；
- 进入房间/带入；
- 重新查询成员和额度。

建议每次操作携带本地递增请求序号，并在响应中校验当前 `clubId`、目标成员 ID、页面生命周期和请求序号。页面关闭后到达的响应不能写入已销毁对象，也不能覆盖新俱乐部数据。

## 9. 分层验证方案

### 9.1 静态检查

- 全局搜索所有 `Account.gold`、`money_type`、`gold,非俱乐部`、`金币不足`、`club_gold`、`quota_fen`。
- 确认每一处都有明确场景归类。
- 检查 TypeScript 类型、未使用变量、重复 action 名、错误字段拼写。
- 检查金额输入是否允许负数、小数、NaN 或超大值。
- 检查不再使用的旧入口和文案是否被错误保留在俱乐部页面。

### 9.2 接口/协议检查

使用抓包、开发日志或测试桩核对：

- 普通兑换发送 `gold,非俱乐部`；
- 俱乐部兑换发送 `gold,<club_id>`；
- 俱乐部带入带有正确 `club_id`，`money` 单位为积分；
- 额度查询请求 clubId 和目标对象正确；
- 授信请求支持 `quota_fen = 0`；
- 赠送和上分能被服务端区分；
- 房间钻石消耗仍发送 `stone`，除非新协议明确变更；
- 失败请求不触发本地余额扣减。

### 9.3 Cocos 编辑器和网页预览

- 确认正式 Prefab/Scene 已导入新节点和绑定。
- 在 Creator 2.4.13 中检查节点名、组件、事件和 `.meta` 关系。
- 浏览器预览只作为交互检查，不等同于 Creator 资源导入或构建通过。
- 检查常见长屏尺寸：积分/额度文字不重叠，按钮不被遮挡，滚动区域正常。
- 检查空态、加载态、失败态和重复点击状态。

### 9.4 构建、真机和真实账号

按以下顺序记录结果：

1. Creator/网页预览；
2. 客户端构建；
3. 真机安装和运行；
4. 真实或测试账号进入普通房间；
5. 真实或测试账号进入俱乐部房间；
6. 盟主、已授信代理、未授信代理、普通成员分别执行权限用例；
7. 重连、切换俱乐部、退出房间、重新登录；
8. 线上/目标环境接口版本确认。

每一层单独记录。网页能显示正确数字不代表服务端扣款正确，接口成功也不代表正式 Prefab 或真机显示正确。

| M-05 | 从 A 切到 B | 打开管理页 | 不显示 A 的缓存余额 |
| M-06 | 俱乐部 clubId 丢失 | 点击兑换/带入 | 不发送空 clubId 请求 |

### 10.2 积分、额度和兑换

| 编号 | 前置条件 | 操作 | 预期 |
|---|---|---|---|
| C-01 | 盟主有直接下级代理 | 查询额度 | 显示 quota_fen 和授信状态 |
| C-02 | 已授信代理 | 向直接下级上分 | 扣可用额度，成功后刷新两侧数据 |
| C-03 | 未授信代理 | 尝试上分 | 客户端入口受限，服务端也拒绝 |
| C-04 | 授信额度为 0 | 保存授信 | 按服务端规则处理，不能被客户端当成缺失 |
| C-05 | 普通成员有积分 | 赠送/兑换 | 扣积分，不误扣额度 |
| C-06 | 额度不足 | 俱乐部兑换 | 显示额度不足，本地余额不变 |
| C-07 | 积分不足 | 俱乐部兑换 | 显示积分不足，本地余额不变 |
| C-08 | `club_gold = -99` | 打开成员页 | 显示数据缺失，不显示负积分 |

### 10.3 失败、恢复和兼容

| 编号 | 场景 | 预期 |
|---|---|---|
| E-01 | 请求超时 | 可重试，余额不提前变化 |
| E-02 | 重复点击授信 | 只有一次有效提交 |
| E-03 | 响应晚于切换俱乐部 | 丢弃旧响应，不污染新俱乐部 |
| E-04 | 服务器返回 PromptInfo | 保留明确业务文案 |
| E-05 | 服务器不支持新接口 | 显示不支持，不回退成平台金币操作 |
| E-06 | 断线重连 | 重新查询当前俱乐部积分/额度 |
| E-07 | 退出俱乐部 | 清理旧积分、额度和授信状态 |
| E-08 | 普通房间钻石消耗 | 仍使用 stone，原功能不回归失败 |

## 11. 推荐实施顺序和提交边界

后续执行模型建议拆成以下可审查批次，每批独立验证：

1. **协议和模型批次**：错误映射、金额单位、俱乐部上下文、返回类型。
2. **房间批次**：俱乐部带入、PromptInfo、结算刷新、重连恢复。
3. **兑换批次**：普通/俱乐部兑换上下文和 `money_type` 分支。
4. **管理批次**：成员积分、总积分、赠送/上分、额度查询。
5. **授信批次**：角色状态、直接下级校验、授信操作和刷新。
6. **入口审计批次**：主界面、钱包、邀请码、房间消费和遗留金币引用。
7. **资源与验收批次**：正式 Prefab/Scene、Creator 导入、预览、构建和真机。

每批只修改必要文件，保留其他任务的未提交修改。未完成真实服务端验证前，不要把“静态通过”写成“功能完成”。

## 12. 需要产品/服务端先确认的问题

以下问题在接口文档中仍可能影响客户端最终实现，执行前必须拿到明确答案：

1. 俱乐部积分在所有“赠送、上分、调整”接口中的字段名、单位和动作枚举分别是什么？
2. “上分（扣额度）”和“赠送（扣自己的积分）”是否已有不同服务端接口或参数？
3. `quota_fen` 的显示规则是什么：直接显示分、换算成元，还是同时显示两者？
4. `is_granted` 缺失、false、true 三态在产品上分别如何展示？
5. `授信_俱乐部_额度` 的 `quota_fen = 0` 是清零、撤销还是有效的零额度？
6. 盟主、manager、已授信 agent、未授信 agent、member 的准确权限矩阵是什么？
7. 俱乐部邀请费用使用平台金币还是俱乐部积分？不同入口是否不同？
8. 房间延时和房间消费是否始终使用 `stone`？新方案是否需要支持俱乐部积分消费？
9. 俱乐部积分/额度是否有实时推送事件？如果没有，推荐查询时机和频率是什么？
10. 新服务端部署版本和旧服务端兼容窗口是什么？客户端是否需要能力探测？
11. 俱乐部兑换的 `money_value` 是否严格要求整数积分，是否存在最小/最大值？
12. `club_gold = -99` 之外是否还有其他特殊值或缺失字段语义？

在这些问题没有确认前，客户端可以先完成类型、模式分支和只读展示，但不要最终定稿授信、上分和兑换的接口参数。

## 13. 完成定义

只有同时满足以下条件，才可以把本次客户端改造标记为完成：

- 普通大厅/普通房间的金币和钻石功能回归通过；
- 俱乐部房间带入使用正确的 clubId、积分单位和错误提示；
- 俱乐部兑换与普通兑换使用不同且正确的 `money_type`；
- 赠送、上分、积分调整在 UI、权限、接口和扣款来源上相互一致；
- 额度查询、额度为 0、未授信、已授信和授信失败均有明确表现；
- 成员积分、总积分、额度和授信状态不会跨俱乐部串数据；
- `club_gold = -99`、缺失字段、接口失败和旧服务端均有可识别处理；
- 断线重连、切换俱乐部、退出房间和重复提交通过验证；
- 正式 Prefab/Scene 已在 Creator 2.4.13 导入确认；
- 已分别完成静态检查、编辑器/预览、构建、真机和真实账号验证，并记录未验证项；
- 未发生将平台金币误当俱乐部积分、将额度误当积分或将未知值误当 0 的情况。
