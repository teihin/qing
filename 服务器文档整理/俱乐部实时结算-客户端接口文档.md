# 俱乐部实时结算 - 客户端接口文档

适用范围：`房间类型 Custom` + `传销扯旋`（`room_daifen_fangka`）。`settle_mode=fixed` 时接口一行为与改动前完全一致，接口二恒返回空。

实现文件：

- `scripts/base/Account.py`：命令注册与参数解析；
- `scripts/server_common/room_daifen_fangka.py`：报文组装与推送。

---

## 1. 接口一：房间内未结算玩家

### 1.1 命令

```json
{"header":"获取_游戏内玩家_信息_命令"}
```

可选参数 `room_id`：不传或传 0 时使用自己当前所在房间。

### 1.2 返回

推送 router：`GamePlayerListInfo`（点对点，只发给请求者）

```json
{
  "GamePlayerListInfo": [
    {
      "status": "ready",
      "num": 3,
      "id": "430994",
      "name": "你",
      "total_score": "49",
      "play_countdown": "23",
      "is_one_rr": "False",
      "optimize01_count": 0,
      "optimize01_chance": 0,
      "client_death": "False"
    }
  ],
  "reward_pool": "0",
  "player_xi_money": "0",
  "boss_xi_money": "0"
}
```

| 字段 | 说明 |
| --- | --- |
| `status` | 玩家状态（`init` 观战/未准备、`ready` 已准备等） |
| `num` | 客户端座位号（观战为 999） |
| `id` / `name` | guuid / 昵称 |
| `total_score` | 当前盈亏（`money_score + boji_score - init_money`），字符串 |
| `play_countdown` | **个人周期剩余倒计时（秒）**：`realtime_play_seconds - (now - enter_time)`，最小 0。未带入、已结算、fixed 模式恒为 `0`；客户端收到后本地逐秒递减，收到新 `PlayerList` 时以服务端值校准 |
| `is_one_rr` | 是否机器人 |
| `client_death` | 客户端是否断线 |
| `reward_pool` / `player_xi_money` / `boss_xi_money` | 房间奖池与喜钱，整场统计口径 |

### 1.3 过滤规则（重要）

**只返回 `init_money > 0` 的玩家**（已带入、未结算）。

- 实时结算到点后玩家被清零（`init_money=0`、`is_realtime_settled=True`），**不会出现在本列表**；
- 还没带入的观战者也不在列表里；
- 所以“房间内所有人都已结算”时本接口返回空数组，这是预期行为。

需要看已结算历史请用接口二。

## 2. 接口二：房间内已结算记录（分页）

### 2.1 命令

```json
{"header":"获取_房间_已结算_玩家_命令", "page":0, "count":20}
```

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `page` | int | 否 | 页码，从 0 开始，默认 0 |
| `count` | int | 否 | 每页条数，默认 20，**上限 100**（超过按 100 处理） |
| `room_id` | int | 否 | 不传或 0 时使用自己当前所在房间 |

### 2.2 返回

推送 router：`SettledPlayerListInfo`（点对点，只发给请求者）

```json
{
  "number": 0,
  "count": 37,
  "result": [
    {"id": "430994", "name": "你",   "score": 49,  "init_money": 250,  "played_count": 3, "time": 1761667200},
    {"id": "496702", "name": "a2",  "score": -30, "init_money": 1000, "played_count": 5, "time": 1761667150}
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `number` | int | 当前页码（回显请求的 `page`） |
| `count` | int | **总条数**（不是本页条数），用于算总页数 |
| `result` | array | 当前页记录，最新结算在最前 |
| `result[].id` | string | 玩家 guuid |
| `result[].name` | string | 昵称 |
| `result[].score` | int | 本次结算的净输赢（已含抽水），可为负 |
| `result[].init_money` | int | **本周期带入总分**（已含补分），与 `GamePlayerListInfo` 的 `init_money` 同口径；在结算清零前快照，用于展示「带入多少」 |
| `result[].played_count` | int | **本周期参与局数**（`round_played_count` 清零前的快照），≥1；不是账号累计手数 |
| `result[].time` | int | 结算时间戳（秒） |

### 2.3 数据语义

- **一条记录 = 一次结算动作**，不是按人聚合：同一个人打满一轮结算后重新带入再结算，会出现两条；
- 记录按结算发生顺序存，返回时**倒序**（`page=0` 是最新的一页，页码越大越旧）；
- 数据存在房间内存，**房间销毁即清空**，不落库、不跨房间；
- 单房间上限 500 条，超出自动丢最旧的；
- 已离开房间的人仍保留在列表里（这就是它和接口一的区别）；
- `init_money` 是**结算那一刻的快照**：玩家对象的 `init_money` 在结算后已被清零，所以服务端在清零前记录入列表，客户端不能指望从别处再读到这个值；
- **只有本周期参与过牌局的结算才进列表**：带入后一局都没开（人不够/没开始）就到点结算的“空周期”不写入列表，避免列表里堆满 `score=0` 的条目。判据是周期计数 `round_played_count`（`Player.Start()` 每局 +1、结算时清零，>0 才算参与过），**不是**累计的 `played_count`。

### 2.4 分页示例

| 请求 | 含义 |
| --- | --- |
| `{"page":0,"count":20}` | 最新 20 条 |
| `{"page":1,"count":20}` | 第 21~40 条 |
| `{"page":0,"count":100}` | 最新 100 条（上限） |
| `{"page":5,"count":20}` | 越界时 `result=[]`，`count` 仍返回真实总数 |

## 3. 两条接口怎么选

| 场景 | 用哪个 |
| --- | --- |
| 房间内“正在打 / 等待带入”的玩家列表 | 接口一 `获取_游戏内玩家_信息_命令` |
| “已结算”分组、历史结算记录、按时间翻页 | 接口二 `获取_房间_已结算_玩家_命令` |
| 需要玩家身上实时字段（座位、准备状态） | 接口一 |
| 需要已离开房间的人 | 接口二 |

两条接口互不影响，可同时使用。

---

## 4. 注意事项

1. `fixed` 模式下接口二恒返回 `count=0`、`result=[]`，客户端可据此隐藏「已结算」入口；
2. 已结算记录不带座位号、不带剩余留座时间：这些是“在座玩家”的概念，走 `PlayerList` / 接口一；
3. 结算列表不做服务端推送，需要刷新时客户端自行请求；
4. 分页参数异常（负数、非数字）按默认值处理，不会报错；
5. `count` 上限 100，避免一次拉取过大报文。
6. `play_countdown` 与 `site_countdown` 同一套刷新方式：服务端只在带入成功、重新带入、结算、状态变化时随 `PlayerList` 下发当前剩余，**不逐秒推送**；客户端需本地每秒递减，收到新消息时以服务端值为准。
