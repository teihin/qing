## 1. 背景与目标

**现象**：盟主/上级给某玩家**开通代理**后，被开通的玩家端**收不到任何消息**，界面不会刷新，必须自己去点「我的代理信息」才看得到"我已是代理/我的码是多少"。

**目标**：开通代理成功后，服务端**主动**给该玩家推一条消息，客户端收到即可刷新界面。

**约束（按需求）**：优先复用项目已有实现，不新造协议、不新造报文格式、不改客户端解析。

---

## 2. 现状：为什么没有消息

`设置_俱乐部_代理` 整条链路只对**操作者**回包，对被设置的人什么都不发（`club_biaozhun.py:314-317`，节选）：

```python
            #首次设置/重新晋升都确保有可用码（旧码在取消时已 disabled）
            self.EnsureClubAgentCode(user_id)

            account.onHallCommand(GlobalConst.GC_OK, ('{"context":"%s", "result":{"error":"", "user_id":"%s", "percent":%s, "has_invite_code":1}}' % (context, user_id, percent)))
```

- `account` 是**操作者**（上级代理或创建者），不是被设置的 `user_id`；
- 目标玩家只被：写库 `club_agent_info`、同步内存 `agent_tree`、置 `sm_client_prop='True'`、加入 `Hall.all_account_agents` 懒加载队列、分配邀请码；
- 命令入口返回 `GC_UNKOWN`（`Hall.py:2330`），客户端拿到的是"无即时响应 + 操作者 0x200"，与目标玩家无关。

`修改_俱乐部_代理_比例` 复用同一入口（`Hall.py:2333` 直接 `return self._actSetClubAgent(account, param)`），情况完全相同。

## 3. 可复用的现成实现（三块，均已存在）

| 需要的能力 | 现成实现 | 复用依据 |
| --- | --- | --- |
| 拿到**指定 guuid** 的账号实体（可能离线） | `hall.boss.createBaseFromGUUID(user_id, "Account", callback)`，回调签名 `(baseRef, dbid, wasActive)` | 项目标准做法：`添加_俱乐部_管理员`（`Hall.py:3270`）、`同意_俱乐部_创建申请`（`Hall.py:3206`）、`删除_俱乐部_管理员`（`Hall.py:3314`）都这么用 |
| 让该账号**常驻代理**（结算写红利的前置条件） | `hall.boss._closeLoadProxy()` 返回的回调 | `Account.py:320-373`：登记进 `Hall.proxys`（`:328-329`）并 `baseRef.is_never_death = True`（`:365`，代理永生）。这就是运行时懒加载代理用的同一段逻辑，不另写 |
| 生成并推送"代理信息"报文 | `club.PushClubAgentInfo(account)` | `club_biaozhun.py:421-485`，推路由 **`ClubAgentInfo`**；内部自己处理"树未加载→挂起补推"、"码查库"、"离线不推" |

**为什么不新造路由**：`ClubAgentInfo` 本来就是 `查询_俱乐部_代理_信息` 的回包，客户端**已有完整解析**；推送和查询回包结构完全一致，客户端只需把"收到即刷新"接上，零新增字段。

> **部署前提（已与业务确认）**：当前线上 `Hall` 与玩家账号在**同一个 baseapp 进程**内，`createBaseFromGUUID` 取到的就是本进程实体，`account.client.onMessage` 必然可达。**本方案不覆盖"Hall 与玩家分属不同 baseapp"的部署形态**；若将来拆分 baseapp，需要重新验证推送可达性。

**"提前加载实体"不是新增副作用**：`_closeSetClubAgent` 本来就把 `user_id` 塞进 `hall.all_account_agents`（`:309-311`），Hall 的 timer 每拍消费一个（日志 `[HALL].onTimer load agent_id=...`），即**首次开通后约 1 秒，该账号无论如何都会变成常驻代理**。本方案只是把这一步提到"开通瞬间"，量级与内存占用完全不变。

## 4. 方案

### 4.1 调用链

```
SetClubAgent 成功（写库/内存树/client_prop 之后）
   └─ EnsureClubAgentCode(user_id, on_done=_pushAgentInfoToUser)      ← 新增可选完成回调
        ├─ 已有 used 码            → on_done()
        └─ 号池分配新码并落库完成  → on_done()
             └─ _pushAgentInfoToUser(user_id)                          ← 新增方法
                  ├─ user_id 已在 Hall.proxys → PushClubAgentInfo(proxys[user_id])
                  └─ 不在                    → hall.boss.createBaseFromGUUID(user_id, "Account", _onLoaded)
                        └─ _onLoaded: 复用 _closeLoadProxy()(baseRef,dbid,wasActive) 登记常驻
                                      → PushClubAgentInfo(baseRef)
```

### 4.2 为什么挂在"码分配完成"之后

`EnsureClubAgentCode` 是异步的（先查有无 used 码，没有才从号池 `update ... limit 1` 取一个）。若在 `_closeSetClubAgent` 末尾立即推，`PushClubAgentInfo` 内部的 `GetClubAgentCode` 可能读到空串，玩家看到"已是代理但没有码"——既影响体验也增加排查成本。挂在完成点可一次到位。

### 4.3 代码形状（与最终实现一致）

```python
# club_biaozhun.py 新增方法
def _pushAgentInfoToUser(self, user_guuid, allow_load=True):
    #2026-10-25 开通/取消代理后主动通知被设置的玩家：复用 ClubAgentInfo 推送（同"查询_俱乐部_代理_信息"）
    hall = KBEngine.globalData["Hall"]
    if user_guuid in hall.proxys.keys():
        #已常驻（再次设置/改比例）：直接用现有实体推，避免重复加载
        self.PushClubAgentInfo(hall.proxys[user_guuid])
        return

    if not allow_load:
        #取消代理路径：只推已常驻的，不为刚被取消的人加载实体、赋予代理永生
        DEBUG_MSG("CLUB[%s]:_pushAgentInfoToUser 目标未常驻且不允许加载，跳过推送 user=%s" % ...)
        return

    if hall.boss is None:
        DEBUG_MSG("CLUB[%s]:_pushAgentInfoToUser boss 未就绪，跳过推送 user=%s" % ...)
        return

    load_proxy_cb = hall.boss._closeLoadProxy()   #复用：登记 Hall.proxys + 代理永生
    def _onLoaded(baseRef, dbid, wasActive):
        if baseRef is None:
            #加载失败必须留痕；且不再调 load_proxy_cb，避免与它内部的 ERROR 重复
            ERROR_MSG("CLUB[%s]:_pushAgentInfoToUser 目标实体加载失败，未推送 user=%s" % ...)
            return
        load_proxy_cb(baseRef, dbid, wasActive)
        self.PushClubAgentInfo(baseRef)
    hall.boss.createBaseFromGUUID(user_guuid, "Account", _onLoaded)

# EnsureClubAgentCode 增加可选完成回调（缺省 None，其它调用点行为不变）
def EnsureClubAgentCode(self, user_guuid, on_done=None): ...
```

**`on_done` 必须覆盖全部终态**（漏一个 = 那种情况静默不推，与本次"查了没反应"同类故障）：

| 函数 | 终点 | 是否调 `on_done` |
| --- | --- | --- |
| `_closeEnsureClubAgentCode` | `errstr` 早退 | 否（打 `ERROR_MSG` 留痕） |
| `_closeEnsureClubAgentCode` | 已有 used 码 | **是** |
| `_closeEnsureClubAgentCode` | 无码 → 转号池分配 | 由下一段负责 |
| `_closeAllocClubAgentCode` | `errstr` 早退 | 否（打 `ERROR_MSG` 留痕） |
| `_closeAllocClubAgentCode` | 分配落库成功 | **是** |

### 4.4 覆盖面

| 入口 | 是否推送 | 说明 |
| --- | --- | --- |
| `设置_俱乐部_代理` | 是 | `Percent` 原值或新值 |
| `修改_俱乐部_代理_比例` | 是 | 与上同一入口，自动覆盖；被改比例的人也需要刷新 |
| `取消_俱乐部_代理`（`DelClubAgent`） | 是（建议一起做） | 推同一条消息即可：`PushClubAgentInfo` 按内存树重算，取消后 `GetClubAgentCode` 返回空 → `is_agent="0"`、`invite_code=""`、不下发上级码；客户端据此收起代理入口 |

## 6. 边界处理

| 场景 | 行为 |
| --- | --- |
| 目标在线 | 立即收到 `ClubAgentInfo`，界面刷新 |
| 目标离线 | 实体仍会被加载（代理本来就要常驻 `Hall.proxys`），`PushClubAgentInfo` 内有 `if not account.client_death and account.client is not None` 守卫（`:460`）→ 不推、不报错；玩家上线后查询即正确 |
| 目标在房间内打牌 | `onMessage` 走实体 client 通道，不打断牌局（需实测确认，见 §8 第 8 条） |
| `hall.boss` 未就绪 | 打 `DEBUG_MSG` 后跳过；开代理本身仍成功（`onHallCommand` 已先回给操作者） |
| `createBaseFromGUUID` 回调 `baseRef is None` | 打 `ERROR_MSG` 留痕后跳过——这条路径失败时客户端表现与"功能没做"完全一样，只有日志能区分 |
| 取号 SQL 报错（`errstr`） | `ERROR_MSG` 留痕，`on_done` 不触发 → 本次不推；开代理本身仍成功，玩家下次查询即正确 |
| 重复开通 / 连改比例 | 每次都推，幂等；客户端按"更新缓存 + 刷新"处理，多条不影响最终值 |
| 首次设置时码刚分配 | 推送在码落库之后触发，`invite_code` 一定有值 |
| 取消代理后 | 推 `is_agent="0"`、`invite_code=""`；该账号仍留在 `Hall.proxys`（代理永生），不影响功能，本次不做移除 |
| 取消代理的推送时机 | 挂在"码置 `disabled`"那条 UPDATE 的回调上，保证推送时查到的码已是 `disabled`；否则并发下可能推出 `is_agent=1` 的旧状态 |
| 取消代理不加载实体 | 传 `allow_load=False`：目标未常驻则跳过（打 `DEBUG_MSG`），避免"取消代理反而被赋予代理永生"的反向副作用 |
| **开通即永生** | 开通瞬间就 `is_never_death=True`，取消代理后也不回收（既有设计，`DisableClubAgentMember` 同样不清）。原本约 1 秒后由 `all_account_agents` 队列加载，方案只是提前，内存量级不变 |
| **取消后 `upper_guuid` 仍非空** | `DelClubAgent` 只把 `status` 置 `disabled`，不清 `upper`，所以推出去的报文会出现 `is_agent=0` 但 `upper_guuid`/`upper_name` 有值。**客户端判断"我是不是代理"必须用 `is_agent`**（接口文档 §2.1 已明确），不能用 `upper_guuid` 是否为空来判定 |

## 7. 客户端契约（无变化，仅新增触发时机）

- **路由**：`ClubAgentInfo`
- **报文**（与 `查询_俱乐部_代理_信息` 完全一致）：

```json
{"number": 0, "count": 1,
 "result": {"club_id": "911912", "user_id": "718968", "user_name": "abc",
            "is_creator": 0, "is_agent": 1, "invite_code": "123456",
            "percent": 30, "upper_guuid": "237737", "upper_name": "天外飞仙",
            "downline_count": 0, "downline": []}}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `club_id` / `user_id` / `user_name` | string | 俱乐部、本人 guuid、本人在该俱乐部的名字 |
| `is_creator` | int | 1=创建者（根代理） |
| `is_agent` | int | **1=当前是代理**（判定口径=持有该俱乐部可用邀请码）；取消代理后推 `0` |
| `invite_code` | string | 代理=本人码；非代理=直接上级码；都没有为空串 |
| `percent` | int | 本层截留比例 |
| `upper_guuid` / `upper_name` | string | 直接上级（非代理/无上级时为空） |
| `downline_count` / `downline` | int / array | 直接下级数量与列表（元素含 `user_id`/`user_name`/`percent`） |

**客户端处理建议**：推送与查询回包结构完全相同（`number=0`、`count=1`），不需要区分来源，统一按"更新本俱乐部代理信息缓存 + 刷新当前界面"处理即可。若玩家正停在「我的成员」列表，收到后可自行重发一次 `查询_俱乐部_成员`。

| 10 | 同一玩家 1 秒内连续改两次比例（30→50） | 收到 2 条，最后一条 `percent=50`；客户端幂等刷新不异常 |

日志判定（三条，缺一即需排查）：

1. `CLUB[<俱乐部>]:PushClubAgentInfo {"number": 0, "count": 1, "result": {...}}` —— 推送已发出（`PushClubAgentInfo` 内 `:459` 既有 DEBUG）；

## 11. 评审记录（2026-10-25）

| 维度 | 结论 |
| --- | --- |
| 复用度 | 高：路由、报文、实体加载、常驻登记全部复用；零新协议、零客户端解析改动 |
| 改动面 | 1 个文件，无数据库、无 `Hall.py`、无配置 |
| 主要风险 | `on_done` 覆盖不全导致"静默不推"（已按 §4.3 的表逐项覆盖）；实体加载失败不可见（已补 `ERROR_MSG`） |

**评审后已并入本文档的 7 条**：

1. `on_done` 必须覆盖 `EnsureClubAgentCode` 的全部终态（3 个正常出口 + 2 个 `errstr` 早退），漏一个就是"某种情况下永远不推且不报错"——与 2026-10-25 成员列表"查了没反应"同类故障；
2. `baseRef is None` / 取号 `errstr` 必须打 `ERROR_MSG`（失败时客户端表现与"功能没做"完全一样，只有日志能区分）；且 `baseRef is None` 时**不再调 `_closeLoadProxy`**，避免与它内部的 ERROR 重复；
3. 取消代理后 `is_agent=0` 但 `upper_guuid` 仍非空（`DelClubAgent` 不清 `upper`），客户端判定"是不是代理"必须用 `is_agent`；
4. 重复操作会产生多条推送，客户端按幂等处理；
5. "开通即永生"：`is_never_death=True` 在开通瞬间生效，取消后不回收（既有设计；原本约 1 秒后由 `all_account_agents` 队列加载，方案只是提前）；
6. **取消代理的推送必须挂在"码置 disabled"那条 UPDATE 的回调上**：`DelClubAgent` 里两条 UPDATE 都是 fire-and-forget，而 `PushClubAgentInfo` 内部要另发一条 SELECT 查码，乱序执行时会推出 `is_agent=1` 的旧状态；
7. **取消代理不加载实体**（`allow_load=False`）：否则一个刚被取消代理的人会被 `createBaseFromGUUID` 加载成常驻代理并拿到代理永生，属反向副作用。
