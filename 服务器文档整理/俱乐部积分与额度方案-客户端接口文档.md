# 俱乐部积分与额度方案 - 客户端接口文档

> **文档定位**：客户端对接用的接口契约。服务端设计见 `doc/俱乐部积分与额度方案.md`；金币/钻石的历史契约见 `doc/俱乐部金币与钻石-客户端接口文档.md`（本文是它在「俱乐部模式」下的补充与变更）。
> **版本**：v1（2026-10-31）。
> **适用范围**：`game_mode = club` 的俱乐部房（房内消费全走钻石）。`game_mode = hall` 时本文所有“俱乐部”相关行为都不生效，客户端按原契约即可。

---

## 1. 三个数字，别混

| | 积分（俱乐部金币） | 额度 | 钻石 |
| --- | --- | --- | --- |
| 谁持有 | 玩家 | 代理（每个俱乐部一份） | 玩家 |
| 单位 | **元**（整数） | **分**（整数） | 个 |
| 表现 | 能带入、能换钻石的筹码 | 代理压在平台的钱 | 房卡/兑换得到的货币 |
| 客户端从哪读 | 成员列表的 `club_gold` 字段 | `查询_俱乐部_额度` 的 `quota_fen` | `Account.stone` 属性 |

**三条换算**：`1 积分 = 100 钻`；`1 额度（元）= 100 分`；`1 积分 = 100 额度分`（带入 1 元扣 100 分）。

---

## 2. 通用约定

- **命令格式**：`{"header":"命令名", ...业务字段..., "context":"客户端自定义串"}`
- **返回**：同步 `GC_OK` / `GC_FAILED`；带数据的走**异步推送**（路由名与命令名不同时，下文单独标注）。
- **错误**：`GC_FAILED` 时 `result` 形如 `{"error":"具体文案"}`
- **单位硬约定**：本文所有 `quota_fen` 一律是**分**，客户端显示时 ÷100；`money` 在房内消费里金币口径是**分**、钻石口径是**个**（见 §10）。

---

## 3. 带入：`坐下_事件`

俱乐部模式和普通房是同一条命令，客户端**参数不变**，但失败原因多了一种。

**请求**

```json
{"header":"坐下_事件", "site":3, "money":100, "ready":1, "type":"直接", "club_id":""}
```

| 字段 | 说明 |
| --- | --- |
| `site` | 座位号 |
| `money` | 本次带入的积分（**元**） |
| `type` | `直接` = 直接带入；`申请` = 余额不足、提交给管理员审批 |
| `club_id` | 遗留字段，俱乐部模式下留空即可（服务端按钱包 club 判断） |

**同步返回**

| 返回 | 触发 |
| --- | --- |
| `GC_OK` | 坐上去了 |
| `GC_FAILED` | 积分不足、**代理额度不足**、已在申请中 |
| `EC_NO_MONEY` | 余额不足（`roomError='nomoney'` 路径） |

**失败时的推送**（`PromptInfo`，客户端直接弹这句话）

| 文案 | 含义 |
| --- | --- |
| `俱乐部金币不足！` | 玩家自己的积分不够 |
| `该俱乐部额度不足` | **玩家上面最近的已授信代理**额度不够（新增） |

> 客户端处理建议：两种失败都提示“联系代理上分/补额度”，不要重试刷屏。

> **实时模式（realtime）补一条**：首次带入且 `money <= 0`、`type='直接'` 时，服务端直接返回 `EC_NO_MONEY`，并推 `PromptInfo:请先选择带入分数`。这不是余额问题，客户端带上玩家选的分数即可。

**审批带入（`type=申请`）的行为**：管理员同意后，带入总额 = 玩家现有积分 + 管理员追加额度。服务端会按**总额**校验代理额度，不足同样提示 `该俱乐部额度不足`，此时不占座、不扣分。

---

## 4. 结算与留座（客户端只需展示）

服务端不会主动推“额度变了”，客户端只需要照旧处理这两类消息：

| 路由 | 内容 | 时机 |
| --- | --- | --- |
| `PromptInfo` | `弹窗,留座` | 局内分不够打下一局（输光） |
| `PromptInfo2` | `["已结算请重新带入","补分"]` | 实时结算到点 |

玩家补分成功后回原座位继续，客户端不需要额外逻辑；**额度变化不会推给客户端**，要展示就重新调 `查询_俱乐部_额度`。

## 5. 查询额度：`查询_俱乐部_额度`

**请求**

```json
{"header":"查询_俱乐部_额度", "club_id":"820084", "user_id":"", "context":"ctx1"}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | 是 | 俱乐部 ID |
| `user_id` | 否 | 目标账号；留空 = 查自己 |
| `context` | 否 | 原样回带 |

**同步返回**：`GC_OK` + `{}`（数据不走返回值）

**异步推送（路由 `GetClubQuota`）**

```json
{"GetClubQuota": {
   "user_id": "496702",
   "quota_fen": 125000,
   "quota": 1250.0,
   "is_agent": 1,
   "is_granted": 1
 },
 "context": "ctx1"}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `user_id` | string | 被查账号 |
| `quota_fen` | int | 可用额度，**分**。主字段，用它做计算 |
| `quota` | float | 同一数值的元，**仅用于展示**，不要参与计算 |
| `is_agent` | int | 1=是本俱乐部代理；0=普通成员 |
| `is_granted` | int | 1=已被上级授信（授信 0 也算）；0=从未被授信 |

**三态展示（客户端必须区分）**

| `is_agent` | `is_granted` | 建议文案 |
| --- | --- | --- |
| 0 | 0 | 不是代理，无额度 |
| 1 | 0 | 等待上级授信 |
| 1 | 1 | 可用额度 `quota_fen / 100` 元（可以是 0） |

**权限**：查自己、或查下线、或群主查全俱乐部；否则 `GC_FAILED` + `{"error":"只能查询自己或自己的下线"}`。

## 6. 授信：`授信_俱乐部_额度`

把额度从自己的账户划给**直属下级代理**。

**请求**

```json
{"header":"授信_俱乐部_额度", "club_id":"820084", "user_id":"496702", "quota_fen":50000}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | 是 | 俱乐部 ID |
| `user_id` | 是 | **直属下级**账号 |
| `quota_fen` | 是 | 授信额度，**分**，≥0；**可以传 0** |

**返回**：成功 `GC_OK` + `{}`；失败 `GC_FAILED` + `{"error":"..."}`。**不回带 `context`**，客户端按 header 自己关联。

**服务端规则（客户端做前置判断可减少失败）**

1. 调用者必须是代理，且自己**已被授信**（群主天然已授信）；
2. `user_id` 必须是自己的**直属下级**，且**对方已经是代理**；
3. 金额从调用者额度划出，调用者额度不足会失败；
4. **传 0 有效**：对方会从「未授信」变成「已授信（额度 0）」，之后他能继续往下授信。

**失败文案对照**

| 文案 | 客户端应先检查什么 |
| --- | --- |
| `只有代理才能授信` | 自己是不是代理 |
| `你还没有被授信，不能往下授信` | 自己的 `is_granted` |
| `只能给自己的直属下级授信` | 目标是不是直接下级 |
| `对方还不是代理，请先把他设为代理` | 目标 `is_agent` |
| `你的额度不足` | 自己 `quota_fen` |
| `授信额度不能为负` | 参数 |
| `不能给自己授信` | 参数 |
| `俱乐部不存在` / `代理数据加载中，请稍后重试` | 稍后重试 |

**成功后**：客户端应重新调 `查询_俱乐部_额度` 刷新双方数字（服务端不主动推）。

---

## 7. 平台注资：`增加_俱乐部_额度`

```json
{"header":"增加_俱乐部_额度", "club_id":"820084", "user_id":"496702", "quota_fen":100000}
```

- 只给**后台 / boss 账号**用，**客户端不要做入口**；
- 服务端不校验调用者来源；
- 给「未授信」的代理注资，等同于注资 + 完成授信；
- 允许负值纠错，但结果不能小于 0。

## 8. 上下分：`添加_俱乐部_成员_积分` / `修改_俱乐部_成员_积分`

**参数结构完全不变**，客户端界面也不用改按钮；变化只在权限和资金来源。

| 调用者 | 能给谁加/减 | 钱从哪来 |
| --- | --- | --- |
| 群主 | 俱乐部内所有成员 | 自己的额度（玩家**带入时**才真正扣） |
| 代理（已被授信） | 自己整棵子树 | 自己的额度（玩家带入时才扣） |
| 代理（未被授信） | 自己整棵子树 | **自己账户里的积分**（赠送） |
| 普通成员 | 自己整棵子树 | **自己账户里的积分**（赠送） |
| 其他玩家 | 无权限 | — |

> 注意：**上分/下分本身不动额度**，只是给玩家发筹码。所以会出现“分已经上了，但代理额度不够，玩家带不进”的情况——这是设计如此。

**关键点**：调用者若没有额度（不是代理或未被授信），上分是从**自己的积分**里扣的。客户端应在界面上区分文案：“上分（扣额度）” vs “赠送（扣自己的积分）”，避免代理以为自己在发平台的钱。

**失败文案**

| 文案 | 场景 |
| --- | --- |
| `只能操作自己下线的成员` | 越权 |
| `你的俱乐部金币不足，无法赠送！` | 赠送时自己积分不够 |
| `玩家分数不能修改成负！` | 目标积分会被扣成负数 |
| `代理数据加载中，请稍后重试` | 树未加载 |

## 9. 兑换钻石

`money_type` 新增一种取值：**`"gold,<club_id>"`**（用俱乐部积分换钻石）。`"gold,非俱乐部"` 是平台通用金币，两者不要混用。

**方式 A：Hall 命令（有密码/限额/版本校验）**

```json
{"header":"调用_方法_Exchange2",
 "target_guuid":"<自己guuid>",
 "money_value":5,
 "money_type":"gold,820084",
 "user_pwd":"******",
 "client_version":"2026103100",
 "context":"ctx3"}
```

**方式 B：Account 直连（无密码、无限额、无版本校验）**

```json
{"receiver":"Account", "method":"reqExChange2", "args":["<自己guuid>", 5, "gold,820084"]}
```

| 项 | 说明 |
| --- | --- |
| 方式 A 字段 | `target_guuid` / `money_value` / `money_type` / **`user_pwd`** / **`client_version`**（10 位年月日序号，低于 `limit_version` 直接失败） |
| `money_value` | **消耗的积分（元）**，服务端只做乘法：钻石 = `money_value × gold_to_stone`（当前 100） |
| 结果 | `onExChange(EC_OK)` / `EC_NO_MONEY` / `EC_FAILED` |
| 校验顺序 | 是否该俱乐部成员 → 积分够不够 → **最近已授信代理的额度够不够** |
| 失败影响 | 积分、额度、钻石**三者都不变** |
| 兑换记录 | `type = '俱乐部金币兑换钻石'`（记录页可见） |

> 额度不足统一返回 `EC_NO_MONEY(0x302)`，客户端提示“该俱乐部额度不足，请联系代理”。

## 10. 消费与加时（强制钻石）

俱乐部模式下 `Account.gold` 不再是玩家资产，**这两类命令必须显式传 `stone`**：

| 命令 | 规则 | 失败 |
| --- | --- | --- |
| `玩家_消费_命令`（房内） | 必须 `"money_type":"stone"`，此时 `money` = **钻石个数** | 不传或传 `gold` → `GC_FAILED` |
| `玩家_消费_命令`（大厅） | 同上 | 同上 |
| `延长时间_命令` | 不传按 `stone` 处理；显式传 `gold` → `GC_FAILED` | — |

加时钻石档位不变：首免 20 秒 / 200 钻 +15 秒 / 400 钻 +10 秒 / 第 4 次拒绝。

> ⚠️ 单位陷阱：金币口径 `money` 是**分**，钻石口径是**个**。所以服务端不接受“缺省值”，客户端必须显式传，否则 `money=50` 会被当成 50 钻。

## 11. 积分从哪读

客户端展示玩家积分，用这两处，**不要自己算**：

| 场景 | 命令 / 路由 | 字段 |
| --- | --- | --- |
| 成员列表里的个人积分 | `查询_俱乐部_成员` → 列表推送 | `club_gold`（**字符串**，单位元） |
| 俱乐部总积分 | `查询_俱乐部_成员_总分` → 路由 `AllPlayerGold` | `total_club_gold`（**字符串**，单位元） |

> `club_gold` 是字符串，客户端解析成数字即可；缺失时服务端给 `-99`（表示“无该俱乐部数据”）。

## 12. 一张表看清“谁会拒绝你”

| 你看到的返回 | 原因 | 客户端建议 |
| --- | --- | --- |
| 带入 `GC_FAILED` + `PromptInfo:俱乐部金币不足！` | 玩家积分不够 | 提示找代理上分 |
| 带入 `GC_FAILED` + `PromptInfo:该俱乐部额度不足` | 代理额度不够 | 提示代理补额度 |
| 兑换 `EC_NO_MONEY` | 积分或额度不够 | 同上 |
| 消费 `GC_FAILED` | 没传 `stone` | 检查参数 |
| 上下分 `GC_FAILED` + `只能操作自己下线的成员` | 越权 | 刷新自己的下线范围 |
| 授信 `GC_FAILED` + `对方还不是代理` | 目标没设代理 | 先设代理再授信 |
| 退会 `GC_FAILED` + `请先清空该成员的俱乐部金币再操作` | 成员还有积分 | 先改积分为 0 |

## 13. 客户端改造清单（6 条）

1. **所有消费类命令显式传 `money_type`**，房内/大厅一致，不依赖缺省值。
2. **额度一律按分收发**：显示 `quota_fen / 100`，不要用 `quota` 浮点字段做计算。
3. **额度三态**：`is_agent=0`、`is_granted=0`、正常，三种文案要区分开。
4. **授信成功后主动重新查询**，服务端不推额度变更。
5. **兑换传 `"gold,<club_id>"`**，不要用 `"gold,非俱乐部"` 换俱乐部积分。
6. **上下分界面区分「扣额度」和「赠送」**：自己没额度时扣的是自己的积分，要提前告知。

## 14. 兼容与回退

| 场景 | 行为 |
| --- | --- |
| `game_mode = hall` | 本文所有俱乐部行为不生效：带入走 `Account.gold`、消费可传 `gold`、兑换只接受 `"gold,非俱乐部"` |
| 老客户端（不传 `money_type`） | 俱乐部门店里**消费会失败**，这是预期（服务端无法安全推断币种） |
| 老客户端（不传 `club_id`） | 带入/兑换按钱包俱乐部处理，不需要额外参数 |
| 回退到 hall | 服务端改 `game_mode` 重启即可，客户端的 `stone` 参数在 hall 下同样被接受（白名单包含 `stone`） |
