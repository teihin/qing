# 俱乐部积分与额度方案 - 客户端接口文档

> **2026-11-03 变更**：联盟模式 V2 已上线——`查询_俱乐部_额度` / `授信_俱乐部_额度` / `增加_俱乐部_额度` 三个命令**已停用**，额度改挂俱乐部（`club_guuid_info.union_quota`），由总群主用 `授信_联盟_额度` 下发。本文档涉及这三个命令的段落仅作历史参考，最新接口见 `doc/俱乐部俱乐部联盟模式V2方案-客户端接口文档.md`。

> **文档定位**：客户端对接用的接口契约。服务端设计见 `doc/俱乐部积分与额度方案.md`；金币/钻石的历史契约见 `doc/俱乐部金币与钻石-客户端接口文档.md`（本文是它在「俱乐部模式」下的补充与变更）。
> **版本**：v2.14（2026-11-05，含独立俱乐部免额度、入盟拦截、额度流水 ALL/agent、总群主查属下俱乐部积分/赠送流水、俱乐部解散限制、额度流水展示映射与房间号）。
> **适用范围**：`game_mode = club` 的俱乐部房（房内消费全走钻石）。`game_mode = hall` 时本文所有“俱乐部”相关行为都不生效，客户端按原契约即可。

---

## 1. 三个数字，别混

| | 积分（俱乐部金币） | 额度 | 钻石 |
| --- | --- | --- | --- |
| 谁持有 | 玩家 | 代理（每个俱乐部一份） | 玩家 |
| 单位 | **元**（整数） | **分**（整数） | 个 |
| 表现 | 能带入、能换钻石的筹码 | 代理压在平台的钱 | 房卡/兑换得到的货币 |
| 客户端从哪读 | 成员列表的 `club_gold` 字段 | `查询_俱乐部_额度` 的 `quota_fen` | `Account.stone` 属性 |

**三条换算**：`1 积分 = 100 钻`；`1 额度（元）= 100 分`；`1 积分 = 100 额度分`（带入 1 元扣 100 分）。

---

## 2. 通用约定

- **命令格式**：`{"header":"命令名", ...业务字段..., "context":"客户端自定义串"}`
- **返回**：同步 `GC_OK` / `GC_FAILED`；带数据的走**异步推送**（路由名与命令名不同时，下文单独标注）。
- **错误**：`GC_FAILED` 时 `result` 形如 `{"error":"具体文案"}`
- **单位硬约定**：本文所有 `quota_fen` 一律是**分**，客户端显示时 ÷100；`money` 在房内消费里金币口径是**分**、钻石口径是**个**（见 §10）。

## 3. 带入：`坐下_事件`

俱乐部模式和普通房是同一条命令，客户端**参数不变**，但失败原因多了一种。

**请求**

```json
{"header":"坐下_事件", "site":3, "money":100, "ready":1, "type":"直接", "club_id":""}
```

| 字段 | 说明 |
| --- | --- |
| `site` | 座位号 |
| `money` | 本次带入的积分（**元**） |
| `type` | `直接` = 直接带入；`申请` = 余额不足、提交给管理员审批 |
| `club_id` | 遗留字段，俱乐部模式下留空即可（服务端按钱包 club 判断） |

**同步返回**

| 返回 | 触发 |
| --- | --- |
| `GC_OK` | 坐上去了 |
| `GC_FAILED` | 积分不足、**代理额度不足**、已在申请中 |
| `EC_NO_MONEY` | 余额不足（`roomError='nomoney'` 路径） |

**失败时的推送**（`PromptInfo`，客户端直接弹这句话）

| 文案 | 含义 |
| --- | --- |
| `俱乐部金币不足！` | 玩家自己的积分不够 |
| `该俱乐部额度不足` | **玩家上面最近的已授信代理**额度不够（新增） |

> 客户端处理建议：两种失败都提示“联系代理上分/补额度”，不要重试刷屏。

> **实时模式（realtime）补一条**：首次带入且 `money <= 0`、`type='直接'` 时，服务端直接返回 `EC_NO_MONEY`，并推 `PromptInfo:请先选择带入分数`。这不是余额问题，客户端带上玩家选的分数即可。

**审批带入（`type=申请`）的行为**：管理员同意后，带入总额 = 玩家现有积分 + 管理员追加额度。服务端会按**总额**校验代理额度，不足同样提示 `该俱乐部额度不足`，此时不占座、不扣分。

## 4. 结算与留座（客户端只需展示）

服务端不会主动推“额度变了”，客户端只需要照旧处理这两类消息：

| 路由 | 内容 | 时机 |
| --- | --- | --- |
| `PromptInfo` | `弹窗,留座` | 局内分不够打下一局（输光） |
| `PromptInfo2` | `["已结算请重新带入","补分"]` | 实时结算到点 |

玩家补分成功后回原座位继续，客户端不需要额外逻辑；**额度变化不会推给客户端**，要展示就重新调 `查询_俱乐部_额度`。

## 5. 查询额度：`查询_俱乐部_额度`

**请求**

```json
{"header":"查询_俱乐部_额度", "club_id":"820084", "user_id":"", "context":"ctx1"}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | 是 | 俱乐部 ID |
| `user_id` | 否 | 目标账号；留空 = 查自己 |
| `context` | 否 | 原样回带 |

**同步返回**：`GC_OK` + `{}`（数据不走返回值）

**异步推送（路由 `GetClubQuota`）**

```json
{"GetClubQuota": {
   "user_id": "496702",
   "quota_fen": 125000,
   "quota": 1250.0,
   "is_agent": 1,
   "is_granted": 1
 },
 "context": "ctx1"}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `user_id` | string | 被查账号 |
| `quota_fen` | int | 可用额度，**分**。主字段，用它做计算 |
| `quota` | float | 同一数值的元，**仅用于展示**，不要参与计算 |
| `is_agent` | int | 1=是本俱乐部代理；0=普通成员 |
| `is_granted` | int | 1=已被上级授信（授信 0 也算）；0=从未被授信 |

**三态展示（客户端必须区分）**

| `is_agent` | `is_granted` | 建议文案 |
| --- | --- | --- |
| 0 | 0 | 不是代理，无额度 |
| 1 | 0 | 等待上级授信 |
| 1 | 1 | 可用额度 `quota_fen / 100` 元（可以是 0） |

**权限**：查自己、或查下线、或群主查全俱乐部；否则 `GC_FAILED` + `{"error":"只能查询自己或自己的下线"}`。

## 6. 授信：`授信_俱乐部_额度`【2026-11-03 已停用，改用 `授信_联盟_额度`】

把额度从自己的账户划给**直属下级代理**。

**请求**

```json
{"header":"授信_俱乐部_额度", "club_id":"820084", "user_id":"496702", "quota_fen":50000}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | 是 | 俱乐部 ID |
| `user_id` | 是 | **直属下级**账号 |
| `quota_fen` | 是 | 授信额度，**分**。`>0` 下拨、`=0` 只标记已授信、`<0` **收回**（从对方划回自己） |

**返回**：成功 `GC_OK` + `{}`；失败 `GC_FAILED` + `{"error":"..."}`。**不回带 `context`**，客户端按 header 自己关联。

**服务端规则（客户端做前置判断可减少失败）**

1. 调用者必须是代理，且自己**已被授信**（群主天然已授信）；
2. `user_id` 必须是自己的**直属下级**，且**对方已经是代理**；
3. 金额从调用者额度划出，调用者额度不足会失败；
4. **传 0 有效**：对方会从「未授信」变成「已授信（额度 0）」，之后他能继续往下授信。
5. **传负数 = 收回**：从对方把额度划回自己（对方 −|N|、自己 +|N|）；对方余额不够时整笔拒绝，不做部分收回；收回后对方仍是「已授信」状态，只是余额变少。

**失败文案对照**

| 文案 | 客户端应先检查什么 |
| --- | --- |
| `只有代理才能授信` | 自己是不是代理 |
| `你还没有被授信，不能往下授信` | 自己的 `is_granted` |
| `只能给自己的直属下级授信` | 目标是不是直接下级 |
| `对方还不是代理，请先把他设为代理` | 目标 `is_agent` |
| `你的额度不足` | 自己 `quota_fen` |
| `对方额度不足，当前可用 X 分` | 收回时对方余额不够（可能已被玩家带入占用） |
| `对方额度不足，当前可用 X 分` | 负数收回时对方余额不够 |
| `不能给自己授信` | 参数 |
| `俱乐部不存在` / `代理数据加载中，请稍后重试` | 稍后重试 |

**成功后**：客户端应重新调 `查询_俱乐部_额度` 刷新双方数字（服务端不主动推）。

## 7. 平台注资

### 7.1 `增加_俱乐部_额度`【2026-11-03 已停用，改用 `增加_联盟_额度`】

```json
{"header":"增加_俱乐部_额度", "club_id":"820084", "user_id":"496702", "quota_fen":100000}
```

- **只给后台 / boss 账号**（`d_users.config["account"]["boss"]`），普通客户端调用返回 `{"error":"无权限"}`，**客户端不要做入口**；
- 给「未授信」的代理注资，等同于注资 + 完成授信；
- 允许负值纠错，但结果不能小于 0。

### 7.2 `增加_俱乐部_钻石`（2026-11-02）

```json
{"header":"增加_俱乐部_钻石", "club_id":"820084", "stone_number":100000}
```

- 同样只给后台 / boss，普通客户端返回 `{"error":"无权限"}`；
- 加到该俱乐部**群主的钻石池**，这是玩家兑换钻石的唯一来源；
- **正数授予、负数扣减**；0 返回 `钻石数量不能为 0`；扣减不能超过群主钻石池，否则 `钻石不足，无法扣减`；
- 流水记在群主名下，`opt_type='钻石授信'`，负数为扣减。

## 8. 上下分：`添加_俱乐部_成员_积分` / `修改_俱乐部_成员_积分`

**2026-11-01 起必须带交易密码**：两个命令都要新增 `user_pwd` 字段（与兑换接口同名字段），否则一律失败。

```json
{"header":"添加_俱乐部_成员_积分", "club_id":"567671", "user_id":"496702",
 "user_add_gold":100, "user_pwd":"******", "context":"..."}

{"header":"修改_俱乐部_成员_积分", "club_id":"567671", "user_id":"496702",
 "user_modify_gold":200, "user_pwd":"******", "context":"..."}
```

| 情况 | 返回 |
| --- | --- |
| 没传或传空 `user_pwd` | `{"error": "请输入交易密码"}` |
| 密码和账号交易密码不一致 | `{"error": "交易密码错误"}` |
| 账号还没设过交易密码 | `{"error": "请先设置交易密码"}` |
| boss / 后台账号 | 豁免，不用传 |

其余字段、返回结构不变。密码校验在权限判断**之前**，所以越权 + 没带密码时会先返回密码类错误。

**权限与资金来源**（与之前一致）：

| 调用者 | 能给谁加/减 | 钱从哪来 |
| --- | --- | --- |
| 群主 | 俱乐部内所有成员 | 自己的额度（玩家**带入时**才真正扣） |
| 代理（已被授信） | 自己整棵子树 | 自己的额度（玩家带入时才扣） |
| 代理（未被授信） | 自己整棵子树 | **自己账户里的积分**（赠送） |
| 普通成员 | 自己整棵子树 | **自己账户里的积分**（赠送） |
| 后台 boss（8890 `/hall/command`，调用者恒为 `d_users` 的 `boss[0]`） | 任意俱乐部的任意成员 | 不扣任何人（平台操作） |
| 其他玩家 | 无权限 | — |

> 注意：**上分/下分本身不动额度**，只是给玩家发筹码。所以会出现“分已经上了，但代理额度不够，玩家带不进”的情况——这是设计如此。

**关键点**：调用者若没有额度（不是代理或未被授信），上分是从**自己的积分**里扣的。客户端应在界面上区分文案：“上分（扣额度）” vs “赠送（扣自己的积分）”，避免代理以为自己在发平台的钱。

**失败文案**

| 文案 | 场景 |
| --- | --- |
| `只能操作自己下线的成员` | 越权 |
| `你的俱乐部金币不足，无法赠送！` | 赠送时自己积分不够 |
| `玩家分数不能修改成负！` | 目标积分会被扣成负数 |
| `代理数据加载中，请稍后重试` | 树未加载 |
| `type` 字段 | `添加积分`（群主/代理上分，走额度）、`赠送`（非代理用自己积分） |
| `请输入交易密码` / `交易密码错误` / `请先设置交易密码` | 密码校验失败（见上文） |
| `修改后的积分不能为负，如需减少请用添加积分` | `修改_俱乐部_成员_积分` 传了负数（本命令是“设为某值”，不是增减） |

### 8.3 玩家间赠送：`赠送_俱乐部_积分`

自己把自己的积分转给**同一个授信代理下**的另一个玩家。

```json
{"header":"赠送_俱乐部_积分", "club_id":"567671", "user_id":"496702",
 "user_add_gold":100, "user_pwd":"******", "context":"..."}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | 是 | 俱乐部 ID |
| `user_id` | 是 | 接收方账号 |
| `user_add_gold` | 是 | 赠送金额，**元**，必须 > 0 |
| `user_pwd` | 是 | 交易密码（boss 豁免） |

**唯一判定：两人带入时必须扣同一个授信代理的额度**

```
允许 ⇔ 授信代理(A) == 授信代理(B)
授信代理(X) = X 自己（若 X 是已授信代理），否则沿 upper 向上最近一个已授信代理
```

| A | B | 授信代理 | 结果 |
| --- | --- | --- | --- |
| 496702（已授信） | 784111 | 496702 = 496702 | 允许 |
| 580629 | 784111 | 496702 = 496702 | 允许 |
| 496702（已授信） | 915929 | 496702 ≠ 718968 | 拒绝 |
| 718968（群主） | 496702（已授信） | 718968 ≠ 496702 | 拒绝 |
| 915929 | 784111 | 718968 ≠ 496702 | 拒绝 |

**不动额度**：只搬积分，额度分文不变。转给谁，以后他带入/兑换就扣谁的授信代理。

**流水**：赠送方 `积分赠送`（负数）、接收方 `积分受赠`（正数），可在 §11.1 积分流水里查到。

**失败文案**：`不能赠送给自己` / `赠送金额必须大于 0` / `你的俱乐部积分不足！` / `对方不在该俱乐部！` / `只能和同一个授信代理下的成员互相赠送` / 三条密码文案。

### 8.4 积分变动推送（2026-11-07 新增）

客户端要求：玩家 A 给玩家 B **上分 / 下分 / 改分 / 赠送**成功后，B 要弹提示。

**推送对象**：只有**被改积分的玩家 B** 收到推送；操作者 A 仍只收原来的 `GC_OK` 回包，不额外推。
覆盖命令：`添加_俱乐部_成员_积分`（正=上分、负=下分）、`修改_俱乐部_成员_积分`、`赠送_俱乐部_积分`。
后台走 `/hall/command` 上分同样会推给 B。铜钱宝旧入口（功能已废止）不覆盖。

**路由**：复用已有的 **`PromptInfo`**（客户端现有弹窗），不新增路由、不改 `Account.def`。
`id` / `word` 的形状与 `Hall._subHandleMessage("PromptInfo")` 完全一致，另附结构化字段；老客户端忽略未知字段即可，直接弹 `word`。

```json
{"id":"496702", "word":"「玩家A」给你上分 100，当前积分 500",
 "club_id":"567671", "type":"上分", "gold":"100", "balance":"500",
 "opter_guuid":"430994", "opter_name":"玩家A", "date":"2026-11-07 01:23:45"}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 接收方 B 的游戏 ID（与账号实体一致） |
| `word` | string | **可直接弹的完整提示文案**，客户端无需自己拼 |
| `club_id` | string | 发生变动的俱乐部 |
| `type` | string | `上分` / `下分` / `积分调整` / `赠送` |
| `gold` | string | 本次变动额，**带正负**；下分为负数 |
| `balance` | string | 变动后 B 在该俱乐部的积分余额 |
| `opter_guuid` / `opter_name` | string | 操作者 A 的 ID / 名字（后台上分时为 boss 账号） |
| `date` | string | 服务端时间 `YYYY-MM-DD HH:MM:SS` |

**文案样例**（`word`，客户端直接展示）：

| 场景 | word |
| --- | --- |
| 上分 100 | `「玩家A」给你上分 100，当前积分 500` |
| 下分 30 | `「玩家A」给你下分 30，当前积分 470` |
| 赠送 50 | `「玩家A」赠送你 50 积分，当前积分 500` |
| 改分 | `「玩家A」把你的积分调整为 500` |

**客户端处理建议**：收到即弹 `word`，同时用 `balance` 刷新当前俱乐部积分显示；若停在「上下分/赠送」或积分流水页，可顺带重查一次该列表（服务端只推这一条，不推流水明细）。推送是通知，重复收到按幂等处理。

**边界**：

| 场景 | 行为 |
| --- | --- |
| B 在线（含正在房间内） | 立即收到 `PromptInfo`，弹提示；牌局不打断 |
| B 离线 / 掉线 | 不推、不报错、不缓存；上线后按原流程查询即可 |
| 改分差额为 0 / 操作失败 / 自己给自己操作 | 不推 |
| 操作者 A | 不推（只有 `GC_OK`） |
| 后台 boss 上分 | 会推给 B，`opter_name` 是 boss 账号名 |

## 9. 兑换钻石

`money_type` 新增一种取值：**`"gold,<club_id>"`**（用俱乐部积分换钻石）。`"gold,非俱乐部"` 是平台通用金币，两者不要混用。

**方式 A：Hall 命令（有密码/限额/版本校验）**

```json
{"header":"调用_方法_Exchange2",
 "target_guuid":"<自己guuid>",
 "money_value":5,
 "money_type":"gold,820084",
 "user_pwd":"******",
 "client_version":"2026103100",
 "context":"ctx3"}
```

**方式 B：Account 直连（无密码、无限额、无版本校验）**

```json
{"receiver":"Account", "method":"reqExChange2", "args":["<自己guuid>", 5, "gold,820084"]}
```

| 项 | 说明 |
| --- | --- |
| 方式 A 字段 | `target_guuid` / `money_value` / `money_type` / **`user_pwd`** / **`client_version`**（10 位年月日序号，低于 `limit_version` 直接失败） |
| `money_value` | **消耗的积分（元）**，服务端只做乘法：钻石 = `money_value × gold_to_stone`（当前 100） |
| 结果 | `onExChange(EC_OK)` / `EC_NO_MONEY` / `EC_FAILED` |
| 校验顺序 | 是否该俱乐部成员 → 积分够不够 → **群主钻石池够不够**（2026-11-02 起不再是代理额度） |
| 失败影响 | 积分、群主池、玩家钻石**三者都不变** |
| 兑换记录 | `usr_exchange_info`（`type='俱乐部金币兑换钻石'`）+ `club_stone_exchange_info`（俱乐部维度明细，见 §11.4） |
| 群主积分入账 | 玩家消耗的积分同步加到群主本俱乐部的 `club_gold`（老板金币）；群主自己兑换也入账（−N 再 +N，净值为 0），写一条群主维度 `钻石兑换` 流水 |

> 池不足统一返回 `EC_NO_MONEY(0x302)`，客户端提示“俱乐部钻石不足，请联系群主补充”。
>
> **2026-11-02 变更**：兑换的钻石来自**群主的俱乐部钻石池**，不再扣“最近已授信代理”的额度；代理额度此后只受带入/结算影响。

## 10. 消费与加时（强制钻石）

俱乐部模式下 `Account.gold` 不再是玩家资产，**这两类命令必须显式传 `stone`**：

| 命令 | 规则 | 失败 |
| --- | --- | --- |
| `玩家_消费_命令`（房内） | 必须 `"money_type":"stone"`，此时 `money` = **钻石个数** | 不传或传 `gold` → `GC_FAILED` |
| `玩家_消费_命令`（大厅） | 同上 | 同上 |
| `延长时间_命令` | 不传按 `stone` 处理；显式传 `gold` → `GC_FAILED` | — |

加时钻石档位不变：首免 20 秒 / 200 钻 +15 秒 / 400 钻 +10 秒 / 第 4 次拒绝。

> ⚠️ 单位陷阱：金币口径 `money` 是**分**，钻石口径是**个**。所以服务端不接受“缺省值”，客户端必须显式传，否则 `money=50` 会被当成 50 钻。

## 11. 积分从哪读

客户端展示玩家积分，用这两处，**不要自己算**：

| 场景 | 命令 / 路由 | 字段 |
| --- | --- | --- |
| 成员列表里的个人积分 | `查询_俱乐部_成员` → 列表推送 | `club_gold`（**字符串**，单位元） |
| 俱乐部总积分 | `查询_俱乐部_成员_总分` → 路由 `AllPlayerGold` | `total_club_gold`（**字符串**，单位元） |

> `club_gold` 是字符串，客户端解析成数字即可；缺失时服务端给 `-99`（表示“无该俱乐部数据”）。

### 11.1 玩家积分流水：`查询_俱乐部_积分流水`

```json
{"header":"查询_俱乐部_积分流水", "club_id":"567671", "user_id":"", "count":10, "page":0, "context":"ctx9"}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | 是 | 俱乐部 ID |
| `user_id` | 否 | 留空 = 查自己 |
| `count` / `page` | 否 | 分页，`count` 默认 10；总条数服务端封顶 100 |
| `only_add` | 否 | `1` = 只看上下分与赠送（`添加积分` + `积分赠送`）；不传/`0` = 全部积分变动 |

同步返回 `GC_OK` + `{}`，数据走推送 **`ClubGoldWater`**：

```json
{"ClubGoldWater":[
  {"number":"0","count":"37","gold":"-100","date":"2026-11-01 15:20:11",
   "type":"带入","remark":"1934","room_id":"123456","opter_name":"","guuid":"496702","name":"a2"},
  {"number":"0","count":"37","gold":"150","date":"2026-11-01 15:52:03",
   "type":"结算","remark":"2084","room_id":"123456","opter_name":"","guuid":"496702","name":"a2"}
]}
```

| 字段 | 说明 |
| --- | --- |
| `gold` | 本次变动，**整数元**，负数 = 减少 |
| `type` | 原样返回 `opt_type`：`带入` / `结算` / `添加积分` / `修改积分` / `积分赠送` / `积分受赠` / `钻石兑换` / `代理红利提取` / `联盟红利提取`（`only_add=1` 时 `添加积分` 会被替换成 `上分` / `下分`，见下） |
| `only_add=1` 时的 `type` | 服务端已直接给语义：`上分`（金额为正）/ `下分`（金额为负）/ `积分赠送`（负=送出去），客户端不用再判断正负 |
| `remark` | **变动后余额**（整数元）。“余额”列直接显示它即可 |
| `guuid` | 流水归属玩家账号 |
| `name` | 流水归属玩家名字（直接展示，不用再查成员列表） |
| `opter_name` | 上分/改分是操作人；`积分赠送`/`积分受赠` 是**交易对方**（见 §11.3）；带入、结算为空 |

> 只包含这四类。审批类记录（同意坐下 / 拒绝坐下 / 踢出玩家）仍在 `查询_同意拒绝_坐下_记录`，不重复展示。

**权限**：自己 / 本俱乐部群主 / **联盟总群主（可查本联盟属下俱乐部任意成员）** / boss 可查；代理只能查自己整棵子树，否则返回 `GC_FAILED` + `{"error":"只能查询自己或自己的下线"}`。联盟总群主按目标俱乐部 `union_id` 归属判定，跨联盟不可查。

### 11.2 额度流水：`查询_俱乐部_额度流水`

推送路由 **`ClubQuotaWater`**。

**请求**

```json
{"header":"查询_俱乐部_额度流水", "club_id":"893347", "user_id":"", "agent_id":"", "count":20, "page":0, "context":"ctx"}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | 是 | 俱乐部 ID |
| `user_id` | 否 | 不传/空 = 自己；`"ALL"` = 俱乐部全部额度流水 |
| `agent_id` | 否 | 指定成员/子树根 ID：返回该成员**当前子树**内节点触发的额度流水；普通成员也可传本人 ID（只返回本人流水）；与 `user_id` 同时传时以 `agent_id` 为准 |
| `count` / `page` | 否 | 分页，总条数服务端封顶 100 |

示例：

```json
{"ClubQuotaWater":[
  {"number":"0","count":"12","quota":"-50000","date":"2026-11-01 15:08:42",
   "type":"带入","remark":"950000","room_id":"123456",
   "opter_name":"测试合伙人下级","actor_guuid":"501208",
   "guuid":"529749","name":"测试盟主"}
]}
```

> **2026-11-05 新增模式**：`user_id="ALL"` 查俱乐部全部额度流水；`agent_id` 查该成员当前子树内节点触发的流水。代理子树按 `club_history_info.opter_guuid` 归属，包含成员自己 + 当前 used 下级。

> **2026-11-05 展示映射**：仅 `ClubQuotaWater` 返回时，`额度占用` → **`带入`**、`额度回补` → **`结算`**；这两类 `remark` 只返回变动后余额（分），不再带 `旧→新`。数据库仍保留原始 `opt_type` 和审计备注，其它额度类型原样返回。`quota` 仍是带符号的变动值（带入为负、结算为正）。

> **2026-11-05 房间号**：`带入`/`结算`（原 `额度占用`/`额度回补`）从 2026-11-05 起写入实际牌局 `room_id`；授信/收回/联盟注资等非房间流水仍为空，历史旧记录也保持空串。

> **2026-11-02 字段改名**：额度流水的金额字段由 `gold` 改为 **`quota`**，与积分流水的 `gold` 区分开（一个分、一个元）。

| 返回 `type` | 原始 `opt_type` | 含义 | `quota` 符号 |
| --- | --- | --- | --- |
| `带入` | `额度占用` | 玩家带入，扣俱乐部额度 | − |
| `结算` | `额度回补` | 结算回本金 | + |
| `额度授信` | 同左 | 上级下拨（旧代理额度） | + |
| `额度收回` | 同左 | 上级收回（旧代理额度） | − |
| `额度转入` | 同左 | 后台注资（旧代理额度） | 可正可负 |
| `额度抽水回补` | 同左 | 抽水里分给该层的那份（旧代理额度） | + |
| `额度兑换` | 同左 | 玩家换钻石（旧代理额度） | − |
| `额度联盟授信` | 同左 | 联盟池拨给俱乐部 / 收回 | 可正可负 |
| `额度联盟注资` | 同左 | 平台给联盟池注资 | 可正可负 |

`quota` 单位是**分**，展示时 ÷100。

| 字段 | 说明 |
| --- | --- |
| `guuid` / `name` | 额度归属账号（当前 V2 通常是俱乐部群主） |
| `opter_name` | 实际触发人名称（V2 额度流水从 `tbl_Account` 补全） |
| `actor_guuid` | `ClubQuotaWater` 额外下发：实际触发人 ID；名称直接用 `opter_name`，历史行没有触发人时为空串 |
| `remark` | `带入`/`结算` 仅返回变动后余额（分）；其它类型保留原备注（通常为 `旧→新`） |
| `room_id` | 牌局房间 ID；`带入`/`结算` 新记录起写入，授信/联盟类与历史旧记录为空串 |

**权限**：

- 普通 `user_id` 模式：自己 / 群主 / boss 可查任意账号；代理只能查自己整棵子树，否则 `{"error":"只能查询自己或自己的下线"}`。
- `user_id="ALL"`：仅俱乐部创建者 / 联盟创建者 / boss；其他返回 `{"error":"只有俱乐部创建者或联盟创建者可以查询"}`。
- `agent_id` 模式：俱乐部创建者 / 联盟创建者 / boss 可查任意子树；代理只能查自己或自己子树。
- 代理树未加载返回 `{"error":"代理数据加载中，请稍后重试"}`。

> `agent_id` 模式按**当前代理树**归属，不做历史快照：玩家改挂、代理取消或退会后，历史流水会随当前树变化；旧流水没有 `opter_guuid` 时无法归属。
>
> `agent_id` 模式只返回 `opter_guuid` 在子树内的流水；`额度联盟授信/注资` 由总群主/boss 操作，普通代理子树不会显示，需要俱乐部全量请用 `user_id="ALL"`。代理树未加载返回“加载中”，客户端可重试。

## 13. 客户端改造清单（6 条）

1. **所有消费类命令显式传 `money_type`**，房内/大厅一致，不依赖缺省值。
2. **额度一律按分收发**：显示 `quota_fen / 100`，不要用 `quota` 浮点字段做计算。
3. **额度三态**：`is_agent=0`、`is_granted=0`、正常，三种文案要区分开。
4. **授信成功后主动重新查询**，服务端不推额度变更。
5. **兑换传 `"gold,<club_id>"`**，不要用 `"gold,非俱乐部"` 换俱乐部积分。
6. **上下分界面区分「扣额度」和「赠送」**：自己没额度时扣的是自己的积分，要提前告知。

## 16. 联盟模式 V2（2026-11-03）

联盟是「总群主 → 俱乐部（盟主）」两级结构：总群主建联盟，给自己的俱乐部和各盟主授额度；**俱乐部带入只用这份联盟额度**，代理不再有独立额度账户（`quota` 相关旧命令已停用，见 §16.10）。

### 16.1 建联盟：`创建_联盟`

```json
{"header":"创建_联盟", "club_id":"567671", "union_name":"XX联盟"}
```

| 项 | 说明 |
| --- | --- |
| 权限 | 只有俱乐部创建者；一个账号只能建一个联盟 |
| 返回 | 推送 **`ClubUnionCreate`**：`{"union_id": "123456"}`（6 位联盟码）；后台调用走 `ret_result` |
| 副作用 | 自己的俱乐部自动绑定该联盟，`union_quota` 从 0 开始 |

### 16.2 我的联盟：`查询_我的_联盟`

```json
{"header":"查询_我的_联盟"}
```

推送 **`ClubMyUnion`**：

```json
{"ClubMyUnion": {"union_id": "123456", "union_name": "XX联盟", "union_quota": "0",
  "members": [
    {"club_id": "567671", "club_name": "a", "owner_guuid": "718968", "owner_name": "abc", "union_quota": "0"}
  ]}}
```

`union_quota` 单位**分**；`members` 是联盟内所有俱乐部（含总群主自己）。

### 16.3 申请加入：`申请_加入_联盟`

```json
{"header":"申请_加入_联盟", "club_id":"535696", "union_id":"123456"}
```

- 只有俱乐部创建者能申请；
- 已有联盟、已有在审申请、联盟号不存在、申请自己的联盟 → 各自拒绝；
- 只写 `union_apply`，审批通过才真正绑定。

### 16.4 待审列表：`查询_联盟_加入申请`

```json
{"header":"查询_联盟_加入申请"}
```

推送 **`ClubUnionApply`**：

```json
{"ClubUnionApply": [{"club_id":"535696","club_name":"b","owner_guuid":"580629","owner_name":"def"}]}
```

### 16.5 审批：`同意_加入_联盟` / `拒绝_加入_联盟`

```json
{"header":"同意_加入_联盟", "club_id":"535696", "agree":1}
{"header":"拒绝_加入_联盟", "club_id":"535696", "agree":0}
```

- 只有总群主能审批；同意后对方俱乐部 `union_id` 写入、`union_apply` 清空；拒绝只清 `union_apply`；
- 方向由**命令名**决定，不需要传 `agree`（老客户端传了也兼容）。

### 16.6 授信：`授信_联盟_额度`

```json
{"header":"授信_联盟_额度", "club_id":"535696", "quota_fen":1000000}
```

| 项 | 说明 |
| --- | --- |
| 单位 | **分**（1 万元 = 1000000） |
| 方向 | 正数 = 授出，负数 = 收回 |
| 效果 | 联盟池 −N、目标俱乐部 +N |
| 失败 | `你的联盟额度不足` / `目标俱乐部额度不足，收回失败` |
| 特殊 | **目标可以是自己**——总群主自己的俱乐部也要先授信才能带入 |

### 16.7 平台注资：`增加_联盟_额度`（仅 boss）

```json
{"header":"增加_联盟_额度", "union_id":"123456", "quota_fen":10000000}
```

只给后台 / boss，客户端不做入口；**正数注资、负数扣减**，0 返回 `调整金额不能为 0`；扣减不能超过联盟池，否则 `联盟额度不足，无法扣减`。

### 16.8 查额度：`查询_联盟_额度`

```json
{"header":"查询_联盟_额度"}
```

不传参数，服务端按身份返回，推送 **`ClubUnionQuota`**（后台调用走 `ret_result`）：

```json
{"union_id": "123456", "union_quota": "10000000", "is_owner": 1}   // 总群主看联盟池
{"union_id": "123456", "union_quota": "1000000",  "is_owner": 0}   // 盟主看自己俱乐部
```

都没有 → `{"error": "你还没有联盟"}`。

### 16.9 代理红利

抽水按 `percent` 逐层累加到 `club_agent_info.bonus`（**分**），不再回补额度；代理要用钱必须先提取成俱乐部积分。

| 命令 | 说明 |
| --- | --- |
| `查询_俱乐部_红利` | 推送 **`ClubBonus`**：`{"bonus_fen": "12345", "bonus": "123.45"}`；权限同积分流水 |
| `查询_俱乐部_红利_明细` | 推送 `ClubBonusList`；群主看全俱乐部，代理只看自己；不含 `clubtotal` 基线与 `unionroot` 联盟上缴 |
| `提取_俱乐部_红利` | 参数 `extract_gold` **单位元、≥1 整数**；扣 `bonus − extract_gold*100`、加 `club_gold + extract_gold`；不足 1 元留在账上 |
| `查询_俱乐部_红利_统计` | 推送 **`ClubBonusStats`**：今日/昨日新增（分/元）、累计提取（分/元）、未提取（分/元）；今日/昨日取 `usr_income_info`，累计提取取 `代理红利提取` 流水，未提取取当前 `bonus` |

`ClubBonusList` 单条：

```json
{"number":"0","count":"12","date":"2026-11-03 10:12:33","guuid":"580629","name":"a3",
 "bonus":"83","level":"club2","room_id":"772975"}
```

`bonus` 单位分；`level` 是分成层级（`clubroot` = 创建者，`club2`/`club3`… = 第几层代理）。

> `提取_联盟_红利` 的积分流水使用独立 `opt_type='联盟红利提取'`，不混入这里的 `代理红利提取` 统计。联盟侧对应统计接口为 `查询_联盟_红利_统计` → `ClubUnionBonusStats`，详见 V2 客户端接口文档 §10.6。

### 16.10 停用的旧命令

以下命令已从命令表移除，调用返回「命令不存在」：

`添加_联盟_成员` / `删除_联盟_成员` / `删除_联盟_加入申请` / `查询_俱乐部_联盟` / `查询_俱乐部_额度` / `授信_俱乐部_额度` / `增加_俱乐部_额度`

> `申请_加入_联盟` / `查询_联盟_加入申请` **名字保留但语义已换**：参数从旧联盟 ID 改成新联盟码，走的是新实现。

### 16.11 创建俱乐部收费（2026-11-03 已取消服务端收费）

`创建_俱乐部` 服务端不再扣钻、不校验余额、不退款；客户端在创建成功后调 `玩家_消费_命令`：

```json
{"header":"玩家_消费_命令", "consume_type":"创建俱乐部", "money":10000, "money_type":"stone"}
```

- `money` 单位是**钻石个数**；
- 消费命令余额不足会**扣到 0 仍返回成功**，客户端必须前置判断 `stone >= 费用`；
- 流水：`usr_consume_info` 的 `消费-创建俱乐部` + `usr_cash_water`（`remark4='创建俱乐部'`、`money_type='stone'`）；
- 服务端**不校验是否已扣费**，直接调 `创建_俱乐部` 可绕过收费；
- 最新接口见 `doc/俱乐部俱乐部联盟模式V2方案-客户端接口文档.md` §11。

### 16.12 带入规则变化

| 场景 | 结果 |
| --- | --- |
| 俱乐部未加入联盟（`union_id` 为空） | **不参与联盟额度**：带入不校验、不占用、不回补 `union_quota`，只校验玩家自己的俱乐部积分 `club_gold`，不足则带入失败（与额度无关） |
| 已入盟俱乐部额度 < 本次带入 | `EC_NO_MONEY`，玩家积分不动 |
| 已入盟俱乐部结算 | 回补到**同一个**俱乐部额度池，不再区分哪个代理出的钱 |
| 解散俱乐部 | 盟主解散前必须没有其它成员/代理且 `union_quota=0`，否则拒绝；独立俱乐部不检查额度；boss 强制解散仍自动退回联盟池 |

> **加入/退出联盟前必须关闭本俱乐部所有房间**。局中不允许切换联盟；服务端在同意加入时会检查该俱乐部是否还有未结束房间/玩家，有则拒绝并返回 `该俱乐部还有未结束的房间，请先关闭所有房间`。否则带入时按当时 `union_id` 判定是否走额度，结算时俱乐部归属可能已变化，导致额度占用/回补不一致。
