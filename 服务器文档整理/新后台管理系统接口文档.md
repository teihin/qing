# 新后台管理系统接口文档

本文档只描述新后台需要调用的接口、数据库读取方式、参数、返回格式和校验方式。实现新后台时只按本文定义调用，不依赖旧系统内部实现。

线上环境信息：

| 项 | 值 |
| --- | --- |
| 游戏服务器 | `154.37.155.17` |
| MySQL 数据库 | `kbedm` |
| 内部 HTTP 地址 | `http://127.0.0.1:8890` |
| 管理后台访问旧服务方式 | 新后台后端在服务器本机调用 HTTP 和 MySQL |
数据库 地址 172.22.161.126  密码同测试服

## 1. 接入原则

新后台只使用两类接口：

1. **MySQL 查询接口**：用于玩家列表、玩家详情、战绩、流水、注册记录、代理关系、俱乐部、联盟、报表统计。
2. **内部 HTTP 管理接口**：用于充值/补分/退款、修改在线玩家属性、修复登录、公告、房间命令、运行配置等会影响游戏运行状态的操作。

禁止新后台前端直接访问旧 HTTP 接口。必须由新后台后端封装接口、鉴权、审计、参数校验后再调用。

## 2. 通用 HTTP 调用规范

### 2.1 健康检查

```http
GET http://127.0.0.1:8890/index
```

成功返回：

```text
index ok
```

### 2.2 通用命令入口

```http
GET http://127.0.0.1:8890/hall/command
```

Query 参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | 命令名，中文字符串，需要 URL encode |
| `param` | JSON string | 是 | 命令参数 JSON 字符串，需要 URL encode |

调用示例：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_获取_玩家_属性' \
  --data-urlencode 'param={"guuid":"292989","name":"gold","context":"admin-20260807-0001"}'
```

返回格式：

```json
{
  "ret_code": 512,
  "ret_result": "1925"
}
```

状态码：

| `ret_code` | 含义 | 新后台处理 |
| ---: | --- | --- |
| `512` | 成功 | 正常解析 `ret_result` |
| `769` | 失败 | 给出失败提示，写审计 |
| `1280` | 已接收/异步处理 | 不能认为业务已完成，需要按本文档的校验 SQL 读取结果 |

约定：

- `context` 建议每次传唯一操作号，例如 `admin-20260807-0001`，便于排查日志和审计。
- `param` 必须是合法 JSON。
- HTTP 只允许新后台后端从本机访问，不允许公网访问。

### 2.3 禁止开放的旧接口

以下接口不得暴露给后台页面，也不得开放给普通管理员：

```text
/beifeng/eval
/beifeng/exec
/beifeng/reload
```

## 3. 通用 MySQL 查询规范

连接库：

```sql
USE kbedm;
```

实现要求：

- 所有 SQL 使用参数化查询。
- 默认分页参数：`page` 从 `1` 开始，`page_size` 建议最大 `100`。
- 查询日期统一使用 `YYYY-MM-DD`。
- 资金字段展示时把 `sm_gold + sm_gold2 / 100` 作为玩家现金余额。
- 除本文明确允许的注册记录外，不要直接 `UPDATE tbl_Account` 的金币、房间、优化、俱乐部积分等字段。

### 4.4 修改玩家属性

旧服务 HTTP：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_设置_玩家_属性' \
  --data-urlencode 'param={"guuid":"292989","name":"role","value":"测试玩家","context":"admin-set-prop"}'
```

参数：

| --- | --- | --- | --- |
| `guuid` | string | 是 | 玩家游戏 ID |
| `name` | string | 是 | 属性名，不带 `sm_` 前缀 |
| `value` | string/int | 是 | 新值 |
| `context` | string | 否 | 操作号 |

允许开放给后台的属性白名单建议：

```text
name, photo, sex, role, client_status, player_setting, client_prop
```

> **`client_prop`（代理的"业绩比例"开通开关）**：`True` = 开通（该代理客户端出现"业绩比例"入口），空串 `""` = 关闭。属性为 `BASE_AND_CLIENT` 持久化属性，目标代理**在线时即时同步**到其客户端；离线则下次登录生效。
>
> **开通前置校验（2026-09-22 补充）**：**开通**时目标账号必须是代理——服务端判据是"该账号在服务器代理集合 `Hall.proxys` 中"（**不要**用 `sm_level`/`sm_role` 判断代理：玩家与代理都可能是 `98`/`新玩家`）。非代理开通会被拒绝，返回 `ret_code=769` + `ret_result={"error": "该账号不是代理，不能开通业绩！"}`，且**不回写属性**；**关闭（`value` 传空串 `""`）不做该校验**，可随时清理误开通。若确认是在册代理却被拒，多为该代理数据尚未加载（`proxys` 为"已加载代理"集合，重启后才新注册且尚无下线的代理可能未加载），稍后重试即可。

```bash
# 开通业绩
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_设置_玩家_属性' \
  --data-urlencode 'param={"guuid":"189836","name":"client_prop","value":"True","context":"admin-20260922-0001"}'

# 关闭业绩: value 传空串 ""
```

> 业绩数据的口径与联调说明见 `doc/奖池提留代理业绩-客户端接口文档.md`、服务端实现见 `doc/奖池提留代理业绩分配方案.md`（§5 步骤 5）。

高危属性，默认不要开放；确需开放必须超级管理员和强审计：

```text
optimize01_man, optimize01_count, optimize01_chance,
```

### 4.5 修改玩家登录密码

新后台接口建议：

```http
POST /api/admin/players/{guuid}/password
```

请求：

```json
{
  "password": "111111",
  "reason": "测试账号重置"
}
```

旧服务 HTTP：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_设置_玩家_属性' \
  --data-urlencode 'param={"guuid":"292989","name":"userPWD","value":"111111","context":"admin-reset-login-pwd"}'
```

说明：

- `value` 传明文，旧服务会保存为 MD5。
- 如该账号来自 `third_marketing_info`，建议同时同步注册表密码：

```sql
UPDATE third_marketing_info
SET player_wxpwd = MD5(?)
WHERE player_guuid = ?;
```

- 这是**客服人工重置路径**，两步缺一不可：只改 `tbl_Account.sm_userPWD` 不同步注册表，玩家依然无法登录，因为登录校验只认 `third_marketing_info.player_wxpwd`（`kbemain.py:onRequestAccountLogin`）。

玩家登录前自助改密（输入账号 + 交易密码 + 新密码）：

- 方案见 `doc/登录前修改密码Web接口方案.md`。
- 该方案由 Web 侧直接写 `third_marketing_info.player_wxpwd`，不需要 `tbl_Account` 写权限；`tbl_Account.sm_userPWD` 由玩家下次登录/重连时的登录自愈同步。
- 两条路径关系：**玩家自助优先，客服人工兜底**。自助接口只服务"注册表有记录且已设置交易密码"的正常账号；从未登录过游戏（无 `tbl_Account` 记录、无交易密码）、创世 boss 账号、以及登录自愈不覆盖的边缘账号，仍走本节的客服路径。

## 7. 财务管理

### 7.1 充值、补分、退款、奖励、红包

新后台接口建议：

```http
POST /api/admin/players/{guuid}/balance-adjustments
```

请求：

```json
{
  "type": "BF",
  "amount": 100,
  "pay_amount": 100,
  "reason": "测试补分",
  "external_order_no": "BF202608070001"
}
```

`type` 建议：

| 类型 | 工单前缀 | 旧服务识别 |
| --- | --- | --- |
| 充值 | `CZ` | 默认按充值 |
| 补分 | `BF` | `work_order` 包含 `BF` |
| 退款 | `TK` | `work_order` 包含 `TK` |
| 奖励 | `JL` | `work_order` 包含 `JL` |
| 红包 | `HB` | `work_order` 包含 `HB` |

旧服务 HTTP：

```bash
SIGN=$(printf '%s%s%s' 'aqCpjryfDbNEHK7s6h8pGEJGmnYRkPW0' '100' '292989' | md5sum | awk '{print $1}')

curl --get 'http://127.0.0.1:8890/newmeng793afw/exchange' \
  --data-urlencode 'param={"coin":"100","coin2":"0","num":"100","guuid":"292989","work_order":"BF202608070001","sgin":"'"$SIGN"'"}'
```

参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `coin` | int string | 是 | 增加金币整数 |
| `coin2` | int string | 是 | 小数部分；当前按 `0` 使用 |
| `num` | int string | 是 | 业务金额，记录用 |
| `guuid` | string | 是 | 玩家游戏 ID |
| `work_order` | string | 是 | 唯一工单号 |
| `sgin` | string | 是 | 签名，字段名固定是 `sgin` |

签名算法：

```text
sgin = md5(exchange2_server_sign + coin + guuid)
```

签名密钥 `exchange2_server_sign`（**正式服，2026-11-19 起生效**）：

```text
aqCpjryfDbNEHK7s6h8pGEJGmnYRkPW0
```

### 10.3 联盟模式 V2：授信记录

> V2 联盟是 `club_union_info` + `club_guuid_info.union_id`，**与 §10.1/§10.2 的旧联盟（`union_guuid_info`）不是一套数据**，旧表已停用。
>
> 游戏命令 `查询_联盟_授信_记录` 是异步 SQL 推送，后台（`Hall.boss` 无 client）拿不到结果，直接查库。一条记录只对应**目标俱乐部**一侧；池侧对手方行用 `remark LIKE '联盟池%'` 排除，否则同一笔会出现两次。
>
> 2026-11-13 起 `额度奖励` 也进本页：API2（总群主→盟主）只取目标侧（`remark NOT LIKE '联盟池%'`）；API1（平台→池）取池侧（`remark LIKE '联盟池奖励%'`），见 §10.4。三类记录不要混查。

授信 / 收回明细（`授信_联盟_额度`）：

```sql
SELECT
  h.id,
  h.date,
  h.user_quota                        AS quota_fen,          -- 有符号：正=授信，负=收回
  SUBSTRING_INDEX(h.remark, '→', -1)  AS quota_after_fen,    -- 变动后俱乐部额度
  h.club_guuid                        AS target_club_guuid,
  c.club_name                         AS target_club_name,
  h.user_guuid                        AS target_guuid,
  h.user_name                         AS target_name,
  h.opter_guuid,
  IFNULL((SELECT sm_name FROM tbl_Account WHERE sm_guuid = h.opter_guuid LIMIT 1), h.opter_name) AS opter_name
FROM club_history_info h
LEFT JOIN club_guuid_info c ON c.club_guuid = h.club_guuid
WHERE h.opt_type = '额度联盟授信'
  AND h.remark NOT LIKE '联盟池%'
  AND h.club_guuid IN (SELECT club_guuid FROM club_guuid_info WHERE union_id = ?)
ORDER BY h.id DESC
LIMIT ? OFFSET ?;
```

平台注资 / 扣减（`增加_联盟_额度`，仅 boss）：

```sql
SELECT
  h.id,
  h.date,
  h.user_quota                        AS quota_fen,          -- 有符号：正=注资，负=扣减
  SUBSTRING_INDEX(h.remark, '→', -1)  AS union_quota_after_fen,
  h.opter_guuid,
  h.opter_name
FROM club_history_info h
JOIN club_union_info u ON u.club_guuid = h.club_guuid
WHERE u.union_id = ?
  AND h.opt_type = '额度联盟注资'
ORDER BY h.id DESC
LIMIT ? OFFSET ?;
```

注意：

- `remark` 的 `→` 后半段是变动后余额（授信=目标俱乐部 `union_quota`，注资=联盟池余额）；前端显示时 ÷100 换元。
- 总条数另跑一条同 `WHERE` 的 `COUNT(*)`。
- 俱乐部解散只把 `club_guuid_info.club_status` 置 `del`，行和 `club_name` 都保留，历史记录仍可 join；游戏内客户端接口因走内存列表，看不到已解散俱乐部。
- 当前余额：联盟池 `club_union_info.union_quota`，俱乐部额度 `club_guuid_info.union_quota`。

### 10.4 联盟模式 V2：奖励记录（2026-11-13）

`发放_总群主_奖励`（API1，平台→池）与 `发放_盟主_奖励`（API2，池→盟主）都写 `opt_type='额度奖励'`，两类记录分开查：

```sql
-- API2：总群主给盟主的额度奖励（目标侧）
SELECT h.id, h.date, h.user_quota AS quota_fen,
       SUBSTRING_INDEX(h.remark, '→', -1) AS quota_after_fen,
       h.club_guuid AS target_club_guuid, c.club_name AS target_club_name,
       h.user_guuid AS target_guuid, h.user_name AS target_name,
       h.opter_guuid,
       IFNULL((SELECT sm_name FROM tbl_Account WHERE sm_guuid = h.opter_guuid LIMIT 1), h.opter_name) AS opter_name
FROM club_history_info h
LEFT JOIN club_guuid_info c ON c.club_guuid = h.club_guuid
WHERE h.opt_type = '额度奖励' AND h.remark NOT LIKE '联盟池%'
  AND h.club_guuid IN (SELECT club_guuid FROM club_guuid_info WHERE union_id = ?)
ORDER BY h.id DESC LIMIT ? OFFSET ?;

-- API1：平台给联盟池的额度奖励（池侧）
SELECT h.id, h.date, h.user_quota AS quota_fen,
       SUBSTRING_INDEX(h.remark, '→', -1) AS union_quota_after_fen,
       h.opter_guuid, h.opter_name
FROM club_history_info h
JOIN club_union_info u ON u.club_guuid = h.club_guuid
WHERE u.union_id = ? AND h.opt_type = '额度奖励' AND h.remark LIKE '联盟池奖励%'
ORDER BY h.id DESC LIMIT ? OFFSET ?;
```

注意：

- API2 的池侧行（`remark='联盟池前→后'`）不查，避免与目标侧重复；
- API1 池侧行只在“全联盟视角”（总群主 / 平台 boss / `union_manage` 授权联盟账号）展示，盟主视角不返回；
- `额度奖励` 与 `额度联盟授信` / `额度联盟注资` 是三种类型，不要用 `opt_type IN (...)` 混算；
- `积分奖励` 不在联盟额度表里，走 `查询_俱乐部_积分流水`（见 `doc/俱乐部积分与额度方案-客户端接口文档.md` §11.1，或配套 `doc/俱乐部后台发放奖励-后台接口文档.md` §5.2）。

```json
{"room_id":241441,"cmd":"{\"header\":\"强制_解散_事件\",\"room_id\":\"241441\"}","context":"xuan-room-force-dissolve"}
```

解散房间时，新后台建议对外提供专用接口，不要让前端直接拼旧服务命令：

| 新后台接口 | 参数 | 旧服务转发 |
| --- | --- | --- |
| `POST /api/game/room-maintenance/{room_id}/dissolve` | `mode=force` | `room_id={room_id}`，`cmd="强制_解散_事件"` |
| `POST /api/game/room-maintenance/{room_id}/dissolve` | `mode=friendly` | `room_id={room_id}`，`cmd="申请_解散_事件"` |
| `POST /api/game/room-maintenance/dissolve-all` | `mode=force` | `room_id=0`，`cmd="强制_解散_事件"` |
| `POST /api/game/room-maintenance/dissolve-all` | `mode=friendly` | `room_id=0`，`cmd="申请_解散_事件"` |

说明：

- `mode=friendly` 不要向 `异步_执行_房间_命令` 额外传 `is_qiangzhi=0`；这条旧服务链路不会读取该字段。
- 单房间强制解散示例：

```bash

  --data-urlencode 'header=异步_执行_房间_命令' \
  --data-urlencode 'param={"room_id":241441,"cmd":"强制_解散_事件","context":"xuan-room-force-dissolve"}'
```

- 单房间友好解散示例：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_执行_房间_命令' \
  --data-urlencode 'param={"room_id":241441,"cmd":"申请_解散_事件","context":"xuan-room-friendly-dissolve"}'
```

返回语义：

- 当前旧服务 `ret_code = 512` 只能表示 `/hall/command` 已接收并执行到大厅命令入口，不能保证房间已经解散。
- 当前旧服务 `异步_执行_房间_命令` 在部分情况下不会把房间 `reqExec()` 的失败原因透传给后台。
- 新后台不能把 `ret_code = 512` 直接当作“解散成功”。
- 新后台调用解散命令后，应再次调用 `查询_大厅_所有房间` 确认目标房间已经不在活跃列表中，或状态已不再是活跃房间，才能向前端提示“解散成功”。
- 如果复查后房间仍存在，应提示“命令已发送，房间仍在，请稍后刷新或重试”，不要提示成功。

要求：

- 只允许超级管理员使用。
- `room_id = 0` 必须二次确认。
- 必须写审计。

### 13.2.1 奖池牌型赔付比例（`reward_card_bili`）

传销扯旋奖池的 5 档赔付比例，键为大厅配置，值必须是 **5 个整数百分比**，按固定顺序对应牌型：

| 顺序 | 牌型 | 组成 | 默认值 |
| --- | --- | --- | --- |
| 1 | 天皇 | 丁二红 + 天对 | 20 |
| 2 | 地皇 | 丁二红 + 地对 | 10 |
| 3 | 朵皇 | 丁二红 + 人对/和对/中三对/下腰对/四滥 | 10 |
| 4 | 朵朵 | 对子 + 对子 | 2 |
| 5 | 丁二皇 | 丁二红 + 杂牌 | 2 |

```
# 读

# 返回 param_value 形如 "20,10,10,2,2"（只有值，顺序即上表）

# 写
```

约束与注意：

- `param_value` 必须是 **5 个整数**（服务端按 `int` 解析并与配置键逐位 `zip`），个数不符会**静默不修改**；传 `2.5`、空值会解析失败返回失败码。

- 相关口径见 `doc/奖池开奖牌型与比例方案.md`；手动补发中奖命令 `添加_奖池_数据` 的牌型白名单与比例也取同一份配置。

### 13.2.2 代理展示规则：总输赢/总贡献调整（`score_percent` / `contrib_add`）

2026-11-07 起，`设置_代理_展示规则` 改为两个独立参数，分别调整代理整条线/多条线的总输赢和总贡献：

| 参数 | 范围 | 作用 |
| --- | --- | --- |
| `score_percent` | `0~100` 整数 | 总输赢保留百分比，只能调少；`80`=保留 80% |
| `contrib_add` | `0~100000000` 整数，单位分 | 总贡献增加额，只能调多 |

两项按字段独立向上就近继承：自己设置优先；未设置沿直属上级找最近设置该字段的代理；到根都没有时 `score_percent=100`、`contrib_add=0`。

存储：`club_agent_info.score_percent` / `club_agent_info.contrib_add`，按 `club_guuid + user_guuid` 一代理一份；`NULL` 分别视为 100 / 0。`show_percent` 保留给红利、抽水、业绩等其他收益展示，不再用于输赢/贡献，也不再由本命令设置。

```
# 读（指定代理）
GET /hall/command?header=查询_代理_展示规则&param={"club_id":"775447","agent_id":"718968","metric":"contrib","context":"admin-get"}
# 写（指定代理，两个参数至少传一个；-1 清空为未设置）
GET /hall/command?header=设置_代理_展示规则&param={"club_id":"775447","agent_id":"718968","score_percent":80,"contrib_add":200,"operator":"admin999","context":"admin-set"}
```

约束与注意：

- 两个参数都只接受整数；`score_percent` 超过 `0~100`、`contrib_add` 为负或超上限设置失败。
- 只传一个参数时另一个保持不变；`-1` 表示清空该字段为未设置，恢复向上继承。
- 只有 `Hall.boss` / `level>=99` 可调用；仅 `game_mode=club` 可用（大厅模式返回 `0x301`）；设置的目标必须是本俱乐部 `status=used` 的代理，创建者始终允许。
- **只影响展示**；结算、余额、提取、钱包、流水、实体属性均按真实值。
- 设置会更新代理树内存并异步 `UPDATE club_agent_info`；重启后随代理树重新加载。
- 成员列表行：raw 的 `today_score` / `*_contrib_fen` 保持真实；展示用 `*_score_display`（按 `score_percent`）/ `*_contrib_display_fen`（按 `contrib_add`，所有行）；行级 `score_percent` / `contrib_add` 是继承后的生效值。
- `查询_代理_展示规则` 返回自己的 `score_percent` / `contrib_add` 和继承后的 `effective_score_percent` / `effective_contrib_add`；`agent_income_show_percent` / `effective_show_percent` 仅保留给其他收益展示。
- “设置规则”弹窗回显自己的两个值；成员列表“规则”列用 `effective_*` 或行级字段。只有代理（含创建者）可设置，普通玩家只能继承。
- 详细字段与错误码见 `doc/俱乐部成员与代理展示-后台接口文档.md`；完整口径见 `doc/代理收益客户端展示折扣方案.md`。

### 14.3 奖池业绩结算报表（每日线下分配用）

用途：运营每天结束后，列出**全部已开通业绩比例（`sm_client_prop='True'`）的代理**当日业绩与应返款，用于线下人工分配。

旧服务 HTTP：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_查询_奖池业绩_结算报表' \
  --data-urlencode 'param={"date":"2026-09-21","context":"admin-20260922-0002"}'
```

参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `date` | string | 否 | 统计日 `YYYY-MM-DD`（**绝对日期**）；**缺省 = 昨天**（每天结束后结算昨日） |
| `context` | string | 否 | 操作号 |

返回示例：

```json
{
  "ret_code": 512,
  "ret_result": "{\"JackpotSettlementReport\":{\"date\":\"2026-09-21\",\"all_performance\":4000,\"pool_performance\":2000,\"rebate_total\":300,\"platform_keep\":1700,\"check_ok\":true,\"count\":2,\"list\":[{\"guuid\":\"182605\",\"name\":\"第二\",\"agent_id\":\"648425\",\"my_performance\":400,\"granted_performance\":100,\"proxy_performance\":300,\"rebate\":150,\"granted_list\":[[\"590326\",\"8LL\",100]]}]}}"
}
```

字段说明（金额单位一律**分**，展示前 `/100` 换算为元）：

| 字段 | 说明 |
| --- | --- |
| `date` | 实际统计日 |
| `all_performance` | 当日全平台奖池提留总额 × 2（与客户端业绩接口同口径，用于算占比） |
| `pool_performance` | 当日提留总额 T = `all_performance / 2` |
| `rebate_total` | Σ应返款 = Σ `list[].rebate` |
| `platform_keep` | 平台保留 = `pool_performance − rebate_total` |
| `check_ok` | `true` 表示 Σ净业绩 ≤ T（即返款总额 ≤ T/2）；`false` 时**先人工复核再打款** |
| `count` | 已开通业绩的代理数 |
| `list[]` | 按净业绩倒序；每项含 `guuid`、`name`（昵称）、`agent_id`（一级上级）、`my_performance`（我/毛）、`granted_performance`（下发）、`proxy_performance`（剩/净）、`rebate`（应返款 = 净/2）、`granted_list`（下发给谁：`[guuid, 昵称, 业绩]`，可为空数组） |

使用要求（重要）：

- **占比展示**：某代理业绩比例 = `proxy_performance / all_performance`（与客户端界面同一口径）；
- **返款核算（易错，务必注意）**：`应返款(元) = 比例 × 当日提留总额 T`，其中 **T = `pool_performance` ÷ 100（元）= `all_performance` ÷ 2 ÷ 100**；**不要用 `all_performance` 相乘**——它是 `T × 2`（比例分母），乘它得到的是"净业绩"本身，金额会**翻倍**（应直接用 `rebate / 100`，元）；
- **取数时点（结算依据）**：结算以"当日对局结束后的**某一次固定导出**"为准；比例依赖取数时刻的 `client_prop` 名单，导出后名单变动不影响本次结算金额（建议把该次导出写入下方"返款登记"表）；报表的链判定依赖服务端内存中已加载的代理，极端情况下个别代理的"下发"会少算 → 用服务端方案 §6.3 的对账 SQL（第 5 条）**复核后再打款**；
- **返款登记（后台自建）**：建议建表记录 `date、guuid、name、my_performance、granted_performance、proxy_performance、rebate、操作人、时间、状态（待付/已付/异常）`，用于防重复返款与对账导出；
- **开通/关闭业绩**：见 §4.4（写 `client_prop`）。

优化操作日志：

> ⚠️ **`usr_opt_info` 列序特殊（2026-09-23 实测修正）**：该表的 `user_name` 列存的是**账号 guuid**、`user_guuid` 列存的是**属性名**（如 `optimize01_chance`）。只有后台属性接口这一路是这么写的（`Account.py:1944/1955/1968/1979/1992`），客户端自助设置那一路（`Account.py:3644-3645`、`3658`）相反。
> 因此**原来的 `WHERE user_guuid = ?` 永远查不到记录**（会误判成"没有审计"）；按账号查请用下面这条（`OR` 兼容两种写入者的列语义）。详见 `doc/发牌优化功能说明与排查指南（主力房）.md` §5.4。

```sql
SELECT
  id,
  date,
  time,
  user_name  AS guuid,   -- 实际存的是账号 guuid
  user_guuid AS prop,    -- 实际存的是属性名（optimize01_man / count / chance）
  option_type,
  remark1,
  remark2,
  remark3
FROM usr_opt_info
WHERE user_name = ? OR user_guuid = ?
ORDER BY id DESC
LIMIT 100;
```

### 15.2 设置优化

当前不建议新后台直接开放优化设置。原因是现有黑盒 HTTP 没有独立的“设置发牌优化”管理接口，只能通过通用属性接口修改多个字段，容易出现部分成功、权限/白名单限制、审计不完整的问题。

## 17. 后台自有管理表

新后台必须自建管理员、角色、审计表。建议与游戏业务表分库或至少表名前缀隔离。

### 17.1 管理员表

```sql
CREATE TABLE admin_user (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  username VARCHAR(64) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  display_name VARCHAR(64) NOT NULL DEFAULT '',
  status VARCHAR(20) NOT NULL DEFAULT 'enabled',
  last_login_at DATETIME NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL
);
```

### 17.2 角色表

```sql
CREATE TABLE admin_role (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  code VARCHAR(64) NOT NULL UNIQUE,
  name VARCHAR(64) NOT NULL,
  created_at DATETIME NOT NULL
);
```

### 17.3 管理员角色关系

```sql
CREATE TABLE admin_user_role (
  user_id BIGINT UNSIGNED NOT NULL,
  role_id BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (user_id, role_id)
);
```

### 17.4 审计表

```sql
CREATE TABLE admin_audit_log (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  operator_id BIGINT UNSIGNED NOT NULL,
  action VARCHAR(128) NOT NULL,
  target_type VARCHAR(64) NOT NULL,
  target_id VARCHAR(64) NOT NULL,
  request_json JSON NULL,
  before_json JSON NULL,
  after_json JSON NULL,
  result_code INT NOT NULL,
  result_message VARCHAR(512) NOT NULL DEFAULT '',
  ip VARCHAR(64) NOT NULL DEFAULT '',
  created_at DATETIME NOT NULL,
  INDEX idx_action_time (action, created_at),
  INDEX idx_target (target_type, target_id)
);
```

建议角色：

| 角色 | 权限 |
| --- | --- |
| `super_admin` | 全部权限 |
| `finance_admin` | 财务查询、充值、补分、退款、红包 |
| `ops_admin` | 玩家查询、公告、修复登录、俱乐部常规管理 |
| `agent_admin` | 代理查询、代理绑定 |
| `viewer` | 只读查询 |

## 18. 管理操作审计要求

以下操作必须写审计：

| 操作 | 审计目标 |
| --- | --- |
| 充值/补分/退款/红包 | 玩家 ID、金额、工单号、操作前后余额 |
| 修改玩家密码 | 玩家 ID、操作者、原因，不记录明文密码 |
| 修改玩家属性 | 玩家 ID、字段名、旧值、新值 |
| 绑定代理 | 玩家 ID、旧上级、新上级 |
| 俱乐部增删成员 | 俱乐部 ID、玩家 ID |
| 俱乐部积分修改 | 俱乐部 ID、玩家 ID、旧积分、新积分 |
| 配置修改 | 配置组、配置键、旧值、新值 |
| 房间命令 | 房间 ID、命令内容 |
| 优化设置 | 玩家 ID、次数、概率、设置人 |
