# 俱乐部联盟模式 V2：新旧差异与客户端改造清单

更新时间：2026-11-03  
适用项目：Cocos Creator 2.4.13 客户端  
范围：俱乐部、联盟、额度、上下分、买入结算、红利、相关按钮和界面

> 本文是对当前 `服务器文档整理` 目录及当前客户端代码的整理结果。本文只做方案和改造清单，**本次没有修改业务代码、Prefab、协议实现或服务器**。

## 一、结论和口径

当前目录中的文档存在新旧内容并存的情况。后续实现时，以《俱乐部俱乐部联盟模式V2方案-客户端接口文档.md》顶部声明的 V2 协议为联盟、额度和红利的唯一现行口径；其他文档中仍然描述 `Union`、双向联盟、代理独立额度、旧代理收益的章节，只能作为历史参考。

V2 的核心变化是：

```text
平台老板
  └─ 联盟总群主（联盟创建者）
       └─ 俱乐部（俱乐部创建者，俱乐部层面的“盟主”）
            └─ 代理（只保留比例和红利，不再拥有独立额度）
                 └─ 玩家
```

额度不再跟随某个代理，而是在“联盟总群主 ↔ 俱乐部”之间流转：

- 联盟总群主持有联盟额度池。
- 俱乐部有自己的 `union_quota`，单位是分；买入时从俱乐部额度扣除。
- 代理没有独立额度，只保留代理比例和产生的 `bonus`。
- 抽水不返还额度，进入代理红利；红利可以提取为俱乐部积分。
- 俱乐部不在联盟中，或俱乐部额度不足时，玩家买入失败。

V2 文档声明相关服务端已部署测试服；本次未向服务器发起真实请求，因此下面的“已核对”指文档和客户端静态核对，不等于测试服、编辑器、构建、真机或双账号验收已经完成。

## 二、新模式与当前模式的差异

| 项目 | 当前客户端/旧文档模式 | V2 模式 | 客户端影响 |
|---|---|---|---|
| 联盟结构 | 旧 `Union`/`union_guuid_info`，以俱乐部间双向链接为核心 | `club_union_info`：一个总群主管理多个俱乐部 | 联盟页面、数据模型、接口全部需要切换；旧双向链接页面停用 |
| 加入联盟 | 旧添加、删除联盟成员和双向链接命令 | 俱乐部创建者输入 6 位联盟码申请，总群主单独同意或拒绝 | 新增申请页、审批页和状态显示 |
| 联盟身份 | 旧文档把某些 `is_leader=1` 的直推代理称为“盟主” | 联盟总群主是联盟创建者；俱乐部创建者才是俱乐部层面的“盟主” | 不能再用直推代理的 `is_leader` 显示“盟主” |
| 额度归属 | `club_agent_info` 的代理额度，旧客户端查询和授信以代理为中心 | `club_guuid_info.union_quota` 的俱乐部额度；总群主从联盟池给俱乐部授信或收回 | 删除成员弹窗中的开通、增加、减少额度；新增联盟额度界面 |
| 额度单位 | 旧流程有代理额度、俱乐部额度和客户端换算混用 | 协议使用 `quota_fen`，界面输入通常是元，客户端提交前乘 100 | 所有额度输入、显示、错误文案统一换算并标明单位 |
| 代理关系 | 代理可有自己的额度并负责给下级上分 | 代理只保留比例、层级和红利；代理上分不扣代理自己的积分 | 上下分按钮不能再按“代理额度余额”做客户端拦截 |
| 买入 | 旧逻辑按最近授信代理额度判断或扣除 | 从当前俱乐部 `union_quota` 扣除；没有联盟或额度不足就失败 | 买入提示、额度刷新和联调断言需要调整 |
| 结算 | 旧方案按代理额度返还 | 结算回当前俱乐部额度池；管理员额外买入部分按服务端规则不返还 | 结算页面要按俱乐部额度解释，不再展示代理额度返还 |
| 抽水 | 旧文档有返额度或代理收益的混合描述 | 抽水进入代理 `bonus`，不返还额度 | 新增红利余额、明细、提取流程 |
| 红利接口 | `查询_俱乐部_代理_收益`、`提取_玩家_红利` 等旧接口 | `查询_俱乐部_红利`、`查询_俱乐部_红利_明细`、`提取_俱乐部_红利` | 现有“管理收益/我的红利”页面需要换协议和字段 |
| 玩家赠送 | 旧实现按同一授信代理限制 | 同俱乐部成员之间即可赠送，不再要求同一授信代理 | 删除旧代理归属限制；保留同俱乐部和服务端权限校验 |
| 创建俱乐部收费 | 当前客户端创建成功后另发一次 `玩家_消费_命令` | V2 由 `创建_俱乐部` 在服务端按 `d_halls.create_club_stone` 原子扣费，失败退款 | 客户端只做余额预检查和提示，不能继续二次扣费 |
| 平台注资 | 客户端文档中曾出现俱乐部额度增加入口 | `增加_联盟_额度` 只给平台老板/后台使用 | 客户端不得新增此按钮或调用入口 |
| 房间归属 | 当前房间和大厅均有 `club_id`，部分页面仍读取旧额度 | V2 买入权威由当前俱乐部额度决定 | 保留房间 `club_id` 语义，避免用大厅选中俱乐部替代房间俱乐部 |

### V2 现行命令

联盟与额度：

| 功能 | 命令 | 权限和结果 |
|---|---|---|
| 创建联盟 | `创建_联盟` | 俱乐部创建者；返回 6 位 `union_id` |
| 查询我的联盟 | `查询_我的_联盟` | 联盟总群主；返回联盟信息、额度池、成员俱乐部及各自额度 |
| 申请加入 | `申请_加入_联盟` | 俱乐部创建者；参数为 `club_id`、6 位 `union_id` |
| 查询加入申请 | `查询_联盟_加入申请` | 联盟总群主；返回待审批俱乐部 |
| 同意/拒绝 | `同意_加入_联盟`、`拒绝_加入_联盟` | 联盟总群主；参数为 `club_id` |
| 授信/收回 | `授信_联盟_额度` | 联盟总群主；正数授信、负数收回，提交单位为分 |
| 查询额度 | `查询_联盟_额度` | 联盟总群主查联盟池，俱乐部创建者查本俱乐部额度；通过 `is_owner` 区分 |
| 查询红利 | `查询_俱乐部_红利` | 查询余额，结果包括 `bonus_fen` 和展示值 `bonus` |
| 红利明细 | `查询_俱乐部_红利_明细` | 分页返回日期、来源、层级、房间和红利 |
| 提取红利 | `提取_俱乐部_红利` | 输入整数元；从红利转入 `club_gold` |

下列旧命令不能再作为 V2 客户端入口：

- `查询_俱乐部_额度`
- `授信_俱乐部_额度`
- `增加_俱乐部_额度`
- `添加_联盟_成员`
- `删除_联盟_成员`
- `删除_联盟_加入申请`
- `查询_俱乐部_联盟`
- `查询_俱乐部_代理_收益`
- 以 `提取_玩家_红利` 作为俱乐部代理红利提取的实现

## 三、现有文档需要怎样调整

### 1. 《俱乐部与联盟功能-客户端接口文档.md》

顶部已经标明旧联盟系统下线，但正文仍保留完整的旧双向联盟章节。需要把以下内容改成“历史接口/已停用”，并在章节开头直接跳转 V2：

- `Union`、`union_guuid_info`、`club_union/new_union` 的数据结构。
- `club_source_id`、`club_target_id` 双向链接。
- `UnionNumberList`、`UnionJoinerList`、`UnionReqInfo`。
- 旧的添加成员、删除成员、删除申请、查询俱乐部联盟流程。
- 旧附录中“联盟相互独立、双方互加”的说明。

俱乐部基础功能仍可保留，但需要补充两条覆盖关系：

- 俱乐部创建收费由 V2 的 `创建_俱乐部` 原子处理，客户端不能另发消费命令。
- 旧的俱乐部额度、买入和结算说明由 V2 联盟额度规则覆盖。

### 2. 《俱乐部代理与邀请码-客户端接口文档.md》

邀请码、代理层级、代理比例、`roomSetting.club_id`、直属成员列表、备注和私聊入口仍有参考价值；但以下内容已经过时：

- 代理拥有独立额度。
- 通过代理额度给下级上分。
- 旧的代理收益查询和提取命令。
- 把某个 `is_leader=1` 直推代理称为联盟“盟主”。

文档应明确：代理比例仍存在，但比例产生的是 `club_agent_info.bonus`；代理额度相关字段不能再作为客户端授权、按钮显示或买入判断依据。

### 3. 《俱乐部盟主-客户端接口文档.md》

当前正文把“盟主”定义为俱乐部创建者的直推代理，这与 V2 冲突。需要重写角色说明：

- 联盟总群主：创建联盟的俱乐部创建者，负责联盟成员审批和联盟池授信。
- 俱乐部盟主：创建俱乐部的账号，负责本俱乐部成员管理。
- 代理：代理层级和比例角色，不显示为联盟盟主。

原 `is_leader` 字段如服务端仍返回，可以继续兼容解析，但不能驱动联盟角色、额度权限或页面标题。

### 4. 《俱乐部积分与额度方案-客户端接口文档.md》

前 1～15 节是 V1 代理额度方案，必须标注历史；第 16 节 V2 方案作为当前接口入口。尤其要把客户端旧清单中的以下按钮和请求标为删除：

- `玩家设置开通额度`
- `玩家设置增加额度`
- `玩家设置减少额度`
- `查询_俱乐部_额度`
- `授信_俱乐部_额度`

建议在文档尾部加上“额度只存在联盟总群主与俱乐部之间”的单独结论，防止后续只读到旧章节。

### 5. 《俱乐部积分与额度方案-客户端改造实施方案.md》

这份文档是旧 V1 客户端改造计划，不能直接作为实施计划。需要保留其中的文件定位和验证方法，但重排实施阶段：

1. 先切换协议和数据模型。
2. 再新增联盟页及审批、授信界面。
3. 再改买入、上下分、赠送、红利和创建收费。
4. 最后做角色矩阵、断线恢复、跨俱乐部和真实房间验收。

### 6. 《俱乐部金币与钻石-客户端接口文档.md》

俱乐部金币仍是玩家在俱乐部内使用的积分，但旧文档中“按最近代理额度校验兑换”的部分不能直接沿用。V2 文档没有完整重述俱乐部金币兑换的 `money_type` 校验和额度扣减规则，实施前必须让服务端补充确认：

- `gold,<club_id>` 是否继续有效。
- 兑换是只影响玩家 `club_gold`，还是需要校验俱乐部 `union_quota`。
- 普通俱乐部、联盟俱乐部、联盟总群主三种身份的兑换权限。

### 7. 《俱乐部实时结算-客户端接口文档.md》

实时结算两个查询接口可以保留，属于房间内辅助页面；但页面中涉及“额度返还、代理收益、买入来源”的文案必须按 V2 解释。实时结算接口本身没有替代联盟额度查询的作用。

### 8. 《1对1私聊消息-详细设计实施方案-v5.md》及代理推送文档

私聊关系、代理开通/取消推送和成员刷新流程可以继续使用。需要调整的是角色显示和权限文案：

- 俱乐部创建者显示为俱乐部盟主/群主，具体使用哪个称呼需要产品统一。
- 直推代理不再显示为联盟盟主。
- 聊天入口不能以旧 `is_leader` 判断联盟管理权限。

## 五、需要新增或调整的按钮和界面

### A. 俱乐部主页/当前俱乐部卡片

需要增加一个“联盟管理”入口，点击后根据身份和状态进入不同内容：

| 身份/状态 | 应显示的入口 |
|---|---|
| 俱乐部创建者，尚未创建或加入联盟 | `创建联盟`、`加入联盟` |
| 联盟总群主 | `我的联盟`、`联盟申请`、`联盟俱乐部额度` |
| 已加入联盟的其他俱乐部创建者 | `联盟信息`、`本俱乐部额度` |
| 代理 | `我的红利`；不显示联盟授信或成员额度按钮 |
| 普通玩家 | 不显示联盟管理入口 |

创建者已经有联盟时，不再显示重复创建；已经提交申请时，加入按钮显示申请中并禁用重复提交。V2 没有定义退出联盟、解散联盟、转让总群主和撤销申请命令，暂时不要在客户端增加这些按钮。

### B. 新增“联盟管理”页面

建议新增 `panelClubUnion`，页面按状态分区，不要把所有按钮堆在成员管理弹窗内。

#### 1. 创建联盟弹窗

- 联盟名称输入。
- 创建按钮。
- 创建结果展示 6 位联盟码。
- 创建失败、重复创建、没有俱乐部创建者权限的提示。
- 创建成功后刷新联盟状态。

对应 `创建_联盟`，只允许俱乐部创建者调用。

#### 2. 加入联盟弹窗

- 6 位联盟码输入。
- 申请按钮。
- 已有联盟、已经申请、联盟码无效、自申请等错误提示。
- 申请中状态和刷新按钮。

对应 `申请_加入_联盟`，绑定关系必须以总群主同意后的服务端返回为准。

#### 3. 总群主联盟主页

- 联盟名称、6 位联盟码。
- 联盟额度池，协议分转元显示。
- 成员俱乐部列表：俱乐部名称、创建者、俱乐部额度。
- `联盟申请`入口和待审批数量。
- 每个俱乐部的 `授信额度`、`收回额度`。
- 刷新、错误和权限状态。

对应 `查询_我的_联盟`、`查询_联盟_加入申请`、`同意_加入_联盟`、`拒绝_加入_联盟`、`授信_联盟_额度`。

#### 4. 俱乐部创建者联盟信息页

- 联盟名称和联盟码（如果服务端返回）。
- 本俱乐部额度。
- 联盟状态和待处理状态。
- 只读成员/总群主信息，除非接口明确返回完整列表。

对应 `查询_联盟_额度`，通过 `is_owner=0` 表示查询的是本俱乐部额度。不能把这个页面误做成总群主额度池页面。

### C. 成员管理和玩家设置

成员管理保留成员、代理、比例、备注、踢出和私聊能力，但需要以下调整：

- 移除 `玩家设置开通额度`、`玩家设置增加额度`、`玩家设置减少额度`。
- 成员列表不要显示个人额度、代理额度或“已授信额度”。
- “上下分”保留为业务操作按钮，但权限由服务端和当前俱乐部关系决定，不能用代理个人额度余额隐藏按钮。
- “赠送金币”统一改成“赠送积分”，并说明同俱乐部成员可操作，最终以服务端权限为准。
- `is_leader` 不再控制“盟主”称号、联盟管理入口或联盟额度权限。
- 需要区分“俱乐部创建者”“联盟总群主”“代理”，避免统一显示成“盟主”。

### D. 红利页面

可以复用 `panelMyHongli` 的视觉框架，但需要改成独立的 V2 数据层：

- 余额：`查询_俱乐部_红利`。
- 明细：`查询_俱乐部_红利_明细`，支持分页和来源层级显示。
- 提取：`提取_俱乐部_红利`，只允许输入整数元，少于 1 元的余额保留在红利中。
- 提取成功后刷新红利和俱乐部积分，不再调用旧 `提取_玩家_红利`。
- 代理只能看自己的红利明细；有管理权限的角色按服务端返回范围显示。

### E. 房间买入、结算和实时结算

- 玩家积分仍然可以显示 `club_gold`，它是玩家在俱乐部内的筹码余额。
- 俱乐部额度显示应该来自 `查询_联盟_额度`，不能从某个成员的额度字段拼装。
- 买入失败至少区分：俱乐部未加入联盟、俱乐部额度不足、玩家积分不足、房间状态错误。
- “请联系代理上分”应改成更准确的提示，例如“该俱乐部额度不足，请联系联盟总群主”；最终以服务端错误码/文案为准。
- 结算列表、已结算玩家列表继续使用实时结算接口，但文案要说明俱乐部额度池的扣除/返还。
- 联盟是否影响房间发现、房间可见范围，V2 文档没有完整定义，必须在服务端联调时单独验收。

## 六、跑通整个流程所需的完整链路

### 阶段 0：服务端和测试账号准备

准备至少以下账号和数据：

- 平台老板/后台账号：只用于注入联盟额度，不作为客户端按钮。
- 联盟总群主：俱乐部创建者，负责创建联盟。
- 第二个俱乐部创建者：申请加入联盟。
- 代理：验证代理比例、上下分和红利。
- 普通玩家：验证买入、赠送、积分和结算。

服务端先确认 V2 命令已经注册，旧额度命令返回“命令不存在”或不再产生旧数据；同时准备 `d_halls.create_club_stone` 和联盟额度池。

### 阶段 1：创建俱乐部

1. 客户端读取创建俱乐部所需钻石并做预检查。
2. 客户端只发送一次 `创建_俱乐部`。
3. 服务端按 `d_halls.create_club_stone` 原子扣费。
4. 创建失败时确认没有扣费；创建成功时确认只扣一次。
5. 客户端刷新俱乐部列表和俱乐部创建者身份。

这是当前代码的高风险点：现有流程在创建成功后还会发送一次 `玩家_消费_命令`，V2 切换时必须去掉二次扣费路径。

### 阶段 2：创建联盟和加入联盟

1. 俱乐部创建者进入 `创建联盟`，输入名称并提交。
2. 服务端返回 6 位 `union_id`，客户端展示并支持复制。
3. 第二个俱乐部创建者输入联盟码，提交 `申请_加入_联盟`。
4. 总群主进入 `联盟申请`，查询待审批列表。
5. 分别测试 `同意_加入_联盟` 和 `拒绝_加入_联盟`。
6. 同意后确认第二个俱乐部的 `union_id` 已绑定；拒绝后确认仍可重新申请。
7. 验证重复申请、无效联盟码、自申请和非俱乐部创建者申请的错误。

### 阶段 3：联盟额度

1. 平台老板/后台为联盟总群主准备联盟额度池；客户端不提供“增加联盟额度”入口。
2. 总群主查询联盟信息和额度池。
3. 总群主给自己的俱乐部授信，确认联盟池减少、俱乐部额度增加。
4. 总群主给第二个俱乐部授信，确认目标俱乐部额度变化。
5. 用负数收回额度，分别验证足额和余额不足。
6. 验证 0、负数收回过多、非本联盟俱乐部、非总群主操作均被拒绝。
7. 第二个俱乐部创建者用 `查询_联盟_额度` 查询自己的俱乐部额度，确认不能看到或修改联盟总池。

### 阶段 4：代理和玩家

1. 按现有代理/邀请码流程建立代理树和代理比例。
2. 验证代理没有独立额度字段和额度按钮。
3. 验证代理上分时不扣代理自己的俱乐部积分；普通非代理上下分仍按服务端规则记录积分变化。
4. 验证同俱乐部玩家之间可以赠送积分，不要求双方属于同一个授信代理。
5. 验证跨俱乐部赠送仍被拒绝。

### 阶段 5：房间买入和结算

1. 使用单层 JSON 的 `roomSetting`，确认 `club_id` 是实际房间俱乐部。
2. 俱乐部加入联盟且额度足够时进入房间并买入。
3. 验证买入扣俱乐部额度、玩家积分和服务端流水。
4. 俱乐部额度不足时验证买入失败，玩家积分不被扣除。
5. 俱乐部未加入联盟时验证买入失败，错误不能伪装成代理额度不足。
6. 结算后验证额度回到同一俱乐部额度池。
7. 验证管理员额外买入部分按服务端规则处理，不被客户端错误返还。
8. 验证抽水进入代理红利，不回到联盟额度池。
9. 重新进入房间、断线重连、切换俱乐部、返回大厅后再次查询，确认上下文和额度没有串俱乐部。

### 阶段 6：红利、兑换和实时数据

1. 代理查询红利余额。
2. 查询红利明细，验证分页、来源、层级和房间号。
3. 输入整数元提取红利，确认 `club_gold` 增加、红利减少。
4. 提取小于 1 元的余额，确认余数保留。
5. 确认俱乐部金币/钻石兑换的 V2 校验后再测试 `gold,<club_id>`。
6. 打开实时结算，验证当前未结算和已结算列表与房间状态一致。

## 八、当前不应直接实现的内容

以下功能在 V2 文档中没有完整服务端契约，不能只根据旧客户端补按钮：

- 退出联盟、解散联盟、转让联盟总群主。
- 撤销待处理的加入申请。
- 联盟申请的独立推送和红点命令。
- 非总群主俱乐部创建者是否能看到完整联盟成员列表。
- 俱乐部金币兑换是否需要校验联盟额度。
- 联盟是否改变房间列表、房间发现或跨俱乐部邀请范围。
- “俱乐部盟主”“群主”“联盟总群主”的最终产品文案。

这些项目需要服务端补充命令、权限、推送或产品确认后再进入 Prefab 和代码实施。

## 九、建议实施顺序

1. 先完成接口模型和旧接口清理：V2 命令、推送、错误码、`union_quota`、`bonus`。

6. 改造红利页面和提取流程。
