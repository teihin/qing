## 1. 通用协议（所有接口共用）

### 1.1 命令通道

客户端登录后持有自己的 Account 实体（base 端），俱乐部/联盟全部走**大厅命令通道**：

| 方向 | 方法 | 说明 |
| --- | --- | --- |
| 客户端→服务器 | `reqHallCommand(param, context)` | 发出命令 |
| 服务器→客户端 | `onHallCommand(ret_code, result)` | 同步响应 |

- `param`：**JSON 字符串**，必须包含 `"header"` 字段（值为命令名），其余字段为命令参数。
- `context`：字符串，新版本格式为 `"p@<任意上下文串>"`，@ 后内容原样回传，用于请求-响应配对。部分接口也允许在 `param` 里再传一个 `context` 字段，服务端会把它带进异步推送的报文里（见 1.3）。

```json
{"header": "查询_俱乐部_信息", "club_id": "123456"}
```

### 1.2 同步响应格式

`onHallCommand` 的 `result` 是 JSON 字符串，外层固定包裹：

```json
{
  "context": "<请求时@后的context原样回传>",
  "result": { /* 各接口自己的返回体 */ }
}
```

异常路径（命令名错误、param 非法 JSON、服务端内部异常）：只回 `{"context":"<ctx>"}`、**没有 `result` 键**且 `ret_code = 0x301`。客户端先判空再解析。

### 1.3 返回码与异步推送

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `GC_OK` | `0x200`(512) | 成功（同步响应里已带全部数据，或数据随后推送） |
| `GC_FAILED` | `0x301`(769) | 失败，`result` 内一般有 `{"error": "原因"}` |
| `GC_UNKOWN` | `0x500`(1280) | 服务端**内部标记**"本次不同步返回"，**该码不会下发给客户端**；查询结果经 `client.onMessage(路由, JSON)` 异步推送，部分命令另有一次 `onHallCommand` 最终回调（`0x200` 成功 / `0x301` 失败） |

**异步推送通道**：成员列表、申请列表、积分、战绩等列表类接口，数据通过客户端通用消息回调 `onMessage(router, msg)` 送达，`router` 为路由名（字符串），`msg` 为 JSON 字符串。客户端需按路由名分发到对应界面。涉及路由名本文档逐接口标注。

### 1.4 编码约定

| 字段 | 约定 |
| --- | --- |
| `club_prop` / `club_desc` | **base64 存储**。客户端设置时传 base64(utf8(原文))；展示时 base64 解码 |
| `is_urlcode` | 仅 `创建_俱乐部` 使用。传 `'1'` 表示 `club_prop`/`club_desc` 按 base64(urlencode(utf8(原文))) 传输，服务端统一转成上面的 base64 约定 |
| `club_name` | 创建时服务端做 `strip` 并去除引号；返回时为明文 |
| 分页参数 | 列表接口统一 `count`（每页条数，默认 10）、`page`（页码，从 0 开始）；返回里 `number`=当前页码、`count`=总条数 |
| `user_id` | 成员查询传 `'ALL'` 或具体玩家 guuid |
| 玩家身份 | guuid 为 6 位字符串 ID，比较时用字符串 |

### 1.5 玩家实体上的俱乐部身份属性（客户端可直接读）

以下 Account 属性为 `BASE_AND_CLIENT`，登录后客户端可直接读取，无需调命令：

| 属性 | 类型 | 含义 |
| --- | --- | --- |
| `club_make` | string | 我创建的俱乐部 ID 串（逗号分隔，普通模式） |
| `club_join` | string | 我加入的俱乐部 ID 串（逗号分隔，普通模式） |
| `club_manage` | string | 我担任管理员的俱乐部 ID 串 |
| `club_gold` | string(JSON) | 各俱乐部我的积分，如 `{"123456": 100}` |
| `club_make2` / `club_join2` / `club_gold2` | 同上 | 茶楼/带分模式（`club_mode` 2/3）的对应属性 |

身份判定：**盟主** = 俱乐部 `club_owner` 等于自己 guuid（或自己 `club_make` 含该 ID）；**管理员** = `club_manage` 含该 ID；**成员** = `club_join` 含该 ID。多数管理操作要求盟主或管理员，文档逐接口标注。

### 1.6 概念：俱乐部模式与新旧联盟

- `club_mode`：`1`=普通模式（当前线上使用）；`2`=茶楼模式；`3`=带分俱乐部。2/3 模式数据走 `*_2` 后缀属性。
- **联盟有两套方案（路由撞名不能混用；2026-09-28 已定为方案 A）**：
  - **方案 A · 旧联盟（俱乐部双向链接）＝当前方案**：无独立实体，就是俱乐部之间的**双向链接**（俱乐部 `all_union` 列表），接口名不带「新」字，**完整接口见本文档 §3**；
  - **方案 B · 新联盟（独立实体）**：独立联盟实体（有联盟 ID、名称、盟主、成员俱乐部列表），接口名带「新联盟」；**已在服务端整块注销冻结，仅存档参考（§4），客户端不要对接**；其"一个俱乐部最多属于一个新联盟"的约束在冻结状态下不适用。
  - 选型过程、切换执行记录与解冻方式见 `doc/俱乐部功能增强移植方案.md` §10。

## 2. 俱乐部接口

### 2.1 创建俱乐部 ★（待实施：`club_desc`、`is_urlcode` 参数，当前传了会被忽略）

- **命令名**：`创建_俱乐部`
- **权限**：任何登录玩家；同名俱乐部不允许；每人最多创建 10 个

请求参数：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | `创建_俱乐部` |
| `club_name` | string | 是 | 俱乐部名称（全服唯一） |
| `club_mode` | string | 否 | 默认 `'1'`（普通模式） |
| `club_prop` | string | 否 | 俱乐部属性（客户端自定义，如头像），base64 |
| `club_desc` ★ | string | 否 | 俱乐部简介，base64；不传或空串则简介为空；**长度上限 250 字符（base64 串，原文约 62 个汉字）**，超长服务端返回错误 |
| `is_urlcode` ★ | string | 否 | `'1'` 时 `club_prop`/`club_desc` 按 base64(urlencode(utf8)) 解码入库 |

请求示例：

```json
{"header": "创建_俱乐部", "club_name": "快乐扯旋", "club_mode": "1", "club_prop": "", "club_desc": "5aLq5a+857q/56eR5oqV6LWE5paH5Y+w", "is_urlcode": "0"}
```

响应（`ret_code = 0x200`）：

```json
{"context": "ctx1", "result": {"result": "创建成功"}}
```

失败：`0x301` + `{"error": "房间名字重复，不允许创建！"}` / `{"error": "创建房间超过10个，不允许创建！"}` / `{"error": "俱乐部简介过长，请精简后再提交！"}`（★ 简介长度校验随移植方案部署后生效）。

> 注意：同步响应只表示创建请求已受理。俱乐部 ID 为服务端随机分配的 6 位数字，创建完成后客户端通过 `查询_玩家_俱乐部_信息`★ 或监听自身 `club_make` 属性变化获取。

### 2.2 删除俱乐部

- **命令名**：`删除_俱乐部`
- **权限**：盟主（或 boss 账号）；茶楼模式且有成员时不允许删除

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `club_id` | string | 是 | 俱乐部 ID |

响应：`0x200` 空 error 即成功；失败 `{"error": "只有俱乐部管理员允许删除！"}` 等。

### 2.3 查询俱乐部信息 ★（待实施：`club_desc` 返回字段，当前无此字段）

- **命令名**：`查询_俱乐部_信息`
- **权限**：任何登录玩家

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `club_id` | string | 是 | 俱乐部 ID |

响应（`0x200`）：

```json
{
  "context": "ctx2",
  "result": {
    "club_id": "123456",
    "club_name": "快乐扯旋",
    "club_notify": "",
    "club_owner": "100001",
    "owner_name": "盟主昵称",
    "club_setting": "",
    "number_count": 35,
    "room_count": 4,
    "club_pay_mode": "老板",
    "proxy_stone": 100,
    "club_prop": "",
    "club_tax": "0",
    "club_level": "1",
    "club_gold": "0",
    "max_number": "100",
    "club_stone_status": "充足",
    "club_desc": "5aLq5a+857q/56eR5oqV6LWE5paH5Y+w"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `club_owner` / `owner_name` | 盟主 guuid / 昵称 |
| `number_count` / `max_number` | 当前人数 / 人数上限（按俱乐部等级 100~1500） |
| `room_count` | 当前活跃房间数 |
| `proxy_stone` / `club_stone_status` | 盟主房卡（石头）余额；`充足`(≥20) / `紧缺`(1~19) / `没有`(0) |
| `club_tax` | 抽水比例 |
| `club_desc` ★ | 俱乐部简介（base64），★ 待实施：当前版本**无此字段**，客户端按缺省空串处理 |

失败：`0x301`，返回体为空模板（俱乐部不存在）。

### 2.4 查询玩家已加入俱乐部列表 ★（待实施：新接口，当前调用返回"命令不存在"）

- **命令名**：`查询_玩家_俱乐部_信息`
- **权限**：任何登录玩家（查的是自己）
- **用途**：「我的俱乐部」列表页一次取全，替代逐个 `查询_俱乐部_信息`

请求参数：仅 `header`。

```json
{"header": "查询_玩家_俱乐部_信息"}
```

响应（`0x200`）：

```json
{
  "context": "ctx3",
  "result": {
    "ListPlayerClubBaseInfo": [
      ["123456", "快乐扯旋", "100001", 35, 100, 4, "", "5aLq5a+8..."],
      ["234567", "夜战联盟", "100002", 80, 200, 12, "", ""]
    ]
  }
}
```

数组每项 8 个元素，顺序固定：

| 下标 | 含义 | 类型 |
| --- | --- | --- |
| 0 | 俱乐部 ID | string |
| 1 | 俱乐部名称 | string |
| 2 | 盟主 guuid | string |
| 3 | 当前人数 | int |
| 4 | 人数上限 | int |
| 5 | 活跃房间数 | int |
| 6 | `club_prop`（base64） | string |
| 7 | `club_desc`（base64） | string |

未加入任何俱乐部时返回空数组 `[]`。数据源为玩家 `club_join`（普通模式）。

### 2.5 查询所有俱乐部（搜索/发现页）

- **命令名**：`查询_所有俱乐部_信息`
- **权限**：任何登录玩家

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `club_name` | string | 否 | 名称（用于创建前占用检查提示，可空） |
| `club_mode` | string | 否 | 默认 `'1'` |
| `count` / `page` | int | 否 | 分页，默认 10 / 0 |
| `join_club_id` | string | 否 | 我已加入的俱乐部 ID 串（逗号分隔），传入后已加入的排在最前 |
| `vip_name_id` | string | 否 | 指定 VIP 俱乐部 ID 串（逗号分隔），只返回这些 |
| `search_name_id` | string | 否 | 模糊搜索：俱乐部 ID 精确 或 名称包含 |

响应（`0x200`）：

```json
{"context": "ctx4", "result": {"all_club_id": ["123456", "234567"], "number": 0, "count": 2}}
```

返回的是按人数降序的俱乐部 ID 数组（当前页切片），客户端再对每个 ID 调 `查询_俱乐部_信息` 取详情。

### 2.6 查询推荐俱乐部

- **命令名**：`查询_推荐_俱乐部`；**权限**：任何登录玩家
- 参数：仅 `header`（内部要求俱乐部总数 > 10000 才返回，否则 `0x301`）
- 响应：字段同 `查询_俱乐部_信息`（无 `club_desc`）

### 2.7 加入 / 退出俱乐部

**申请加入**：`申请_加入_俱乐部`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `club_id` | string | 是 | 目标俱乐部 |
| `init_club_gold` | int | 否 | 初始俱乐部积分（默认 -1 不设置，项目定制参数） |
| `remark` | string | 否 | 申请留言 |
| `context` | string | 否 | 透传上下文 |

响应：普通俱乐部 `0x200`（申请已登记，等管理员审批）；官方俱乐部（`bigclub` 配置）直接入 club 不等审批，**无即时响应**（服务端内部用 `0x500` 标记，该码不下发），结果经 `onHallCommand` 送达（`0x200` 成功 / `0x301` 失败）。失败 `{"error": "俱乐部号不存在！"}`。

**申请退出**：`申请_退出_俱乐部`，参数 `club_id`；`0x200` 登记退出申请。

> **2026-10-25 起该流程暂时关闭**：命令仍注册（不会报"命令不存在"），但服务端直接返回 `0x301` + `{"error": "退出俱乐部功能暂时关闭，如需退出请联系俱乐部盟主"}`，且不登记申请、不产生红点。客户端建议按钮置灰或提示该文案；恢复时服务端把 `d_halls` 的 `club_exit_apply_on` 改成 `True` 即可，客户端无需改动。

> 加入/退出均为**申请-审批制**：玩家申请后进申请列表，由盟主/管理员执行 `添加_俱乐部_玩家`（同意）或 `删除_俱乐部_加入申请`（拒绝）。成员身份变化最终体现在 `club_join` 属性和成员列表推送上。

### 2.8 申请列表（盟主/管理员）

**查询加入申请**：`查询_俱乐部_加入申请`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `club_id` | string | 否 | 俱乐部 ID；**传空** = 查询自己管理的所有俱乐部的申请汇总 |
| `count` / `page` | int | 否 | 分页 |
| `mode` | int | 否 | `0`=待审批新申请（默认），`1`=历史记录 |

响应：`0x200`，数据经 onMessage 推送；`club_id` 为空时同时刷新各俱乐部申请计数推送（路由 `ClubReqInfo`，含 `req_count`/`number_count`）。

> **2026-10-26 `ClubReqInfo` 收件人口径（最终）**：申请到达/处理后的广播**只发给"该申请所用邀请码的归属代理"**，
> `req_count` = 他自己码带来的待审数（对应 `查询_俱乐部_代理_申请`）。
> **创建者、管理员、其他成员一律收不到这条推送**（原先创建者会拿到全量，客户端表现为老板也有红点）。
> 若申请所用邀请码归属于创建者本人（创建者即根代理、持有自己的码），则他**作为码归属者**正常收到，且只拿自己码的条数。
>
> 清红点：**服务端不会补发 `0`**。代理处理完自己最后一条申请后不再在分组结果里，不会再收到该俱乐部的 `ClubReqInfo`，
> 请客户端在"同意/拒绝"成功后**自行清零**该俱乐部红点（重新打开列表或重连也会自然归零）。
>
> 例外：`ClubReqInfo` 还用于"玩家加入/退出俱乐部后的定向刷新"（服务端 `target_id=该玩家`），该场景仅推给这一个玩家，
> 数值仍按角色给数（创建者/管理员=全量，在职代理=自己码的数，其他=`"0"`），行为未变。
> `ClubAgentReqInfo` 仍只在代理查询列表时作为回包，不会主动推送。

**查询退出申请**：`查询_俱乐部_退出申请`，参数 `club_id` + 分页；推送路由 `ExiterList`。

### 2.9 成员管理（盟主/管理员）

| 命令名 | 用途 | 关键参数 | 权限 | 返回 |
| --- | --- | --- | --- | --- |
| `添加_俱乐部_玩家` | 同意加入 / 直接拉人 | `club_id`, `user_id`, `init_gold`(否), `init_club_gold`(否), `context` | 盟主或管理员 | **无即时响应**（内部 0x500 不下发）；最终 `0x200` 成功 / `0x301` 失败 |
| `删除_俱乐部_玩家` | 踢出成员 | `club_id`, `user_id` | 盟主或管理员或本人 | `0x200` |
| `删除_俱乐部_加入申请` | 拒绝加入申请 | `club_id`, `user_id`, `context` | 盟主、管理员，**或该申请所用邀请码归属的代理**（2026-10-25 扩展；见代理文档 §4.8.1） | 无权限时异步回 `0x301`；有权限 `0x200` |
| `删除_俱乐部_退出申请` | 驳回退出申请 | `club_id`, `user_id` | 仅盟主 | `0x200` |

### 2.10 查询俱乐部成员

- **命令名**：`查询_俱乐部_成员`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `club_id` | string | 是 | 俱乐部 ID |
| `user_id` | string | 否 | `'ALL'`（默认）或指定玩家（指定玩家为单成员详情，不走直属口径） |
| `agent_id` | string | 否 | **2026-10-26 新增**：指定下钻的下级代理 ID；缺省/空 = 调用者自己（见下方直属口径说明） |
| `count` / `page` | int | 否 | 分页 |
| `search_name_id` | string | 否 | 模糊查成员（ID 或昵称；**同样只在直属范围内搜索**） |
| `context` | string | 否 | 透传 |

响应：**无即时响应**（内部 0x500 不下发）；成员数据经 onMessage 推送，路由 **`NumberList`**（含分页 `number`/`count`、成员数组与 `context`），随后回 `0x200`（带 `context`）。

> **2026-10-26 成员列表改为"代理直属口径"**：`user_id='ALL'`（含模糊搜索）不再返回俱乐部全量成员，只返回
> **被查节点自己 + 其直属成员（直属下级代理 + 直属普通玩家）**，并按 **创建者 → 代理 → 普通玩家** 排序
> （同角色内仍按 游戏中 > 在线 > 离线）。规则：
> ① 调用者即"当前代理"（创建者=根代理同样适用）；不传 `agent_id` / 传空 / 传自己 ID → 返回自己的直属列表（首行为自己）；
> ② `agent_id` 传自己**子树内**的下级代理 ID（任意层级）→ 返回该代理的直属列表（首行为该代理）；
> ③ `agent_id` 传子树外的 ID（树外/非本俱乐部/已取消代理）→ 推送**空列表**（`count=0`），不报错；
> ④ **普通玩家（非代理）调用 → 空列表**（无成员数据可返回）；
> ⑤ 推送的 `count` 字段 = 本次过滤后的直属人数（不再是全量成员数；俱乐部总人数仍以 `ClubReqInfo`/`RefreshClubInfo` 的 `number_count` 为准）。
> 直属判定以代理关系表为准（`upper=被查节点` 且关系有效）；功能上线前加入、无代理关系的历史成员兜底挂在**创建者**直属。

> **2026-10-23 新增成员字段 `is_agent`**：该成员在本俱乐部**是否是代理**（`"1"`=是，`"0"`=否；本路由字段均为字符串；判定口径=持有本俱乐部可用邀请码）。
> 仅在**俱乐部模式**（`game_mode='club'`）下有意义；大厅模式下恒为 `"0"`。代理信息接口里的同名字段是数字（见下条文档）。
> 字段说明见 `doc/俱乐部代理与邀请码-客户端接口文档.md` §2.1。

> **2026-10-25 新增成员字段 `percent`**（本路由为字符串）：该成员在本俱乐部的**本层截留比例**（0~100），
> 口径与 `ClubAgentInfo.percent` 完全一致——从"当前剩余"中截留，多层链**逐层扣减**，不是占总额比例、也不是级差。
> **字段恒定存在**：非代理 / 已取消代理（关系被置 `disabled`）/ 大厅模式 / 代理树未加载时一律 `"0"`，客户端不需要判空。
> 与 `is_agent` 的关系：`is_agent` 判定"是否持有本俱乐部可用邀请码"，`percent` 取内存在职关系；正常情况下两者一致
> （`percent="0"` 也可能是"是代理但比例为 0"，**"是不是代理"仍以 `is_agent` 为准**）。

> **2026-10-24 新增成员统计字段（7 个，均为字符串）**：`NumberList` 每行在原有字段（`number`/`count`/`guuid`/`name`/`gold`/`club_gold`/`role`/`is_agent`/`percent`/`status`）之外，新增下表字段。
> **字段恒定存在**：不计算时（大厅模式 / 模糊搜索 / 代理树未加载 / 聚合失败）值为 `"0"`，客户端**不需要判空**。

| 字段 | 类型 | 单位 | 说明 |
| --- | --- | --- | --- |
| `team_count` | string | 人数 | 该成员**整条下线**人数（递归所有下级，**不含自己**） |
| `today_score` | string | **积分**（可负） | 该成员 + 整条下线的今日输赢（只统计本俱乐部入口的局） |
| `yesterday_score` | string | 积分（可负） | 同上，昨日 |
| `total_score` | string | 积分（可负） | 同上，累计 |
| `today_contrib_fen` | string | **分** | 该成员 + 整条下线今日在本俱乐部创造的抽水（展示时 **÷100**） |
| `yesterday_contrib_fen` | string | 分 | 同上，昨日 |
| `total_contrib_fen` | string | 分 | 同上，累计 |

**使用注意**：

1. **`*_score` 与 `club_gold` 不是同一个数**：`club_gold` 是**俱乐部积分余额**（当前值），`*_score` 是**某时间段的净输赢**（变动），两者同量纲但不要互相校验；
2. **单位不同**：`*_score` 是积分，`*_contrib_fen` 是**分**（客户端展示需 ÷100，否则差 100 倍）；
3. **只有俱乐部模式有值**：`game_mode != 'club'` 时 7 个字段恒为 `"0"`（字段不省略）；
4. **搜索/茶楼·铜钱宝列表不计算**：这些入口字段同样返回、值恒为 `"0"`；
5. **老客户端无需改动**：纯增量字段，忽略未知字段的解析器可直接继续用；若启用严格模式（`ignoreUnknownKeys=false` / `MissingMemberHandling.Error`），需放开；
6. **查单个成员时也是团队口径**：`user_id` 传具体玩家时，返回的 `team_count` / `*_score` / `*_contrib_fen` 仍是"该成员 + 整条下线"的数据，不是他一个人的；
7. 统计口径（整条线、按入口俱乐部、按结算日、退会即移出团队等）见 `doc/俱乐部成员列表统计字段方案.md` §2/§10。

### 2.12 俱乐部房间（系统自动创建）

> **2026-10-21 起：俱乐部房间由服务端按平台同款配置自动创建（每个俱乐部一套）；成员只进房、不能自己开房；俱乐部房免房卡、走大厅配分。**

**查询_俱乐部_房间_信息**：参数 `club_id`(必)、`count`/`page`、`is_have_site`(`'1'` 只看有空位)、`fillter_01`(special 过滤)、`is_zip_result`(`'1'` 压缩返回)；返回 `0x200`，房间数据经 onMessage 推送，路由 **`AllRoomInfo`**（`{"number":页码, "count":总数, "result":[房间...]}`）。

> **返回格式（2026-10-21）**：`is_zip_result='1'` 时 `result` 为**与大厅「查询_所有_自创_房间」完全同构的 9 元数组**，每项：
> `[房号, 状态(参与过/准备/游戏中), 备注("45分钟"), 在座+持座旁观人数, 人数上限, 底皮, 时长规则, 房间名, 是否地九王(0/1)]`；
> `is_zip_result` 缺省/`'0'` 时保持原有完整字段字典（旧客户端兼容）。

> 权限：返回**该俱乐部 + 其联盟俱乐部**的房间（不做成员限制，`level >= 99` 同样放行）。

> **2026-10-25 起不分页**：`count`/`page` 仅为兼容保留，服务端**一次返回该俱乐部 + 联盟俱乐部的全部房间**；客户端请固定传 `page=0`、只请求一次，**不要按 `count` 翻页**（翻页会重复拿到同一份全量列表）。响应里的 `count` 是真实总数，`number` 原样回显请求页码。兜底上限为服务端硬编码常量 `Club.CLUB_ROOM_LIST_MAX = 300`（不做配置，调整需发版）：极端联盟导致可见房间超限时按建房时间截断并打 `ERROR` 日志，`count` 仍是真实总数，客户端按"总数为准、列表可能少几条"处理即可。
>
> 房间名（9 元数组第 8 位）来自服务端下发的 `game.special_rule` 中 `房间名称:<档位>-<房号>` 这一条（例 `1-448003`）；"小皮/中皮/大皮"这类文字服务端不下发，由客户端按底皮档位自行映射。

**查询_所有_俱乐部_房间**：参数 `count`/`page`、`is_have_site`、`fillter_01`；推送路由 **`AllClubRoomInfo`**。这是「俱乐部大厅房间列表」的入口。

> **可见范围（2026-10-21 修正）**：返回**我加入的俱乐部 + 这些俱乐部的联盟俱乐部**的房间；联盟房**不再需要** `'联盟分享'` 标记。联盟的其它联动见 §3.8 说明。

**服务端行为（2026-10-21 俱乐部房间混合模式）**：

| 项 | 行为 |
| --- | --- |
| 房间来源 | 成员查询上述列表时，服务端按**平台自动房同一套配置**为"本俱乐部 + 联盟俱乐部"补齐缺失房间（档位/时长/数量沿用 `d_halls` 的 `create_room_count`、`enable_create_room`、`room_rule_1_time`；线上当前为 5 档 × 1 小时档，每俱乐部共 7 间） |
| 房间命名 | `<selfname><底皮档位>-<roomID>`，与大厅自动房**完全同一套拼法**（`selfname` 取 `d_halls` 的 `room.selfname`，线上为空 → 实际就是 `1-851724`、`2-851725` 这种）；**2026-10-25 起不再带俱乐部名前缀**。归属靠 `roomClubID`/`club_id` 字段判断，客户端不要解析名字 |
| 可见范围 | **本俱乐部成员 + 联盟内俱乐部成员**可见（联盟房默认共享，不需要「联盟分享」标记）；其它玩家在大厅/俱乐部列表里看不到 |
| 进入限制 | 非本俱乐部、非联盟成员进房返回 `GC_ROOM_NO_CLUB_NUMBER`；`level >= 99`（老板/运营）放行 |
| 开房权限 | **成员不能自己开俱乐部房**：请求带 `club_id` 且需服务端新建房时返回 `GC_FAILED`（开关 `club_member_create_room=False`）。成员直接用列表返回的 `room_id` 进房 |
| 房卡 | **免房卡**：不扣任何账号金币，也不产生「开房支付/退款」流水；因此俱乐部房**不计入**「当天有效开房数」 |
| 配分 | **大厅配分模式**（平台金币账），不涉及俱乐部分（`club_gold`/`club_gold2`） |
| 回收与补齐 | 房间无人约 2 小时后服务端回收；成员再次查询列表时自动补齐（客户端无需处理） |
| 大厅列表 | 俱乐部房**不会**出现在大厅「查询_所有_自创_房间」列表里 |

> 客户端注意：**不要为俱乐部房间开放「创建房间」入口**；进房直接使用列表返回的 `room_id`。

> **进房参数（2026-10-23 新增，必须）**：客户端请求进入**已有房间**时，必须在 `roomSetting` 里带 `club_id`（玩家从哪个俱乐部的房间列表点的这间房），例：
> `{"special_rule": "观战", "club_id": "414954"}`。
> 服务端用它决定该玩家抽水归属的代理链（入口俱乐部）；`club_id` 缺失、不属于玩家、或房间对该俱乐部不可见时，**不阻断进房**，但该玩家不参与俱乐部分成（该份抽水留平台）。
>
> **2026-10-25 补充：`roomSetting` 必须是标准 JSON（单层花括号），服务端不做兼容。** 线上实测有版本下发 `{{"special_rule": "观战", "club_id": "710701"}}`（多包一层），`json.loads` 失败 → `club_id` 取不到 → 该玩家本局抽水全留平台、成员统计也不计他。详见 `doc/俱乐部代理与邀请码-客户端接口文档.md` §4.9。

## 3. 联盟接口（当前方案：俱乐部双向链接／旧方案）

> **本节为本次选型的正式方案（2026-09-28 决定），客户端按本节对接。** 服务端代码线上已完整具备（`club_biaozhun.py` + `Hall.py`），**无需部署新文件、无需数据库迁移**即可启用。
>
> **调用约定（最关键）**：`club_source_id` 的含义是"**本次操作的发起方（我）**"，`club_target_id` 是"对方"；服务端权限校验的是 `club_source_id` 这个俱乐部的盟主。因此**谁操作就把自己的俱乐部填进 `club_source_id`**：申请结盟时我=申请方；同意/拒绝/解除时我=收申请方。填反会返回"只有俱乐部管理员允许操作！"。
>
> **数据模型**：盟友关系是俱乐部的**双向链接**——`Club.all_union` ↔ DB `club_guuid_info.club_union`（逗号分隔的俱乐部 ID 串，VARCHAR 800）；结盟申请存在 `club_banzhen_info`（`opt_type='申请联盟加入'`，`user_guuid`=申请方俱乐部 ID、`club_guuid`=收申请方俱乐部 ID）。关系**点对点**，无联盟名/盟主/等级概念。
>
> **三条推送路由**：`UnionNumberList`（盟友列表）、`UnionJoinerList`（结盟申请列表）、`UnionReqInfo`（申请红点）。**与 §4 方案 B 的路由同名但字段不同，客户端只能对接一套（只对接本节）。**

### 3.1 查询_俱乐部_联盟（盟友列表）

| 项 | 内容 |
| --- | --- |
| 参数 | `club_id`（要查询的俱乐部 ID）；`count`（每页条数，默认 10）；`page`（页码，从 0 开始）；`context`（原样回传） |
| 权限 | 无（任何玩家可查询任一存在的俱乐部） |
| 同步响应 | `0x200` + `{}`（数据走异步推送）；`club_id` 不存在时同样返回 `0x200`，但不会有推送 |
| 推送路由 | `UnionNumberList` |

推送报文（`context` 原样带回）：

```json
{"UnionNumberList": [
    {"number": "0", "count": "2", "club_guuid": "100001", "club_name": "某某俱乐部"}
 ], "context": "客户端自定义"}
```

- `number` = 当前页页码；`count` = 盟友**总数**（据此算总页数）；每个元素一个盟友俱乐部。
- 分页：`offset = count * page`；超出范围时列表为空。

### 3.2 申请_加入_联盟（发起结盟申请）

| 项 | 内容 |
| --- | --- |
| 参数 | `club_source_id`（我，申请方）；`club_target_id`（对方，收申请方）；`context`（客户端可传，服务端当前忽略） |
| 权限 | **必须是我（`club_source_id`）的盟主**（boss 账号放行）；否则 `0x301` + `{"error": "只有俱乐部盟主允许申请！"}` |
| 成功 | `0x200` + `{}`；写入对方俱乐部的申请记录（`club_banzhen_info`）；对方盟主收到 `UnionReqInfo` 红点 |
| 失败 | 任一方俱乐部 ID 不存在：`0x301` + `{"error": "俱乐部号不存在！"}` |
| 备注 | 重复申请会覆盖旧记录（不产生多条）；申请成功 ≠ 已结盟，需对方同意才建立双向链接；服务端不校验"是否已有盟友"，可同时与多个俱乐部互发申请 |

### 3.3 查询_联盟_加入申请（我收到的结盟申请）

| 项 | 内容 |
| --- | --- |
| 参数 | `club_id`（我的俱乐部 ID）；`count`（每页条数，默认 10）；`page`（页码，从 0 开始） |
| 权限 | **数据只推送给 `club_id` 的盟主**；非盟主调用不报错，但收到空列表（不泄露申请方信息） |
| 同步响应 | `0x200` + `{}`（数据走推送）；`club_id` 不存在时同样 `0x200`，无推送 |
| 推送路由 | `UnionJoinerList` |

推送报文：

```json
{"UnionJoinerList": [
    {"number": "0", "count": "1", "club_guuid": "100002", "club_name": "申请方俱乐部", "date": "2026-09-28 12:00:00", "remark": ""}
 ]}
```

- `club_guuid`/`club_name` = **申请方**俱乐部；`count` = 申请总数；`number` = 当前页页码；`remark` 当前恒为空（旧方案接口不写留言）。
- 注意：本路由字段与 §4 方案 B 的 `UnionJoinerList` 不同（没有 `gold`/`room_id`/`union_guuid`）。

### 3.4 添加_联盟_成员（同意结盟）

| 项 | 内容 |
| --- | --- |
| 参数 | `club_source_id`（我，收申请方）；`club_target_id`（对方，申请方）；`context`（可不传） |
| 权限 | **必须是我（`club_source_id`）的盟主**；否则 `0x301` + `{"error": "只有俱乐部管理员允许操作！"}` |
| 成功 | `0x200` + `{"error": ""}`；双方 `club_union` 互写并落库；对方对我的申请记录被清除；双方盟主各收一次 `UnionReqInfo` 刷新 |
| 失败 | 俱乐部 ID 不存在：`0x301` + `{"error": "添加失败"}`；写入失败：`0x301` + `{"error": "添加联盟失败"}` |
| 备注 | 对已结盟的对方重复同意不会报错（幂等）；同意后**双方互见**（各自盟友列表各多一个）。注意：服务端**不校验对方是否已提交申请**（盟主可直接把对方加为盟友，双向生效），也**不校验** `club_source_id ≠ club_target_id`——客户端只在申请列表页调用、并避免自己加自己即可 |

### 3.5 删除_联盟_加入申请（拒绝结盟）

| 项 | 内容 |
| --- | --- |
| 参数 | `club_source_id`（我，收申请方）；`club_target_id`（对方，申请方） |
| 权限 | 必须是我（`club_source_id`）的盟主；否则 `0x301` + `{"error": "只有俱乐部管理员允许操作！"}` |
| 成功 | `0x200` + `{}`；申请记录被删除，红点计数刷新（`UnionReqInfo`） |
| 备注 | 只删申请，不影响已有盟友关系 |

### 3.6 删除_联盟_成员（解除结盟）

| 项 | 内容 |
| --- | --- |
| 参数 | `club_source_id`（我）；`club_target_id`（对方） |
| 权限 | 必须是我（`club_source_id`）的盟主；否则 `0x301` + `{"error": "只有俱乐部管理员允许操作！"}` |
| 成功 | `0x200` + `{}`；**双向移除**并落库（双方盟友列表各少一个） |
| 备注 | 不存在"半结盟"（服务端两边同时删）；对方的盟友视图同步消失；俱乐部 ID 不存在时也返回 `0x200`（无操作） |

### 3.7 `UnionReqInfo`（结盟申请红点，服务端主动推送）

提交申请、同意、拒绝后，服务端会向**收申请俱乐部的盟主**推送：

```json
{"club_id": 100001, "club_name": "我的俱乐部", "req_count": 3, "number_count": 25, "source": "AddUnionJoinerList"}
```

- `club_id`/`club_name`：**收到结盟申请的俱乐部**（即盟主自己的俱乐部）；`req_count`：待处理结盟申请数（红点数字）；`number_count`：该俱乐部**成员玩家数**；`source`：触发来源（`AddUnionJoinerList`=新申请，`""`=同意/拒绝后的刷新）。
- 该路由**只有盟主会收到**（非盟主不推）。
- 注意：本路由的 `club_id` 是"我的俱乐部"，与 §4 方案 B 的 `UnionReqInfo`（联盟维度 `union_id`/`union_name`）字段含义完全不同。

### 3.8 盟友房间与已知边界

- 盟友房间（2026-10-21 修正）：**默认可见、可进**——`查询_所有_俱乐部_房间` 返回"我加入的俱乐部 + 其联盟俱乐部"的房间；`查询_俱乐部_房间_信息` 返回"该俱乐部 + 其联盟俱乐部"的房间；进房校验放行联盟成员。**不再需要** `'联盟分享'` 标记；
- **盟友关系影响**：盟友列表（`UnionNumberList`）、结盟申请（`UnionJoinerList`/`UnionReqInfo` 红点）、房间可见性与进房、房间数统计口径（`GetRoomCount` 把盟友房计入数量）；**不影响结算/收益**（俱乐部房走大厅配分）；
- 已知边界（需同步给产品/客服）：
  - 联盟**没有名字、没有盟主、没有等级**，客户端只能展示"结盟俱乐部：A、B、C…"；
  - 关系是**点对点**：A 与 B、A 与 C 分别结盟后，**B 与 C 互不可见**（各自只看到 A）；要做成"一个联盟"的观感必须逐对互链（n 个成员需 n(n-1)/2 对操作）；
  - 盟友数量受 DB 列长度限制（`club_union` VARCHAR 800，约百余个 ID）。

### 3.9 联调验证清单（建议按序执行）

| # | 步骤 | 预期 |
| --- | --- | --- |

| 8 | 重启 baseapp 后复查第 5 步 | 盟友关系仍在（验证 `club_union` 落库生效，2026-09-28 已修复落库 SQL） |

## 4. 附录：方案 B（独立联盟实体）——已冻结，客户端不要对接

> **本方案已冻结（2026-09-28）**：本项目联盟采用旧方案（§3 俱乐部双向链接），下面 13 条"新联盟"命令已在 `Hall._init_hall_command` 中**整块注销**——客户端调用会走大厅"命令不存在"异常路径（`ret_code=0x301`、响应体只有 `{"context":...}` 无 `result`）。`scripts/server_common/union_biaozhun.py` 保留在仓库但**不部署、不调用**；如需改用本方案（含解冻步骤），见 `doc/俱乐部功能增强移植方案.md` §10.6。
> 以下内容保留作存档参考，**不要对接**。

关系模型：联盟是独立实体；**成员是俱乐部**（不是玩家）。一个俱乐部最多加入一个联盟；俱乐部 `new_union` 字段记录所属联盟 ID。联盟盟主 = 创建联盟的俱乐部的盟主。

### 4.1 创建联盟

- **命令名**：`创建_新联盟`
- **权限**：俱乐部盟主；该俱乐部尚未加入任何联盟；联盟名全服唯一

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `club_id` | string | 是 | 以哪个俱乐部身份创建（该俱乐部成为联盟第 1 个成员） |
| `union_name` | string | 是 | 联盟名称 |
| `union_mode` | string | 否 | 默认 `'1'` |
| `union_prop` | string | 否 | 联盟属性（base64，客户端自定义） |

响应：`0x200`，`result` 为 `{"result": "创建成功"}`；失败 `{"error": "只有俱乐部盟主允许创建联盟！"}`（调用者不是该俱乐部盟主）/ `{"error": "联盟名字重复，不允许创建！"}` / `{"error": "创建联盟超过1个，不允许创建！"}`。

> 注意：同步响应只表示创建请求已受理，**响应里不返回联盟 ID**（与创建俱乐部一致）。客户端创建完成后用 `查询_新联盟_信息`（传 `club_id`，或读自身俱乐部 `new_union` 变化）获取联盟 ID 与信息。

### 4.2 删除联盟

- **命令名**：`删除_新联盟`；**权限**：联盟盟主（或 boss）
- 参数：`union_id`；响应 `0x200`，无权限 `{"error": "只有联盟管理员允许删除！"}`

### 4.3 查询联盟信息

- **命令名**：`查询_新联盟_信息`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `union_id` | string | 否 | 联盟 ID；与 `club_id` 二选一 |
| `club_id` | string | 否 | 传俱乐部 ID 时查它所属的联盟 |

响应（`0x200`）：

```json
{
  "context": "ctx5",
  "result": {
    "union_id": "654321",
    "union_name": "夜战大联盟",
    "union_notify": "",
    "union_owner": "123456",
    "owner_name": "快乐扯旋",
    "union_setting": "",
    "number_count": 3,
    "union_pay_mode": "老板",
    "proxy_stone": 100,
    "union_prop": "",
    "union_tax": "0",
    "union_level": "1",
    "union_gold": "0",
    "max_number": "100"
  }
}
```

`union_owner`/`owner_name` 为联盟第 1 个成员俱乐部的 ID 与名称；`number_count` 为成员俱乐部数。失败 `0x301` `{"error": "俱乐部联盟不存在！"}`。

> 注意：`union_owner`/`owner_name` 是**展示字段**（取成员列表第 1 个俱乐部）；服务端权限判定用的是**创建联盟的账号**（`proxy`）。正常情况两者一致；若创建者俱乐部先退盟，展示值会变成新的第 1 个成员，但管理权限仍在原创建账号手里——**客户端不要用 `union_owner` 做权限判断**。
>
> `max_number` 为按联盟等级计算的成员俱乐部数上限（等级 0~11 对应 5~15），服务端**不强制拦截**超限加入；客户端可在成员数达到上限时给出提示，由联盟盟主自行控制。

### 4.4 查询联盟成员（成员俱乐部列表）

- **命令名**：`查询_新联盟_成员`
- 参数：`union_id`(必)、`user_id`（默认 `'ALL'`）、`count`/`page`、`context`；其中 `user_id`、`count`/`page` **当前实现未使用**（一次返回全部成员俱乐部，联盟成员上限小，无需分页）
- 响应：命令会同步回一个 `0x200` 的 `{"context": ...}` 空壳响应（**没有 `result` 字段**，不代表业务结果，只表示请求已处理）；**成员数据经 onMessage 异步推送**，路由 **`UnionNumberList`**：

```json
{
  "NumberList": [
    {"guuid": "123456", "name": "快乐扯旋", "proxy_guuid": "100001", "number_count": "35"},
    {"guuid": "234567", "name": "夜战联盟", "proxy_guuid": "100002", "number_count": "80"}
  ],
  "context": "<请求透传的context>"
}
```

数组元素为**成员俱乐部**（`guuid`/`name` 为俱乐部，`proxy_guuid` 为该俱乐部盟主），不是玩家。

### 4.5 加入 / 退出联盟

**申请加入**：`申请_加入_新联盟`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `union_id` | string | 是 | 目标联盟 |
| `club_id` | string | 是 | 以哪个俱乐部加入（须未加入任何联盟） |
| `remark` | string | 否 | 申请留言 |
| `context` | string | 否 | 透传 |

响应：`0x200` 已登记；失败 `{"error": "只有俱乐部盟主允许申请！"}`（调用者不是该俱乐部盟主）/ `{"error": "只能加入一个联盟！"}` / `{"error": "俱乐部号不存在！"}` / `{"error": "联盟号不存在！"}`。

**申请退出**：`申请_退出_新联盟`，参数 `union_id`（服务端自动从调用者创建的俱乐部里解析出属于该联盟的那个俱乐部登记，客户端不用传 `club_id`）；`0x200` 已登记；失败 `{"error": "你的俱乐部不在该联盟！"}` / `{"error": "联盟号不存在！"}`。

> 加入/退出申请均为"俱乐部级"申请，只有**俱乐部盟主**能发起；审批方是该联盟盟主。

### 4.6 联盟审批（盟主）

| 命令名 | 用途 | 参数 | 权限 | 返回 |
| --- | --- | --- | --- | --- |
| `查询_新联盟_加入申请` | 待审批列表 | `union_id`（**可空**：空 = 查自己创建的唯一联盟）、`count`, `page` | 盟主 | `0x200`；列表经路由 **`UnionJoinerList`** 推送（分页 `number`/`count`，行含俱乐部 `guuid`/`name`/`gold`/`date`/`room_id`/`remark`/`union_guuid`/`union_name`） |
| `查询_新联盟_退出申请` | 退出申请列表 | `union_id`, `count`, `page` | 盟主 | `0x200`；列表经路由 **`UnionExiterList`** 推送（字段同上，无 union 字段） |
| `添加_新联盟_成员` | 同意加入 | `union_id`, `club_id`, `context` | 仅盟主 | `0x200`；失败 `{"error": "新增联盟成员失败"}` |
| `删除_新联盟_成员` | 移除成员俱乐部 | `union_id`, `club_id` | 盟主 | `0x200` |
| `删除_新联盟_加入申请` | 拒绝加入 | `union_id`, `club_id` | 仅盟主 | `0x200` |
| `删除_新联盟_退出申请` | 驳回退出 | `union_id`, `club_id` | 仅盟主 | `0x200` |

加入是**双向绑定**：联盟实体与俱乐部实体互相登记，成功后俱乐部 `new_union` 有值。

> 同意加入时，服务端会拒绝**已属于其他联盟**的俱乐部（返回 `{"error": "新增联盟成员失败"}`）；客户端应提示盟主让该俱乐部先退出原联盟。成员数 `number_count` 会随加入/移除同步（推送红点里的成员数即实际成员俱乐部数）。

> 权限说明：`查询_新联盟_加入申请` / `查询_新联盟_退出申请` 的列表数据**只推送给联盟盟主**（服务端校验 `proxy`）；非盟主调用会得到空列表（不会报错，也不泄露申请内容）。

申请计数还会主动推送给联盟盟主（用于红点/角标），客户端按路由处理即可：

| 路由 | 触发时机 | 字段 |
| --- | --- | --- |
| `UnionReqInfo` | 有新的加入申请登记 / 同意或拒绝后刷新 | `union_id`、`union_name`、`req_count`（待审批加入申请数）、`number_count`（成员数）、`source` |
| `UnionReqInfo2` | 有新的退出申请登记 / 驳回后刷新 | `union_id`、`union_name`、`exit_req_count`（待审批退出申请数）、`number_count`、`source` |

### 4.7 修改联盟信息

- **命令名**：`修改_新联盟_信息`；**权限**：仅联盟盟主
- 参数：`union_id`(必)、`union_name`、`union_notify`、`union_setting`、`union_pay_mode`、`union_tax`、`union_prop`、`union_level`（可选，传什么改什么）
- 响应：`0x200`；无权限 `{"error": "只有联盟管理员允许操作！"}`

> 注意：`union_tax`（抽水）与 `union_gold`（资产）目前**没有业务逻辑**（不会产生联盟抽水或联盟资产变动），客户端界面**不要设计联盟分红/联盟资产**相关功能；`union_level` 只影响后续查询返回的 `max_number` 值（服务端不强制拦截超限加入）。

4. 积分修改类接口在目标玩家处于房间内会被拒绝（`玩家在房间内，不能修改俱乐部积分！`），客户端应在玩家离房后再操作或提示。

## 6. 典型接入流程建议

1. **我的俱乐部**：登录后读 `club_make`/`club_join`/`club_manage` → 逐个 `查询_俱乐部_信息` 渲染列表（★ `查询_玩家_俱乐部_信息` 待实施后可用它一次到位）。
2. **发现/搜索俱乐部**：`查询_所有俱乐部_信息`（带 `search_name_id` 或 `join_club_id` 置顶已加入）→ 对选中 ID 调 `查询_俱乐部_信息` 看详情（房间数、盟主房卡状态；`club_desc` 简介为 ★ 待实施项）。
3. **加入俱乐部**：`申请_加入_俱乐部`（可带 `remark` 留言）→ 等待审批；管理员侧 `查询_俱乐部_加入申请` → `添加_俱乐部_玩家`（同意）/ `删除_俱乐部_加入申请`（拒绝）。
4. **俱乐部大厅**：`查询_所有_俱乐部_房间`（我加入的俱乐部 + 联盟房间汇总）→ 进房；进房后 `查询_玩家_加入房间的所属俱乐部_信息` 确定计分俱乐部。
5. **成员/积分管理**（盟主/管理员）：`查询_俱乐部_成员` → `添加/修改_俱乐部_成员_积分`（注意玩家在房限制）→ 流水用 `查询_俱乐部_成员_积分_添加/修改_记录` 对账。
6. **联盟（旧方案/双向链接，本文档 §3）**：俱乐部盟主 `申请_加入_联盟`（source=我、target=对方）发起结盟 → 对方盟主红点 `UnionReqInfo` → `查询_联盟_加入申请` 看申请 → `添加_联盟_成员`（同意，source=我）/ `删除_联盟_加入申请`（拒绝）→ `查询_俱乐部_联盟` 查看盟友、`查询_所有_俱乐部_房间` 看盟友房间；解除用 `删除_联盟_成员`。注意逐对操作、无联盟名、盟友视野只有一跳（边界见 §3.8）。
