# 补芒与带入修复 - 客户端接口文档（讨论稿）

> 状态：2026-11-16 服务端已实施，待客户端联调；字段均为新增，老客户端忽略。
>
> 关联方案：`doc/补芒与带入修复方案.md`
>
> 范围：传销扯旋/俱乐部实时房/大厅房的补芒查询、带入弹窗、坐下校验。只讨论协议字段和客户端行为，不改代码。

| --- | --- | --- | --- |

## 2. `玩家_补芒_查询`

### 2.1 请求

客户端通过现有 `reqGameCommand` 发送：

```json
{"header":"玩家_补芒_查询","context":"弹窗"}
```

`context` 原样带回，客户端可用于区分 `弹窗`、`坐下0`、`坐下2` 等场景。

### 2.2 响应

服务端同步返回 `GC_OK`，并通过 `PromptInfo2` 推送数组：

```json
["需要补芒 100 分", "弹窗", "500", "500", "5000"]
```

不需要补时：

```json
["不补芒", "弹窗", "0", "500", "5000"]
```

前两个元素保持旧格式（老客户端只读前两个即可）；后三个是新增的可选元素：

| 下标 | 含义 |
| --- | --- |
| 0 | 提示文本，X = `need` |
| 1 | `context` 原样带回 |
| 2 | `buy_in_min`：本次最少带入 |
| 3 | `buy_in_step`：该房一簸 |
| 4 | `buy_in_max`：当前可带入上限 |

观战者不接收 `当前_玩家_消息` 时，也能从 `PromptInfo2` 后三个元素拿到弹窗最低值。

### 2.3 语义变化（重要）

现状：

```text
X = 全局累计需要（没有减已付）
```

修复后：

```text
X = max(0, required_total - paid_total)
```

- `required_total` = 历史已发生 + 下一手预留；
- `paid_total` = 该玩家当前房间/周期已付；
- 客户端拿到的 X 是“还差多少”，不是“累计需要”。

示例（数字为概念示例；实际按下一手封顶公式）：

| 场景 | 现状返回 | 修复后返回 |
| --- | --- | --- |
| 累计 600，已付 500 | 600 | **100** |
| 累计 760，已付 0（新玩家） | 760 | **760** |
| 累计 600，已付 600 | 不补芒 | 不补芒 |
| 累计 600，已付 700 | 不补芒 | 不补芒（多出的 100 按产品口径处理） |

### 2.4 金额明细

`PromptInfo2` 前两个元素保持原文案/context，后三个元素附带 `buy_in_min`/`buy_in_step`/`buy_in_max`；完整明细同时通过 `当前_玩家_消息` 的字段下发（见第 3 节）：

- `mang_required`：累计需要；
- `mang_paid`：已付；
- `mang_need`：还差；
- `buy_in_min`：本次最少加多少；
- `buy_in_step`：该房一簸（10 皮=500，其他底皮按各自最小带入）；
- `buy_in_max`：可带入上限；
- `buy_in_default`：默认值。

## 3. `当前_玩家_消息` 字段

现有字段（保持不变，老客户端继续可用）：

| 字段 | 含义 |
| --- | --- |
| `init_money` | 本周期带入总分 |
| `min_bj` | 当前总簸箕下限（现状是 `max(min_boji_score, boji_score)`，10 皮为 1000；本轮先不动，作为兼容字段） |
| `max_bj` | 当前总余额（`money_score + boji_score`） |
| `money_score` | 可用分（可能已减下注） |
| `bj_score` | 簸箕分 |
| `mang_pi_times` / `xiu_mang_times` / `xiu_mang_count` | 现有芒果展示/计数 |

本次建议新增（服务端下发，老客户端忽略未知字段）：

| 字段 | 类型 | 含义 | 示例 |
| --- | --- | --- | --- |
| `mang_required` | string/int | 当前周期累计需要（历史 + 下一手） | 600 |
| `mang_paid` | string/int | 该玩家已付 | 500 |
| `mang_need` | string/int | 还差多少 | 100 |
| `buy_in_min` | string/int | 本次最少加多少，已按该房 `unit` 向上取整 | 500（10 皮） |
| `buy_in_step` | string/int | 该房一簸：10 皮=500，其他底皮按各自最小带入 | 500（10 皮） |
| `buy_in_max` | string/int | 本次最多可加多少（俱乐部金币/额度） | 5000 |
| `buy_in_default` | string/int | 带入弹窗默认值，等于 `buy_in_min` | 500 |

说明：

- `mang_*` 用于弹窗显示“累计/已付/还差”，避免玩家只看到“补 600”；
- `buy_in_*` 是**本次带入**的约束，不是总簸箕下限；
- 老字段 `min_bj`/`max_bj` 保留，但不再作为新弹窗的唯一依据；
- 服务端值是唯一权威，客户端字段不能直接提交作为已付/需要。

## 4. `坐下_事件` 带入校验

### 4.1 请求

沿用现有命令：

```json
{"header":"坐下_事件","money":500,"site":0,"type":"直接"}
```

- `money`：玩家确认的带入分（按该房 `unit` 的倍数；10 皮为 500，其他底皮见方案 §4.5）；
- `site`/`type` 等保持现状。

### 4.2 服务端计算

服务端不信任客户端金额，重新计算：

```text
need          = max(0, required_total - paid_total)
need_balance  = need + 底注 + 首注 + 本局芒皮
min_add       = ceil(max(0, need_balance - 当前簸箕余额) / unit) * unit
max_add       = 当前可带入上限
```

### 4.3 校验规则

| 条件 | 结果 |
| --- | --- |
| `money < min_add` | 拒绝，`PromptInfo`：“至少需要 X 分” |
| `money % unit != 0` | 拒绝：“带入必须是该房一簸的倍数” |
| `money > max_add` | 走现有额度/金币不足提示 |
| `min_add > max_add` | 拒绝：“可带入额度不足，至少需要 X 分” |
| 通过 | 加分、坐下；`paid`/`init_money` 按现有流程更新 |

**不允许**：

- 服务端自动把 500 改成 1000；
- 服务端先扣 500，再让玩家反复补；
- 只扣到剩底分的“部分补分”。

### 4.4 错误文案

建议统一：

- `至少需要 1000 分才能坐下（当前 500）`
- `带入必须是该房一簸（10 皮 500）的倍数`
- `可带入额度不足，至少需要 1500 分`

客户端收到错误后重新调用 `玩家_补芒_查询` 或刷新 `当前_玩家_消息`，不要本地猜测。

## 5. 带入弹窗交互

### 5.1 推荐流程

```text
客户端打开带入弹窗
  → 读取 buy_in_min / buy_in_step / buy_in_max / buy_in_default
  → 默认值 = buy_in_default，最小值 = buy_in_min，步长 = buy_in_step
  → 玩家选择金额（只能选该房 unit 的倍数且 >= buy_in_min）
  → 确定按钮：不满足时禁用
  → 发送 坐下_事件 {money}
  → 服务端重新计算并校验
      → 通过：坐下/加分
      → 拒绝：PromptInfo 错误 + 刷新字段
```

### 5.2 弹窗显示建议

> 下面以 10 皮（`unit=500`）为例；其他底皮按该房 `unit` 显示。

```text
累计需要：600
已付：500
还差：100
本次最少带入：500（1 簸）
可带入上限：5000
[ 500 ] [ 1000 ] [ 1500 ] ...
```

- 玩家点 500 时，如果 `buy_in_min=1000`，确定按钮应禁用；
- 不能把固定值（如 10 皮的 500）作为默认值，默认值取 `buy_in_default`；
- 不能由客户端自动加钱。

### 5.3 老客户端

- 不读 `buy_in_*`，仍显示 500；
- 服务端会拒绝不足金额，但玩家仍能先选 500，体验不完整；
- 如果要求“弹窗就不能选不够”，必须客户端按新字段控制。

## 6. 示例

> 以下示例均按 10 皮房（`unit=500`）；其他底皮把 500 换成该房 `unit`，例如 20 皮 `unit=1000`、3 簸=3000。

### 6.1 老玩家：累计 600，已付 500

服务端字段：

```json
{
  "mang_required": "600",
  "mang_paid": "500",
  "mang_need": "100",
  "buy_in_min": "500",
  "buy_in_step": "500",
  "buy_in_max": "5000",
  "buy_in_default": "500"
}
```

- 查询返回 `["需要补芒 100 分","弹窗","500","500","5000"]`；
- 弹窗显示“累计 600 / 已付 500 / 还差 100”，最低 500；
- 玩家点 500 可以；服务端扣 100 补芒，剩余按带入处理。

### 6.2 新玩家：累计 760，已付 0

```json
{
  "mang_required": "760",
  "mang_paid": "0",
  "mang_need": "760",
  "buy_in_min": "1000",
  "buy_in_step": "500",
  "buy_in_default": "1000"
}
```

- 查询返回 `["需要补芒 760 分","弹窗","1000","500","..."]`；
- 弹窗最低 1000（2 簸），500 不可选；
- 如果客户端发 500，服务端拒绝：“至少需要 1000 分”。

### 6.3 需要 1260

```json
{
  "mang_required": "1260",
  "mang_paid": "0",
  "mang_need": "1260",
  "buy_in_min": "1500",
  "buy_in_step": "500",
  "buy_in_default": "1500"
}
```

- 3 簸 = 1500；
- 一次补够，不自动扣。

### 6.4 已付 500、还差 100、余额 300

```text
need_balance = 100 + 40 = 140
140 - 300 < 0
min_add = 0
```

- 不需要再加簸，但本手可以打；
- 弹窗可以不显示，或显示“无需补充”。

## 7. 兼容性

| 对象 | 影响 |
| --- | --- |
| 老客户端 + 新字段 | 忽略未知字段，继续用 `PromptInfo2`/旧 `min_bj`；服务端仍校验，不足会拒绝 |
| 老客户端 + 500 弹窗 | 可能仍允许选 500；服务端拒绝并提示，需客户端改才能彻底解决 |
| 新客户端 | 用 `buy_in_*` 控制最小值/步长/默认值，体验完整 |
| 旧记录/旧房间 | 不涉及；补芒账本从新周期开始 |
| 大厅/俱乐部 | 同一套协议，无模式差异 |
| fixed/realtime | 同一套字段；realtime 结算后 `paid` 保留，只补新增 |

## 8. 排查

| 现象 | 检查 |
| --- | --- |
| 查询返回 600，而不是 100 | 服务端还在用累计公式，或 `paid` 没减 |
| 玩家已付 500，回座又补 500 | `MovePlayerToWatcher` 是否清零了 `paid`/`xiu_mang_count` |
| 点 500 也能坐下 | 服务端直接带入分支是否只校验 `di_times*50`；客户端是否没读 `buy_in_min` |
| 弹窗默认 500 | 客户端是否仍用固定 500/`max_bj`，没有用 `buy_in_default` |
| 需要 760，弹窗最低 500（10 皮） | `min_add` 是否按该房 `unit` 向上取整；`buy_in_min` 是否下发 |
| 补芒后只剩 10/40 | 是否还走“部分补分”分支；应改为不部分扣 |
| 10 皮 `min_bj=1000`、弹窗 500 | `min_boji_score` 本轮先不动，仍为 1000；新弹窗以 `buy_in_min` 为准（10 皮 1 簸=500），已知不一致，后续单独评估 |

## 9. 已确认 / 已决策

### 9.1 已确认

1. 新字段放在 `当前_玩家_消息`，老客户端忽略未知字段；不新增路由。
2. 客户端可按 `buy_in_min`/`buy_in_step` 控制弹窗，不满足时禁用确定。
3. `PromptInfo2` 的“需要补芒 X 分”保持原文案，只把 X 改成差额（`mang_need`）。
4. `min_boji_score` 本轮先不动，保留现状（10 皮 1000）；新字段/校验用 `unit`，已知与 10 皮 1 簸 500 不一致，后续单独评估。
5. 结算后重新带入、被踢未结算、离开房间再回来（房间还在），`paid` 都保留；只有换房/周期重置/房间销毁清零。
6. 多付/超额留作下次抵扣，不结算退回；周期重置时随 `paid` 清零。
7. 上线首局初始化：在座玩家 `paid = CalcMangDebt(xiu_mang_count)`；新进玩家 `paid=0`。
8. 揍芒/休芒按各自实际下一手（倍数/封顶）算；如果两者公式不同，分别计算。

### 9.2 已决策

1. 补芒债跟 `xiu_mang_count` 链走；池子余额是独立奖池，新玩家不补池子历史；`count` 清零只清 `paid`（`CalcMangDebt(0)=0`），不动 `table_mang_times`。
2. `paid` 只是并行账本；补款仍走现有 `boji_score` → `xiu_mang_score`/`mang_pi_score` → 芒果池，不能只记 `paid` 不入池。
