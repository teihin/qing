## 1. 通用协议

### 1.1 命令通道

与既有俱乐部接口完全一致，本文不重复：

| 方向 | 方法 | 说明 |
| --- | --- | --- |
| 客户端→服务器 | `reqHallCommand(param, context)` | 发出大厅命令 |
| 服务器→客户端 | `onHallCommand(ret_code, result)` | 同步响应 / 异步最终回调 |
| 服务器→客户端 | `onMessage(string router, string json)` | 列表数据与红点推送 |

- `param`：**JSON 字符串**，必须包含 `"header"` 字段（值为命令名）。
- 返回码：`0x200` 成功 / `0x301` 失败（`result.error`）/ `0x500` 仅服务端内部标记（**不会下发**）。
- 完整协议、分页约定（`number`=页码、`count`=总条数）、金额单位见 `doc/俱乐部代理与邀请码-客户端接口文档.md` §1。

### 1.2 模式开关

服务端 `game_mode != 'club'` 时，代理相关命令统一返回 `0x301` + `{"error": "俱乐部代理功能未启用"}`；
大厅模式下不存在代理树，`is_leader` 恒为 `0`（`NumberList` 内为 `"0"`）。

| # | 命令 / 路由 | 类型 | 变更内容 |
| --- | --- | --- | --- |

## 2. 数据结构

### 2.1 `ClubAgentInfo`（我的代理信息，新增 `is_leader`）

```json
{
  "club_id": "820084",
  "user_id": "580629",
  "user_name": "a3",
  "is_creator": 0,
  "is_agent": 1,
  "is_leader": 1,
  "invite_code": "482913",
  "percent": 30,
  "upper_guuid": "237737",
  "upper_name": "天外飞仙",
  "downline_count": 2,
  "downline": [
    {"user_id": "121500", "user_name": "a4", "percent": 20}
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `is_creator` | int | `1`=我是该俱乐部创建者（根代理）。**口径不变** |
| `is_agent` | int | `1`=我在该俱乐部是代理（持有可用邀请码）。**口径不变** |
| `is_leader` | int | **本次新增**。`1`=我是**盟主**（创建者的直属代理）；`0`=不是。**必定是 `is_agent=1` 的子集**：`is_leader=1` 时 `is_agent` 必为 `1`，`is_creator=1` 时 `is_leader` 必为 `0` |
| `invite_code` / `percent` / `upper_guuid` / `upper_name` / `downline` | — | **口径全部不变**，见 `doc/俱乐部代理与邀请码-客户端接口文档.md` §2.1 |

> 「盟主」= 创建者的**直属**代理（`upper_guuid` 等于创建者）。层级再深的下级代理 `is_leader=0`。

### 2.2 `ClubAgentReq`（入会申请行，字段不变、语义扩展）

```json
{
  "req_id": 128,
  "user_id": "580629",
  "user_name": "a3",
  "date": "2026-10-30 17:20:11",
  "invite_code": "482913",
  "agent_guuid": "237737",
  "agent_name": "天外飞仙",
  "remark": "申请留言"
}
```

| 字段 | 说明 |
| --- | --- |
| `invite_code` | 该申请使用的邀请码（**之前恒等于本人码**，现在可能是下级的码） |
| `agent_guuid` / `agent_name` | **该申请所用邀请码的归属代理**（即申请人的直属上级）。**不再恒等于本人**，见下表 |
| `remark` / `date` / `req_id` / `user_id` / `user_name` | 不变 |

| 列表视角 | `agent_guuid` 的取值 |
| --- | --- |
| 普通代理 | 恒等于本人（只返回自己码带来的申请） |
| 盟主 | 本线各层代理：可能等于本人，也可能是本人下级代理 |
| 创建者 | 全俱乐部任意持码代理，**可能为空串**（无码申请，`invite_code=''`、`agent_name=''`） |

> 客户端展示建议：`agent_name` 非空时显示"归属：XXX"；为空时显示"无邀请码"（创建者视角才会出现）。
> **不要**再用 `agent_guuid == 本人` 判断"这一行我能不能批"——列表范围已经等于可审批范围，能看到的行就一定批得动（见 §3）。

### 2.3 `NumberList` 成员行（新增 `is_leader`）

```json
{
  "number": "0",
  "count": "12",
  "guuid": "237737",
  "name": "天外飞仙",
  "gold": "0",
  "club_gold": "1000",
  "role": "玩家",
  "is_agent": "1",
  "is_leader": "1",
  "percent": "20",
  "team_count": "5",
  "status": "在线"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `is_leader` | **string** | **本次新增**。`"1"`=该成员是盟主（创建者的直属代理）；`"0"`=不是。**字段恒定存在**：非代理 / 非直属 / 已取消代理 / 大厅模式 / 代理树未加载 一律 `"0"`，客户端不需要判空 |
| `role` | string | **不变**，仍为 `老板` / `管理员` / `玩家`。盟主**不改变** `role`，请用 `is_leader` 渲染"盟主"角标 |
| 其他字段 | — | 口径不变，见 `doc/俱乐部与联盟功能-客户端接口文档.md` §2.10 |

> 与 `is_agent` 的关系：`is_leader="1"` 必然 `is_agent="1"`；反向不成立（普通代理 `is_agent="1"`、`is_leader="0"`）。
> `is_leader` 与 `is_agent` 一样是**派生字段**：创建者把某人改挂到别的代理下、或取消其代理，`is_leader` 立即变 `"0"`，无需客户端额外处理。

### 2.4 `ClubReqInfo`（红点，字段不变、数值口径变更）

```json
{
  "club_id": 820084,
  "club_name": "示例俱乐部",
  "req_count": 3,
  "number_count": 56,
  "source": "AddJoinerList"
}
```

| 字段 | 说明 |
| --- | --- |
| `req_count` | **该收件人自己需要处理的待审数**。口径按收件人身份区分，见 §4.5 |
| `number_count` | 俱乐部总人数，**不变** |
| `source` | 触发来源（`AddJoinerList`=新申请；`""`=同意/拒绝后的刷新），**不变** |

## 3. 角色与权限矩阵

| 角色 | 判定方式（客户端） | 申请列表可见范围（4.2） | 可审批/可拒绝（4.3 / 4.4） |
| --- | --- | --- | --- |
| 创建者（老板） | `ClubAgentInfo.is_creator == 1` 或俱乐部 `club_make` 含该 club | **本俱乐部全部**待审（含无码申请） | **全部**（含无码申请） |
| **盟主** | `ClubAgentInfo.is_leader == 1` | **本人整条线**（本人 + 全部下级代理带来的申请） | **本人整条线**的申请 |
| 代理 | `is_agent == 1` 且 `is_leader == 0` | 仅**本人码**带来的申请 | 仅本人码带来的申请 |
| 俱乐部管理员 | `club_manage` 含该 club | 仅本人码带来的申请（**不变**） | **全部**（Hall 侧既有放行，**不变**） |
| 普通成员 | 以上都不是 | 空列表 | 无权 |

> **一句话**：`查询_俱乐部_代理_申请` 返回的行 = 你**一定**能审批/拒绝的行（管理员例外：他仍能批全部，但列表只给自己码的，属既有行为，本次不动）。
> 审批通过后，玩家仍绑定到**该申请所用邀请码的归属代理**（`agent_guuid`）名下，**不是**绑到盟主名下——分账关系不变。
>
> 盟主的权限**只覆盖「已有申请记录」**：用 `添加_俱乐部_玩家` 主动拉一个没有申请记录的玩家，盟主与普通代理一样会被拒（`只有俱乐部管理员允许操作！`）。
> 审批权与列表范围都按**当前代理树**实时计算：申请挂起期间代理被改挂/取消，权限随之变化，不留申请时快照。

## 4. 接口详述

### 4.1 查询_俱乐部_代理_信息（字段新增）

**无可调参数变化**，仅返回体新增 `is_leader`。

- **命令名**：`查询_俱乐部_代理_信息`
- **权限**：本俱乐部成员
- **参数**：`club_id`(必)

```json
{"header": "查询_俱乐部_代理_信息", "club_id": "820084"}
```

- **同步响应**：`0x200`，`result` 为 `{}`（数据随后推送）
- **推送路由**：`ClubAgentInfo`
- **推送报文**：`{"number": 0, "count": 1, "result": { /* §2.1，含 is_leader */ }}`

**客户端用法**：

| 场景 | 判断 |
| --- | --- |
| 显示"盟主"身份角标 | `is_leader == 1` |
| 是否展示「代理申请」入口 | `is_creator == 1` 或 `is_agent == 1`（盟主必为 `is_agent`，自动覆盖） |
| 是否展示「设置下级为代理」 | 仍按既有口径（创建者 / 有 `downline` 管理能力的代理），本次不变 |

---

### 4.2 查询_俱乐部_代理_申请（可见范围变更）

**参数、响应方式完全不变**，只是返回的**行范围**按调用者身份变化。

- **命令名**：`查询_俱乐部_代理_申请`
- **参数**：`club_id`(必)、`count`、`page`（`count` 返回的是**过滤后的总条数**）

```json
{"header": "查询_俱乐部_代理_申请", "club_id": "820084", "page": 0, "count": 20}
```

- **同步响应**：`0x200`，`result` 为 `{}`
- **推送路由**：`ClubAgentReqInfo`
- **推送报文**：

```json
{
  "number": 0,
  "count": 2,
  "result": [ /* ClubAgentReq 数组，见 §2.2 */ ]
}
```

**返回范围**：

| 调用者 | 返回 |
| --- | --- |
| 创建者 | 本俱乐部**全部**待审申请（按 `id` 倒序）；**包含无码申请**（`invite_code=""`、`agent_guuid=""`、`agent_name=""`） |
| 盟主 | **本人整条线**（本人 + 全部下级代理的码带来的申请），按下级层级不限深度 |
| 普通代理 | 仅本人当前有效邀请码带来的申请（**与 2026-10-26 版本完全一致**） |
| 无有效码且非创建者/盟主 | 空列表（`count=0`），不报错 |
| 代理树未加载完成（服务端启动后极短窗口） | **盟主身份暂时失效** → 回退为"只看本人码"；**创建者不受影响**（其身份不依赖代理树，仍返回全量） |

示例（盟主 A 视角，A 的下级是 B，B 的码带来两条申请）：

```json
{
  "number": 0,
  "count": 2,
  "result": [
    {"req_id": 131, "user_id": "600001", "user_name": "m1", "date": "2026-10-30 18:01:10",
     "invite_code": "482913", "agent_guuid": "237737", "agent_name": "B", "remark": ""},
    {"req_id": 129, "user_id": "600002", "user_name": "m2", "date": "2026-10-30 17:20:11",
     "invite_code": "482913", "agent_guuid": "237737", "agent_name": "B", "remark": "朋友推荐"}
  ]
}
```

> 与老接口 `查询_俱乐部_加入申请`（路由 `JoinerList`，全量、无权限校验）**并存**，两者互不影响。盟主请优先使用本接口，它与审批权限同口径。

### 4.3 添加_俱乐部_玩家（审批权限扩展）

**参数、响应方式完全不变**，只是权限判定放宽。

- **命令名**：`添加_俱乐部_玩家`（**注意**：不是 `添加_俱乐部_玩家_积分`）
- **参数**：`club_id`(必)、`user_id`(必)、`init_gold`(可选)、`init_club_gold`(可选)、`context`

```json
{"header": "添加_俱乐部_玩家", "club_id": "820084", "user_id": "600001", "context": "p@approve"}
```

- **响应**：**无即时响应**（内部 `0x500` 不下发），结果经 `onHallCommand` 异步回包；`0x200` 成功 / `0x301` 失败

**权限（扩展后）**：

| 可审批 | 说明 |
| --- | --- |
| 创建者 | 任意申请（含无码） |
| 俱乐部管理员（`club_manage`） | 任意申请（**既有行为，不变**） |
| **该申请所用邀请码的归属代理**（直属上级） | 仅自己的码带来的申请（既有） |
| **该申请链路上的盟主** | **本次新增**：申请人的上级链上存在一个"创建者直属代理"，且就是本人 |

| 错误 | 说明 |
| --- | --- |
| `只有俱乐部管理员允许操作！` | 无权（含"盟主批外线申请"、"盟主批无码申请"） |
| `金币为零，不能申请加入` / `积分不足，不能新增玩家` / `玩家不存在！` | 既有错误，逻辑不变 |

> 通过后：成员加入该俱乐部，并在代理树中挂到 **该申请所用邀请码的归属代理** 名下（无码则挂创建者）。**不会**因为"是盟主批的"就挂到盟主名下。

---

### 4.4 删除_俱乐部_加入申请（拒绝权限扩展）

与 4.3 完全同口径，同样**参数与响应方式不变**。

- **命令名**：`删除_俱乐部_加入申请`
- **参数**：`club_id`(必)、`user_id`(必，申请人)、`context`
- **响应**：异步回调；`0x200` 成功 / `0x301` 无权（`只有俱乐部管理员允许操作！`）
- **行为**：只删除本俱乐部该申请人的「申请加入」记录（不跨俱乐部）

**权限**：创建者、`club_manage` 管理员、该申请的码归属代理、**该申请链路上的盟主（本次新增）**。

### 4.5 `ClubReqInfo`（红点口径变更）

申请到达、同意、拒绝后，服务端主动推送，**字段不变**，`req_count` 按收件人身份给数，**统一推真实值（含 0）**：

| 收件人 | `req_count` | 说明 |
| --- | --- | --- |
| 创建者 | **全俱乐部待审数**（含无码申请） | **本次新增**：创建者会收到此推送（此前 2026-10-26 起不推） |
| **盟主** | **本人整条线的待审数合计** | **本次新增** |
| 普通代理 | 本人码带来的待审数 | 数值口径不变；**2026-10-30 起待审为 0 也会下发**（原先不下发） |
| 其他成员 | 不推 | 不变 |

**是否推 0（清红点）**：创建者、盟主、普通代理**一律下发**（含 `req_count=0`）。

> **为什么普通代理也改成下发 0**：盟主/创建者可以替下级代理处理申请，该代理自己没做任何操作；
> 若仍"不下发 0"，他的待审数被清空后收不到任何消息，红点会残留到重开列表或重连。
> 统一推真实值后，客户端**收到即覆盖**即可，**不再需要"同意/拒绝成功后自行清零"**的补丁逻辑。

> 例外不变：`ClubReqInfo` 还用于"玩家加入/退出俱乐部后的定向刷新"（只推给该玩家，数值按 `club_make`/`club_manage`/代理身份给），该场景行为**未变**。
>
> 客户端建议：收到 `req_count` 直接覆盖该俱乐部红点数值（`0` 也覆盖），删掉旧的"处理成功后主动清零"。普通代理的 `req_count` 现在同样是权威值。
> 同一俱乐部短时间内可能连续收到多次（申请到达、同意/拒绝、俱乐部资料修改都会触发），**幂等覆盖即可，不需要去重或防抖**。
>
> **入口归属（需客户端确认）**：创建者本次会重新收到全量红点（2026-10-26 曾因"老板端也有红点"被收紧）。
> 请把 `is_creator` / `is_leader` 的 `req_count` 挂在**「代理申请」入口**（即 `查询_俱乐部_代理_申请` 的界面），
> 不要同时挂到老的「加入申请」入口（`JoinerList`），否则老板会看到两个红点、数值还可能不一致。
> 若产品希望只在老入口展示，则本次红点改造需另行讨论，代码侧只需调整 `_closeClubReqCount` 一个分支。

### 4.6 查询_俱乐部_成员（`NumberList` 新增 `is_leader`）

**无可调参数变化**，仅 `NumberList` 每行新增 `is_leader` 字符串字段（见 §2.3）。

- **命令名**：`查询_俱乐部_成员`；参数 `club_id`、`user_id`、`agent_id`、`count`、`page`、`search_name_id`、`context` 全部不变
- 直属口径、排序、`count` 语义均不变（见 `doc/俱乐部与联盟功能-客户端接口文档.md` §2.10）

**客户端用法**：成员行渲染"盟主"角标（建议与 `role=老板`、`is_agent` 角标并列展示）；**不要**用 `role` 表达盟主。

## 5. 典型时序

```text
创建者（老板）
  └─ 设置_俱乐部_代理(A, 20%)                 → A 是创建者直属代理 ⇒ is_leader=1（盟主）
        A 有码 482913，并设置_俱乐部_代理(B, 30%)  → B is_agent=1、is_leader=0
              B 把码分给玩家 M

M 申请_加入_俱乐部 {invite_code: B 的码}

  - B 收到 ClubReqInfo(req_count=自己剩余)
  - A 收到 ClubReqInfo(req_count=本线剩余，可能为 0)
  - 创建者收到 ClubReqInfo(req_count=全俱乐部剩余，可能为 0)
```

## 6. 客户端注意事项

| # | 事项 |
| --- | --- |
| 1 | 本次**无新增命令、无参数变更**、无新增推送路由；只需解析 `is_leader` 并按新范围展示列表 |
| 2 | `is_leader`（`ClubAgentInfo`）是 **int** `0/1`；`is_leader`（`NumberList`）是 **string** `"0"/"1"`——与 `is_agent` 的类型差异完全一致，别混用 |
| 3 | 判定"盟主"只认 `is_leader`；不要用 `upper_guuid == 创建者` 自行推断（普通成员也可能挂创建者，但 `is_leader=0`），也不要用 `percent` 推断 |
| 4 | 盟主的 `role` 仍是 `玩家`（或 `管理员`），**不要**把 `role` 当盟主标识 |
| 5 | 申请行的 `agent_guuid` 不再恒等于本人：盟主视角下它是**下级代理**、创建者视角下可能是空串（无码申请）；界面请按"归属人"展示 |
| 6 | 列表返回的行**都可审批/拒绝**（管理员例外，见 §3 注），客户端不需要再逐行计算权限 |
| 7 | **三种身份都会收到 `req_count=0`**（本次口径变更）：收到即覆盖红点，删掉旧的"处理成功后自行清零"。创建者的全量红点请挂在**「代理申请」入口**，不要再挂老的「加入申请」入口（见 §4.5 注） |
| 8 | `is_leader` 是派生字段，盟主被改挂/取消代理后会随下一次推送立即变为 `0`；客户端不要本地缓存该身份 |
| 9 | 老版本客户端忽略 `is_leader` 也能正常工作，唯一差别是没有"盟主"角标、看不到本线申请（服务端权限已放开，不会报错） |
| 10 | 盟主**不等于**创建者：盟主不能改俱乐部信息、不能设管理员、不能取消他人代理，也**不能主动拉人**（`添加_俱乐部_玩家` 对没有申请记录的玩家仍会被拒）。唯一新增能力是"审批/拒绝本线已有申请" |
