> 配套方案文档：`doc/俱乐部代理与邀请码设计说明.md`（服务端实现、DB 变更、结算口径）
> 本文档面向客户端（Unity），只描述**怎么调、传什么、收什么**，不涉及服务端内部实现。
> 状态：**设计定稿，服务端未实施**。标注「新增」的 6 个命令在服务端上线前调用会返回 `0x301`（命令不存在）；「改造」的 2 个命令为既有命令增加参数/权限，旧参数保持兼容。

## 1. 通用协议（所有接口共用）

### 1.1 命令通道

| 方向 | 方法 | 说明 |
| --- | --- | --- |
| 客户端→服务器 | `reqHallCommand(param, context)` | 大厅命令（本文件除"进房"外全部走这里） |
| 服务器→客户端 | `onHallCommand(ret_code, result)` | 同步响应 |
| 客户端→服务器 | `reqEnterRoom(roomType, roomID, roomSetting)` | **进房**（实体方法，见 §4.9） |

- `param`：**JSON 字符串**，必须包含 `"header"` 字段（值为命令名），其余字段为命令参数。
- `context`：字符串，新版本格式为 `"p@<任意上下文串>"`，`@` 后内容原样回传，用于请求-响应配对。

```json
{"header": "查询_俱乐部_代理_信息", "club_id": "820084"}
```

### 1.2 同步响应格式

`onHallCommand` 的 `result` 是 JSON 字符串，外层固定包裹：

```json
{
  "context": "<请求时@后的context原样回传>",
  "result": { /* 各接口自己的返回体 */ }
}
```

> 异常路径（命令名不存在、`param` 非法 JSON、服务端内部异常）：只回 `{"context":"<ctx>"}`、**没有 `result` 键**，且 `ret_code = 0x301`。客户端先判空再解析。

### 1.3 返回码

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `GC_OK` | `0x200`(512) | 成功 |
| `GC_FAILED` | `0x301`(769) | 失败，`result` 内一般有 `{"error": "原因"}` |
| `GC_UNKOWN` | `0x500`(1280) | 服务端**内部标记**"本次不同步返回"，**该码不会下发给客户端**；最终结果经 `onHallCommand` 回调送达（`0x200` 成功 / `0x301` 失败，见 §1.4） |

### 1.4 异步推送

列表类接口（查询代理信息 / 申请 / 收益）走**同步响应 + 异步推送**：`onHallCommand` 返回 `0x200` 且 `result` 为空对象，真正的数据由：

```csharp
onMessage(string router, string json)
```

送达。客户端按 `router` 分发。本文档逐接口标注路由名与报文结构。

> 推送**不带** `context`，客户端用"路由 + 当前请求的 club_id/页码"配对；同一界面避免并发发起多个同路由请求。

**操作类命令（4.1~4.3、4.7）的响应**：因为要查库（校验成员/权限、分配邀请码），它们采用项目里同类俱乐部命令的既有做法——**服务端不返回即时响应**（内部用 `0x500` 标记"异步"，**该码不会下发**），**最终结果**在几十毫秒内经 `onHallCommand` 回调送达（`0x200` 成功 / `0x301` 失败）。客户端**只处理最终回调**即可。

**模式开关**：服务端 `game_mode` 不为 `club` 时，6 个新增命令统一返回 `0x301` + `{"error": "俱乐部代理功能未启用"}`。

### 1.5 分页与时间

| 约定 | 说明 |
| --- | --- |
| `count` / `page` | 列表接口统一：每页条数（默认 10）、页码（**从 0 开始**）；JSON 数字或数字字符串均可 |
| 返回 | `number` = 当前页码；`count` = **总条数**（不是本页条数）；`result` = 本页数组 |
| `date` | 收益查询用 `YYYY-MM-DD`；不传默认今天 |

### 1.6 角色与权限

| 角色 | 判定 | 本组接口权限 |
| --- | --- | --- |
| 创建者（根代理） | 俱乐部 `club_owner` = 自己 guuid | 可管理本俱乐部**任意**代理；查看全部申请 |
| 俱乐部管理员 | `club_manage` 含该 club_id | **只参与申请查看/审批**；不能设置/修改/取消代理 |
| 代理 | 在 `club_agent_info` 中 `status='used'` 且持有邀请码 | 只能管理**自己的直接下级**；只看**自己码带来的**申请 |
| 普通成员 | `club_join` 含该 club_id | 只能查询自己的代理信息/收益（通常为空） |

> 一个玩家可同时加入多个俱乐部；**所有接口都必须带 `club_id`**，不同俱乐部的代理关系、比例、邀请码互相独立。

### 1.7 金额与比例

| 字段 | 单位 | 说明 |
| --- | --- | --- |
| `amount_fen` / `base_fen` / `total_fen` | **分**（int） | 展示为元时 ÷100；与红利账户 `hongli` 同单位 |
| `percent` | 整数 0~100 | 该代理**从"当前剩余"中截留**的比例；不是"占总额比例"、也不是"级差" |
| `invite_code` | 6 位数字字符串 | 全局唯一，用掉不回收 |

## 2. 数据结构

### 2.1 `ClubAgentInfo`（我的代理信息）

```json
{
  "club_id": "820084",
  "user_id": "580629",
  "user_name": "a3",
  "is_creator": 0,
  "is_agent": 1,
  "invite_code": "482913",
  "percent": 30,
  "upper_guuid": "237737",
  "upper_name": "天外飞仙",
  "downline_count": 2,
  "downline": [
    {"user_id": "121500", "user_name": "a4", "percent": 20}
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `is_creator` | int | `1`=我是该俱乐部创建者（根代理，比例固定为 100 占位，不可修改） |
| `is_agent` | int | **`1`=我在该俱乐部是代理**（持有可用邀请码）；`0`=普通成员。**判断"我是不是代理"一律用这个字段**——`invite_code` 对非代理会返回上级的码，不能用它判定 |
| `invite_code` | string | **代理=本人的邀请码**；**非代理=其直接上级代理的邀请码**；都没有则为空串 |
| `percent` | int | 我作为代理时的截留比例；普通成员为 0 |
| `upper_guuid` / `upper_name` | string | 我在**该俱乐部**的直接上级；创建者为空串 |
| `downline` | array | **直接下级**（一层），不含下级的下级；普通成员/无下级为空数组 |
| `downline[].invite_code` | — | **不返回**（下级代理的码不下发，避免扩散） |

### 2.2 `ClubAgentReq`（入会申请）

```json
{
  "req_id": 128,
  "user_id": "580629",
  "user_name": "a3",
  "date": "2026-10-23 17:20:11",
  "invite_code": "482913",
  "agent_guuid": "237737",
  "agent_name": "天外飞仙",
  "remark": "申请留言"
}
```

| 字段 | 说明 |
| --- | --- |
| `agent_guuid` / `agent_name` | 该申请走的邀请码归属代理；创建者视角用于分组显示 |
| 代理视角 | 只返回自己码带来的申请（`agent_guuid` = 自己） |

### 2.3 `ClubAgentIncome`（收益明细）

```json
{
  "date": "2026-10-23",
  "time": "18:05:12",
  "room_id": 851724,
  "room_name": "1-851724",
  "winner_name": "a4",
  "base_fen": 1000,
  "percent": 20,
  "level": 2,
  "amount_fen": 200
}
```

| 字段 | 说明 |
| --- | --- |
| `base_fen` | 该玩家本局产生的**代理份额**（抽水的 50%，分） |
| `percent` | 我这一层当时的截留比例 |
| `level` | 我在链上的层级：`1`=离玩家最近，`2`…；创建者行为 `0`（根） |
| `amount_fen` | 本层实际所得（分） |

> `room_name` 为房间名：**2026-10-25 起**与大厅自动房同一套拼法 `<selfname><底皮档位>-<roomID>`（线上 `selfname` 为空，实际就是 `1-851724` 这种），此前为带俱乐部名的 `<俱乐部名>-<档位>-<roomID>`。该列存的是**当时**的房间名，历史记录仍可能是旧格式，客户端按字符串原样展示即可。

## 4. 接口详述

### 4.1 设置_俱乐部_代理（新增）

把某个**本俱乐部成员**指定为自己的直接下级代理，设置其截留比例，并自动为其分配一个 6 位邀请码。

- **命令名**：`设置_俱乐部_代理`
- **通道**：`reqHallCommand` / `onHallCommand`
- **权限**：调用者必须是该成员在**本俱乐部**的直接上级；或该俱乐部创建者

#### 请求参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | `设置_俱乐部_代理` |
| `club_id` | string | 是 | 俱乐部 ID |
| `user_id` | string | 是 | 被设置为代理的玩家 guuid（必须是本俱乐部成员） |
| `percent` | int | 是 | 该代理从"当前剩余"中截留的比例，`0~100` |

#### 请求示例

```json
{"header": "设置_俱乐部_代理", "club_id": "820084", "user_id": "580629", "percent": 20}
```

#### 响应示例（ret_code = 0x200）

```json
{
  "context": "set_agent_01",
  "result": {"error": "", "user_id": "580629", "percent": 20, "has_invite_code": 1}
}
```

> 邀请码不在此返回；被设置的代理本人通过 4.4 查看自己的码并分享。

#### 失败（ret_code = 0x301）

```json
{"context": "set_agent_01", "result": {"error": "只能设置自己的下级为代理"}}
```

#### 规则与错误

| 情况 | 错误文案 |
| --- | --- |
| `club_id` 无效 | `俱乐部号不存在！` |
| `user_id` 在账号表查不到 | `玩家不存在` |
| 目标不是本俱乐部成员 | `该玩家不是本俱乐部成员` |
| 目标是自己或创建者 | `不能设置自己或创建者为代理` |
| `percent` 非 0~100 整数 | `比例必须在 0~100 之间` |
| 链深超过 150 | `代理层级超出上限` |
| 无权限（不是该成员的直接上级，也不是创建者） | `只能设置自己的下级为代理` |

- 幂等：目标已是代理时，等价于"修改比例"，不会重复建关系；
- 首次设置才分配邀请码；已取消的代理重新设置时取**新码**（旧码永久失效）。

#### 关于"目标本来就是代理"

| 情况 | 行为 |
| --- | --- |
| 目标已是代理，调用者 = **他当前的直接上级** | 允许，但只改比例（`upper_guuid` 写回同一个人，等于没动），**不会换上级、不会把别人的下线抢过来** |
| 目标已是代理，调用者 = **其他人**（包括他的上上级、其他分支） | 拒绝 `只能设置自己的下级为代理`，不会改变任何关系 |
| 目标已被取消（`status=disabled`） | 允许，视为**重新晋升**：重新生效并分配**新码**，旧码永久失效 |
| 目标是自己 / 俱乐部创建者 | 拒绝 `不能设置自己或创建者为代理` |
| 调用者是创建者 | 可调整本俱乐部任意成员的归属与比例；其原有下级关系不会被清空 |

> 客户端建议：列表里对"已是代理"的成员，入口显示为"修改比例"；对普通成员显示"设为代理"。

### 4.3 取消_俱乐部_代理（新增）

- **命令名**：`取消_俱乐部_代理`
- **权限**：该代理的直接上级 / 创建者
- **参数**：`club_id`(必)、`user_id`(必)
- **响应**：`0x200` `{"error":"","user_id":"580629"}`

| 错误 | 说明 |
| --- | --- |
| `该成员还有下级代理，不能取消` | **只允许取消叶子**，需先取消其下级 |
| `创建者不能被取消` | 根代理不可取消 |

- 取消后：该代理比例归零、邀请码失效（不可再用）、历史收益保留；
- 其下线的绑定关系不动（因为只允许取消叶子）。

### 4.4 查询_俱乐部_代理_信息（新增）

查询**我在该俱乐部**的代理信息与直接下级。普通成员也可调用（比例为 0、码按下面的规则给）。

- **命令名**：`查询_俱乐部_代理_信息`
- **权限**：本俱乐部成员
- **参数**：`club_id`(必)

```json
{"header": "查询_俱乐部_代理_信息", "club_id": "820084"}
```

- **同步响应**：`0x200`，`result` 为 `{}`（数据随后推送）
- **推送路由**：`ClubAgentInfo`
- **推送报文**：

```json
{
  "number": 0,
  "count": 1,
  "result": { /* 见 §2.1 ClubAgentInfo */ }
}
```

> 说明：`count` 固定 1（单对象），`result` 是**对象**不是数组。创建者首次调用会自动完成根代理初始化（幂等），返回 `is_creator=1`、`percent=100`、自己的邀请码。

#### `invite_code` 的取值规则（2026-10-23 客户端反馈后调整）

| 玩家身份 | 返回的 `invite_code` |
| --- | --- |
| **代理**（自己持有可用邀请码） | **自己的邀请码**（与上级无关，逻辑不受影响） |
| **非代理**（自己没有邀请码） | **其直接上级代理的邀请码**；上级不是代理 / 上级没有可用码 / 没有上级 → 空串 |

- 只下发**直接上级**一个码，不下发整条链；
- 用该码申请入会的玩家，审批后**挂在码的主人（上级代理）名下**，与使用者的身份无关；
- 客户端展示建议标注归属，例如"你的推荐人：XXX（邀请码 482913）"。

> **判定"我是不是这个俱乐部的代理"**：用 `is_agent`（`1`=代理，`0`=普通成员）。
> 不能用 `invite_code` 是否为空来判——非代理也会拿到上级的码；也不能用 `percent`（代理可自设为 0%）；`is_creator` 只表示创建者（根代理）。
> 服务端判定口径：**我在该俱乐部是否持有可用邀请码**（`club_invite_code_info` 中 `status='used'` 且属于我）。

### 4.5 查询_俱乐部_代理_申请（新增）

查询"待审批"的入会申请：

- 创建者/管理员：本俱乐部**全部**待审申请；
- 代理：**只有自己码带来的**申请；
- 普通成员：返回空列表（不报错）。

- **命令名**：`查询_俱乐部_代理_申请`
- **参数**：`club_id`(必)、`count`、`page`

```json
{"header": "查询_俱乐部_代理_申请", "club_id": "820084", "page": 0, "count": 20}
```

- **同步响应**：`0x200`，`result` 为 `{}`
- **推送路由**：`ClubAgentReqInfo`
- **推送报文**：

```json
{
  "number": 0,
  "count": 3,
  "result": [ /* ClubAgentReq 数组，见 §2.2 */ ]
}
```

> 与既有 `查询_俱乐部_加入申请`（路由 `JoinerList`）并存：老命令行为不变（创建者视角全量），本命令用于"代理看待自己下线的申请"。

### 4.6 查询_俱乐部_代理_收益（新增）

查询**我**在该俱乐部的抽水分成明细（不是俱乐部总收入）。

- **命令名**：`查询_俱乐部_代理_收益`
- **权限**：本人（任何成员可调，非代理返回空）
- **参数**：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | 是 | 俱乐部 ID |
| `date` | 否 | `YYYY-MM-DD`，默认今天；格式非法时服务端按今天处理 |
| `count` / `page` | 否 | 分页 |

```json
{"header": "查询_俱乐部_代理_收益", "club_id": "820084", "date": "2026-10-23", "page": 0, "count": 20}
```

- **同步响应**：`0x200`，`result` 为 `{}`
- **推送路由**：`ClubAgentIncomeInfo`
- **推送报文**：

```json
{
  "number": 0,
  "count": 2,
  "summary": {"date": "2026-10-23", "total_fen": 520, "total_count": 2},

}
```

> `summary` 是**当日合计**（不受分页影响）；无数据时 `count=0`、`total_fen=0`，正常返回。

### 4.7 申请_加入_俱乐部（改造：+`invite_code`）

在原有申请入会参数上增加邀请码。带码时，审批通过后自动绑定到码归属代理名下。

- **命令名**：`申请_加入_俱乐部`
- **参数**：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `club_id` | string | 否 | 俱乐部 ID。**带 `invite_code` 时可省略**（服务端以码解析出的俱乐部为准；两者都带且不一致时同样以码为准） |
| `invite_code` | string | 否 | 6 位邀请码；不带则按原流程申请，审批后挂创建者 |
| `init_club_gold` | int | 否 | 原参数，不变 |
| `remark` | string | 否 | 申请留言 |
| `context` | string | 否 | 原参数，不变 |

```json
{"header": "申请_加入_俱乐部", "club_id": "820084", "invite_code": "482913", "remark": "朋友推荐"}
```

- **响应**：不带 `invite_code` 时与既有行为一致（同步 `0x200`，等待审批）；**带 `invite_code` 时为异步回调**（需先查码，**无即时响应**，最终结果随后经 `onHallCommand` 送达 `0x200`/`0x301`）

| 错误 | 说明 |
| --- | --- |
| `邀请码不存在或已失效` | 码未分配 / 已取消 / 已停用 |
| `你已加入该俱乐部` | 已经是该俱乐部成员 |
| `俱乐部不存在` | 码解析出的俱乐部已被删除 |

- 同一玩家**可以同时加入多个俱乐部**（每次走对应俱乐部的码即可）。

---

### 4.8 添加_俱乐部_玩家（改造：审批权限扩展）

审批入会申请并把玩家拉入俱乐部（沿用既有命令，参数不变）。

> **命令名注意**：真实命令是 `添加_俱乐部_玩家`（Hall 注册表 10462 行）；**不要**写成 `添加_俱乐部_玩家_积分`——那是另一条真实命令（加积分），名字极像，调错会改玩家积分。

- **命令名**：`添加_俱乐部_玩家`
- **参数**：`club_id`(必)、`user_id`(必)、`init_gold`(可选)、`init_club_gold`(可选)、`context`
- **权限（新增）**：除创建者/管理员外，**该待审申请的 `invite_code` 归属代理**也可审批自己带来的申请
- **响应**：与 4.1 一样为**异步回调**（**无即时响应**，最终结果随后经 `onHallCommand` 送达）；`0x200` 成功 / `0x301` 失败

| 错误 | 说明 |
| --- | --- |
| `只有俱乐部管理员允许操作！` | 既不是管理，也不是该申请的码归属代理 |
| `玩家不存在！` | `user_id` 无效（目标账号不存在） |
| `金币为零，不能申请加入` | `init_gold=0` 时（沿用原逻辑） |
| `积分不足，不能新增玩家` | 沿用原逻辑 |
| `该成员还有下级代理，不能退出` | 退出/踢人时目标仍带下级代理（新增） |

- 审批通过后：成员加入该俱乐部，并在该俱乐部的代理树中挂到**码归属代理**；无码申请挂创建者；
- 审批前服务端会**复核邀请码仍有效**（在加入流程内完成），失效则按无码处理挂创建者（旧申请里若已留过失效码，不会绑到失效代理）。

---

### 4.9 进房：`reqEnterRoom`（改造：`roomSetting.club_id` 必带）

抽水归属由**玩家从哪个俱乐部的房间列表进入**决定，客户端进房时必须把该俱乐部 ID 放进 `roomSetting`。

- **调用**：`reqEnterRoom(roomType, roomID, roomSetting)`
- **`roomSetting`**（JSON 字符串）：在原内容上增加 `club_id`

```json
{"special_rule": "观战", "club_id": "820084"}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | **是**（俱乐部房） | 玩家点击该房间时所在的俱乐部（即房间列表请求里的 `club_id`） |

- 服务端校验（**不通过不阻断进房**，仅影响该玩家的抽水分成）：
  1. `club_id` 存在，且俱乐部未删除；
  2. 玩家 `club_join/club_join2` 含该俱乐部；
  3. 该房间对该俱乐部可见（本俱乐部或盟友俱乐部的房）。
- 校验不通过或未带：玩家**正常进房、正常游戏**，但他本局产生的抽水**不参与俱乐部分成**（该份留平台）。
- 大厅房（非俱乐部房）不需要该参数。

> 客户端务必：**从哪个俱乐部的房间列表点的房，就传哪个 `club_id`**；拼错/复用上一个俱乐部会导致分成归错（不可撤回）。

## 6. 典型时序

```text
创建者（根代理）
  └─ 设置_俱乐部_代理(A, 20%)            → A 获得邀请码 482913
        A 把码分享给新玩家 M
              M 调用 申请_加入_俱乐部 {invite_code:"482913"}
                    → 创建者 / A 的 查询_俱乐部_代理_申请 都能看到
              A 调用 添加_俱乐部_玩家 {user_id: M}
                    → 通过；M 在俱乐部的上级 = A
              M 从 A 所在俱乐部的房间列表进房（roomSetting.club_id = 该俱乐部）
                    → 牌局结束，抽水按 M→A→…→创建者 逐级分成
              A / 创建者 查询_俱乐部_代理_收益 查看明细
              代理调用 提取_玩家_红利（既有命令）把红利换成金币
```

> 多俱乐部：M 也可以再用 Y 俱乐部的码申请并加入 Y，Y 的上级/比例与 X 完全独立；进 Y 的房时 `club_id` 传 Y。

## 7. 客户端注意事项

| # | 事项 |
| --- | --- |
| 1 | 列表类接口（4.4/4.5/4.6）**同步响应为空**，必须等推送；不要用 `result` 判断有无数据 |
| 2 | 推送不带 `context`，请用"路由 + club_id + 页码"配对，避免同界面并发请求 |
| 3 | `percent` 是"从当前剩余截留"的比例，不是占总额比例；界面文案建议写"分成比例（从剩余中）" |
| 4 | 金额一律用 `*_fen`（分），展示时 ÷100；不要自己换算成"元"参与计算 |
| 5 | 邀请码只对**本人**可见（`invite_code` 仅在 4.4 返回自己的）；不要尝试展示下级的码 |
| 6 | 创建者根代理的 `percent` 固定 100（占位），客户端应置灰不可编辑 |
| 7 | 6 位邀请码与账号 ID/俱乐部 ID 同形，输入框标题必须区分（"邀请码"≠"俱乐部号"） |
| 8 | 进房 `club_id` 是**分账依据**，不是可见性依据；传错不会导致进不去，但会分成归错且不可撤回 |
| 9 | 取消代理后，其码立即失效；新申请用失效码会返回"邀请码不存在或已失效"，而**已在申请中、审批时码才失效**的，按无码处理（挂创建者），不会绑到已取消的代理 |
| 10 | 俱乐部模式下代理提红利**免门槛**（与平台模式不同），客户端不需要额外提示"5 个下级打满 100 手" |
