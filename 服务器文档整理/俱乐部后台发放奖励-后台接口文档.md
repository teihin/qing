# 俱乐部后台发放奖励 - 后台接口文档

> 版本：v1.3（2026-11-13）
> 配套方案：`doc/俱乐部后台发放奖励方案.md`
> 调用方：新后台管理系统（服务端本机调用 `http://127.0.0.1:8890`）
> 适用范围：仅俱乐部模式（`game_mode='club'`）；大厅模式不适用
> 状态：**契约定稿，服务端已实施并上传测试服（2026-11-13），待重启**

---

## 1. 概览

### 1.1 三个命令

| 命令 | 同步/异步 | 用途 | 写库类型 | 权限 |
| --- | --- | --- | --- | --- |
| `发放_总群主_奖励` | 同步 | 平台给指定总群主的联盟池发额度 | `额度奖励` | 仅后台 |
| `发放_盟主_奖励` | 同步 | 指定总群主给下属盟主俱乐部发额度 | `额度奖励` | 仅后台 |
| `异步_发放_玩家_奖励` | 异步 | 指定盟主给下属玩家发俱乐部积分 | `积分奖励` | 仅后台 |

"仅后台"的口径与 `异步_设置_俱乐部_管理范围` 一致：`Hall.boss` 或 `level>=99` 的账号。普通客户端调用直接返回"无权限"。

运行环境默认**单 baseapp、单 Hall**（项目既定约束）；待补内存与房间结算在同一进程内，不为此做跨进程同步。

### 1.2 与老命令的关系

| 老命令 | 新命令 | 差异 |
| --- | --- | --- |
| `增加_联盟_额度` | `发放_总群主_奖励` | 类型改为 `额度奖励`；只接受正数；池侧 `remark` 加 `联盟池奖励` 前缀 |
| `授信_联盟_额度` | `发放_盟主_奖励` | 类型改为 `额度奖励`；只接受正数；池侧流水改记**总群主**（老命令记操作人） |
| `添加_俱乐部_成员_积分` | `异步_发放_玩家_奖励` | 类型改为 `积分奖励`；支持批量；返回逐人结果 |

老命令继续保留原行为，客户端和其它后台业务不受影响。**扣减、冲正一律使用老命令**（负数），不产生奖励类型流水。

### 1.3 通用调用方式

```http
GET http://127.0.0.1:8890/hall/command?header=<命令名>&param=<URL encode 的 JSON>
```

示例：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=发放_总群主_奖励' \
  --data-urlencode 'param={"owner_guuid":"648425","quota_fen":1000000,"context":"admin-20261113-001"}'
```

返回：

```json
{
  "ret_code": 512,
  "ret_result": "{\"union_id\":\"123456\",\"union_quota\":\"1000000\",\"add_fen\":\"1000000\"}"
}
```

| `ret_code` | 含义 | 后台处理 |
| ---: | --- | --- |
| `512` | 成功 | 解析 `ret_result`（JSON 字符串） |
| `769` | 失败 | 展示 `ret_result.error`，写审计 |

> 三个新命令都是"处理完再返回"：不会出现老上分命令的 `1280`（已受理但结果未知）。异步命令在内部逐人处理完成后返回最终结果。

`context` 建议每次传唯一操作号，便于日志追溯；服务端只回包，不写库。

## 2. 发放_总群主_奖励

平台给指定总群主的联盟池增加额度。

### 2.1 请求

```json
{"header":"发放_总群主_奖励","owner_guuid":"648425","quota_fen":1000000,"context":"admin-20261113-001"}
```

或直接传联盟号：

```json
{"header":"发放_总群主_奖励","union_id":"123456","quota_fen":1000000}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `union_id` | 二选一 | 联盟号；与 `owner_guuid` 同时传时以本字段为准 |
| `owner_guuid` | 二选一 | 总群主账号 ID，服务端反查其联盟 |
| `quota_fen` | 是 | **分**，必须为正整数；1 万元 = 1000000 |
| `context` | 否 | 操作号，只回包 |

### 2.2 效果

```text
club_union_info.union_quota += quota_fen          （内存 + 立即 update）
club_history_info 一条：
    opt_type   = 额度奖励
    user_guuid = 总群主
    club_guuid = 联盟自己的俱乐部（club_union_info.club_guuid）
    user_quota = +quota_fen
    remark     = 联盟池奖励<变动前>→<变动后>
    opter      = 后台账号
```

成功后向总群主推送 `ClubUnionQuota`（`is_owner=1`，新池余额）。

### 2.3 返回

```json
{"union_id":"123456","union_quota":"1000000","add_fen":"1000000"}
```

| 字段 | 说明 |
| --- | --- |
| `union_quota` | 发放后的联盟池余额（分，字符串） |
| `add_fen` | 本次发放额（分） |

### 2.4 失败文案

| 场景 | `error` |
| --- | --- |
| 非后台调用 | `无权限` |
| 未传 `union_id` 且 `owner_guuid` 查不到联盟 | `联盟不存在` |
| `quota_fen` ≤ 0 | `发放金额必须大于 0` |
| `quota_fen` 非数字 | 解析失败，不返回业务文案；调用方必须传 JSON 整数 |

## 3. 发放_盟主_奖励

指定总群主把联盟池额度发给下属盟主俱乐部。

### 3.1 请求

```json
{"header":"发放_盟主_奖励","owner_guuid":"648425","club_id":"535696","quota_fen":1000000,"context":"admin-20261113-002"}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `union_id` / `owner_guuid` | 二选一 | 联盟定位，规则同 §2 |
| `club_id` | 是 | 目标盟主俱乐部 ID |
| `quota_fen` | 是 | **分**，正整数 |
| `context` | 否 | 操作号 |

### 3.2 效果

```text
联盟池 −quota_fen、目标俱乐部 union_quota +quota_fen
club_history_info 两条（同一笔）：
  ① 池侧：opt_type=额度奖励, user_guuid=总群主, club_guuid=联盟俱乐部,
           user_quota=−quota_fen, remark=联盟池<前>→<后>
  ② 目标侧：opt_type=额度奖励, user_guuid=盟主, club_guuid=目标俱乐部,
           user_quota=+quota_fen, remark=<前>→<后>
     （由 Club.AddUnionQuota 写入，opter_guuid=后台账号；
       该方法的 opter_name 落库为空串，额度流水查询会按 opter_guuid 关联
       tbl_Account 补全操作人名称）
```

成功后：

- 目标盟主收到 `ClubUnionQuota`（`is_owner=0`，新额度与上缴比例）；
- 总群主收到 `ClubUnionQuota`（`is_owner=1`，新池余额）。

### 3.3 返回

```json
{"union_id":"123456","club_id":"535696","union_quota":"9000000","club_quota":"1000000"}
```

| 字段 | 说明 |
| --- | --- |
| `union_quota` | 发放后联盟池余额（分） |
| `club_quota` | 发放后目标俱乐部额度（分） |

### 3.4 失败文案

| 场景 | `error` |
| --- | --- |
| 非后台调用 | `无权限` |
| 联盟不存在 | `联盟不存在` |
| 俱乐部不存在 | `俱乐部不存在` |
| 俱乐部不属于该联盟 | `该俱乐部不在你的联盟里` |
| `quota_fen` ≤ 0 | `发放金额必须大于 0` |
| 池余额不足 | `你的联盟额度不足` |

> 失败时池余额与目标额度均不变；写池侧流水放在目标侧成功之后，避免留下"资金已回滚但流水还在"的假记录（沿用 2026-11-09 的修复口径）。
> 新命令只加不减，`AddUnionQuota` 不会返回 `None`；代码仍保留"目标侧失败即回滚池"的兜底分支。

## 4. 异步_发放_玩家_奖励

指定盟主给其俱乐部下属玩家发放俱乐部积分。**不校验、不扣减俱乐部额度**，与上分同构。

### 4.1 请求

```json
{"header":"异步_发放_玩家_奖励","club_id":"535696","user_ids":["292989","293000"],"gold":100,"context":"admin-20261113-003"}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `club_id` | 是 | 盟主俱乐部 ID |
| `user_ids` | 是 | 玩家 ID 数组，或逗号分隔字符串；去重后 1~50 个 |
| `gold` | 是 | **每人**发放的积分，单位**元**，正整数 |
| `context` | 否 | 操作号 |

"所有玩家"由后台先查成员列表，再分批调用（单次 ≤50）。服务端不提供 `ALL`。

### 4.2 效果

```text
每个玩家：加载账号实体 → 校验是该俱乐部成员（club_id 在 club_gold 里）
            → 再判是否在房间（任意房型 isInRoomByID）

A. 不在房间（立即入账）：
    Account.club_gold[club_id] += gold      （club_mode=2/3 实际写 club_gold2）
    writeToDB()
    club_history_info 一条：
        opt_type   = 积分奖励
        user_guuid = 玩家
        club_guuid = club_id
        user_gold  = +gold
        remark     = 变动后余额（纯数字）
        opter      = 后台账号
    在线玩家收到 PromptInfo：您收到平台发放的 <gold> 金币

B. 在房间内（延迟补发）：
    Club.pending_reward[玩家] += gold        （内存，不写库、不写流水）
    等该玩家在本俱乐部房间完成一次结算
    （Player.addClubGold(..., is_over=True)）时：
        钱包 += 待补金额
        写一条 积分奖励 流水（remark=补发后余额）
        推同样的提示
```

不改 `club_guuid_info.union_quota`、不改 `club_agent_info.bonus/stone`、不改 `Account.gold/stone`。

### 4.3 返回

```json
{
  "club_id": "535696",
  "gold": "100",
  "count": 2,
  "success": ["292989"],
  "pending": ["293000"],
  "failed": []
}
```

部分失败示例：

```json
{
  "club_id": "535696",
  "gold": "100",
  "count": 2,
  "success": ["292989"],
  "pending": [],
  "failed": [{"guuid": "293000", "error": "玩家不属于该俱乐部"}]
}
```

| 字段 | 说明 |
| --- | --- |
| `count` | 本次请求的玩家数（去重后） |
| `success` | 已即时入账的玩家 ID |
| `pending` | 玩家在房间内，已登记内存待补，结算后自动入账的玩家 ID |
| `failed[].error` | 单人文案，见下表 |

> `success + pending + failed` 恒等于 `count`（同一玩家只进一个列表），后台可直接用三个列表对账。

### 4.4 失败文案

| 场景 | `error` |
| --- | --- |
| 非后台调用 | `无权限` |
| 俱乐部不存在 | `俱乐部不存在` |
| `user_ids` 为空 | `请选择玩家` |
| 去重后超过 50 | `单次最多 50 人，请分批发放` |
| `gold` ≤ 0 或非整数 | `发放积分必须大于 0` |
| 单人：玩家不存在 | `玩家不存在` |
| 单人：不是本俱乐部成员 | `玩家不属于该俱乐部` |
| 单人：实体加载失败 | `玩家数据加载失败` |

> 玩家在房间内不算失败，返回在 `pending` 里，不写 `failed`。
> 单人失败不影响其他人，不整批回滚；不涉及额度，无需资金回滚。

### 4.5 房间内延迟补发

| 项 | 规则 |
| --- | --- |
| 判定 | 该玩家在任意房间内（`isInRoomByID`）即延迟，无论坐桌还是观战 |
| 存储 | `Club.pending_reward`（内存，guuid → 元）；同一玩家多次发放累加 |
| 触发 | 该俱乐部房间结算时 `Player.addClubGold(..., is_over=True)`，自动并入钱包 |
| 流水 | 补发时才写一条 `积分奖励`（`remark`=补发后余额）；补发前查不到 |
| 生命周期 | 仅内存：进程重启、俱乐部解散即丢失；不做持久化 |
| 运行环境 | 默认单 baseapp、单 Hall（项目既定约束）；待补与房间结算在同一进程，不做跨进程同步 |
| 跨俱乐部 | 按俱乐部实例记账；玩家在哪个俱乐部的房间结算就补哪个俱乐部，不做跨俱乐部合并 |
| 长期不结算 | 奖励一直挂在待补，不产生流水、不重复发 |
| 记账时间 | 补发流水的 `date` 是**补发时间**，不是后台操作时间；对账时按响应和流水额匹配，不要按操作时间匹配 |
| 重发规则 | `pending` 玩家**离开房间前一律不重发**；离开后查流水，确认玩家不在任何房间且仍无流水，才人工补发并备注补发单号 |

## 5. 流水查询契约

### 5.1 额度流水：`查询_俱乐部_额度流水`（`ClubQuotaWater`）

```json
{"number":"0","count":"12","quota":"1000000","date":"2026-11-13 10:00:00",
 "type":"额度奖励","remark":"联盟池奖励0→1000000","room_id":"",
 "opter_name":"admin","actor_guuid":"100001","guuid":"648425","name":"总群主"}
```

| 项 | 说明 |
| --- | --- |
| 取数 | `opt_type like '额度%'`，`额度奖励` 自动命中，无需改查询 |
| `type` | 原样返回 `额度奖励` |
| `quota` | 带符号（分）；池侧进账为正、授出为负 |
| `remark` | 池侧 `联盟池奖励前→后` / `联盟池前→后`；目标侧 `前→后` |
| `opter_name` | 后台账号名 |

### 5.2 积分流水：`查询_俱乐部_积分流水`（`ClubGoldWater`）

```json
{"number":"0","count":"20","gold":"100","date":"2026-11-13 10:05:00",
 "type":"积分奖励","remark":"600","room_id":"",
 "opter_name":"admin","guuid":"292989","name":"测试玩家"}
```

| 项 | 说明 |
| --- | --- |
| 取数 | 白名单已加入 `积分奖励`（全量与 `only_add=1` 两个列表） |
| `type` | 原样返回 `积分奖励`（不会被改写成"上分"） |
| `gold` | 本次变动（元） |
| `remark` | 变动后余额，客户端余额列直接显示 |

### 5.3 授信记录：`查询_联盟_授信_记录`（`ClubUnionGrantList`）

新增第三类 `额度奖励`：

```json
{"number":"0","count":"5","date":"2026-11-13 10:00:00",
 "type":"额度奖励","quota":"1000000","quota_after":"1000000","remark":"1000000",
 "club_id":"535696","club_name":"测试盟主","guuid":"529749","name":"测试盟主",
 "opter_guuid":"100001","opter_name":"admin",
 "is_inject":0,"is_reward":1,"is_self":0}
```

| 项 | 说明 |
| --- | --- |
| API1（平台→池） | 只取池侧行：`club_guuid = 联盟俱乐部` 且 `remark like '联盟池奖励%'`；`club_id`/`club_name` 返回空 |
| API2（总群主→盟主） | 只取目标侧行：`remark not like '联盟池%'`；池侧对手方不返回，避免同一笔出现两次 |
| `type` | `额度奖励` |
| `is_reward` | 新增字段，奖励行为 `1`，其余为 `0` |
| `quota_after` | `remark` 中 `→` 的后半段（分） |
| 计数 | 授信、注资、奖励三路 `count` 相加，不封顶 100 |

> API1 的池侧行只在**全联盟视角**（总群主 / 平台 boss / `union_manage` 授权联盟账号，不传 `club_id`）出现；盟主视角只能看到自己俱乐部的目标侧行，与现有注资记录的口径一致。

## 6. 后台 SQL

### 6.1 定位总群主 / 联盟

```sql
SELECT union_id, union_name, owner_guuid, owner_name, union_quota
FROM club_union_info
WHERE owner_guuid = ? AND status = 'used';
```

### 6.2 定位盟主俱乐部

`club_guuid_info.account_id` 是创建者的 `tbl_Account.id`，不是 guuid：

```sql
SELECT c.club_guuid, c.club_name, c.union_id, c.union_quota
FROM club_guuid_info c
JOIN tbl_Account a ON a.id = c.account_id
WHERE a.sm_guuid = ? AND c.club_status <> 'del';
```

### 6.3 盟主俱乐部成员（接口 3 的发放对象）

`club_mode=1` 用 `sm_club_join`，`club_mode=2/3` 用 `sm_club_join2`：

```sql
SELECT a.sm_guuid, a.sm_name, a.sm_club_gold, a.sm_club_gold2
FROM tbl_Account a
JOIN club_guuid_info c ON c.club_guuid = ?
WHERE find_in_set(c.club_guuid,
        CASE WHEN c.club_mode = '1' THEN a.sm_club_join ELSE a.sm_club_join2 END) > 0;
```

### 6.4 发放结果复核

```sql
-- 额度：池与俱乐部余额
SELECT union_quota FROM club_union_info WHERE union_id = ?;
SELECT union_quota FROM club_guuid_info WHERE club_guuid = ?;

-- 奖励流水（额度）
SELECT id, date, user_guuid, user_name, user_quota, club_guuid, remark, opter_name
FROM club_history_info
WHERE opt_type = '额度奖励'
  AND club_guuid IN (?, ?)
ORDER BY id DESC LIMIT 20;

-- 奖励流水（积分）
SELECT id, date, user_guuid, user_name, user_gold, club_guuid, remark, opter_name
FROM club_history_info
WHERE opt_type = '积分奖励' AND club_guuid = ? AND user_guuid = ?
ORDER BY id DESC LIMIT 20;
```

> 接口 3 返回 `pending` 的玩家在补发前查不到上面的行，补发后才会出现；不要用"查不到"直接判定失败。
>
> 目标侧额度行（`AddUnionQuota` 写入）的 `opter_name` 落库为空，展示/对账时按 `opter_guuid` 关联 `tbl_Account.sm_name`；授信记录接口已在 SQL 里补全。

### 6.5 发放总额统计

平台奖励与联盟内部划转分开统计，避免同一笔钱被算两次：

```sql
-- ① 平台给某联盟池发放的奖励总额（API1，分）
SELECT SUM(user_quota)
FROM club_history_info
WHERE club_guuid = ?                    -- club_union_info.club_guuid（联盟自己的俱乐部）
  AND opt_type = '额度奖励'
  AND remark LIKE '联盟池奖励%';

-- ② 某盟主俱乐部收到的奖励总额（API2，分）
SELECT SUM(user_quota)
FROM club_history_info
WHERE club_guuid = ?                    -- 目标盟主俱乐部
  AND opt_type = '额度奖励'
  AND remark NOT LIKE '联盟池%';

-- ③ 某俱乐部玩家积分奖励总额（接口 3，元）
SELECT SUM(user_gold)
FROM club_history_info
WHERE club_guuid = ? AND opt_type = '积分奖励';
```

> ① 是平台注资，② 是联盟内部划转（池 −N、俱乐部 +N），③ 是平台发筹码；三者口径不同，不要直接相加。

## 7. 错误文案总表

| 文案 | 出现位置 |
| --- | --- |
| `无权限` | 三个新命令，调用者不是后台 |
| `联盟不存在` | 接口 1、2 |

## 8. 边界与调用约束

1. **只发正数**：三个新命令都不接受 0 和负数；扣减、冲正走 `增加_联盟_额度` / `授信_联盟_额度`（负数），流水类型仍是老类型。因此 `额度奖励` / `积分奖励` 的统计是**发放毛额**，冲正不会冲减它，运营对账时要把老类型负数单独看。
2. **接口 3 不动额度**：玩家积分在带入时按现有模型扣俱乐部 `union_quota`；后台不要指望"发了奖励额度就减少"。
3. **接口 3 不校验额度**：允许发超过当前额度的积分，玩家带入时才会报"该俱乐部额度不足"；如运营要求强约束，需另行确认（本期不做）。
4. **批量上限 50**：超过请分批；单次请求内逐人加载实体，人数越多耗时越长。建议 20 人一批，降低 HTTP 超时概率。
5. **不做整批回滚**：接口 3 部分失败时已成功的玩家不回退，后台按 `failed` 重试即可；`pending` 不是失败，不要重发。
6. **超时不要直接重试**：后台 HTTP 超时后服务端可能已经处理完。先查 `club_history_info`（`opt_type='积分奖励'`、`user_guuid`、`club_guuid`）确认；对返回 `pending` 的玩家，**离开房间前一律不重发**（查不到流水不代表没发放），离开后再核对；后台用自己的操作单号做幂等记录。
7. **离线可用**：三个接口都直接改内存 + 落库，玩家离线也能发放；推送只在在线时送达。房间内玩家走待补，离线玩家直接入账。
8. **不保证并发安全**：单进程单线程，依赖调用约束；不要并发对同一联盟/俱乐部重复发放。
9. **审计**：`club_history_info.opter_guuid` / `opter_name` 记后台账号，按 `opt_type` 可区分奖励与常规授信/上分。
10. **参数类型**：`union_id` / `owner_guuid` / `club_id` 一律传字符串，金额传 JSON 整数；服务端未做宽松类型归一（`club_id` 传数字会报"俱乐部不存在"）。
