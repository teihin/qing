# 俱乐部金币与钻石-客户端接口文档

> **文档定位**：金币 / 钻石相关**客户端接口**的长期维护文档，后续新增同类接口（不限兑换/消费）在本文件追加章节。
> **服务端设计**：见《俱乐部金币与钻石设计说明.md》。
> **版本**：v1（2026-10-26）金币兑换钻石（有密码/无密码两种入口）；v1.1 `玩家_消费_命令` 支持钻石消费；v1.2 牌桌消费与加时支持钻石；**v1.3 新增金币/钻石两个流水查询接口（§3.8 / §3.9）**。

---

## 1. 通用约定

### 1.1 金币兑换的两个入口（二选一，客户端自定）

| | **方式 A（有密码，推荐）** | **方式 B（无密码）** |
| --- | --- | --- |
| 入口 | Hall 命令 `调用_方法_Exchange2` | Account 直连 `reqExChange2(target_guuid, money_value, money_type)` |
| 密码 | **需要** `user_pwd`（登录密码，服务端 MD5 校验） | **不需要** |
| 单笔限额 | 受 `exchange2_limit_num`（50000）/`exchange2_low_num`（1）约束 | 不校验 |
| 客户端版本 | 低于 `limit_version` 直接失败 | 不校验 |
| 交易黑名单 | 校验（`usr_hash_info`） | 不校验 |
| 弹窗形态 | 需要密码输入框 | 只要"确认兑换" |

> **两者共用同一套兑换实现与业务校验**：汇率（`gold_to_stone`）、`money_value > 0`、币种 `gold`、目标 `非俱乐部`、金币余额、钻石逆向兑换禁止 —— 这些在两种方式下完全一致，差别只在"外层风控"（密码/限额/版本/黑名单）。
> **金币消费（§3）只有一个入口**：Hall 命令 `玩家_消费_命令`，没有有/无密码之分。

### 1.2 结果回包

- 兑换结果**统一看 `onExChange(INT32)`**；方式 A 额外有 Hall 命令同步响应（`0x200` + 空 `result`，部分失败分支也是 `0x200`），**只是"命令已受理"，不要用它判断成败**；方式 B 没有同步响应。
- 消费结果**看 Hall 命令的同步响应** `ret_code`（`0x200` 成功 / `0x301` 失败），没有独立推送。

### 1.3 返回码（`onExChange`，兑换用）

| 码 | 常量 | 含义 | 出现场景 |
| --- | --- | --- | --- |
| `0x200` | `EC_OK` | 成功 | A / B |
| `0x301` | `EC_FAILED` | 失败（参数非法、功能未开启、超限、被拒绝等） | A / B |
| `0x302` | `EC_NO_MONEY` | 金币不足 | A / B |
| `0x307` | `EC_NO_PWD` | 未传密码 | 仅 A |
| `0x308` | `EC_PWD_ERR` | 密码错误 | 仅 A |

> 兑换失败**不会**产生任何货币变动（服务端先校验再执行）。

### 1.4 记录

- 兑换成功写 `usr_exchange_info`，「记录」页通过 `reqGetExchangeInfo` 查询（§4.1），`type='金币兑换钻石'`；
- 消费不写该表：**Hall 侧**金币消费写 `usr_cash_water`、钻石消费写 `usr_consume_info`（§3.5）；**牌桌侧**金币与钻石都写 `usr_cash_water`，用 `money_type` 字段区分（§3.6）。**客户端记录页不展示**，仅运营/后台可查。

## 2. 金币兑换钻石（v1）

- **判定规则**：`target_guuid` 传**自己的 guuid** 时，服务端执行"货币兑换"；传他人 guuid 是转账（与本文档无关）。
- 两种入口不需要新增命令或字段，按下列参数调用。

### 2.1 参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `target_guuid` | string | 是 | **填自己的 guuid**（兑换模式标志） |
| `money_value` | int | 是 | **要消耗的金币数量**（整数，必须 > 0）。服务端按汇率做乘法得到钻石数，不做除法取整 |
| `money_type` | string | 是 | 固定格式 `"gold,非俱乐部"`：前面是支付币种（`gold`=玩家金币），后面是目标（必须是字面量 `非俱乐部`；**传俱乐部 ID 会被拒绝**） |
| `user_pwd` | string | 仅方式 A | 登录密码（明文传入，服务端 MD5 校验） |
| `client_version` | string | 仅方式 A | 10 位版本号（`年月日+序号`，如 `0001010101`） |
| `context` | string | 否（仅 A） | 透传上下文 |

> **`money_type` 必须带英文逗号**（`"gold,非俱乐部"`）。这是研发约束，服务端按逗号解析、不做容错；传错（如只传 `"gold"`）会失败。
> **逆向兑换已禁止**：传 `"stone,..."`（钻石/房卡换金币）一律失败，客户端不要提供该入口。
> ⚠️ 兑换的 `money_type`（`"gold,非俱乐部"`）与消费的 `money_type`（`gold` / `stone`）**格式不同**，不要互相复用常量。

### 2.2 汇率与档位（`gold_to_stone = 100`）

| 钻石档位 | 消耗金币（= 传给 `money_value` 的值） |
| --- | --- |
| 100 | 1 |
| 200 | 2 |
| 500 | 5 |
| 1000 | 10 |
| 2000 | 20 |
| 5000 | 50 |
| 10000 | 100 |
| 20000 | 200 |

> 汇率由服务端配置（`d_halls` 的 `gold_to_stone`）决定，客户端**不要硬编码换算**；底部文案"兑换 100 钻石需消耗 1 金币"按当前配置撰写，改配置时文案与档位换算需同步。
> 汇率**热生效**（每次兑换请求服务端都会重读配置），改完配置不需要重启；但客户端文案仍需同批发版。

### 2.3 调用示例

**方式 A（有密码）**

```text
reqHallCommand(
    header        = "调用_方法_Exchange2",
    target_guuid  = 我的 guuid,            # 例 864747
    money_value   = 5,                     # 消耗的金币数（500 钻）
    money_type    = "gold,非俱乐部",
    user_pwd      = 登录密码,
    client_version= "0001010101",
    context       = "exchange_dialog"
)
# 同步响应 0x200 + 空 result（不代表兑换成功）
# 结果：onExChange(0x200 / 0x301 / 0x302 / 0x307 / 0x308)
```

**方式 B（无密码）**

```text
reqExChange2(
    target_guuid = 我的 guuid,             # 例 864747
    money_value  = 5,                      # 消耗的金币数（500 钻）
    money_type   = "gold,非俱乐部"
)
# 无同步响应
# 结果：onExChange(0x200 / 0x301 / 0x302)
```

### 2.4 失败场景对照

| 场景 | `onExChange` | A | B |
| --- | --- | --- | --- |
| 汇率配置为 0（功能未开启） | `0x301` | ✔ | ✔ |
| `money_value` ≤ 0（负数/零） | `0x302`（A 的命令层先拦截）/ `0x301` | ✔ | ✔（无货币变动） |
| `money_value` 低于下限或高于上限 | `0x301` | ✔（1~50000） | — |
| `money_type` 不是 `gold` 或后半段不是 `非俱乐部` | `0x301` | ✔ | ✔ |
| 传 `stone`（钻石换金币，**已禁止**） | `0x301`，货币不变 | ✔ | ✔ |
| 未传密码 / 密码错误 | `0x307` / `0x308` | ✔ | — |
| 客户端版本低于 `limit_version` | `0x301`（同步响应带"当前版本失效…"） | ✔ | — |
| 账号被加入交易黑名单 | `0x301` | ✔ | — |
| 金币不足 | `0x302` | ✔ | ✔ |
| 成功 | `0x200` | ✔ | ✔ |

## 3. 玩家消费：`玩家_消费_命令`（v1.1 支持钻石）

- **命令名**：`玩家_消费_命令`（Hall 命令，`reqHallCommand`）
- **兼容性**：不传 `money_type` 时与原用法完全一致（金币），老客户端无需改动。

### 3.1 参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | 固定 `"玩家_消费_命令"` |
| `consume_type` | string | 是 | 业务类型（如 `看数据`），写入流水；**超过 20 字按 20 字截断**（服务端截断，不报错） |
| `money` | int | 是 | **金币消费 = 分**（`50` = 0.5 元）；**钻石消费 = 钻石个数**（`20` = 20 钻）；必须 ≥ 0 |
| `money_type` | string | 否 | 白名单：不传 / `gold` / 空串 = 金币；`stone` = 钻石；**其它值返回失败**（不会猜测） |
| `context` | string | 否 | 透传 |

> ⚠️ **同一个 `money` 参数，两种币种单位不同**：金币按"分"、钻石按"个"。这是最容易联调出错的点，传参处必须显式区分。

### 3.2 单次上限

| 项 | 值 |
| --- | --- |
| 单次最大金额 | `player_consume_max`（服务端配置，**缺省 100000**） |
| 含义 | 金币消费时 100000 = 1000 元；钻石消费时 100000 = 100000 钻 |
| 超限 | `0x301` 失败，不扣任何货币 |

### 3.3 调用示例

```text
# 金币消费（原用法，完全不变）
reqHallCommand('{"header":"玩家_消费_命令","consume_type":"看数据","money":50}', "玩家_消费_命令");

# 钻石消费（新增）
reqHallCommand('{"header":"玩家_消费_命令","consume_type":"看数据","money":20,"money_type":"stone"}', "玩家_消费_命令");
```

### 3.4 返回与失败场景

成功返回 `0x200`（`result='{}'`）；失败返回 `0x301`。**没有独立推送**，结果以同步响应为准；余额以账号属性为准。

| 场景 | 返回 | 货币变动 |
| --- | --- | --- |
| 金币消费成功 | `0x200` | 金币按"分"扣减（`gold`+`gold2`） |
| 钻石消费成功 | `0x200` | 钻石按"个"扣减 |
| `money` < 0 | `0x301` | 无 |
| `money_type` 非白名单（`"STONE"`、`"gold,非俱乐部"` 等） | `0x301` | **无**（不会退化成扣金币） |
| `money` 超过单次上限 | `0x301` | 无 |
| 钻石不足 | `0x200` | **扣到 0 为止**（与金币"清零继续"口径一致） |
| 金币不足 | `0x200` | **扣到 0 为止**（原行为，未改） |
| `money = 0`（钻石） | `0x200` | 无；且不写流水 |
| `money = 0`（金币） | `0x200` | 无；仍会写一条 0 金额流水（原行为） |
| boss/运营账号（`level ≥ 99`）钻石消费 | `0x200` | **不扣、不写流水**（`decStoneNumber` 对 boss 空转） |

> **余额不足回 `0x200` 是本接口的既有语义**：客户端**不要**按"请求金额"本地扣减，务必以属性（`gold`/`gold2`/`stone`）刷新后的值为准，否则界面会与真实余额不一致。

### 3.5 流水（客户端不可见，供运营/后台）

| 币种 | 表 | 关键字段 |
| --- | --- | --- |
| 金币 | `usr_cash_water` | `option_type='消费'`、`remark4=consume_type`、`add_money=-money`（分） |
| 钻石 | `usr_consume_info` | `option_type='消费-<consume_type>'`、`money_type='stone'`、`money_number=-money`、`total_money=扣后余额` |

> 客户端「记录」页只查 `usr_exchange_info`（兑换/转账）；**消费流水用下面 §3.8 / §3.9 两个查询接口**（金币、钻石分开）。

### 3.6 牌桌通道（房间内）消费：同一个 header，另一条通道

对局中客户端调用的是**房间命令通道**（`reqGameCommand`），header 同样是 `玩家_消费_命令`，参数与 §3.1 完全一致（`money_type` 白名单、`stone` 时 `money`=钻石个数）。

| 差异点 | Hall 通道（§3.1） | 牌桌通道（本节） |
| --- | --- | --- |
| 免费逻辑 | 无 | `强制秀牌` / `看下一张牌` 每状态首次免费（服务端 `consum_num_map`） |
| 钻石流水 | `usr_consume_info` | `usr_cash_water`（`money_type='stone'`、`remark1=房间号`） |
| 余额不足 | 钻石扣到 0 仍成功 | 同为扣到 0 仍成功 |
| 返回 | `0x200` / `0x301` | 同（`GC_OK` / `GC_FAILED`） |

> 牌桌侧的 `money_type` 白名单与单位规则和 Hall 侧完全一致；不传仍按金币处理。

### 3.7 对局加时：`延长时间_命令`

- **命令名**：`延长时间_命令`（房间命令通道）
- **参数**：`money_type`（白名单，缺省/空/`gold`=金币，`stone`=钻石；其它失败）；无 `money` 参数（价格由服务端决定）

| 本局第几次加时 | 金币路径（原逻辑，未改） | 钻石路径（新增） |
| --- | --- | --- |
| 第 1 次 | 免费，+20 秒 | 免费，+20 秒 |
| 第 2 次 | 2 金币，+20 秒 | **200 钻**，+15 秒 |
| 第 3 次 | 4 金币，+20 秒 | **400 钻**，+10 秒 |
| 第 4 次及以后 | 8/16/32 金币（封顶 32），+20 秒 | **拒绝（`0x301`）** |

- 钻石不足 → `0x301`，不扣钻；
- 加时流水写 `usr_cash_water`（`remark4='延长时间'`、`money_type` 标币种）；
- 次数按"本局累计"计（金币与钻石共用同一计数）。

### 3.8 金币消费流水：`查询_玩家_现金流水`（存量接口，结构不变）

- **参数**：`user_id`（玩家 guuid）、`count`（默认 10）、`page`、`context`
- **推送路由**：`ListPlayerCashWater`
- **行字段**：`date`（日期+时间）、`option_type`、`user_name`、`user_guuid`、`remark1`、`remark2`、`add_money`、`new_money`；外层 `number`/`count`/`context`
- **范围**：最近 8 天（今天 ~ 今天-7）；服务端已排除中奖/战绩/活动等类型
- **2026-10-26 变更**：服务端只返回**金币**行（`money_type='gold'`），不再混入钻石消费；**返回结构未变**，老客户端无影响
- **单位**：`add_money` 为**元**（两位小数，负数=支出），`new_money`=变动后金币余额

### 3.9 钻石消费流水：`查询_玩家_钻石流水`（新增）

- **命令名**：`查询_玩家_钻石流水`（Hall 命令）
- **参数**：与 3.8 完全一致（`user_id`、`count`、`page`、`context`）
- **推送路由**：`ListPlayerStoneWater`（新路由，客户端需新增处理）
- **行字段**：

| 字段 | 说明 |
| --- | --- |
| `date` | 日期+时间 |
| `option_type` | `消费`（Hall 与牌桌消费）、`延长时间`（加时） |
| `remark4` | **消费类型**：Hall 为客户端传的 `consume_type`（如 `换头像`、`看数据`）；牌桌为 `强制秀牌`/`看下一张牌` 等；加时为 `延长时间` |
| `remark5` | 明细文案，如 `用100钻-余200钻`（消费行与加时行都会返回；Hall 行为 `用<请求>钻-余<余额>钻`） |
| `remark1` / `remark2` / `remark3` | 牌桌行：房间号 / 房间名 / 局数；Hall 行为空 |
| `add_money` | **本次钻石变动（钻石个数，一律负数=消耗，按实际扣减额）**；消费与加时符号一致（2026-10-26 修正前加时为正，已改） |
| `new_money` | 变动后钻石余额 |
| `money_type` | 固定 `stone` |

- **范围**：最近 8 天（与金币流水一致）；`add_money=0` 的行不返回
- **覆盖**：牌桌消费/加时 + Hall 侧钻石消费（换头像等）
- **历史缺口**：本次上线（重启）之前只记在扣费台账里的钻石消费**不会**出现在此列表
- **示例**：

```text
reqHallCommand('{"header":"查询_玩家_钻石流水","user_id":"864747","count":10,"page":0}', "查询_玩家_钻石流水");
# 同步响应 0x200（result 为空壳）；列表经 ListPlayerStoneWater 推送
```

> 两个接口都**不校验** `user_id` 归属（与现状一致）；上线顺序必须是**服务端先上**，否则客户端调用会得到"命令不存在"（`0x301` 且无 `result`）。

## 4. 相关接口

### 4.1 兑换/转账记录：`reqGetExchangeInfo(page)`

- 参数：`page`（int，0 起，每页 15 条）；
- 结果：`onGetExchangeInfo(INT32)`，列表经现有记录通道下发（`usr_exchange_info`）；
- 兑换产生的记录 `type='金币兑换钻石'`；列表已自动排除 `提取红利` 流水。

### 4.2 余额属性

- `gold`（金币，整数元）、`gold2`（金币，分）、`stone`（钻石，整数）随账号属性下发；
- 兑换/消费成功后服务端主动同步，客户端无需再发查询命令。

## 5. 客户端注意事项

| # | 事项 |
| --- | --- |
| 1 | 兑换/消费弹窗顶部余额直接用账号属性，不要本地累加；以服务端同步后的属性为准 |
| 2 | 兑换：`money_value` 传**金币数**（消耗量），不要传钻石数；钻石数 = 金币数 × `gold_to_stone`，由服务端计算 |
| 3 | 兑换：`money_type` 必须 `"gold,非俱乐部"`（英文逗号 + 字面量 `非俱乐部`）；研发约束，服务端不做容错 |
| 4 | **兑换入口二选一**：要密码/风控走 A（`调用_方法_Exchange2`）；只要一键兑换走 B（`reqExChange2`） |
| 5 | 选 A 必须传 `user_pwd` 与 `client_version`；选 B 无密码、无单笔限额，客户端自行防连点 |
| 6 | 兑换结果**只认 `onExChange`**；A 的同步响应是空壳，不能据此提示成功 |
| 7 | **消费与兑换的 `money_type` 格式不同**：消费是 `gold`/`stone`，兑换是 `"gold,非俱乐部"`；不要复用常量 |
| 8 | **消费的 `money` 单位随币种变化**（金币=分、钻石=个）；金币消费传 `50` 是 0.5 元，钻石消费传 `50` 是 50 钻 |
| 9 | 消费**余额不足仍返回 `0x200`**（扣到 0 为止）；不要按请求金额本地扣减，按属性刷新 |
