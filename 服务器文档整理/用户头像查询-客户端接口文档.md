# 用户头像查询 — 客户端接口文档

状态：2026-11-18 服务端已实现并上传测试服，待重启 baseapp 后联调；客户端批量改造待接入

## 1. 用途与背景

客户端列表页（俱乐部成员、全量玩家、战绩、排行等）需要按玩家 ID 显示头像。

- 头像不是图片 URL，而是**头像索引**：`Account.photo`，取值 `1~100`，客户端对应本地 `avatars/头像` 资源。
- 单查接口 `查询_用户_头像` 是早期遗留接口：一次只能查一个 ID，且是推送式回包。列表页 N 行就是 N 次请求，实测单账号同一秒最多 8 次，单日 1366 次请求只命中 64 个不同玩家。
- 本方案新增 `查询_用户_头像_批量`，客户端把头像一个批次合并成一次请求；单查接口保持原样，兼容老客户端。

## 2. 单查（遗留接口，保留兼容）

请求：

```json
{"header": "查询_用户_头像", "user_id": "819586"}
```

成功时服务端推送 `UserList`（不是命令回包）：

```json
{"id": 819586, "photo": "76"}
```

已知行为（客户端需知）：

- `photo` 为空或非法时，客户端 `NormalizeAvatarIndex` 会回退到 `"1"`。
- 7~9 位 ID 静默无回包；≥10 位走 `robot_name` 配置（当前线上无此配置）。
- 命令层会额外回一条 `{"context":"查询_用户_头像","result":}`，**不是合法 JSON**，客户端不要依赖这条回包。

## 3. 批量查询 `查询_用户_头像_批量`

### 3.1 请求

通道：客户端 `reqHallCommand(param, "P@查询_用户_头像_批量")`。

```json
{
  "header": "查询_用户_头像_批量",
  "user_ids": ["819586", "333333", "580629"],
  "context": "avatar:xxxx"
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `user_ids` | 是 | 玩家 ID 数组；也兼容逗号串 `"819586,333333"`。传客户端界面上显示的 ID 即可（靓号会自动反解成真实 guuid） |
| `context` | 否 | 原样带回。使用 `P@` 形式时服务端会把 `P@` 前缀剥离后再放进 `context` |

限制：

- 去重、去首尾空白后按原顺序处理；
- **单次最多 100 个**，超出返回失败，由客户端分片；
- 非纯数字的 ID 不会查库，按“查不到”返回空头像（不整单失败）。

### 3.2 成功回包

`onHallCommand(0x200, ...)`：

```json
{
  "context": "查询_用户_头像_批量",
  "result": {
    "count": 3,
    "list": [
      {"id": "819586", "photo": "76"},
      {"id": "333333", "photo": "53"},
      {"id": "580629", "photo": ""}
    ]
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `result.count` | 本次返回条数，等于去重后的请求条数 |
| `result.list[].id` | **逐字回显请求里的原始 ID**（客户端传靓号就回靓号），用于对齐客户端头像缓存 |
| `result.list[].photo` | 头像索引字符串；查不到/非法 ID 给 `""`，客户端回退默认头像 |

约定：

- 请求里每个去重后的 ID 都会出现在 `list` 里，顺序与请求一致，客户端不需要判空。
- 不回其它玩家属性，只回头像。

### 3.3 失败回包

`onHallCommand(0x301, ...)`：

```json
{"context": "查询_用户_头像_批量", "result": {"error": "单次最多 100 个玩家，请分批查询"}}
```

| 场景 | error |
| --- | --- |
| 参数不是 JSON 对象 | `参数错误` |
| `user_ids` 为空 | `请选择玩家` |
| 去重后超过 100 个 | `单次最多 100 个玩家，请分批查询` |
| 数据库查询失败 | `查询失败，请稍后重试` |

## 4. 客户端接入建议

1. 头像管理器不再在 `AddWaitFreshImage2Catch` 里立即发单查，而是把待取 ID 放进 set。
2. 50ms 去抖后取最多 100 个发一次批量请求；超过 100 个分片串行发送。
3. 回包按 `id` 写 `mapID2Avatar`，并回填 `mapID2ImageSave` 中等待该 ID 的图片节点。
4. 已在 `mapID2Avatar` 或正在请求中的 ID 不重复加入。
5. 批量失败时降级：可按原单查逐个补，或直接显示默认头像，不能阻塞列表渲染。
6. 单查接口继续保留，老客户端和老路径不受影响。

## 5. 口径与已知限制

1. **头像是索引不是 URL**：当前线上 93 个账号的 `sm_photo` 都是 1~2 位数字。若历史库/后台写入 URL，客户端会按非法索引回退到默认头像。
2. **系统号占位**：6 位且在 `d_users.system_guuid` 里的 ID，服务端沿用单查的历史占位 `http://localhost/server/pp/100N.jpg`，客户端会归一到默认头像；不要真去加载该地址。
3. **boss 号**：与单查一致走 `d_halls.boss_name`（当前是空映射），返回空串，客户端显示默认头像；不会读库里的 `sm_photo`。
4. **机器人号**：≥10 位 ID 需要昵称才能查 `robot_name`，批量不带昵称，统一返回空；线上没有此类 guuid。
5. **靓号**：`user_ids` 不在 `pretty_no.RealParam` 的键名白名单里，服务端用 `pretty_no.RealID()` 逐个反解。号池缓存 60 秒 TTL，刚重启后的极短窗口内可能反解不到，按真实 ID 直查也能命中，不影响正常玩家。
6. **无服务端缓存**：每次批量都查一次库，走 `idx_sm_guuid`；当前数据量下开销可忽略。
7. **索引非唯一**：`sm_guuid` 是普通索引，重复行优先取非空头像，不会像单查那样因多行直接丢弃。

## 6. 实现落点

- `scripts/base/Hall.py`：`_actListUserPhotoBatch` / `_closeListUserPhotoBatch` / `_userPhotoValue` / `_userPhotoBatchFail`，命令注册名 `查询_用户_头像_批量`。
- `scripts/server_common/pretty_no.py`：新增 `RealID(value)`（靓号→真实 guuid，找不到原样返回）。
- 无 DDL、无新增表、无新增客户端推送路由。

## 7. 测试清单

1. 0 个 / 1 个 / 2 个 / 100 个 ID；101 个拒绝。
2. 数组与逗号串两种传法结果一致。
3. 重复 ID 去重，回包顺序与请求一致。
4. 靓号 `333333` 与真实 ID 混合：`id` 逐字回显，`photo` 正确。
5. 不存在 ID、空 photo、非法 ID → `photo` 为 `""`，不整单失败。
6. boss 号、`system_guuid` 号与单查结果一致（空串/占位 URL）。
7. 同一批 ID 分别调单查和批量，正常玩家 `photo` 一致。
8. 客户端成员列表/全量玩家列表：一页请求数从 N 降到 1，头像显示正确。
9. 数据库异常时回 `GC_FAILED`，客户端不挂起。
