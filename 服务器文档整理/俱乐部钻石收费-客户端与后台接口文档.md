## 1. 通用说明

### 1.1 本期没有新增客户端/后台命令

房间钻石收费由**服务端自动执行**（建房时、每秒心跳），客户端**不需要调用任何扣费命令**。本期只复用两个已有接口读写价格，外加一张收费明细表：

| # | 接口 / 数据 | 通道 | 用途 | 是否新增 |
| --- | --- | --- | --- | --- |
| 1 | `查询_哈希_信息` | 客户端 `reqAccountCommand` | 读 `消费钻石价格` 价目表（含本收费项） | 否（已有） |
| 2 | `设置_哈希_信息` | 客户端 `reqAccountCommand` | 运营改价（沿用现有行为，本期不加门禁） | 否（已有） |
| 3 | 服务端自动扣费 | 无客户端调用 | 建房扣一次 + 首局开局后每 `realtime_play_seconds` 扣一次 | 是（服务端内部） |
| 4 | `查询_俱乐部_钻石流水` | 客户端 `reqHallCommand` | 群主看资产账本（新增 `钻石房间扣费` 类型） | 否（已有，白名单加类型） |
| 5 | `club_charge_log` SQL | 后台数据库 | 收费事件明细 / 对账 | 是（新表） |

> **不要**为扣费新增客户端协议，也不要让客户端调 `玩家_消费_命令` 扣本项目——服务端已经从俱乐部钻石池扣，客户端再扣就是双扣。
>
> 2026-11-10 补充：**入座收费**同样不新增客户端/后台命令，只新增建房规则 token、比例 hash 和提示，见 §11。

### 1.2 响应与通道（与现有账号/大厅命令一致）

- 客户端读价：`reqAccountCommand(param, context)`；`param` 为 JSON 字符串，必须含 `"header"`；
- 客户端命令结果：`onAccountCommand(ret_code, context)`；`ret_code=512` 成功、`769` 失败；
- 读价的内容不在 `ret_result` 里，而是服务端另推一条客户端消息：

```json
{"UserHashInfo":{"key":"消费钻石价格","context":"club-fee-1","content":"<原始字符串>"}}
```

- 查不到行时推：

```json
{"UserHashError":{"context":"club-fee-1"}}
```

- 后台 HTTP 走 `/hall/command`，**不能**调 `查询_哈希_信息` / `设置_哈希_信息`（它们是 Account 命令）；后台请直接读写 `usr_hash_info` 或走管理页。

### 1.3 实现文件

- `scripts/server_common/club_room_fee.py`：价格缓存、建房/心跳扣费、提示、解散；
- `scripts/server_common/club_charge.py`：统一收费入口（扣池 + 写 `club_charge_log`）；

## 2. 价格：`usr_hash_info['消费钻石价格']`

### 2.1 数据定义

| 项 | 取值 |
| --- | --- |
| `hash_key` | `消费钻石价格`（测试服既有价目表，**不新建 key**） |
| 收费项目 | `俱乐部实时房间时长费` |
| 内容 | **base64(URL 编码) 后的 JSON**（与价目表其它项目一致）：解码后 `{"项目名": 钻石数, ...}` |
| 单位 | 钻石个数（整数），不是分、不是金币 |
| 0 / 缺省 | 显式 0 = 免费；项目缺失/内容非法 = 回落 `d_halls.config["room"]["club_realtime_room_stone_fee"]`（当前 0） |
| 上限 | 1,000,000（代码 clamp） |

解码后的示例（只列相关两项，线上还有其它项目）：

```json
{"创建俱乐部":10000,"俱乐部实时房间时长费":100}
```

### 2.2 客户端读价 `查询_哈希_信息`

请求：

```json
{
  "header": "查询_哈希_信息",
  "key": "消费钻石价格",
  "context": "club-fee-1"
}
```

服务端推送（`onMessage`）：

```json
{
  "UserHashInfo": {
    "key": "消费钻石价格",
    "context": "club-fee-1",
    "content": "JTdCJTIyJUU1JTg4JTlCJUU1JUJCJUJBJUU0JUJGJUIxJUU0JUI5JTkwJUU5JTgzJUE4JTIyJTNBMTAwMDAlMkMlMjIlRTQlQkYlQjElRTQlQjklOTAlRTklODMlQTglRTUlQUUlOUUlRTYlOTclQjYlRTYlODglQkYlRTklOTclQjQlRTYlOTclQjYlRTklOTUlQkYlRTglQjQlQjklMjIlM0ExMDAlN0Q="
  }
}
```

客户端处理（顺序不能反）：

1. 取 `content`；
2. `base64 decode` 得到 URL 编码串（测试服实测是 `base64(URL 编码 JSON)`）；
3. `decodeURIComponent` 得到 JSON；
4. `JSON.parse`；
5. 取 `["俱乐部实时房间时长费"]`，缺失按 0 展示为"未开启"。

> 服务端兼容明文 JSON / 仅 URL 编码 / base64(URL 编码) 三种写法；客户端按后台实际存储的 base64(URL 编码) 处理即可。

> 查不到 `消费钻石价格` 行时，服务端推 `UserHashError`；此时服务端按默认值 0 计费（不收费）。

### 2.3 后台改价

**推荐：后台管理页直接编辑 `消费钻石价格`**，新增/修改项目 `俱乐部实时房间时长费`，保持整份内容的 **base64(URL 编码)** 格式（管理页会处理）。

如果走 `设置_哈希_信息`（Account 命令）：

```json
{
  "header": "设置_哈希_信息",
  "key": "消费钻石价格",
  "content": "<base64(URL 编码) 后的完整 JSON>",
  "context": "club-fee-set-1"
}
```

约束：

- 本期**不新增** boss/`level>=99` 门禁，`设置_哈希_信息` 保持现有行为；
- `content` 是**整份价目表**，必须包含其它项目，不能只写本项；内容里不要带单引号（该命令直接拼 SQL）；
- 该 key 必须只有 1 行：多行时 `设置_哈希_信息` 会因 `len(result) > 1` 静默不写；出现多行先按方案文档 §5.5.5 去重；
- 服务端不校验内容格式；写错会走"格式错误 → 回落默认值 + ERROR 日志"；
- 改完最多 **10 秒**进入服务端缓存；已存在房间的**下一个周期**按新价，不追溯。

> 不建议手工 SQL 改这个 key：必须自己把整份内容重新生成 **base64(URL 编码)**，容易写坏其它项目。

### 2.4 兜底默认值

`scripts/data/d_halls.py` → `config["room"]`：

```python
"club_realtime_room_stone_fee": 0
```

- 价目项缺失/内容非法时用它；当前 0 = 不收费；
- 它只作默认值，**不是改价入口**；后台不要用 `设置_大厅_配置数据` 改它（该命令也改不到 `config`）。

## 3. 扣费规则（客户端展示口径）

| 项 | 口径 |
| --- | --- |
| 谁付费 | 房间所属俱乐部的**群主钻石池**（`club_agent_info.stone`），不扣玩家 |
| 联盟房 | 扣**总群主俱乐部**的池，不是成员俱乐部 |
| 开房 | 建房成功扣 1 次 |
| 周期 | **首局正式开局后**才开始计时，之后每 `realtime_play_seconds` 扣 1 次 |
| 未开局 | 只付开房费，不启动计时、不续费；未开局空房最多 2 小时后关闭 |
| 局中扣费失败 | 先提示、置待解散；**本局打完**再关房，不打断牌局 |
| 非局中扣费失败 | 立即提示 + 结算 + 关房 |
| 改价 | 最多 10 秒生效；已存在房间下一个周期按新价 |
| 退款 | 不退款、不按分钟折算 |
| 错过周期 | 只扣 1 次并顺延，不一次性补扣 |

示例（单价 100，周期 30 分钟）：

```text
T0        建房，扣 100
T0+10min  首局开局，开始计时
T0+40min  扣 100（第 2 笔）
T0+70min  扣 100（第 3 笔）
若一直无人开局：只扣 T0 的 100
```

### 3.1 余额不足提示

服务端向房内玩家推 `PromptInfo`（单播）：

| 场景 | 文案 |
| --- | --- |
| 联盟房（房间所属俱乐部有 `union_id`） | `联盟钻石池余额不足，房间解散` |
| 独立俱乐部 | `俱乐部钻石池余额不足，房间解散` |
| 联盟房（扣后余额 < 下一周期单价） | `联盟钻石池余额不足，下周期房间将解散`（提前提示） |
| 独立俱乐部（扣后余额 < 下一周期单价） | `俱乐部钻石池余额不足，下周期房间将解散`（提前提示） |

- 开房阶段余额不足：**不建房**，只打服务端 DEBUG 日志，不向群主推送；
- 周期阶段余额不足：局中等到本局结束，非局中立即关房；
- 关房沿用现有流程（`OverRoom` 结算 + `closeRoom`），客户端房间列表会收到"关闭"行，无需新协议。

## 4. 流水与对账

### 4.1 资产账本 `club_history_info`（余额以此为准）

每次扣费由 `AddOwnerStone` 写一行：

| 列 | 值 |
| --- | --- |
| `club_guuid` | 被扣的俱乐部（联盟房=总群主俱乐部） |
| `user_guuid` / `user_name` | 群主账号 |
| `user_stone` | `-单价`（负数） |
| `opt_type` | `钻石房间扣费` |
| `remark` | `扣费前→扣费后`（如 `1000→900`） |
| `room_id` | 房间号；房间类收费由 `AddOwnerStone` 写入（其它授钻/兑换为空） |

群主「钻石流水」页面（`查询_俱乐部_钻石流水`）已把 `钻石房间扣费` 加入白名单，能看到该行。

### 4.2 收费明细 `club_charge_log`（一次收费一行）

| 列 | 说明 |
| --- | --- |
| `date` | `YYYY-MM-DD HH:MM:SS` |
| `charge_type` | `房间时长费`（后续收费类型各占一个值） |
| `club_guuid` | 被扣俱乐部（联盟房=总群主） |
| `union_guuid` | 联盟 id；独立俱乐部为空 |
| `room_id` | 房间号 |
| `amount_stone` | 本次收费（正数） |
| `before_stone` / `after_stone` | 扣费前后池余额 |
| `opt_type` | `钻石房间扣费`（对应资产账本类型） |
| `reason` | `开房` / `周期` |
| `remark` | 预留 |

> `club_history_info` 是资产主账（余额/对账只认它）；`club_charge_log` 是收费事件明细。明细写失败时资产账本仍正确，服务端只打 ERROR，按账本人工补录。

### 4.3 后台查询 SQL

```sql
-- 当前价目表（base64(URL 编码) JSON）
select id, hash_key, hash_content from usr_hash_info where hash_key = '消费钻石价格';

-- 某个房间的收费明细
select date, charge_type, amount_stone, before_stone, after_stone, reason
from club_charge_log
where room_id = '123456'
order by id desc;

-- 某俱乐部按日/类型汇总
select date, club_guuid, charge_type, count(*) cnt, sum(amount_stone) cost_stone
from club_charge_log
where club_guuid = '<俱乐部ID>'
group by date, club_guuid, charge_type
order by date desc;

-- 两表核对（同一天同一俱乐部金额应一致）
select date, club_guuid, sum(amount_stone) charge_sum
from club_charge_log
where charge_type = '房间时长费'
group by date, club_guuid;
```

## 5. 客户端对接

1. **读价**：进入俱乐部房间列表/充值页时调一次 `查询_哈希_信息`（key `消费钻石价格`），解码后取 `俱乐部实时房间时长费`；建议本地缓存，不要每次刷新都拉。
2. **展示**：按"每 `realtime_play_seconds` 分钟 X 钻石，开房扣一次"展示；价格为 0 或项目缺失时显示"未开启"。
3. **不要扣玩家**：本项目由服务端扣俱乐部池，客户端**不要**调 `玩家_消费_命令` 扣同一项目，避免双扣。
4. **提示**：监听 `PromptInfo` 的两种文案；收到后房间即将解散（局中会等本局结束），按现有"房间关闭"逻辑处理即可。
5. **无新房间字段**：房间列表/牌桌不新增字段；价格由客户端从价目表读。
6. **无推送**：改价不推送，客户端按需重新拉价目表；服务端缓存最多 10 秒。

---

## 6. 后台对接

1. **建表**：执行 `res/server/database.sql` 中 `call create_club_invite_code();` 之前的 `club_charge_log` 建表（测试/线上各一次，老库不会自动建）。
2. **加项目**：在 `消费钻石价格` 里新增 `俱乐部实时房间时长费`，先填 `0`。
3. **调价**：观察一版无异常后，把项目值改成正式单价；最多 10 秒生效。
4. **核对**：`select hash_content from usr_hash_info where hash_key='消费钻石价格'`，确认只有 1 行且内容为 base64(URL 编码) JSON。
5. **写权限**：本期不新增门禁；价目表由后台写库/管理页维护，`设置_哈希_信息` 保持现状。
6. **对账**：`club_history_info` 看余额，`club_charge_log` 看收费事件；两表按日金额应一致。

## 7. 错误与日志

### 7.1 客户端可见

| 现象 | 触发 |
| --- | --- |
| `UserHashError` | `消费钻石价格` 行不存在 |
| `PromptInfo`：`联盟/俱乐部钻石池余额不足，房间解散` | 周期扣费失败 |
| `PromptInfo`：`联盟/俱乐部钻石池余额不足，下周期房间将解散` | 周期扣费成功，但扣后余额已不够下一周期（提前提示） |
| 房间列表出现"关闭" | 扣费失败关房（或正常到期） |

### 7.2 服务端日志（排查用）

| 日志 | 含义 |
| --- | --- |
| `[CLUB_FEE]价目表未配置 key=消费钻石价格，回落默认值 0` | 没有该 key，按默认值 |
| `[CLUB_FEE]价目项未配置 key=... item=...，回落默认值 0` | key 存在但缺项目 |
| `[CLUB_FEE]价目表格式错误 key=... item=...` | 内容不是合法 JSON（URL/明文都失败） |
| `[CLUB_FEE]价格刷新 ... value=100` | 读价成功 |
| `[CLUB_FEE]开房扣费失败关房 ...` | 建房时池不足，房间已关 |
| `[CLUB_CHARGE]扣费 club=... type=房间时长费 amount=... 前→后 room=... reason=开房/周期` | 扣费成功 |
| `[CLUB_CHARGE]insert log err: ...` | 明细表写入失败（资产账本仍正确） |

## 8. 口径与边界（验收用）

| 项 | 口径 |
| --- | --- |
| 生效模式 | 仅 `settle_mode=realtime`；fixed 房不扣 |
| 生效房型 | 仅 `roomClubID != '0'` 的俱乐部房；大厅房不扣 |
| 扣费池 | 房间所属俱乐部群主池；联盟房=总群主 |
| 开房 | 建房成功扣一次；手工建房路径（默认关闭）不扣开房费 |
| 未开局 | 不启动周期计时、不续费；这类房最多 2 小时后关闭 |
| 首局 | `round_count > 0` 后第一次 tick 启动计时 |
| 解散投票中 | 玩家已发起解散、房间未关：不扣新周期，等房间关闭 |
| 成员旧房 | 入盟后成员俱乐部的旧房：单价 > 0 时不建、不收开房费；周期费始终不扣（单价 0 沿用原建房行为） |
| 局中不足 | 等本局结束再关房；牌局不中断 |
| 改价 | 最多 10 秒进入缓存；已存在房间下一个周期生效 |
| 退款 | 不退、不折算 |
| 双扣 | 客户端不要对同一项目再扣玩家 |
| 明细失败 | 资产账本仍正确；`club_charge_log` 可能缺行，ERROR 日志，人工补录 |
| 手工/老房 | 首次被 tick 看到按"已过开房费"处理，不补扣 |
| 入座收费 | 仅 `俱乐部配分模式` + `special_rule` 含 `入座收费`；大厅/old 模式不接 |
| 入座比例 | `usr_hash_info['俱乐部积分对应钻石输赢比']`，默认 1:1；10 秒缓存 + 建房快照 |
| 入座结算 | 带入扣钻、结算按最终积分退回；不是按输赢差值重复扣 |

## 11. 补充功能：入座收费与钻石输赢同步（2026-11-10）

> 仅 `俱乐部配分模式`，且房间 `special_rule` 含 `入座收费`；大厅/old 模式不接。
> 不依赖 `settle_mode`：fixed / realtime 的俱乐部配分模式都覆盖。
> 不新增客户端/后台命令，不新增表/DDL。

### 11.1 客户端建房

客户端在原有建房参数 `special_rule` 中带：

```text
入座收费
```

- 不勾选：不传该 token，行为完全不变；
- 勾选：服务端开启钻石同步；
- 当前 `all_special_rule = ['默认所有']`，服务端不过滤；若某套配置是显式白名单，需加 `'入座收费'`。

### 11.2 比例数据

后台在 `usr_hash_info` 维护：

```text
hash_key     = 俱乐部积分对应钻石输赢比
hash_content = 0.1
```

| 项 | 说明 |
| --- | --- |
| 格式 | 纯小数字符串，如 `0.1`；不是 JSON、不是 URL/base64 |
| 默认 | 缺行/空/非法/负数 → `1.0` |
| 0 | 显式 `0` 表示不扣钻石 |
| 行数 | 只保留 1 行 |
| 生效 | Hall 每 10 秒缓存；建房时快照；老房不变，新房用新值 |
| 重启 | 改比例**不需要重启**；最多 10 秒后新建房生效 |

> 不要删行。`_loadData` 空结果不会清掉旧内存值；要恢复 1:1 请把值改成 `1.0`。

### 11.3 客户端可见行为

- 带入时：

```text
带入积分 × 比例 = 扣玩家钻石
```

- 结算时：

```text
最终退回积分 × 比例 = 加回玩家钻石
```

示例（比例 0.1）：

| 带入 | 带入扣钻 | 结算积分 | 结算退钻 | 净钻石 |
| --- | --- | --- | --- | --- |
| 100 | -10 | 80 | +8 | -2 |
| 100 | -10 | 120 | +12 | +2 |
| 100 | -10 | 0 | 0 | -10 |

- 钻石不足：

```json
{"PromptInfo": "钻石不足请兑换"}
```

- 审批带入时，钻石不足只弹这一条；俱乐部金币/额度不足才弹“该俱乐部额度不足”。
- 客户端不需要自己扣钻石，也不能再调 `玩家_消费_命令`，避免双扣。

### 11.4 后台/数据

- 扣钻写 `usr_consume_info`，`optionType='入座收费'`；
- 结算退钻写 `usr_consume_info`，`optionType='入座结算'`；
- **钻石变动本身**只写 `usr_consume_info`；俱乐部积分变动仍按原逻辑写 `club_history_info`；
- 不新增 `club_charge_log` 行（这是玩家个人钻石，不是俱乐部池收费）；
- 无新表、无新字段。

### 11.5 边界

- 仅俱乐部配分模式；`old俱乐部配分模式` 不接；
- 审批带入按“钱包 + 额度追加”的总额扣钻；
- 审批失败提示：钻石不足只弹“钻石不足请兑换”；俱乐部金币/额度不足弹“该俱乐部额度不足”；
- Boss `level >= 99` 不扣/不退；
- 比例精度四舍五入到整数钻石；
- 最终积分为负时不退钻，净损失等于带入冻结钻石；
- 启动后首次比例回调未返回时，新房可能按默认 1.0 建出，属于极短窗口。
