# 注册安全改造 · 完整方案

日期：2026-11-15
范围：客户端注册链路 + XuanManager 注册接口 + 限流/风控
前提：不加任何第三方验证码服务（自研拼图滑块），不加新的中间件依赖（复用现有 MySQL）

---

## 0. 结论

**推荐路线：自研拼图滑块 → 一次性票据 → 注册接口只认票据，三层防线叠加。**

一句话逻辑：验证码不是"注册前的一个装饰"，而是**注册的唯一入场券**。攻击者过不了滑块就拿不到票据，拿不到票据就建不了号。

配套两条铁律：

- **不做客户端可信校验**。客户端只负责采集"我拖到哪、怎么拖的"，判定全部在服务端。
- **不做强制一刀切**。上线用 `off → soft → enforce` 三段灰度，老版本客户端不会突然注册失败。

总工作量 **3.5 人日**：服务端 1.5 天 + 客户端 1 天 + 素材与联调 1 天。

四个动作，缺一个都拿不到号。

## 2. 三层防线

验证码只解决"脚本能不能自动注册"。真正让攻击者赔本的是三层叠在一起。

- **接入层**：HTTPS 强制、Caddy 级连接限速、蜜罐字段、IP 黑名单。
- **应用层（核心）**：拼图滑块、一次性票据、多维计数、日总量熔断。
- **业务层**：新号 24 小时限制交易、新人奖励延迟发放、代理拉新按"有效活跃"结算。

只做应用层，打码平台 1 分钱一次就能绕过；只做业务层，服务器会被刷爆。两层都得有。

## 4. 服务端设计

### 4.1 数据表（069 迁移）

不需要 Redis。注册量一天几百到几千，MySQL 完全扛得住，也少一个运维组件。

```sql
CREATE TABLE IF NOT EXISTS mgr_registration_ticket (
  id          CHAR(32)     NOT NULL,
  kind        ENUM('captcha','register') NOT NULL,
  answer_x    SMALLINT     NOT NULL DEFAULT 0 COMMENT '缺口正确 x（图片坐标）',
  tile_y      SMALLINT     NOT NULL DEFAULT 0,
  bg_index    SMALLINT     NOT NULL DEFAULT 0,
  shape_seed  INT          NOT NULL DEFAULT 0,
  ip_hash     CHAR(16)     NOT NULL DEFAULT '',
  risk_score  TINYINT      NOT NULL DEFAULT 0,
  used_at     DATETIME     NULL DEFAULT NULL,
  expires_at  DATETIME     NOT NULL,
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_expires (expires_at),
  KEY idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- `kind='captcha'` 是出题记录，`kind='register'` 是签发的注册票据；两种都用同一张表，消费时按 `used_at IS NULL` 判定。
- 消费必须原子：

```sql
UPDATE mgr_registration_ticket
SET used_at = NOW()
WHERE id = ? AND kind = ? AND used_at IS NULL AND expires_at > NOW();
-- affected_rows = 1 才算消费成功，否则一律拒绝
```

- 清理：后台每天跑一次 `DELETE FROM mgr_registration_ticket WHERE created_at < NOW() - INTERVAL 2 DAY`。

### 4.2 出题：`POST /api/game/captcha`

请求：

```json
{ "scene": "register" }
```

响应：

```json
{
  "ok": true,
  "data": {
    "cid": "9f2c...",
    "bgUrl":   "https://154-37-155-17.nip.io/xuanmanager/api/game/captcha/9f2c.../bg.png",
    "tileUrl": "https://154-37-155-17.nip.io/xuanmanager/api/game/captcha/9f2c.../tile.png",
    "imgWidth": 320,
    "imgHeight": 160,
    "tileSize": 48,
    "tileY": 57,
    "expiresIn": 300
  }
}
```

要点：

- `cid` = 16 字节随机 hex，与 IP 哈希一起入库，有效期 300 秒。
- **只返回 cid 和 y，绝不返回 x**。x（答案）只活在这条数据库记录里。
- 出题时按 IP 限流：20 次 / 10 分钟。超了直接 429，不给图。

### 4.3 图片：`GET /api/game/captcha/{cid}/bg.png` 与 `/tile.png`

- 按库里的 `bg_index / shape_seed / answer_x / tile_y` 实时渲染，不落盘、不缓存。
- 纯 Go 标准库：`image/jpeg` 读素材、`image/png` 编码、手动像素循环抠图（48×48 很小，没必要引 `x/image`）。
- **素材预处理成固定 320×160**，服务端只做裁剪和挖洞，完全避开缩放质量问题，也就不用加依赖。

抗识别细节（都是几行代码的事）：

- 缺口形状随机 8 边形，半径 20–28，每个顶点角度抖动 ±6°，**不要固定方形**。
- 缺口内做 40% 深色遮罩，边缘 1px 描边 + 随机噪点，避免纯色块被模板匹配。
- 拼图块单独输出为透明 PNG，边缘同样描边，否则玩家看不清。

> 为什么用 URL 而不是 base64：Cocos Creator 2.4 的原生端（JSB）加载 `data:image/png;base64,...` 不可靠，`cc.loader.load` 在原生上经常拿到空纹理；用 http URL 三端都稳，还能吃到浏览器缓存。

### 4.4 校验：`POST /api/game/captcha/{cid}/verify`

请求：

```json
{
  "x": 143,
  "track": [[0,0],[16,3],[32,9],[48,17],[63,28],[79,41]]
}
```

判定顺序（任一不过则失败，失败计数 +1，3 次锁该 IP 30 分钟）：

1. 记录存在、未用、未过期、IP 哈希一致；
2. `|x - answer_x| <= 4`（可配，图片坐标）；
3. 轨迹采样点 ≥ 12，总时长 600ms – 30s；
4. 轨迹合理性：把轨迹按时间三段求平均速度，要求 `v1 < v2` 且 `v3 < v2`（存在加速与减速），偏差容忍 20%。

通过后：

- 标记该 cid `used_at = NOW()`；
- 插入一条 `kind='register'` 记录，`expires_at = NOW() + 5min`，`ip_hash` 绑定当前 IP；
- 返回 `{ "ticket": "a7bd..." }`。

**轨迹判定要做成"打分"而不是"硬拒"**：命中 1 条降级为 +2 风险分，命中 2 条以上才拒。低端安卓机采样稀疏，硬拒会误杀真实玩家——误杀一个真实玩家的代价比放过一个脚本高得多。风险分落到注册审计里，用于事后封号。

### 4.5 注册接口改造（`handleCreateGameRegistration`）

在现有流程**最前面**插入，顺序不能变：

```go
// 1. 蜜罐：正常客户端永远不填这个字段，填了直接封 IP
if input.Website != "" {
    s.banIP(clientIP(r), 24*time.Hour, "registration honeypot")
    writeError(w, http.StatusForbidden, "REGISTRATION_REJECTED", "请求被拒绝")
    return
}

// 2. 票据（enforce 模式才强制）
if s.cfg.RegCaptchaMode == "enforce" || s.cfg.RegCaptchaMode == "soft" && input.Ticket != "" {
    if !s.consumeRegistrationTicket(r.Context(), input.Ticket, clientIP(r)) {
        writeError(w, http.StatusForbidden, "CAPTCHA_REQUIRED", "请先完成验证")
        return
    }
}

// 3. 多维限流（原有按 IP 的 10 次/10 分钟保留，另加下面几条）
//    - 单 IP 成功注册 5 个/小时、15 个/天
//    - 单设备 ID 1 个/24 小时
//    - 全局日新增上限 REG_DAILY_LIMIT（默认 3000），超了返回 503 并告警
```

原有校验（昵称、账号、邀请码、设备绑定）**全部保留，一行不动**。

另外补三件小事：

- 账号枚举：`LOGIN_NAME_EXISTS` / `NICKNAME_EXISTS` 统一成 `ACCOUNT_UNAVAILABLE` + "账号或昵称不可用"，并加 200–500ms 随机延迟。
- `Access-Control-Allow-Origin: *` 改成白名单（网页版域名 + `null` 给原生 WebView）。
- 注册成功后写入 `registration_source`（web/android/ios）、`registration_ip`、`registration_risk` 三列（`third_marketing_info` 加列，默认空）。

### 4.6 限流矩阵

| 维度 | 限制 | 说明 |
|---|---|---|
| 单 IP 取验证码 | 20 次 / 10 分钟 | 防刷图 |
| 单 IP 验证失败 | 3 次 → 锁 30 分钟 | 防暴力对位 |
| 单 IP 注册成功 | 5 个 / 小时、15 个 / 天 | 现在是 10 次/10 分钟，对"成功注册"太松 |
| 单设备 ID 注册 | 1 个 / 24 小时 | deviceId 客户端可伪造，只作为一维信号 |
| 单账号/昵称冲突 | 3 次 / 10 分钟 | 防枚举 |
| 全局日新增 | `REG_DAILY_LIMIT`，默认 3000 | 被打时自动熔断，避免数据库被打满 |

**现有 `registrationRateLimiter` 是进程内 map**（`server.go:77`），重启清零、多实例不共享。改造时把这套计数也落到 `mgr_registration_ticket` 旁边的计数表，或直接复用审计表做窗口统计。不求精确，求重启不丢。

### 4.7 配置项（`config.go`）

```
XUAN_REG_CAPTCHA_MODE=off|soft|enforce     # 默认 off，灰度用
XUAN_REG_CAPTCHA_TOLERANCE=4               # 像素容差
XUAN_REG_CAPTCHA_TTL=300                   # 秒
XUAN_REG_DAILY_LIMIT=3000
XUAN_REG_IP_HOURLY=5
XUAN_REG_CAPTCHA_BG_DIR=/www/html/.xuanmanager/captcha-bg
```

全部走环境变量，和现有 `XUAN_*` 风格一致，改配置重启即生效，不用发版。

### 5.2 Prefab 节点树（`panelLogin.prefab` → 注册资料框）

在「确认注册」按钮上方插一行：

```
注册资料框
└─ 验证滑块            (Widget: left+right, 高 96)
   ├─ 拼图区           (Sprite, 320×160 等比缩放到面板宽)
   │  ├─ 背景图        (Sprite)
   │  └─ 拼图块        (Sprite, 48×48, 锚点 0,0.5)
   └─ 滑块条           (Sprite, 高 44)
      ├─ 滑块底
      └─ 滑块按钮      (Widget: left, 宽 44) ← 触摸监听挂这里
```

硬约束（项目已踩过的坑）：

- 「验证滑块」「滑块按钮」都必须带 `cc.Widget`，实机画布 750×1624，不能写死 center 坐标。
- 「滑块按钮」的 `contentSize` 要显式设大（≥44×44），触摸命中范围只认节点自己的 size，跟子节点无关；不设就点不动。
- 「验证滑块」放在注册弹窗内，**必须给它设比弹窗更高的 zIndex**（`ClubManagementView.raisePopups()` 那套），否则会被大厅按钮抢走触摸。
- 滑块拖动开始时 `blurRegisterInputs()`，否则键盘弹起会压住拼图区。

### 5.3 交互（`panelLogin.ts`）

**不要用 `cc.Slider`**：脚本可以直接 `slider.progress = 1` 跳过滑块，而且不会触发任何触摸事件，等于没防。自己挂事件：

```ts
// 拉到图之后
cc.loader.load(bgUrl, (err, tex) => this._captchaBg.spriteFrame = new cc.SpriteFrame(tex));
cc.loader.load(tileUrl, (err, tex) => { /* 放在 tileY 对应的高度，x=0 */ });

this._sliderBtn.node.on(cc.Node.EventType.TOUCH_START, this.onCaptchaTouchStart, this);
this._sliderBtn.node.on(cc.Node.EventType.TOUCH_MOVE,  this.onCaptchaTouchMove,  this);
this._sliderBtn.node.on(cc.Node.EventType.TOUCH_END,   this.onCaptchaTouchEnd,   this);
```

坐标换算：面板上拼图区显示宽度 / 图片宽度 = `scale`，提交时 `x = Math.round(tileX / scale)`（换回 320 宽的图片坐标），否则服务端按图片坐标比对会一直差。

提交注册时多带两个字段：

```ts
request.send(JSON.stringify({
  ...原有字段,
  ticket: this._captchaTicket,
  website: ""            // 蜜罐，正常客户端恒为空
}));
```

失败处理：滑块验证失败 → 停在原地提示"验证失败，请重新拖动"并**重新取题**（一次一题，不复用）；连续 3 次失败 → 提示 30 分钟后再试。

### 5.4 降级

- 取题接口 5xx / 超时 → 滑块区显示"验证服务暂不可用，请稍后重试"，禁用「确认注册」，**不做自动跳过**（跳过就等于开了后门）。
- 老版本客户端（没有滑块代码）依赖服务端的 `soft` 模式放行，客户端不需要任何兼容代码。

## 6. 灰度与兼容（最容易翻车的一步）

已发布的 APK 和网页版都不带 ticket，直接 `enforce` 会让**所有老用户注册失败**。必须三段切：

| 阶段 | 服务端配置 | 行为 | 观察期 |
|---|---|---|---|
| 1. 上线服务端 | `off` | 新接口存在，注册逻辑完全不变 | 1 天 |
| 2. 热更客户端 | `soft` | 带 ticket 的走校验；不带的放行，但记 `captcha_ok=0` | 3 天 |
| 3. 强制 | `enforce` | 没 ticket 一律 403 | 长期 |

阶段 2 的判断依据：看审计里 `captcha_ok=0` 的占比。降到 5% 以下就切 `enforce`；还有大量老版本在注册就再等。

回滚只改环境变量重启，**不需要回滚代码**——这是把开关做成配置而不是写死的唯一理由。

## 9. 明确不做的

- **不做短信验证码**：要运营商通道、按条收费，且国内 Android 读短信权限容易被拒审。
- **不做第三方 SDK**（极验/防水墙/Turnstile）：你的要求就是不计三方，且引入 SDK 会牵扯隐私合规和包体。
- **不做纯前端校验**：客户端判定等于没判定。
- **不做数学题/字符验证码**：OCR 识别率 95%+，等于送。
- **不在这一步动密码存储（MD5 → 加盐）**：那要改 KB 服务端账号鉴权，影响全员登录，风险比收益大，单独排期做（见审计报告 P2）。

### 四道闸的判定顺序

1. **尝试次数**：原有 `registrationRateLimiter`，10 次 / 10 分钟 / IP（纯内存，防连点）。
2. **蜜罐**：请求带 `website` 非空 → 封该 IP 24 小时，直接 403。正常客户端不会填这一栏，误伤概率接近零。
3. **成功数配额**：
   - 单 IP 10 个 / 小时（默认开）
   - 单 IP 20 个 / 天（默认开）
   - 单设备 0 个 / 24 小时（默认关，开了会误伤一人多号）
   - 全服 0 个 / 天（默认关，被打时手动开）
4. **业务校验**：昵称/账号/邀请码，原逻辑一行没动。

关键细节：**只有 `result='ok'` 才计入配额**。被拒的请求不占额度，否则攻击者可以用失败请求把某个 IP 的配额刷满，连带把同 IP 的真实玩家挡在外面。

### 顺手修的一个放大器

`applyRegistrationAvatar` 原来是「每秒查一次游戏库，连查 2 分钟」——玩家注册完不登录时必然空转。1000 个批量注册 = 1000 个 goroutine 每秒打一次库，持续两分钟，这是「乱注册」能把数据库拖垮的真实路径。已改成：

- 分段退避 `1s→2s→4s→8s→15s→15s→30s→45s`，总时长仍约 2 分钟，查询次数从 120 次降到 8 次；
- 并发上限 16，队列满了直接放弃（补头像是次要功能，不跟主流程抢库）。

### 观察窗口与调参

上线后看三天 `mgr_registration_event`：

```sql
-- 每天成功注册量
SELECT DATE(created_at) d, COUNT(*) FROM mgr_registration_event WHERE result='ok' GROUP BY d;

-- 单 IP 注册最多的前 10 个（判断配额是否过紧/过松）
SELECT ip_hash, COUNT(*) c FROM mgr_registration_event
WHERE result='ok' AND created_at > NOW() - INTERVAL 1 DAY
GROUP BY ip_hash ORDER BY c DESC LIMIT 10;

-- 被拦了多少
SELECT result, COUNT(*) FROM mgr_registration_event
WHERE created_at > NOW() - INTERVAL 1 DAY GROUP BY result;
```

调参建议：

- 前 10 名里如果出现「正常网吧 IP 达到 15 个/天」，把 `XUAN_REG_IP_DAILY` 提到 50；
- 确认真实日注册量后，把 `XUAN_REG_GLOBAL_DAILY` 设成「峰值 × 2」，作为被打时的硬兜底；
- 如果发现大量「一机多号」，再开 `XUAN_REG_DEVICE_DAILY=2`（注意：一人多号的老玩家会被拦，先小范围试）。

### 这一轮没做的

- **滑块验证码**：要客户端配合，下一轮。
- **CORS 收窄**：现在还是 `*`，改了怕影响网页版，放到验证码那一轮一起测。
- **HTTPS**：客户端 URL 还没换，属于客户端改动。

所以现在这套能挡住「同一 IP 用脚本连点/换账号狂注册」，但**挡不住换 IP 池的分布式注册**——那种要靠下一轮的滑块票据 + 全局日上限。这也是为什么建议尽快确认真实日注册量，好开全局兜底。
