# 后台系统 + 客服系统 · 上线安全加固方案

日期：2026-11-15
范围：XuanManager（后台，8891）+ ChatTool（客服，8893）+ 承载它们的 Caddy / CentOS 7 / MySQL 5.7
性质：公网生产环境的攻击面体检 + 加固方案（不含游戏服 KBEngine 内核侧）

---

## 0. 结论

**代码写得比部署好。真正能让攻击者一击得手的地方，全在部署层，不在业务代码里。**

三句话：

1. **最致命的是全站明文 HTTP。** `http://154.37.155.17/xuanmanager/` 直接 200，不跳转 HTTPS，Cookie 的 `Secure=false`。任何能碰链路的中间人（同网段、公共 WiFi、上游运营商、被入侵的路由器）抓到一个 `xuan_session`，就等于拿到超管：改余额、发石头、重置玩家密码、全服发包。
2. **后台不该对全世界开放。** 路径 `/xuanmanager/*` 没有任何来源 IP 限制，账号规则又可枚举。
3. **没有异地备份，磁盘只剩 2.5G。** 这两件事叠加，等于"被攻击后无法恢复"和"被灌满即全线宕机"。

代码层已有的防护是及格甚至良好的（bcrypt cost 12、HttpOnly+SameSite=Strict、CSRF 双提交、单会话踢线、TOTP、审计表、上传图片头嗅探、SQL 全参数化、服务间 loopback+token 隔离）。所以本方案**不做大改造**，只补 4 个致命口子 + 6 个高危项 + 1 套检测响应。

工作量：**P0 约 3 小时（今天可做完），P1 约 2 人日，P2 约 5 人日。**

## 1. 体检结果（含实测证据）

### 1.1 做得对的部分（不要动）

| 项 | 现状 |
|---|---|
| 密码存储 | bcrypt cost=12；`HashPassword` 统一入口 |
| 会话 | 服务端存 `sha256(token)`；HttpOnly + `SameSite=Strict`；登录即踢掉同账号其他会话 |
| CSRF | 双提交 + `Origin` 同源校验，写操作强制校验 |
| 二次验证 | TOTP 已实现（含恢复码、防重放 step） |
| 审计 | `mgr_audit_log` 记录操作人/前后值/结果/IP |
| 服务间通道 | `serviceAuthorized` 要求 loopback 直连 + Bearer token，拒绝带 `X-Forwarded-For` 的请求 |
| 输入 | `MaxBytesReader` + `DisallowUnknownFields` + 只允许单个 JSON 对象 |
| 上传 | 按文件头识别 JPEG/PNG/WebP，拒绝 SVG/HTML；客户端自报尺寸不采信 |
| 媒体访问 | HMAC 短期票据（10 分钟），不暴露静态目录 |
| 限流 | 客服登录 8 次/10 分钟、消息 30 次/分钟、上传限流、玩家会话票据 TTL 15 分钟 |
| SQL | 全仓无用户输入拼接（仅一处静态 `Sprintf` 拼列名白名单） |
| 内部端口 | 8891 / 8893 / 3306 / 6379 / 8890 / Caddy admin 2019 **全部只监听 127.0.0.1**（这点很关键，做对了） |

### 1.2 实测到的攻击面

| 事实 | 证据 |
|---|---|
| 后台可明文访问 | `curl http://154.37.155.17/xuanmanager/` → `200`，无 301/308 |
| HTTPS 证书不可信 | `issuer=CN=Caddy Local Authority - ECC Intermediate`，`notAfter` 仅 12 小时 → 浏览器必然报警，实际上没人走 HTTPS |
| Cookie 未加密传输 | 服务器 `XUAN_COOKIE_SECURE=false`、`CHAT_COOKIE_SECURE=false` |
| 客服公网地址是 http | `CHAT_PUBLIC_BASE_URL=http://154.37.155.17/chattool` |
| 客户端硬编码 http | `GameDef.ts:61,67`、`ConfigManager.ts:96-98` 全为 `http://154.37.155.17/...` |
| 后台无来源限制 | Caddyfile 中 `/xuanmanager/*` 只有 `reverse_proxy`，无 `remote_ip` 匹配 |
| Caddy admin 无鉴权 | Caddyfile 未写 `admin` 指令 → 默认开在 `127.0.0.1:2019`，可无认证改路由 |
| 系统过期 | `CentOS Linux 7.8.2003`（EOL）、内核 `3.10.0-1127`、`MySQL 5.7.44`（EOL） |
| 磁盘将满 | `/dev/vda1 30G，已用 28G（92%），剩 2.5G`；`_processed` 8.5G、`.xuanmanager` 3.2G |
| 无数据库备份 | crontab 无 `mysqldump`；`.xuanmanager/backups` 只有同盘二进制快照，无异地、无库 |
| 上传上限过大 | Caddy `/chattool/*` 设 `max_size 110MB`（聊天图片只需 5–10MB） |
| 配置目录可写扩散 | `.xuanmanager/runtime.env` 权限 `-rw--w----`（同组可写），且位于站点根目录内 |
| 历史版本堆积 | `/www/html/.chattool/` 下 10+ 个 `web.previous-*` 目录仍在服务器上 |
| 公网监听 | 80/443、2233(SSH)、4041、15010–15060、15901–15917、25036、58088 |
| 入侵防护 | fail2ban 已安装（进程存在），但 jail 是否覆盖 Caddy/SSH 需 root 核实 |

### 1.3 攻击者会怎么打（按性价比排序）

1. **抓会话（10 分钟，零成本）**：明文 HTTP 下抓 `xuan_session` → 直接以超管身份登录 → 调余额、重置玩家密码、发全服通知。这是唯一一条"不需要任何漏洞"的路径。
2. **撞库（小时级）**：后台账号是 4–32 位字母数字，可从别处泄露的库直接撞。目前只按账号 5 次锁定，没有 IP 维度限流。
3. **锁死管理员（分钟级，DoS）**：连续 5 次错密码即锁 15 分钟。攻击者用一份字典轮流砸所有管理员账号，夜间提现/客服工单全部停摆。
4. **灌满磁盘（分钟级，全线宕机）**：客服上传 110MB/请求，磁盘剩 2.5G。十几路并发就能把盘写满 → MySQL 写失败 → 游戏、后台、客服一起异常。
5. **借道 Caddy admin（拿到本机任意低权后）**：`127.0.0.1:2019` 无鉴权，可把 3306/8891 直接反代到公网。
6. **改配置持久化**：`runtime.env` 组可写 + watchdog 每分钟拉起 → 改一次文件即获得服务重启后的执行效果。
7. **内部人抹痕**：审计表与业务同库，若应用账号有 `UPDATE/DELETE` 权限，调账后删日志无法追溯。
8. **旧版本钓鱼**：`web.previous-*` 里带旧逻辑的页面若仍可访问，可用来钓管理员或绕过新校验。

## 2. P0：上线前必须做（约 3 小时，不涉及发版）

### P0-1 后台改成"只有自己人能进"（15 分钟，收益最大）

不必等域名和证书，先在 Caddy 加来源限制。在 `http://154.37.155.17` 站点块里、`import common_routes` **之前**加：

```caddyfile
@xuan_blocked {
    path /xuanmanager/*
    not remote_ip 你的办公出口IP 你的家宽出口IP 你的手机4G出口 备份线路
}
respond @xuan_blocked 403
```

注意两点：
- 必须在 `import common_routes` 前面，靠 matcher 顺序生效。
- 服务器上还有 `install-caddy-route.sh` 每分钟往 admin API 注入同名路由（`qing_xuanmanager_proxy`）。改完 Caddyfile 后要 `caddy reload`，再确认 `curl 127.0.0.1:2019/id/qing_xuanmanager_proxy` 的返回没有把旧路由盖在前面。**最稳的做法是顺手把那条 cron 注入口去掉**，路由统一由 Caddyfile 管。

验收：从非白名单网络访问 `/xuanmanager/` 应 403；白名单内正常登录。

### P0-2 关掉 Caddy 管理接口（5 分钟）

Caddyfile 顶部加：

```caddyfile
{
    admin off
}
```

以后需要用 admin API 时临时 `caddy reload --config ...` 或本地起一次带 `admin localhost:2019` 的实例。收益：本机任何低权进程（含未来任何一处 SSRF/命令注入）都改不动反代规则。

### P0-3 收紧文件与目录权限（20 分钟）

```bash
chmod 600 /www/html/.xuanmanager/runtime.env
chmod 600 /www/html/.chattool/deploy/centos7-user/runtime.env
chmod 700 /www/html/.xuanmanager /www/html/.chattool
```

并且**把 runtime.env 移出站点根目录**（如 `/www/etc/qing/`），`start.sh` 里改读取路径。理由：站点根目录里任何一处上传/备份/旧版本目录被写，都不该顺带改到服务配置。

### P0-4 上传限额降到业务真实值（5 分钟）

Caddy `/chattool/*` 的 `max_size` 从 110MB 改到 **10MB**；ChatTool 侧 `MaxImageBytes` 同步核对。同时给 `uploads` 加每日配额（见 P1-4），避免磁盘被慢慢吃穿。

### P0-5 清理磁盘，留出安全余量（30 分钟，择机）

按占用从大到小：`/www/html/_processed` 8.5G → `/www/html/.xuanmanager` 3.2G（其中大量历史二进制与 `web.previous-*`）→ `/www/html/laba` 642M → `web.previous-*` 十余份。

目标：根分区 **使用率降到 70% 以下**。注意 `_processed` 是不是产物目录要先确认，别当缓存直接删（项目里 `build/` 有同样教训）。

### P0-6 立即改口令与密钥

基线动作，一条命令都不省：
- 所有后台账号密码重置为 ≥12 位随机串（密码管理器存），超管单独一套。
- 轮换 `XUAN_SERVICE_TOKEN`、`CHAT_XUAN_SERVICE_TOKEN`、`CHAT_PLAYER_LINK_KEY`、`CHAT_DIRECT_TICKET_KEY`、`XUAN_CREDENTIAL_KEY`（改完要重启两个服务，并同步游戏侧票据密钥）。
- 清空 `mgr_session`、`chat_agent_session`，强制所有人重新登录。

## 3. P1：上线后第一周完成（约 2 人日）

### P1-1 上 HTTPS（真正解决"裸奔"）

**必须有真域名**：`nip.io` 在公共后缀列表里，Let's Encrypt 不给签，所以现在只能用 Caddy 内部 CA（12 小时自签证书），浏览器必然报警 —— 这就是大家一直在用 http 的根因。

步骤：
1. 买一个域名（`.com`/`.vip` 均可，约 10 美元/年），加两条 A 记录 `admin.域名`、`kefu.域名` 指向 154.37.155.17。
2. Caddyfile 站点地址由 IP 改为域名，Caddy 自动申请并续期证书。
3. 两个服务设 `XUAN_COOKIE_SECURE=true`、`CHAT_COOKIE_SECURE=true`；`CHAT_PUBLIC_BASE_URL` 改 `https://kefu.域名/chattool`；`CHAT_DIRECT_CORS_ORIGINS` 同步为 https。
4. 加 HSTS：`header Strict-Transport-Security "max-age=31536000; includeSubDomains"`。
5. **80 端口只留给老版本客户端**，后台路径在 80 上一律 308 跳 443。

### P1-2 客户端切 HTTPS（1 天，需热更）

改 4 处常量：`GameDef.ts:54,61,67`、`ConfigManager.ts:96-98`。策略：
- 新旧同时可用（Caddy 同时监听域名 443 与 IP 80），客户端热更到 https 后不影响老版本。
- 观察 2 周老版本占比，再关闭 IP 80 上的注册/改密接口（这两条是玩家账号密码，明文传输风险与后台同级）。
- 客服页面在 WebView 内加载，切 https 后要确认真机无混合内容拦截（一旦页面是 https，内部 http 请求会被拦）。

### P1-3 强制 TOTP + 口令策略 + 登录限流

- **超管、财务、能调余额的角色强制 TOTP**，未开启则登录后只能进"安全设置"页。现状 TOTP 是可选。
- 后台密码最短长度 6 → **12**，加弱口令字典拦截（`admin123`、`a123456` 这类）。
- **后台登录加 IP 维度限流**（当前只有账号维度，可被用来批量锁号）：同 IP 10 次/10 分钟，超限 429；连续失败按 IP 递延而非直接锁账号，避免"锁死所有管理员"的 DoS。
- 登录成功的 IP 与上次不同 → 页面提示 + 记审计（`mgr_audit_log` 已有 ip 字段，加一条比对即可）。

### P1-4 磁盘与上传的硬约束

- `uploads` 每日新增配额（如 2G/天），超限拒绝并告警。
- 消息保留期已有（48h 客服 / 720h 直聊），确认清理任务真的在跑，并加"清理失败"告警。
- 磁盘水位 75% 告警、85% 严重告警。

### P1-5 备份：这是"被攻击后还能不能活"的唯一保障

现状：只有同盘二进制快照，**没有数据库备份，没有异地**。一旦被勒索或误删，全灭。

最低可行：
```bash
# 每日 03:10 全量（两个库），保留 14 天本地
mysqldump --single-transaction --routines --triggers webcm | gzip > /www/backup/webcm-$(date +%F).sql.gz
mysqldump --single-transaction kbedm | gzip > /www/backup/kbedm-$(date +%F).sql.gz
# 每日 04:00 同步到异地（对象存储 / 另一台机器）
```
要求：
- **异地**（对象存储或另一台服务器），与生产不同故障域。
- 保留 7 日 + 每周 1 份保留 30 日。
- **每月做一次恢复演练**（恢复到临时库，校验行数与抽样数据）。没演练过的备份不叫备份。
- 备份文件加密，密钥不与备份放一起。

### P1-6 检测与告警（把"没人知道"变成"十分钟内知道"）

- **fail2ban 加 jail**：`sshd`（2233）、Caddy access log 里的 `/xuanmanager/api/auth/login` 与 `/chattool/api/agent/auth/login` 401/403 频次。确认现有 fail2ban 服务真在跑而不是装了个壳。
- **关键动作实时告警**（推到微信/邮件）：单笔调账超过阈值、批量重置玩家密码、下发全服通知、超管登录、非白名单 IP 的 403 突增。
- **每日摘要**：登录失败 Top IP、403 来源、新出现的 UA、异常大的请求体。
- 日志留存 90 天（Caddy 已配 720h，够）；审计日志需异地归档。

## 4. P2：一个月内（约 5 人日）

### P2-1 换掉过期的底座

CentOS 7.8 和 MySQL 5.7 都已 EOL，**不会再有安全补丁**。任何新披露的漏洞（内核、OpenSSL、MySQL 认证绕过）在这台机器上都是永久可利用。

路线（择一，建议 A）：
- **A（推荐）**：整体迁移到云厂商的受支持镜像（Rocky/Alma 9 或 Ubuntu 22.04）+ 云数据库 MySQL 8。游戏服对内核依赖不大，迁移窗口 4–6 小时。
- B：先只把 MySQL 换成云托管（杀掉了最大的一块"本地库"风险），操作系统随后再迁。

过渡期补偿：把公网暴露面收到最小（只留 80/443/2233 + 游戏必需端口），并在云安全组层面限制来源。

### P2-2 高权限动作双人复核

后台能一笔改余额、批量发石头、改抽水比例。**单账号被盗 = 直接经济损失。** 建议：
- 调账类动作超过阈值时，需要第二个有权限的账号在 30 分钟内确认，否则不生效。
- 或者退一步：超阈值动作强制当场再输一次 TOTP（成本低，能挡住"会话被盗后批量操作"）。

### P2-3 权限最小化对账

导出一份"账号 × 权限"矩阵，逐条确认：非超管账号不得持有 `game.player.balance_adjust`、`game.player.reset_password`、`game.club.stone_pool_adjust`。每季度复核一次。

### P2-4 审计日志防篡改

- 应用数据库账号对 `mgr_audit_log` **只授予 INSERT/SELECT**，不给 UPDATE/DELETE。这样内部人删不掉痕迹。
- 每日把审计表增量导出到异地，独立保存 180 天。

### P2-5 上线前做一次"自己打自己"

在授权范围内做一轮验证（半天）：
1. 从公网扫端口，确认 8891/8893/3306/6379/2019 不可达。
2. 用错误密码连打 20 次，确认限流生效且不会把管理员全锁死。
3. 拿普通角色账号直接请求超管接口，确认 403。
4. 上传一个改名成 `.png` 的 HTML 文件，确认被拒。
5. 构造跨站请求（无 `X-CSRF-Token`），确认 403。
6. 检查响应头：`CSP`、`X-Frame-Options`、`nosniff` 齐全（代码里已有，确认没被反代吞掉）。

## 6. 出事后的 30 分钟处置顺序

1. **止血**：Caddy 把后台路径整体 403 / 云安全组封掉可疑 IP；必要时停掉 8891、8893（先保数据）。
2. **断凭据**：清空所有 session 表、重置全部后台与客服密码、轮换全部密钥（服务 token、票据 key、credential key）。
3. **取证**：`/var/log/caddy/update-access.log`、`mgr_audit_log`、`chat_audit_log`、`/var/log/secure` 先打包异地，**别急着清理**。
4. **查影响面**：按审计表筛出该时段内的调账、重置密码、封号、通知发送记录，逐条核对。
5. **恢复**：从异地备份恢复，确认数据完整性后再开服。
6. **复盘**：写清入口、时间线、影响金额、已补的口子；把这一条补进本文件的"攻击面"表。

## 7. 排期与决策点

| 阶段 | 内容 | 工时 | 何时 |
|---|---|---|---|
| P0 | 来源限制、关 admin、权限、上传限额、清盘、改口令 | 3h | 今天 |

**需要你拍板的三件事：**

1. **买不买域名。** 不买就只能继续自签（浏览器报警），HTTPS 这条路走不通。建议买，10 美元/年。
2. **后台是否只允许固定 IP 进。** 建议是（办公 + 几个常用出口）。如果运营需要随时随地上，那就改上 Cloudflare Access（免费版够用），代价是后台流量过第三方。
3. **能否给一个 4–6 小时停机窗口**做系统/数据库迁移。给不了就先做 P2-1 的 B 方案（只换云数据库），窗口缩到 1 小时。
