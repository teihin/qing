# XuanManager 部署说明

## 安全基线

- 服务和 MySQL 部署在同一台游戏服务器，数据库地址固定为 `127.0.0.1`。
- 用户已明确要求 XuanManager 使用纯 HTTP，不配置 HTTPS。后端仍只监听 `127.0.0.1:8891`，由现有 Caddy 通过公网 HTTP 入口反向代理。
- 不直接开放 8891 端口；公网只访问 Caddy 提供的 XuanManager HTTP 页面和同源 API。
- HTTP 无法加密后台账号、密码和管理数据，链路上的网络设备或中间人可能读取或篡改内容。若保持纯 HTTP，应至少限制访问来源 IP、使用防火墙白名单或仅允许可信内网/VPN 访问。
- 运行环境文件权限设为 `0600`，不得写入 Git、Web 根目录或审计日志。
- 首个超级管理员创建后，立即从运行环境删除 `XUAN_BOOTSTRAP_ADMIN_PASSWORD`。

## 构建

```bash
cd web
npm ci
npm run lint
npm run build

cd ../server
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags="-s -w" -o bin/xuanmanager ./cmd/xuanmanager
```

部署包只需要：

```text
server/bin/xuanmanager
web/dist/
```

数据库迁移已嵌入 Go 二进制，后端启动时只执行尚未记录在 `mgr_schema_migration` 中的迁移。
迁移适配现有 `webcm_user` 权限，不依赖 MySQL `REFERENCES` 权限；角色、模块、权限和用户之间的关联完整性由后端接口校验。

## 运行环境

环境变量样例见 `.env.example`。生产环境必须至少配置数据库账号、数据库密码、Cookie 安全标记和静态页面目录：

```text
XUAN_HTTP_ADDR=127.0.0.1:8891
XUAN_DB_HOST=127.0.0.1
XUAN_DB_PORT=3306
XUAN_DB_NAME=webcm
XUAN_GAME_ADMIN_URL=http://127.0.0.1:8890
XUAN_NOTIFICATION_CAROUSEL_WORKER=true
XUAN_COOKIE_SECURE=false
XUAN_STATIC_DIR=/path/to/xuanmanager/web/dist
```

数据库和超级管理员的真实账号密码不写入本文件。
`XUAN_GAME_ADMIN_URL` 只允许 `http://127.0.0.1:8890` 或等价的 `localhost` 地址，不能配置公网主机、其他端口或附加路径。
`XUAN_NOTIFICATION_CAROUSEL_WORKER` 只允许正式8891进程设置为 `true`；本地开发和8892候选验证必须显式保持 `false`，防止同一轮播被多个进程重复发送。

## 上线前检查

1. Caddy 的公网 HTTP 路由能访问 XuanManager，8891 仍只监听服务器本机。
2. 公网无法直接连接 MySQL、旧管理端口 8890 和 XuanManager 内部端口 8891。
3. 若有固定办公网络，已配置来源 IP 白名单；否则已明确接受公网 HTTP 明文传输风险。
4. 使用超级管理员完成登录、改密、创建角色、创建测试后台用户、分配权限和退出登录。
5. 使用受限角色确认无权限菜单不可见，同时直接请求无权限接口返回 403。
6. 在 `mgr_audit_log` 中确认创建用户、修改角色、分配权限和登录失败都有记录，且没有明文密码。
7. 使用代理查询角色确认 `game.agent.view` 菜单和接口可用，并验证无权限角色直接请求代理接口返回 403。
8. 在代理详情中抽查至少一条非 BOSS 链路能回溯到 BOSS，直属代理/玩家数量及下级获授比例与游戏数据一致。
9. 抽查代理红利：累计总红利等于已提取加剩余红利，来源流水合计与累计总红利一致；按来源玩家、房间和日期筛选正确，每笔收入均能说明来源玩家、房间、基数和比例。存在账户累计提取但缺少历史提取明细时，页面必须明确提示，不能伪造逐笔记录。
10. 使用交易查询角色确认 `game.transaction.view` 菜单和接口可用，并验证无权限角色直接请求交易接口返回 403。
11. 按玩家 ID 抽查金币流水：列表首尾余额连续、汇总净变化等于各行 `new_money - old_money` 之和，游戏/道具/消费筛选无重复记录，页面不显示钻石。
12. 使用房间战绩角色确认 `game.room_record.view` 菜单和接口可用；房间列表默认加载，按房间号、房间名、参与玩家和日期筛选及分页均正确，列表与详情不显示创建人；启用地九王时只显示“地九王”标签，未启用时留空，且与真实房间规则一致。无权限角色直接请求接口返回 403。
13. 从房间列表点击进入真实房间，抽查总战绩与逐局明细：参与玩家和局数完整、牌面花色与点数正确、操作时间线顺序正确；最终输赢优先等于结算返还减累计带入，原始战绩分数不一致时页面明确提示，并能返回原房间列表。
14. 从玩家管理点击真实玩家，核对基本资料、资金情况和房间战绩三个页签；资金汇总与交易记录一致，房间数、局数、带入、返还和输赢与总战绩一致，且可继续跳转到完整交易记录和指定房间战绩。缺少 `game.transaction.view` 或 `game.room_record.view` 时，对应页签不可越权访问。
15. 使用公告只读角色确认 `configuration.announcement.view` 可读取当前内容但不能保存；使用修改角色保存后应核对 `usr_hash_info` 的“系统公告”只有客户端兼容编码，并确认回读内容、审计前后值和操作者一致。线上表为 MyISAM，故障测试不能把 `ROLLBACK` 当作恢复手段。
16. 使用通知只读角色确认只能查看记录和轮播状态；`configuration.notification.send` 控制立即发送，`configuration.notification.carousel.update` 独立控制轮播增删、排序、开始时间、每条间隔、循环次数和启停。启用轮播必须至少一条内容并显式确认；一轮定义为从第一条播放到最后一条，循环次数0表示持续循环，指定次数完成后应自动停用。正式8891必须启用唯一轮播工作进程，候选8892必须禁用。立即通知和轮播公告均按 `,,,,<正文>` 传输，玩家端只显示后台正文、不添加“系统广播”字样，并使用普通通知黑色半透明背景。真实全服通知只能在有明确业务内容时测试。
17. 使用奖池只读角色确认 `configuration.reward_pool.view` 能看到9个皮池金额、基础放奖、全局不发奖、本档不发奖、预计实际放奖和平台固定提留，但输入区不可编辑；金额池页面必须以“元”显示并允许两位小数，HTTP API和旧奖池金额服务仍以整数“分”交互，例如页面 `999.99` 元对应接口 `99999` 分。`reward_modify` 本身就是整数元，不再乘以100；概率必须是0～100的整数。当前正式配置的 `reward_rate/reward_modify` 只有前8档，`reward_nopai_dipi` 有9档，100/200档缺失项必须显示不可配置，不能补默认值。预计实际放奖按`基础×(1-全局拦截)×(1-本档拦截)`显示。修改角色必须具备 `configuration.reward_pool.update`，未勾选确认时前后端均拒绝。保存前记录四项完整配置和全部奖池金额；生产环境只做读取、输入/恢复和未确认校验，不得为了测试改变真实奖池。实际业务保存后必须核对四项回读、9项金额、页面单位和审计，任一配置写入或回读失败时确认原配置已恢复。
18. 使用封号只读角色确认 `game.ban.view` 可以查看全部当前已封游戏账号以及分页封号历史，但不能执行封号或解封；历史记录应支持按玩家/原因/操作人、封号或解封、成功或失败筛选，并显示操作时间、当时原因和结果说明。封号和解封分别要求 `game.ban.create`、`game.ban.remove`。前后端未勾选确认时必须拒绝操作，玩家 ID 必须为6位数字；上线验证不得为了测试封禁真实玩家。业务确需操作时，应核对玩家身份、玩家端提示、`sm_client_status` 回读结果及 `mgr_audit_log` 的操作前后状态。`admin999` 执行的历史只允许 `admin999` 自己查看；其他账号的历史按正常角色权限显示。
19. 登录工作台核对累计玩家、今日新注册玩家和今日登录；新增数必须严格等于北京时间当天 `00:00–24:00` 范围内的 `tbl_Account.sm_reg_time` 首次注册记录数，不能依赖 MySQL 服务器 UTC 日期的 `CURDATE()`，并与玩家列表按注册日期筛选的结果一致，封号和解封记录不得参与统计。页面说明显示“每日新注册玩家”，并确认页面不显示当前在线、今日在线峰值或小时在线对比。今日登录仍按中国运营日统计；当前服务没有权威在线会话接口，禁止用 `kbe_entitylog`、玩家持久化属性或最后登录时间推算在线人数。
20. 新建普通角色时，玩家优化的查看、新增、调整、删除四项权限应能分别勾选；只有查看权限时页面不出现写操作入口，授予对应写权限后普通后台用户可操作，直接请求未授权接口仍返回 403。玩家优化页面下方应显示可分页筛选的新增、调整、删除历史，参数变化需明确展示修改前后次数和概率；`admin999` 的操作记录只有 `admin999` 自己能看到，包括其他 `super_admin` 角色账号在内的所有账号都必须被后端过滤。其他账号记录按正常权限显示。
21. 房间维护整个模块只允许 `super_admin` 超级管理员角色访问，不得只依赖账号的历史 `is_super` 标记。先确认该角色下的每个账号都能收到房间维护菜单并访问页面；普通账号的导航、模块列表和角色权限列表均不出现房间维护，数据库中模块26的权限只关联超级管理员角色，普通账号直接请求实时列表、创建开关和解散接口必须返回403。超级管理员角色账号请求 `GET /api/admin/hall/rooms?page=1&page_size=50`，确认后端调用本机 `查询_大厅_所有房间`、页码正确转换、每页最大200且只返回 `Custom` 活跃房间；页面紧凑显示房间号、房间名、状态、局数、玩家/观战/等待带入人数、创建时间和备注，不显示玩法、规则、房间类型、俱乐部、创建人、玩家明细、手牌、GPS、IP或发牌优化。抽查游戏中/等待中/准备或其他/解散中卡片分别使用青绿/浅蓝/中性灰白/浅红整卡背景和左侧色条，不能只改变状态小标签。旧服务返回769、不可达或响应结构错误时页面必须清空列表并明确报错，不能回退读取 `tbl_Account.sm_roomID`。使用只读请求核对 `GET /api/game/room-maintenance/creation-control` 与正式 `can_all_create_room` 一致；写入 `param_value` 必须是 JSON 布尔值，要求页面基准校验、二次确认、写后回读和失败恢复。QA不得为了验收擅自切换正式开关。解散联调必须抓取旧服务请求并确认 `cmd` 分别是纯字符串 `强制_解散_事件`/`申请_解散_事件`，没有嵌套 JSON 或无效 `is_qiangzhi`；`ret_code=512/1280` 仅算命令已发送，页面只有在再次查询实时列表确认房间消失或最终关闭时才能提示成功。全部房间操作必须先取完整实时列表后逐房发送，并继续保留超级管理员、`ALL_ROOMS`、审计和部分失败汇总保护。
22. 新建普通角色，分别验证交易黑名单查看、新增、修改、删除四项权限。读取 `GET /api/game/transaction-blacklist` 时核对 `npc` 名单和 `disable_cash_exchange` 总开关；未勾确认、玩家ID非6位、玩家不存在、页面版本过期时写接口必须拒绝。业务确需测试时，先记录原名单和开关，只对已核对的测试玩家执行新增、替换、删除与启停，并确认每步游戏服务回读、页面状态和 `mgr_audit_log` 前后值一致，最后恢复原配置。
23. 在玩家管理权限组确认存在 `game.player.reset_password`，无此权限的普通角色不能看到重置入口且直接请求返回403；验证时只检查未确认请求被拒绝，未经授权不得重置真实玩家密码。业务实际重置后应确认 `tbl_Account.sm_userPWD` 和关联 `third_marketing_info.player_wxpwd` 均与新密码MD5一致，审计中只有“密码已修改”标记而没有明文或摘要。只有 `admin999` 打开玩家详情时才显示并按需读取IP/GPS；`admin`及其他所有账号前端不渲染该区域，直调敏感接口必须返回403。响应禁止缓存，有合法坐标时地图链接应按WGS84及“经度,纬度”顺序打开正确标记。
24. 使用宽度不超过620px的手机视口检查底部导航：菜单可横向滑动，切换页面后当前项会自动滚动到可见位置，右侧“全部”入口可以按目录选择当前账号有权限的任何模块；无权限模块在底栏和全部菜单中都不能出现，全面屏底部安全区不能遮挡菜单或页面内容。
25. 在玩家管理中选择一名 `roomId > 0` 的房间内玩家，确认加分和减分按钮均可提交，不再返回 `PLAYER_IN_ROOM`；页面必须提示本次只调整账号金币、不直接修改桌面已带入积分。未经业务授权不得为真实玩家执行验证，可用未勾确认请求或自动化测试证明房间状态不再作为拒绝条件；余额并发变化、减分超过账号余额、金额越界和未确认仍必须拒绝。
26. 打开玩家管理的玩家基本资料，代理关系区只显示直属代理，不能出现大代理、合伙人或总裁；注册与其他参数区不能出现优化1或优化2。玩家列表接口也不再返回这些详情冗余字段，但直属代理查询条件和独立“玩家优化”模块必须保持可用。
27. 使用同一后台账号先后在两个独立浏览器登录：第二处登录成功后，第一处再次请求 `GET /api/auth/me` 必须返回401，第二处保持200；`mgr_session` 中该 `user_id` 只能有一行。并发登录完成后同样只能保留一条会话，登录事务必须先更新并锁定对应 `mgr_user` 行，再删除旧会话和插入新会话。旧页面收到401时立即返回登录页；即使没有业务请求，也会在重新获得焦点或最多60秒的会话检查后退出。单次退出仅结束当前会话；修改密码、管理员重置密码、停用账号和角色权限变更仍按原规则清退相关旧会话。
28. 在后台用户、操作审计、玩家、代理及下级/红利、交易、封号及历史、防盗号、房间战绩、玩家优化及历史等查询页，保持条件和页码不变连续点击两次查询；浏览器网络面板必须出现两次对应 GET 请求，第二次不能复用浏览器缓存，并应显示服务端最新结果。重置按钮在条件已经为空时也应重新查询。
29. 注册接口必须继续强制有效邀请码。使用只读方式核对一条“第四层或更深代理→逐级上级→BOSS”链时，接口应沿直属关系完整回溯并拒绝断链/循环；新注册记录继续兼容写入前三层 `upper_guuid/upper2_guuid/upper3_guuid`，人数则必须以完整直属关系图计算，并用一条更新语句同步链上所有具有营销承载行的代理。各级代理累计下级数应等于任意深度关系聚合值，今日新增数只统计 `third_marketing_info.date=CURDATE()` 的注册记录。重复执行人数刷新不得重复增加；旧 `today_lower_date` 对应的缓存读取必须为0。顶级 BOSS 缺少营销承载行时只能使用关系聚合展示，不得为了计数伪造注册账号。
30. 支付配置只有部分默认通道已初始化时，`GET /api/configuration/payments` 仍必须为每个通道返回数组型 `infoFields`，不能返回 `null`。整体保存会为尚未配置的默认通道创建 `支付配置_<通道>`，回读时空资料字段的 `null` 与 `[]` 应按同一业务值处理；如果其他字段确实不一致，日志只允许记录 `channels[索引].字段名` 等路径，不能输出支付域名、说明或客户端配置正文。生产验证不得为了测试保存或改变真实支付配置，可用单元测试和候选只读接口确认。
31. 使用至少一个仅因角色属于 `super_admin`、历史 `is_super` 标记曾为0的超级管理员账号，确认“平台收益”位于“系统配置”最后一项，汇总和明细接口可用；普通后台账号即使角色曾残留 `game.platform_revenue.view` 也必须看不到菜单、模块和权限项，直接请求返回403。今日、本月和累计金额必须与只读SQL逐项核对，普通抽水按结算键去重，玩家消费排除“延长时间”。玩家消费金额必须使用 `ABS(add_money)`，明细中的消费前后余额必须读取 `old_money/new_money`；`remark5` 的“余X分”只是金币小数部分，禁止当作账户剩余总额。提现手续费只统计 `third_cash_info` 中已完成且 VIP 标记为1的提现订单并按金额2%计算，普通通道和未完成订单不计入。指定明细强制日期范围且单次不超过31天，重复点击查询会重新请求；原表查询最多单并发并在4秒超时，不能改游戏表或为统计临时给MyISAM大表建索引。首次历史未完全同步时累计卡片必须明确显示同步中。候选8892必须关闭轮播工作进程，正式发布后核对缓存同步状态、正式资源哈希和桌面/手机无横向溢出，再停止候选进程。
