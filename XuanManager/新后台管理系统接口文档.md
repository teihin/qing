# 新后台管理系统接口文档

本文档只描述新后台需要调用的接口、数据库读取方式、参数、返回格式和校验方式。实现新后台时只按本文定义调用，不依赖旧系统内部实现。

线上环境信息：

| 项 | 值 |
| --- | --- |
| 游戏服务器 | `154.37.155.17` |
| MySQL 数据库 | `kbedm` |
| 内部 HTTP 地址 | `http://127.0.0.1:8890` |
| 管理后台访问旧服务方式 | 新后台后端在服务器本机调用 HTTP 和 MySQL |

## 1. 接入原则

新后台只使用两类接口：

1. **MySQL 数据接口**：默认用于玩家列表、详情、战绩、流水、注册记录、代理关系和报表查询；仅本文明确授权的注册、公告和发牌优化等流程允许后端执行限定写入。
2. **内部 HTTP 管理接口**：用于充值/补分/退款、修改在线玩家属性、修复登录、公告、房间命令、运行配置等会影响游戏运行状态的操作。

禁止新后台前端直接访问旧 HTTP 接口。必须由新后台后端封装接口、鉴权、审计、参数校验后再调用。

### 1.1 XuanManager 后台账号会话

后台账号采用单点登录：同一账号只允许保留最近一次成功登录产生的 `mgr_session`。创建新会话时，后端必须在同一事务中先更新对应 `mgr_user` 行取得行锁，使同账号并发登录串行执行，再删除该 `user_id` 的旧会话并插入当前会话；上线迁移会清理此前遗留的重复会话。旧设备后续访问受保护接口返回401并回到登录页，前端在窗口重新获得焦点时检查会话，并提供最多60秒一次的兜底检查。单次退出只删除当前会话；修改密码、管理员重置密码、停用账号或角色权限变更继续按既有规则清退旧会话。

## 2. 通用 HTTP 调用规范

### 2.1 健康检查

```http
GET http://127.0.0.1:8890/index
```

成功返回：

```text
index ok
```

### 2.2 通用命令入口

```http
GET http://127.0.0.1:8890/hall/command
```

Query 参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | 命令名，中文字符串，需要 URL encode |
| `param` | JSON string | 是 | 命令参数 JSON 字符串，需要 URL encode |

调用示例：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_获取_玩家_属性' \
  --data-urlencode 'param={"guuid":"292989","name":"gold","context":"admin-20260807-0001"}'
```

返回格式：

```json
{
  "ret_code": 512,
  "ret_result": "1925"
}
```

状态码：

| `ret_code` | 含义 | 新后台处理 |
| ---: | --- | --- |
| `512` | 成功 | 正常解析 `ret_result` |
| `769` | 失败 | 给出失败提示，写审计 |
| `1280` | 已接收/异步处理 | 不能认为业务已完成，需要按本文档的校验 SQL 读取结果 |

约定：

- `context` 建议每次传唯一操作号，例如 `admin-20260807-0001`，便于排查日志和审计。
- `param` 必须是合法 JSON。
- HTTP 只允许新后台后端从本机访问，不允许公网访问。

### 2.3 禁止开放的旧接口

以下接口不得暴露给后台页面，也不得开放给普通管理员：

```text
/beifeng/eval
/beifeng/exec
/beifeng/reload
```

## 3. 通用 MySQL 查询规范

连接库：

```sql
USE kbedm;
```

实现要求：

- 所有 SQL 使用参数化查询。
- 默认分页参数：`page` 从 `1` 开始，`page_size` 建议最大 `100`。
- 查询日期统一使用 `YYYY-MM-DD`。
- 资金字段展示时把 `sm_gold + sm_gold2 / 100` 作为玩家现金余额。
- 除 15.2 明确允许的发牌优化三个白名单字段外，不要直接 `UPDATE tbl_Account` 的金币、房间、俱乐部积分或其他字段。

## 4. 玩家管理

### 4.1 玩家列表

新后台接口建议：

```http
GET /api/admin/players?keyword=292989&page=1&page_size=50
```

参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `keyword` | string | 否 | 匹配游戏 ID、登录账号、昵称 |
| `page` | int | 否 | 默认 `1` |
| `page_size` | int | 否 | 默认 `50`，最大 `100` |

SQL：

```sql
SELECT
  a.id,
  a.sm_guuid,
  a.sm_wxID,
  a.sm_name,
  a.sm_photo,
  a.sm_gold,
  a.sm_gold2,
  a.sm_stone,
  a.sm_level,
  a.sm_agentID,
  a.sm_reg_time,
  k.accountName,
  FROM_UNIXTIME(k.lasttime) AS last_login_time,
  k.numlogin
FROM tbl_Account a
LEFT JOIN kbe_accountinfos k ON k.entityDBID = a.id
WHERE
  (? = '' OR a.sm_guuid = ? OR a.sm_wxID = ? OR a.sm_name LIKE CONCAT('%', ?, '%') OR k.accountName = ?)
ORDER BY a.id DESC
LIMIT ? OFFSET ?;
```


### 4.5 修改玩家登录密码

XuanManager 已实现接口：

```http
POST /api/game/players/{playerId}/password
```

请求：

```json
{
  "password": "111111",
  "reason": "玩家完成身份核验后申请重置",
  "confirm": true
}
```

旧服务 HTTP：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_设置_玩家_属性' \
  --data-urlencode 'param={"guuid":"292989","name":"userPWD","value":"111111","context":"admin-reset-login-pwd"}'
```

说明：

- 接口要求 `game.player.reset_password`，该权限可在角色权限中独立配置；超级管理员动态拥有全部权限。
- 玩家ID必须是6位数字；新密码必须为6～32个字符、首尾不能有空格，操作备注选填且最多120个字符。
- 请求必须显式提交 `confirm=true`；接口和审计都不返回、不记录明文密码或MD5摘要。
- `value` 传明文，旧服务会保存为 MD5。
- 旧服务返回成功后，XuanManager 会回读 `tbl_Account.sm_userPWD` 与 `MD5(?)` 比对；确认一致后同步注册表密码并再次回读校验：

```sql
UPDATE third_marketing_info
SET player_wxpwd = MD5(?)
WHERE player_guuid = ?;
```

### 4.5.1 超级管理员查看玩家IP和GPS

```http
GET /api/game/players/{playerId}/sensitive
```

- 基础访问要求 `game.player.view`，接口内部还会强制校验当前登录账号是受保护根账号 `admin999`；仅属于 `super_admin` 角色但不是 `admin999` 的账号也返回 HTTP 403。该能力不进入角色权限矩阵。
- 普通管理员即使知道接口地址并直接请求也返回 HTTP `403`，玩家列表接口本身不会批量返回IP或GPS。
- 成功响应包含 `ip`、原始 `gps`、解析后的 `latitude`、`longitude`、`locationAvailable` 和说明；响应设置 `Cache-Control: no-store`。
- 客户端上报格式为“纬度,经度”。页面跳转高德地图时按官方URI要求转换为 `position=经度,纬度`，并声明 `coordinate=wgs84`，只对合法范围内且非零的坐标显示定位按钮。
- 每次成功读取敏感信息都会写入 `game.player.sensitive.view` 操作审计，但审计只记录读取了IP/GPS字段，不保存具体IP或坐标值；该条 `admin999` 审计对其他所有账号隐藏。

### 4.8 封号管理与历史记录

XuanManager 接口：

```http
GET  /api/game/bans
POST /api/game/bans
POST /api/game/bans/{playerId}/unban
GET  /api/game/bans/history
```

- 当前封号列表和历史记录均要求 `game.ban.view`。
- 封号要求 `game.ban.create`，解封要求 `game.ban.remove`。
- 当前封号状态以 `tbl_Account.sm_client_status` 非空为准；封号和解封仍通过本机8890的 `异步_设置_玩家_属性` 修改 `client_status`，成功返回前必须回读数据库确认。
- 历史接口读取 `mgr_audit_log` 中 `game.player.ban`、`game.player.unban` 两类记录，不从当前账号状态反推历史。
- 历史接口支持 `keyword`、`operation=ban|unban`、`result=success|failed`、`page` 和 `pageSize`；关键字可匹配玩家ID、昵称、登录账号、封号原因和后台操作人。
- 解封记录的“当时封号原因”读取操作前审计快照；即使当前 `client_status` 已清空，仍能说明解除的是哪一条封号提示。
- 成功和失败操作都保留，返回操作结果与服务端结果说明。`admin999` 执行的封号、解封或失败记录只有 `admin999` 自己可见；其他后台账号（包括其他 `super_admin` 角色账号）的记录按正常权限显示。

## 5. 注册账号管理

### 5.1 登录字段说明

注册表字段：

| 字段 | 说明 |
| --- | --- |
| `player_wxid` | 登录账号，唯一 |
| `player_wxname` | 昵称 |
| `player_wxpwd` | 登录密码 MD5 |
| `player_guuid` | 玩家首次进入游戏后回填的游戏 ID |
| `upper_guuid` | 直属代理 ID，由注册邀请码确定 |
| `upper2_guuid` | 二级上级代理 ID，注册时根据邀请码代理的关系链写入 |
| `upper3_guuid` | 三级上级代理 ID，注册时根据邀请码代理的关系链写入；旧表只提供到该层 |
| `all_lower_count` | 该代理任意深度的累计注册下级数，由直属关系图幂等重算 |
| `today_lower_count` | 该代理今天注册下级数，必须结合 `today_lower_date` 读取 |
| `today_lower_date` | 今日人数所属的数据库日期，格式 `YYYY-MM-DD` |

客户端登录账号填写 `player_wxid`，不是 `player_wxname`。

### 5.2 客户端注册账号

XuanManager 已提供无需后台登录态的公开注册接口，供游戏客户端注册页调用：

```http
POST /api/game/registrations
Content-Type: application/json
```

请求：

```json
{
  "invitationCode": "648425",
  "nickname": "测试Player",
  "loginName": "User001",
  "password": "111111",
  "avatarIndex": "12"
}
```

字段映射：

| 客户端字段 | 游戏表字段 | 校验规则 |
| --- | --- | --- |
| `invitationCode` | `upper_guuid` | 6 位数字，且必须是有效代理或盟主的游戏 ID |
| `nickname` | `player_wxname` | 1～32 个字符，只允许中文、英文字母或数字，不允许空格或符号；全局不可重复 |
| `loginName` | `player_wxid` | 6～16 位英文字母或数字，全局不可重复；客户端登录时填写此值 |
| `password` | `player_wxpwd` | 6～32 个字符，按旧游戏兼容要求保存为 MD5 |
| `avatarIndex` | `tbl_Account.sm_photo` | 头像编号 `1`～`100`；省略时兼容默认为 `1` |

为兼容本文旧字段，接口也接受 `upper_guuid`、`player_wxid`、`player_wxname`，头像兼容字段为 `photo`；若新旧字段同时提交，内容必须一致。成功返回 HTTP `201`，密码及摘要均不会出现在响应、日志或审计记录中。接口允许游戏客户端跨域调用，并按来源 IP 限制为 10 分钟最多 10 次请求。

邀请码是注册必填项，注册成功即完成直属代理绑定，不存在单独的“未绑定注册”状态。接口在写入新记录前从邀请码代理开始沿直属上级逐层回溯，必须最终到达 BOSS，最多保护性检查64层，并拒绝断链、无效上级或循环关系。旧表结构仍只固化 `upper_guuid/upper2_guuid/upper3_guuid` 前三层供游戏兼容；完整上级链保留在本次注册处理内，用于一次更新链上所有具有营销记录的代理。

累计和今日人数不依赖三层字段展开，而是以每条注册记录的直属 `upper_guuid` 构建关系图并逐层遍历，因此第四层及更深代理也能准确累计。注册后对完整上级链重新计算累计下级数和今天注册数，再用单条 `UPDATE ... JOIN` 同步整条链；不直接执行缓存字段 `+1`，所以相同刷新重复执行不会重复累计。顶级 BOSS 没有 `third_marketing_info` 承载行时，代理查询使用同一直属关系图实时聚合返回准确人数，不伪造 BOSS 注册记录。

注册表 `third_marketing_info` 没有头像字段。接口写入注册记录后会等待游戏服生成 `player_guuid`，再通过服务器本机 `8890` 的 `异步_设置_玩家_属性` 命令把头像编号写入 `tbl_Account.sm_photo`；客户端首次登录也会使用本地保存的注册选择补设一次，避免异步回写期间头像丢失。

成功响应示例：

```json
{
  "ok": true,
  "data": {
    "registrationId": 123,
    "invitationCode": "648425",
    "loginName": "User01",
    "nickname": "测试Player",
    "avatarIndex": "12",
    "message": "注册成功，请使用登录账号和密码进入游戏"
  }
}
```

常见错误：

| HTTP 状态 | 错误码 | 说明 |
| --- | --- | --- |
| `400` | `INVALID_REGISTRATION` | 字段缺失或格式不正确 |
| `400` | `INVALID_INVITATION_CODE` | 邀请码不是有效代理或盟主 |
| `409` | `NICKNAME_EXISTS` | 昵称已存在（英文大小写不同也视为重复） |
| `409` | `LOGIN_NAME_EXISTS` | 登录账号已存在 |
| `503` | `REGISTRATION_BUSY` | 同一昵称正在被其他注册请求处理，请稍后重试 |
| `429` | `REGISTRATION_RATE_LIMITED` | 同一来源请求过于频繁 |

SQL：

```sql
INSERT INTO third_marketing_info
  (date, time, upper_guuid, upper2_guuid, upper3_guuid,
```

- `all_lower_count` 是当前关系字段中包含该代理的全部注册记录数。

旧服务 HTTP：

```bash
  --data-urlencode 'header=异步_执行_房间_命令' \

```

参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `room_id` | int | 是 | KB 大厅实时列表中当前存在的房间 ID |
| `cmd` | string | 是 | 房间事件名纯字符串，禁止嵌套 JSON |
| `context` | string | 否 | 操作号 |

解散命令映射：

- 强制解散：`cmd="强制_解散_事件"`。
- 友好解散：`cmd="申请_解散_事件"`。
- `is_qiangzhi` 不属于 `异步_执行_房间_命令` 的有效参数，不能用它区分友好和强制解散。
- 禁止把 `{\"header\":\"强制_解散_事件\",...}` 序列化后塞入 `cmd`；这会被房间当成无法识别的命令。

结果判定：

- `ret_code=512/1280` 只表示旧服务入口接受或转发了命令，不能证明 `room.reqExec()` 已执行，更不能直接显示“解散成功”。
- 命令发送后必须再次调用 `查询_大厅_所有房间`。只有目标房间消失，或明确进入“已关闭/已解散”等最终状态，才返回 `status=dissolved`、`verified=true`。
- 房间仍存在时返回 HTTP 202、`status=pending`、`verified=false`；列表复查失败时返回 `status=verification_unavailable`，两者均不得向操作员显示为成功。
- “解散全部”不再向不存在的 `room_id=0` 发送单个房间命令；XuanManager 先读取完整实时房间列表，再逐房发送相同的纯字符串命令，并汇总接受、失败和复查仍存在的数量。

安全要求：

- 房间维护整个模块仅 `super_admin` 超级管理员角色可访问；普通后台账号即使历史角色残留房间权限，直接调用接口仍返回 HTTP 403。
- 指定房间操作在超级管理员身份基础上还校验内部权限 `game.room_maintenance.dissolve`。
- 全部房间操作在超级管理员身份基础上还校验内部权限 `game.room_maintenance.dissolve_all`，并输入 `ALL_ROOMS` 二次确认。
- 必须写审计。

```sql
FROM usr_hash2_info
WHERE hash_key = ?;
```

更新：

```sql
INSERT INTO usr_hash_info (hash_key, hash_content)
VALUES (?, ?)
ON DUPLICATE KEY UPDATE hash_content = VALUES(hash_content);
```


### 14.3 奖池爆奖概率与平台提留

`GET /api/configuration/reward-pools/controls` 同时读取以下大厅配置：

- `reward_rate`：各底皮基础放奖概率，0～100。
- `reward_nopai_on`：全局不发奖概率，0～100。
- `reward_nopai_dipi`：各底皮不发奖概率，0～100。
- `reward_modify`：各底皮产生奖池累积金额时，平台先固定提留的金额，单位为“元”。该字段不按分换算。

预计实际放奖概率按执行顺序展示为：

```text
预计实际放奖概率
= reward_rate
× (100 - reward_nopai_on) / 100
× (100 - reward_nopai_dipi) / 100
```

例如基础放奖100%、全局不发奖0%、对应底皮不发奖70%，页面显示预计实际放奖约30%，不能只把 `reward_rate=100` 展示成实际中奖100%。

正式游戏配置的真实存储格式为逗号分隔字符串：


## 15. 优化管理

### 15.1 查询发牌优化

当前游戏只使用发牌优化，即 `sm_optimize01_man/count/chance`。`sm_optimize02_*` 属于其他玩法遗留字段，本后台不查询、不展示、不修改。`sm_optimize01_man` 保留为游戏运行所需的 BOSS ID，不能把它显示成后台操作账号；列表与详情优先读取最近一条成功的 `mgr_audit_log.operator_name` 作为 `configuredBy`，并返回 `configuredSource='admin'`。没有后台成功审计的历史配置才回退显示游戏设置人，并标记 `configuredSource='game'`。关键字查询同时支持后台操作账号。

XuanManager 接口：

```http
GET /api/game/player-optimization?status=active&keyword=&minChance=&maxChance=&page=1&pageSize=50
GET /api/game/player-optimization/history?keyword=&operation=&result=&page=1&pageSize=20
GET /api/game/player-optimization/{playerId}
POST /api/game/player-optimization
PUT /api/game/player-optimization/{playerId}
DELETE /api/game/player-optimization/{playerId}
```

历史接口复用 `game.player_optimization.view` 权限，从 `webcm.mgr_audit_log` 读取本后台产生的新增、调整、删除记录。`operation` 可选 `create/update/delete`，`result` 可选 `success/failed`；关键字可匹配玩家 ID、昵称、登录账号或操作人。响应只返回可读的操作前后次数与概率，不向浏览器透传原始审计 JSON。`admin999` 执行的记录由服务端统一可见性条件过滤，只有 `admin999` 自己可以查看；包括其他 `super_admin` 角色账号在内的所有账号，通过页面或直调接口都看不到这些记录。其他账号的操作记录按正常角色权限显示。

### 15.2 新增、调整与删除优化

XuanManager 已按用户授权把发牌优化拆成三个独立操作：`create` 只为当前未启用的玩家新增，`update` 只调整已经启用的参数，`delete` 只删除已经启用的优化。三个接口分别校验 `game.player_optimization.create/update/delete` 权限，是否允许操作完全由后台角色权限矩阵决定，不再额外要求当前登录者是超级管理员。新增、调整和删除均不要求填写原因，页面不显示原因输入框；兼容调用方若提供非空 `reason`，后端仍做长度与控制字符校验并写入审计。所有操作要求显式确认；调整和删除还提交页面基准值，避免覆盖其他管理员刚完成的修改。

发牌优化是本系统直接写游戏数据库的明确例外。后端必须使用只连接服务器本机 `127.0.0.1` 的独立游戏库账号，浏览器不能接触该连接或凭据。禁止调用只适用于在线实体的 `异步_设置_玩家_属性`；否则离线玩家会出现接口返回成功但数据库未完整生效的问题。

`tbl_Account` 为 InnoDB。新增、调整和删除必须在同一个事务中锁定目标玩家、校验旧值、一次更新 `sm_optimize01_man`、`sm_optimize01_count`、`sm_optimize01_chance` 三个白名单字段，并在提交前回读。示例：

```sql
START TRANSACTION;

SELECT sm_optimize01_man, sm_optimize01_count, sm_optimize01_chance
FROM tbl_Account
WHERE sm_guuid = ?
FOR UPDATE;

UPDATE tbl_Account
SET sm_optimize01_man = ?,
    sm_optimize01_count = ?,
    sm_optimize01_chance = ?
WHERE sm_guuid = ?;

SELECT sm_optimize01_man, sm_optimize01_count, sm_optimize01_chance
FROM tbl_Account
WHERE sm_guuid = ?;

COMMIT;
```

新增时目标玩家当前次数必须小于等于 0；调整和删除时数据库锁定后的三个旧值必须与请求中的页面基准完全一致。删除的目标值固定为空设置人、0 次、0%。任一步失败都回滚整个事务，不会留下部分字段。事务提交成功后，把操作人、原因（如有）、操作前后值和 `writeMode=direct-database-transaction` 写入 `webcm.mgr_audit_log`。该流程不依赖玩家在线状态。

XuanManager 新增请求：

```json
{
  "playerId": "292989",
  "remainingCount": 10,
  "chance": 30,
  "confirm": true
}
```

XuanManager 调整请求：

```json
{
  "remainingCount": 10,
  "chance": 30,
  "expectedManager": "648425",
  "expectedCount": 58,
  "expectedChance": 100,
  "confirm": true
}
```

XuanManager 删除请求：

```json
{
  "expectedManager": "648425",
  "expectedCount": 58,
  "expectedChance": 100,
  "confirm": true
}
```

删除会在同一事务中把 `sm_optimize01_count`、`sm_optimize01_chance` 归零并清空 `sm_optimize01_man`。调整不再接受 0 次；运营需要停用时必须使用明确的删除接口，避免普通参数调整误删优化。

校验：

```sql

  sm_guuid,
  sm_name,
  sm_optimize01_man,
  sm_optimize01_count,
  sm_optimize01_chance
FROM tbl_Account
WHERE sm_guuid = ?;

SELECT operator_name, action, request_json, before_json, after_json, created_at
FROM webcm.mgr_audit_log
WHERE target_type = 'game_player'
  AND target_id = ?
  AND action IN ('game.player_optimization.create', 'game.player_optimization.update', 'game.player_optimization.delete')
ORDER BY id DESC
LIMIT 20;
```

## 21. XuanManager 平台收益统计

XuanManager 已新增“系统配置 → 平台收益”，并固定在系统配置目录最后一项。该模块允许所有 `super_admin` 超级管理员角色账号查看和调用；`is_super` 只用于识别并隐藏 `admin999` 根账号，不作为平台收益能力判定。普通后台账号不会收到菜单或模块数据，即使角色历史上残留 `game.platform_revenue.view` 权限也会被后端拒绝，角色权限配置页不提供该权限。本期为运营统计口径，不是财务结算账本；“当期”按中国运营日当天 `00:00–24:00` 统计，另显示本月和全部已同步历史。

当前平台净收益公式：

```text
平台净收益
= 大厅普通结算抽水
+ 大厅奖池中奖折扣
+ 玩家消费
+ 提现手续费
- 大厅普通代理红利
- 大厅奖池代理红利
- 抽奖池转入
```

提现手续费按已完成的 VIP 提现订单金额的 `2%` 计入；普通提现通道不收手续费，不计入本项。充值手续费暂未计入。`remark4` 记录的代理奖池待分配金额单独展示，但不重复作为支出扣减；奖池代理实际支出以 `usr_income_info2.tax_number / 100` 为准。

### 21.1 汇总接口

```http
GET /api/game/platform-revenue/summary
Access: super administrator only
```

系统配置路径同时提供 `GET /api/configuration/platform-revenue/summary`，返回结构和权限规则完全一致。

返回今日、本月、累计三个周期的净收益、收入流入、代理支出、抽奖池转入及全部构成项；金额统一为“元”。累计值只从 `mgr_platform_revenue_daily` 每日缓存汇总，接口同时返回 `historyComplete`、已同步日期范围和最近刷新时间。历史较长时按最多31天一批逐步补齐，未完整前页面必须显示“历史同步中”，不能把部分历史标成完整总收益。

- `withdrawal_fee`：已完成的 VIP 提现手续费。

开始和结束日期必填且包含首尾日期，单次最多31天。返回所选来源的时间段汇总、每日汇总和分页逐笔明细。

### 21.3 数据口径与性能保护

- 大厅房间用 `usr_total_score.remark LIKE '0,%'` 确认，并按同一 `date + roomID` 关联收益流水。
- 普通抽水读取 `usr_income_info.remark3`（元），按 `date + roomID + winner_guuid + time + remark3` 去重；同一结算的 `tax_number`（分）仍全部累计为普通代理红利支出。
- 奖池中奖折扣读取 `usr_cash_water_sub_zhongjiangzhekou` 的 `option_type='中奖折扣'`；`add_money`、`remark4`、`remark5` 均按元解释。
- 奖池代理实际支出读取 `usr_income_info2.tax_number / 100`。
- 玩家消费读取 `usr_cash_water` 的 `option_type='消费'`，金额使用 `ABS(add_money)`；专门统计 `玩家_消费_命令` 时排除 `remark4='延长时间'` 和零金额。
- 玩家消费原始备注可能使用容易误读的“角/分”标签，例如 `用1000角-余0分`。其中“余X分”只对应消费后金币的小数部分，不是账户总余额；平台收益明细不得据此显示“剩余金额”。消费金额使用 `ABS(add_money)`，消费前后账户余额分别使用 `old_money/new_money`，例如 `5843.00 -> 5833.00` 显示为“消费前余额 5843.00 元，消费后余额 5833.00 元”。
- 提现手续费读取 `third_cash_info`：仅统计 `work_type='提现'`、`status='完成'`、`money>0` 且备注末段 VIP 标记为 `1` 的订单，费率固定为 `2%`；`money` 按元解释，普通通道和未完成订单不计入。
- 原游戏表保持只读，不新增索引、不改变 MyISAM 结构；所有原表 SQL 必须带日期范围并优先使用 `date` 索引。
- 汇总落入 `webcm.mgr_platform_revenue_daily`，同步状态落入 `mgr_platform_revenue_cache_state`。同一进程最多执行一个收益原表查询，查询上下文4秒超时；页面打开只刷新汇总，逐笔明细必须由用户点击后才读取。所选日期每日缓存已经齐全时，明细接口直接复用缓存计算时间段汇总，不因缓存超过60秒而再次扫描五类原始汇总；当前运营日的60秒刷新只由汇总接口触发。
- 当前普通抽水表依赖代理分成记录。若玩家完全没有任何代理分成行，现有数据可能无法还原该笔抽水，页面必须保留这一统计边界说明。

## 22. XuanManager 时间口径

XuanManager 所有页面、查询日期和配置时间统一使用北京时间（中国标准时间，UTC+8），前端不得依赖操作人员电脑或浏览器当前时区。页面顶部常驻显示“北京时间 UTC+8”；包含具体时刻的表头和详情应明确标注北京时间。

正式服务器当前存在混合时间来源，不能通过修改数据库连接时区或给所有字段统一加8小时处理：

- `usr_cash_water`、房间战绩、平台收益、`tbl_Account.sm_reg_time`、`third_marketing_info.reg_proxy_date/reg_proxy_time`、活动配置和轮播执行时间等业务字符串已经按北京时间写入，接口保持原值。
- `mgr_audit_log.created_at`、`mgr_user.created_at/last_login_at`、管理表默认 `CURRENT_TIMESTAMP`、后台注册关系的 `third_marketing_info.date/time` 和当前 MySQL `FROM_UNIXTIME(lasttime)` 结果为UTC，XuanManager查询时转换为北京时间后再返回。
- 后端返回带时区的时间戳时，前端固定用 `Asia/Shanghai` 渲染；后端返回无时区的游戏业务字符串时，前端按北京时间解释。
- `datetime-local` 输入没有时区信息，轮播公告等页面必须明确按北京时间解析，再提交带偏移的ISO时间；重新读取时仍还原为同一个北京时间墙上时刻。
- “今日”“本月”和日期范围都按北京时间边界计算。工作台每日新注册使用显式北京时间 `00:00–24:00` 查询 `sm_reg_time`，管理审计的北京时间日界线需换算成UTC后查询原始审计列。

接口调用方不应再对 XuanManager 已返回的时间手工加减8小时。
