# 新后台管理系统接口文档

本文档只描述新后台需要调用的接口、数据库读取方式、参数、返回格式和校验方式。实现新后台时只按本文定义调用，不依赖旧系统内部实现。

线上环境信息：

| 项 | 值 |
| --- | --- |
| 游戏服务器 | `154.37.155.17` |
| MySQL 数据库 | `kbedm` |
| 内部 HTTP 地址 | `http://127.0.0.1:8890` |
| 管理后台访问旧服务方式 | 新后台后端在服务器本机调用 HTTP 和 MySQL |

## 1. 接入原则

新后台只使用两类接口：

1. **MySQL 数据接口**：默认用于玩家列表、详情、战绩、流水、注册记录、代理关系和报表查询；仅本文明确授权的注册、公告和发牌优化等流程允许后端执行限定写入。
2. **内部 HTTP 管理接口**：用于充值/补分/退款、修改在线玩家属性、修复登录、公告、房间命令、运行配置等会影响游戏运行状态的操作。

禁止新后台前端直接访问旧 HTTP 接口。必须由新后台后端封装接口、鉴权、审计、参数校验后再调用。

### 1.1 XuanManager 后台账号会话

后台账号采用单点登录：同一账号只允许保留最近一次成功登录产生的 `mgr_session`。创建新会话时，后端必须在同一事务中先更新对应 `mgr_user` 行取得行锁，使同账号并发登录串行执行，再删除该 `user_id` 的旧会话并插入当前会话；上线迁移会清理此前遗留的重复会话。旧设备后续访问受保护接口返回401并回到登录页，前端在窗口重新获得焦点时检查会话，并提供最多60秒一次的兜底检查。单次退出只删除当前会话；修改密码、管理员重置密码、停用账号或角色权限变更继续按既有规则清退旧会话。

## 2. 通用 HTTP 调用规范

### 2.1 健康检查

```http
GET http://127.0.0.1:8890/index
```

成功返回：

```text
index ok
```

### 2.2 通用命令入口

```http
GET http://127.0.0.1:8890/hall/command
```

Query 参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `header` | string | 是 | 命令名，中文字符串，需要 URL encode |
| `param` | JSON string | 是 | 命令参数 JSON 字符串，需要 URL encode |

调用示例：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_获取_玩家_属性' \
  --data-urlencode 'param={"guuid":"292989","name":"gold","context":"admin-20260807-0001"}'
```

返回格式：

```json
{
  "ret_code": 512,
  "ret_result": "1925"
}
```

状态码：

| `ret_code` | 含义 | 新后台处理 |
| ---: | --- | --- |
| `512` | 成功 | 正常解析 `ret_result` |
| `769` | 失败 | 给出失败提示，写审计 |
| `1280` | 已接收/异步处理 | 不能认为业务已完成，需要按本文档的校验 SQL 读取结果 |

约定：

- `context` 建议每次传唯一操作号，例如 `admin-20260807-0001`，便于排查日志和审计。
- `param` 必须是合法 JSON。
- HTTP 只允许新后台后端从本机访问，不允许公网访问。

### 2.3 禁止开放的旧接口

以下接口不得暴露给后台页面，也不得开放给普通管理员：

```text
/beifeng/eval
/beifeng/exec
/beifeng/reload
```

## 3. 通用 MySQL 查询规范

连接库：

```sql
USE kbedm;
```

实现要求：

- 所有 SQL 使用参数化查询。
- 默认分页参数：`page` 从 `1` 开始，`page_size` 建议最大 `100`。
- 查询日期统一使用 `YYYY-MM-DD`。
- 资金字段展示时把 `sm_gold + sm_gold2 / 100` 作为玩家现金余额。
- 除 15.2 明确允许的发牌优化三个白名单字段外，不要直接 `UPDATE tbl_Account` 的金币、房间、俱乐部积分或其他字段。

## 4. 玩家管理

### 4.1 玩家列表

新后台接口建议：

```http
GET /api/admin/players?keyword=292989&page=1&page_size=50
```

参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `keyword` | string | 否 | 匹配游戏 ID、登录账号、昵称 |
| `page` | int | 否 | 默认 `1` |
| `page_size` | int | 否 | 默认 `50`，最大 `100` |

SQL：

```sql
SELECT
  a.id,
  a.sm_guuid,
  a.sm_wxID,
  a.sm_name,
  a.sm_photo,
  a.sm_gold,
  a.sm_gold2,
  a.sm_stone,
  a.sm_level,
  a.sm_agentID,
  a.sm_reg_time,
  k.accountName,
  FROM_UNIXTIME(k.lasttime) AS last_login_time,
  k.numlogin
FROM tbl_Account a
LEFT JOIN kbe_accountinfos k ON k.entityDBID = a.id
WHERE
  (? = '' OR a.sm_guuid = ? OR a.sm_wxID = ? OR a.sm_name LIKE CONCAT('%', ?, '%') OR k.accountName = ?)
ORDER BY a.id DESC
LIMIT ? OFFSET ?;
```

返回字段建议：

```json

      "login_name": "900001",
      "name": "test01",

      "agent_id": "648425",
```

### 4.5 修改玩家登录密码

XuanManager 已实现接口：

```http
POST /api/game/players/{playerId}/password
```

请求：

```json
{
  "password": "111111",
  "reason": "玩家完成身份核验后申请重置",
  "confirm": true
}
```

旧服务 HTTP：

```bash
curl --get 'http://127.0.0.1:8890/hall/command' \
  --data-urlencode 'header=异步_设置_玩家_属性' \
  --data-urlencode 'param={"guuid":"292989","name":"userPWD","value":"111111","context":"admin-reset-login-pwd"}'
```

说明：

- 接口要求 `game.player.reset_password`，该权限可在角色权限中独立配置；超级管理员动态拥有全部权限。
- 玩家ID必须是6位数字；新密码必须为6～32个字符、首尾不能有空格，操作备注选填且最多120个字符。
- 请求必须显式提交 `confirm=true`；接口和审计都不返回、不记录明文密码或MD5摘要。
- `value` 传明文，旧服务会保存为 MD5。
- 旧服务返回成功后，XuanManager 会回读 `tbl_Account.sm_userPWD` 与 `MD5(?)` 比对；确认一致后同步注册表密码并再次回读校验：

```sql
UPDATE third_marketing_info
SET player_wxpwd = MD5(?)
WHERE player_guuid = ?;
```

### 4.5.1 超级管理员查看玩家IP和GPS

```http
GET /api/game/players/{playerId}/sensitive
```

- 基础访问要求 `game.player.view`，接口内部还会强制校验 `is_super=true`；该能力不进入普通角色权限矩阵。
- 普通管理员即使知道接口地址并直接请求也返回 HTTP `403`，玩家列表接口本身不会批量返回IP或GPS。
- 成功响应包含 `ip`、原始 `gps`、解析后的 `latitude`、`longitude`、`locationAvailable` 和说明；响应设置 `Cache-Control: no-store`。
- 客户端上报格式为“纬度,经度”。页面跳转高德地图时按官方URI要求转换为 `position=经度,纬度`，并声明 `coordinate=wgs84`，只对合法范围内且非零的坐标显示定位按钮。
- 每次成功读取敏感信息都会写入 `game.player.sensitive.view` 操作审计，但审计只记录读取了IP/GPS字段，不保存具体IP或坐标值。

### 4.8 封号管理与历史记录

XuanManager 接口：

```http
GET  /api/game/bans
POST /api/game/bans
POST /api/game/bans/{playerId}/unban
GET  /api/game/bans/history
```

- 当前封号列表和历史记录均要求 `game.ban.view`。
- 封号要求 `game.ban.create`，解封要求 `game.ban.remove`。
- 当前封号状态以 `tbl_Account.sm_client_status` 非空为准；封号和解封仍通过本机8890的 `异步_设置_玩家_属性` 修改 `client_status`，成功返回前必须回读数据库确认。
- 历史接口读取 `mgr_audit_log` 中 `game.player.ban`、`game.player.unban` 两类记录，不从当前账号状态反推历史。
- 历史接口支持 `keyword`、`operation=ban|unban`、`result=success|failed`、`page` 和 `pageSize`；关键字可匹配玩家ID、昵称、登录账号、封号原因和后台操作人。
- 解封记录的“当时封号原因”读取操作前审计快照；即使当前 `client_status` 已清空，仍能说明解除的是哪一条封号提示。
- 成功和失败操作都保留，返回操作结果与服务端结果说明。普通后台用户不能看到超级管理员执行的封号、解封或失败记录；超级管理员可查看完整历史。

## 5. 注册账号管理

### 5.1 登录字段说明

注册表字段：

| 字段 | 说明 |
| --- | --- |
| `player_wxid` | 登录账号，唯一 |
| `player_wxname` | 昵称 |
| `player_wxpwd` | 登录密码 MD5 |
| `player_guuid` | 玩家首次进入游戏后回填的游戏 ID |
| `upper_guuid` | 上级代理 ID |

客户端登录账号填写 `player_wxid`，不是 `player_wxname`。

### 5.2 客户端注册账号

XuanManager 已提供无需后台登录态的公开注册接口，供游戏客户端注册页调用：

```http
POST /api/game/registrations
Content-Type: application/json
```

请求：

```json
{
  "invitationCode": "648425",
  "nickname": "测试Player",
  "loginName": "User001",
  "password": "111111",
  "avatarIndex": "12"
}
```

字段映射：

| 客户端字段 | 游戏表字段 | 校验规则 |
| --- | --- | --- |
| `invitationCode` | `upper_guuid` | 6 位数字，且必须是有效代理或盟主的游戏 ID |
| `nickname` | `player_wxname` | 1～32 个字符，只允许中文、英文字母或数字，不允许空格或符号；全局不可重复 |
| `loginName` | `player_wxid` | 6～16 位英文字母或数字，全局不可重复；客户端登录时填写此值 |
| `password` | `player_wxpwd` | 6～32 个字符，按旧游戏兼容要求保存为 MD5 |
| `avatarIndex` | `tbl_Account.sm_photo` | 头像编号 `1`～`100`；省略时兼容默认为 `1` |

为兼容本文旧字段，接口也接受 `upper_guuid`、`player_wxid`、`player_wxname`，头像兼容字段为 `photo`；若新旧字段同时提交，内容必须一致。成功返回 HTTP `201`，密码及摘要均不会出现在响应、日志或审计记录中。接口允许游戏客户端跨域调用，并按来源 IP 限制为 10 分钟最多 10 次请求。

注册表 `third_marketing_info` 没有头像字段。接口写入注册记录后会等待游戏服生成 `player_guuid`，再通过服务器本机 `8890` 的 `异步_设置_玩家_属性` 命令把头像编号写入 `tbl_Account.sm_photo`；客户端首次登录也会使用本地保存的注册选择补设一次，避免异步回写期间头像丢失。

成功响应示例：

```json
{
  "ok": true,
  "data": {
    "registrationId": 123,
    "invitationCode": "648425",
    "loginName": "User01",
    "nickname": "测试Player",
    "avatarIndex": "12",
    "message": "注册成功，请使用登录账号和密码进入游戏"
  }
}
```

常见错误：

| HTTP 状态 | 错误码 | 说明 |
| --- | --- | --- |
| `400` | `INVALID_REGISTRATION` | 字段缺失或格式不正确 |
| `400` | `INVALID_INVITATION_CODE` | 邀请码不是有效代理或盟主 |
| `409` | `NICKNAME_EXISTS` | 昵称已存在（英文大小写不同也视为重复） |
| `409` | `LOGIN_NAME_EXISTS` | 登录账号已存在 |
| `503` | `REGISTRATION_BUSY` | 同一昵称正在被其他注册请求处理，请稍后重试 |
| `429` | `REGISTRATION_RATE_LIMITED` | 同一来源请求过于频繁 |

SQL：

```sql
INSERT INTO third_marketing_info
  (date, time, upper_guuid, player_wxid, player_wxname, player_wxpwd, status, level)
VALUES
  (CURDATE(), CURTIME(), ?, ?, ?, MD5(?), '', 0);
```

头像异步回写：

```text
header=异步_设置_玩家_属性
param={"guuid":"<player_guuid>","name":"photo","value":"12","context":"<operation-context>"}
```

唯一键冲突处理：

```sql
SELECT id, player_guuid, player_wxid, player_wxname
FROM third_marketing_info
WHERE player_wxid = ?;
```

### 15.1 查询发牌优化

当前游戏只使用发牌优化，即 `sm_optimize01_man/count/chance`。`sm_optimize02_*` 属于其他玩法遗留字段，本后台不查询、不展示、不修改。`sm_optimize01_man` 保留为游戏运行所需的 BOSS ID，不能把它显示成后台操作账号；列表与详情优先读取最近一条成功的 `mgr_audit_log.operator_name` 作为 `configuredBy`，并返回 `configuredSource='admin'`。没有后台成功审计的历史配置才回退显示游戏设置人，并标记 `configuredSource='game'`。关键字查询同时支持后台操作账号。

```http

GET /api/game/player-optimization/history?keyword=&operation=&result=&page=1&pageSize=20
```

### 15.2 新增、调整与删除优化

XuanManager 已按用户授权把发牌优化拆成三个独立操作：`create` 只为当前未启用的玩家新增，`update` 只调整已经启用的参数，`delete` 只删除已经启用的优化。三个接口分别校验 `game.player_optimization.create/update/delete` 权限，是否允许操作完全由后台角色权限矩阵决定，不再额外要求当前登录者是超级管理员。新增、调整和删除均不要求填写原因，页面不显示原因输入框；兼容调用方若提供非空 `reason`，后端仍做长度与控制字符校验并写入审计。所有操作要求显式确认；调整和删除还提交页面基准值，避免覆盖其他管理员刚完成的修改。

发牌优化是本系统直接写游戏数据库的明确例外。后端必须使用只连接服务器本机 `127.0.0.1` 的独立游戏库账号，浏览器不能接触该连接或凭据。禁止调用只适用于在线实体的 `异步_设置_玩家_属性`；否则离线玩家会出现接口返回成功但数据库未完整生效的问题。

`tbl_Account` 为 InnoDB。新增、调整和删除必须在同一个事务中锁定目标玩家、校验旧值、一次更新 `sm_optimize01_man`、`sm_optimize01_count`、`sm_optimize01_chance` 三个白名单字段，并在提交前回读。示例：

```sql
START TRANSACTION;

SELECT sm_optimize01_man, sm_optimize01_count, sm_optimize01_chance
FROM tbl_Account
WHERE sm_guuid = ?
FOR UPDATE;

UPDATE tbl_Account
SET sm_optimize01_man = ?,
    sm_optimize01_count = ?,
    sm_optimize01_chance = ?
WHERE sm_guuid = ?;

SELECT sm_optimize01_man, sm_optimize01_count, sm_optimize01_chance
FROM tbl_Account
WHERE sm_guuid = ?;

COMMIT;
```

新增时目标玩家当前次数必须小于等于 0；调整和删除时数据库锁定后的三个旧值必须与请求中的页面基准完全一致。删除的目标值固定为空设置人、0 次、0%。任一步失败都回滚整个事务，不会留下部分字段。事务提交成功后，把操作人、原因（如有）、操作前后值和 `writeMode=direct-database-transaction` 写入 `webcm.mgr_audit_log`。该流程不依赖玩家在线状态。

XuanManager 新增请求：

```json
{
  "playerId": "292989",
  "remainingCount": 10,
  "chance": 30,
  "confirm": true
}
```

XuanManager 调整请求：

```json
{
  "remainingCount": 10,
  "chance": 30,
  "expectedManager": "648425",
  "expectedCount": 58,
  "expectedChance": 100,
  "confirm": true
}
```

XuanManager 删除请求：

```json
{
  "expectedManager": "648425",
  "expectedCount": 58,
  "expectedChance": 100,
  "confirm": true
}
```

删除会在同一事务中把 `sm_optimize01_count`、`sm_optimize01_chance` 归零并清空 `sm_optimize01_man`。调整不再接受 0 次；运营需要停用时必须使用明确的删除接口，避免普通参数调整误删优化。

校验：

```sql
SELECT
  sm_guuid,
  sm_name,
  sm_optimize01_man,
  sm_optimize01_count,
  sm_optimize01_chance
FROM tbl_Account
WHERE sm_guuid = ?;

SELECT operator_name, action, request_json, before_json, after_json, created_at
FROM webcm.mgr_audit_log
WHERE target_type = 'game_player'
  AND target_id = ?
  AND action IN ('game.player_optimization.create', 'game.player_optimization.update', 'game.player_optimization.delete')
ORDER BY id DESC
LIMIT 20;
```

## 18. 管理操作审计要求

| 配置修改 | 配置组、配置键、旧值、新值 |
| 房间命令 | 房间 ID、命令内容 |
| 优化设置 | 玩家 ID、次数、概率、设置人 |
