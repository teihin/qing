# XuanManager

XuanManager 是游戏运营团队自己的后台管理系统。后台账号与游戏玩家严格分离；系统设置管理后台自身账号和权限，游戏管理默认只读接入业务数据，仅对注册、公告、奖池、封号等已明确授权的流程开放最小写入能力。

## 当前功能

- 后台账号密码登录、单点会话、会话退出和登录失败锁定；同一后台账号只保留最近一次成功登录，新设备登录后旧设备会话立即失效。后台密码只要求至少 6 位，不强制字符组合，bcrypt 的 72 字节上限保持不变。
- `super_admin` 超级管理员角色中的账号均拥有全部功能权限；`is_super` 不再代表角色能力，只保留为 `admin999` 根账号隐藏标记。除 `admin999` 自己外，所有其他后台账号（包括同属 `super_admin` 的 `admin`）都不能看到 `admin999` 的账号资料、用户/数量统计、审计记录、业务操作人、设置人或修改时间归属，猜测其用户 ID 发起管理操作时也只返回“用户不存在”。其他超级管理员角色账号仍可使用房间维护、平台收益等角色级专属功能，但不能查看玩家 IP/GPS。
- 后台用户创建、编辑、启停、角色分配和密码重置。
- 角色创建、编辑和权限矩阵配置。
- 功能模块与操作权限管理。
- 菜单可见性和服务端接口权限双重校验。
- 管理操作审计，不记录明文密码。
- 所有后端查询页的“查询、搜索、应用条件、重置”都会显式触发一次新请求；即使查询条件和当前页码没有变化，也会重新读取服务器数据。管理接口的 GET 请求统一禁用浏览器缓存，避免重复查询继续显示旧结果。
- 工作台只展示当前能够准确计算的累计玩家、今日新注册玩家和今日登录玩家。新增玩家严格按北京时间当天 `00:00–24:00` 的 `tbl_Account.sm_reg_time` 首次注册记录统计，不依赖 MySQL 服务器的 UTC `CURDATE()`，并与玩家列表展示的注册日期一致；封号或解封操作不参与统计。今日登录继续按中国运营时间统计。经真实在线人数对照确认，`kbe_entitylog` 中的账号实体包含历史残留，不能代表当前在线；在游戏服务提供权威在线会话接口前，当前在线、今日峰值和小时在线对比均不展示，也不使用最后登录或账号实体数量推算。
- 后台所有日期时间统一按北京时间（UTC+8）显示和筛选，页面顶部常驻显示时区。正式服务器操作系统与 MySQL 会话时区都是 UTC+8（`@@time_zone = SYSTEM`），所以 `mgr_` 审计/用户时间、MySQL `FROM_UNIXTIME` 结果以及游戏流水、房间、注册及代理授权等业务时间**全部已经是北京时间墙上时间，后端一律原值返回，不得再加8小时**；数据库连接 `Loc` 固定为 `Asia/Shanghai`，不要依赖 `time.Local`。（2026-09-19 修：此前按“`mgr_` 与 `FROM_UNIXTIME` 是 UTC”的错误前提加过8小时，导致整页时间偏8小时、16:00 后跨到次日。）
- 系统配置包含“游戏公告设置”和“游戏通知发送”：长期公告采用纯文本保真格式，逐字保留换行、空行、段首缩进和连续空格；编辑区和预览区同步切换客户端“进入大厅公告弹窗”与“大厅公告详情页”，编辑框按对应客户端真实文字宽度、字号和行高进行1:1排版，预览区展示等比例缩略效果，保证两边自动换行位置一致；保存后进行客户端编码回读校验。游戏通知支持立即发送和持久轮播：轮播可增删、排序多条正文，设置开始时间、每条间隔和循环次数，指定轮数完成后自动停止；正文原样显示，不添加系统前缀，背景与普通通知一致。
- 系统配置中的“奖池设置”实时读取9个底皮档位的奖池金额和总额，并展示/配置基础放奖概率、全局不发奖概率、按底皮不发奖概率、预计实际放奖概率及平台固定提留。奖池金额页面按元展示但旧接口按分交互；`reward_modify` 本身按整数元保存。页面支持逐项编辑、修改预览、刷新/恢复、完整基准冲突校验、二次确认、设置后循环回读和失败恢复。
- 系统配置最后一项为仅 `super_admin` 超级管理员角色可见的平台收益：展示今日、本月、累计及指定日期范围的大厅普通抽水、奖池中奖折扣、玩家消费、提现手续费、代理红利支出和抽奖池转入；VIP提现手续费按已完成订单金额2%计入，普通提现通道不收费。玩家消费金额读取 `ABS(add_money)`，消费前后余额直接读取权威字段 `old_money/new_money`，不把 `remark5` 的“余X分”误认为账户余额。游戏原表保持只读，查询按日期索引、最多31天、单并发和4秒超时运行，日汇总缓存到管理库，避免统计拖慢游戏服务器。
- 游戏玩家查询支持玩家 ID、昵称、登录账号、房间、客户端状态和注册日期等组合筛选；列表展示钻石余额和所在俱乐部，点击玩家可在“基本资料、所在俱乐部、房间战绩”三个页签中继续查看账号状态、每个俱乐部的角色/俱乐部金币/上级，以及该玩家在该俱乐部中的全部下级玩家。玩家登录密码重置由独立角色权限控制，不读取旧密码；IP和GPS采用按需接口读取并固定只允许 `admin999` 查看，其他账号完全不渲染该区块，GPS可按WGS84原始坐标跳转高德地图定位。
- 封号管理支持按 6 位游戏玩家 ID 精确封号、填写玩家端提示、查看全部当前已封账号并解除封号；同一页面提供可分页筛选的封号历史，展示封号/解封、当时原因、操作人、时间和成功/失败结果。封号与解封均要求二次确认、服务端回读校验和操作审计，后台用户不受影响。
- 房间维护是 `super_admin` 超级管理员角色专属的**只读**模块：普通后台账号不返回菜单、模块或角色可分配权限，绕过前端直调接口也会被后端拒绝。页面通过 `GET /api/game/room-maintenance/clubs` 调用服务器本机 KB 命令 `查询_大厅_所有房间`，按俱乐部聚合当前活跃房间：一级显示俱乐部名称、俱乐部 ID、创建者、创建者邀请码、房间/玩家/观战/等待带入数量，展开二级显示该俱乐部的房间号、状态、玩法规则、局数、玩家/上限、观战、等待带入、创建时间和备注。支持按俱乐部 ID/名称、创建者 ID/名称或创建者邀请码筛选，按俱乐部分页。列表严格要求旧服务返回 `ret_code=512`、对象型 `ret_result` 和数组型 `result`；失败时清空列表，不回退 `tbl_Account.sm_roomID` 或历史战绩。2026-11-03 起已移除房间解散、全部解散和全局创建开关的页面入口及后台写接口，当前只做展示、不操控房间。
- 玩家优化只实现本游戏实际使用的“发牌优化”，不展示或修改优化2/胡牌优化字段；支持按玩家、状态、概率范围、后台设置账号和历史游戏设置人查询。列表优先显示实际执行操作的 XuanManager 后台账号，没有后台审计的旧数据才回退显示游戏历史设置人，不再把固定 BOSS ID 当作后台操作人。页面提供独立的“新增发牌优化”“调整参数”“删除优化”入口；三种操作均无需填写原因，并分别由 `game.player_optimization.create/update/delete` 角色权限控制，不再硬编码只限超级管理员。页面下方新增可分页筛选的历史记录，直观展示操作前后次数、概率、操作人、时间和成功/失败结果；只有 `admin999` 执行的记录对其他所有账号隐藏，其他后台账号（包括其他 `super_admin` 角色账号）的记录仍按正常权限显示。写操作仍要求显式确认、事务基准校验和完整前后值审计，并由后端使用独立的服务器本机游戏库连接，在 InnoDB 事务中锁定玩家行并一次更新三个发牌优化字段，因此玩家离线时也能操作。
- 支付通道配置采用“通道总览 → 单通道分区编辑 → 全局支付与提现设置 → 保存摘要”的操作流程；可管理支付1～支付12、VIP充值、自助充值、提现等现有通道的启停、玩家端图标、固定/自定义金额、玩家资料、提示文字、支付地址和提现说明。图标可逐通道选择客户端默认、支付宝、银联、微信或其他支付；每个充值或提现通道均可独立一键初始化客户端原有的14家常用银行，并可视化新增、修改、删除和调整银行展示顺序；保存时自动转换为客户端现有配置格式。
- 全局支付与提现设置支持银行卡、支付宝、USDT 三个独立提现开关及 USDT 汇率（1 USDT 对应人民币金额），写入现有哈希配置。USDT 默认关闭，开启必须填写有效汇率；银行/支付宝未配置新开关时兼容旧 `提现类型`，保存时同步旧值。
- 活动管理采用“活动总开关 → 三项活动卡片 → 时间、榜单奖励、玩家说明 → 手数倍率”的操作流程；支持玩家手数榜、玩家赢分榜和代理红利榜的发布/停止、时间区间、领取开关、展示名次、奖励规则与玩家说明。
- 代理管理只读查询，支持 BOSS、代理、盟主、合伙人和总裁分类，按条件筛选、逐级回溯 BOSS 授权链、检查断链/循环/双表冲突，以及查看直属或全部下级代理和玩家。
- 公开注册在俱乐部模式下允许不填写邀请码并保持未绑定；若请求带有邀请码，后台仍会校验并完成代理绑定。标准模式继续要求有效邀请码。后台沿直属上级递归回溯到BOSS，在注册记录中兼容固化直属、二级和三级上级，并按完整直属关系图与数据库当天注册日期幂等重算任意层级代理的累计下级数、今日新增数；完整上级链使用一条更新语句同步。代理查询对缺少营销承载行的顶级BOSS使用同一关系聚合，不伪造注册记录。
- 代理详情展示直属下级获授的盟主分红比例、合伙人比例，以及关系表中的小盟主、大盟主、合伙人和总裁层级槽位。
- 俱乐部管理列出全部俱乐部（群主按账号 `club_make` 反查、代理数按有效邀请码统计），点进去可看该俱乐部成员与代理树：以群主为根，按 `club_agent_info.upper_guuid` 逐层嵌套，可折叠；成员行显示角色、盟主标记、俱乐部积分和邀请码。上级不在本俱乐部、指向自己或成环的成员不会被硬挂进树，而是单独列为「关系异常的成员」并给出核对提示；没有直属上级记录的成员按群主直属兜底，但会在提示里写明这是推断关系。`club_gold` 兼容数字与 `{"俱乐部ID":积分}` 两种历史形态，`-99` 显示为「暂无数据」而不是 0。联盟模式 V2 下，俱乐部所属联盟取 `club_guuid_info.union_id`，俱乐部额度取 `club_guuid_info.union_quota`；不再读已停用的 `club_agent_info.quota`。

新增「联盟管理」（`/game/unions`，权限 `game.union.view`）：列出 `club_union_info` 中的联盟、总群主、联盟池、已分配额度和成员俱乐部数；行内提供「加额度 / 减额度」，点「详情」跳到俱乐部管理并按 `unionId` 过滤出该联盟下的全部俱乐部。额度调整（`game.union.quota_adjust`）调用游戏服 `增加_联盟_额度`（仅 boss），增加传正数、扣减传负数，输入元、换算成分、成功后回读联盟池；俱乐部额度仍由联盟总群主在游戏内用 `授信_联盟_额度` 下发，后台不直接改额度表。回读失败时明确提示人工确认，额度不落后台表，唯一真相在游戏服。
- 代理详情展示累计总红利、已提取红利和剩余红利，并提供可分页筛选的红利收入/提取流水；每笔收入明确显示来源玩家、来源房间、红利基数、计算比例和收益层级。
- 交易记录按玩家 ID 只读查询该玩家全部金币变化，支持游戏输赢、道具、消费、调整等分类，以及方向、业务类型、关键字和日期筛选；展示当前金币、流入、流出、净变化、游戏净输赢和道具支出。
- 交易列表和明细会按业务类型解释关联参数，明确显示房间、局数、累计带入、本次带入、操作后牌桌余额、消费项目和结算类型，不向运营人员展示无标签的原始数字。
- 交易黑名单用于限制指定游戏玩家赠送金币，支持名单总开关以及按6位玩家ID新增、替换和删除用户。查看、新增、修改、删除分别由角色权限控制；所有写操作要求二次确认、页面版本冲突校验、游戏服务写后回读和操作审计。该功能不会封禁账号，也不影响玩家登录或进入房间。
- 房间战绩采用“房间列表 → 房间详情”两级浏览：列表默认按最新战绩排序，支持按房间号、房间名、参与玩家、俱乐部 ID/名称、创建者邀请码和日期筛选、分页；列表和详情展示俱乐部名称、俱乐部 ID、创建者及创建者邀请码，启用地九王时显示“地九王”标签。点击房间后展示开局和结束时间、参与玩家、累计带入、结算返还、最终输赢、全部局次，以及每局玩家身份、下注、芒果、输赢、两组牌面和操作时间线。俱乐部信息来自 `usr_total_score.club_guuid`、`club_guuid_info` 和 `club_invite_code_info`，由后端按页批量补齐。
- 房间战绩的最终输赢优先按“结算返还－累计带入”计算；缺少结算流水时才回退到总战绩原始分数。两者不一致时页面会同时展示并标记数据异常，便于运营核查。
- 玩家管理以钻石余额为主要资产展示；现金余额和平台金币流水不再出现在玩家列表、玩家基本资料或玩家详情页签中。

## 数据与部署约束

- XuanManager 自有数据使用游戏服务器本机 MySQL 实例中的 `webcm` 数据库。
- XuanManager 自有表全部以 `mgr_` 开头，不修改现有游戏业务表。
- `kbedm` 默认作为游戏业务数据的只读来源，与后台自身数据分库；只有公开注册写入 `third_marketing_info`、游戏公告写入 `usr_hash_info` 等已明确批准的流程可以使用独立的服务器本机写连接；发牌优化改由 8890 游戏服命令 `异步_设置_玩家_属性` 写入并回读校验。
- 玩家管理通过后端跨库只读查询 `kbedm.tbl_Account`、`kbedm.kbe_accountinfos`、`kbedm.club_guuid_info` 及俱乐部成员表；玩家列表的所在俱乐部由账号表五个俱乐部关系列合并去重后批量补名称，不逐玩家查询，也不向浏览器暴露数据库连接。
- 代理管理通过后端只读查询 `kbedm.tbl_Account` 和 `kbedm.third_marketing_info`。直属关系以 `upper_guuid` 为主，并与账号表的 `sm_agentID` 交叉校验；不会直接修改代理授权或分红比例。
- 代理红利汇总以 `tbl_Account.sm_all_hongli`、`sm_use_hongli`、`sm_hongli` 为权威值，原始单位按百分之一红利展示；逐笔收入来源读取 `usr_income_info`，不与同内容的 `usr_activity_info_sub_hongli` 正向红利记录重复相加。提取明细只读取明确标记为提取或负数的记录，历史提取明细缺失时页面保留账户累计提取值并提示差额。
- 交易记录以 `kbedm.usr_cash_water` 为唯一完整流水来源，不合并中间表或辅助表，避免重复统计。实际金币变化统一按 `new_money - old_money` 计算；`add_money` 仅作为原始业务金额展示，不能直接当作钱包增减方向。
- 交易黑名单只由后端调用服务器本机旧服务的 `获取_副本_配置数据`、`设置_副本_配置数据`：`npc` 保存逗号分隔的6位游戏玩家ID，`disable_cash_exchange=True/False` 控制名单是否生效。浏览器不直接读写原始配置；修改时提交页面 `revision`，后端写入后循环回读，不一致则尝试恢复原值并记录审计。
- 房间战绩只读关联 `kbedm.usr_total_score`、`kbedm.usr_round_score`、`kbedm.usr_paipu_log` 和结算流水：总战绩提供房间与参与者元数据，逐局战绩提供输赢和牌面，牌谱日志提供下注动作时间线，结算流水用于校正最终输赢。历史房间是否启用地九王以 `usr_total_score.remark` 的第 11 个逗号字段为准：“地方”为是，“标准”为否；`remark2` 中的数值不是地九王开关。
- 玩家详情的所在俱乐部页签要求 `game.player.view`，俱乐部成员树和下级列表复用既有俱乐部管理的只读查询；房间页复用 `game.room_record.view` 权限。没有对应权限的后台角色不能通过玩家详情绕过房间战绩权限。
- 玩家管理的基本资料不展示等级、角色、直属代理和平台金币；所在俱乐部及角色在独立页签展示。发牌优化参数只在独立“玩家优化”模块按对应权限查看和操作，不在玩家基本资料或玩家列表接口中重复返回。
- 游戏账号封禁以 `tbl_Account.sm_client_status` 为权威状态：非空表示封号并作为玩家端提示，清空表示解封。XuanManager 只通过服务器本机旧服务的 `异步_设置_玩家_属性` 修改 `client_status`，不直接更新游戏玩家表；封号列表则从数据库只读查询全部非空状态，因此能包含历史或其他受控工具执行的封号。
- 玩家管理提供钻石发放入口：按玩家发放正整数钻石，只调用游戏服 `异步_增加_玩家_钻石`（仅 boss，正数增加 `Account.stone`），成功后回读 `tbl_Account.sm_stone` 校验并写入操作审计；不提供金币加减入口。旧服务的 `/newmeng793afw/exchange` 金币加减接口仅保留后端兼容，签名密钥仍只通过 `XUAN_GAME_EXCHANGE_SIGN` 运行环境提供，浏览器和审计均不接触，玩家管理页面不暴露该入口。页面同时提供「发放记录」，按后台账号、玩家、发放数量、发放前后余额、原因和时间追溯每次成功发放；发放权限独立为 `game.player.grant_stone`。
- 玩家管理提供「设置管理员」配置：弹窗直接勾选可管理的联盟和未入盟独立俱乐部（`GET /api/game/players/manage-scope/options`），不再手输编号；保存写入游戏服 `异步_设置_俱乐部_管理范围` 并回读 `tbl_Account` 校验。玩家列表的浅红行和「大小BOSS」筛选只看 `union_manage` / `club_manage`，不再看等级 99 / 董事长 / 总裁；列表按名称展示已配置的联盟/俱乐部，配置权限独立为 `game.player.manage_scope`，并发编辑用页面旧值做基准校验，全程写操作审计。
- 玩家登录密码重置只由后端调用服务器本机旧服务 `异步_设置_玩家_属性` 修改 `userPWD`，旧服务按游戏兼容规则保存MD5；成功后回读账号表并同步 `third_marketing_info.player_wxpwd`。密码明文和摘要均不进入接口响应、应用日志或审计。IP/GPS查询直接读取 `tbl_Account.sm_ip/sm_gps`，前后端均只允许 `admin999` 根账号访问并设置禁止缓存；包括 `admin` 在内的其他超级管理员角色账号直调也返回403。
- 联盟模式 V2 的额度调整只由后端调用游戏服 `增加_联盟_额度`（仅 boss、只能增加，单位**分**），浏览器不直接读写游戏库；后台不保存额度账本，唯一真相在游戏服。后台只增加联盟池（总群主额度），不直接改单个俱乐部的 `union_quota`；俱乐部额度由联盟总群主在游戏内用 `授信_联盟_额度` 下发。写入后循环回读联盟池，回读不到时返回 `verified=false` 并提示人工确认，不当作成功。成员树的读写全部只读查询游戏库，推断出来的代理关系（无上级记录按群主兜底）必须在界面明示，不能静默改写。
- 实时房间列表的唯一权威来源是本机旧服务 `查询_大厅_所有房间` 返回的 KB 大厅内存数据；`tbl_Account.sm_roomID` 不是房间实体状态，禁止用于当前房间列表或接口失败时的降级数据。列表接口只读且不返回玩家明细、手牌、牌堆、GPS、IP或发牌优化。全局创建房间开关只由后端调用 `获取_大厅_配置数据`/`设置_大厅_配置数据` 管理 `can_all_create_room`，写入的 `param_value` 必须是JSON布尔值而不是字符串；关闭仅阻止后续新建，不解散现有房间。解散仍通过独立的 `异步_执行_房间_命令` 转发现有房间命令，不直接修改玩家房间字段；`cmd` 必须是事件名纯字符串，不得传嵌套JSON。旧服务的 `ret_code=512/1280` 只表示命令入口已接受，XuanManager 会再次查询 KB 实时房间列表，只有目标消失或进入最终关闭状态才返回已确认成功；复查失败或目标仍存在时只返回待确认状态。
- 发牌优化查询读取 `tbl_Account.sm_optimize01_man/count/chance`，设置人名称通过账号表自关联展示；优化2字段在当前真实数据和客户端流程中均未使用。新增、调整和删除由后端调用游戏服 `异步_设置_玩家_属性` 写入 `optimize01_chance`、`optimize01_count`（删除写 0），写后回读 `tbl_Account` 校验，任一步失败时把两个字段恢复为操作前值。`optimize01_man` 是可选设置人标记、不参与判定，后台不再要求唯一 BOSS。概率支持 1～100（正优化）和 -1～-100（负优化），0 不允许。浏览器不接触游戏库凭据。
- 支付配置继续使用 `usr_hash_info`：`支付管理` 保存启用通道，`支付配置_<通道>` 保存兼容客户端 `btoa(encodeURIComponent(JSON))` 的结构化配置；其中 `icon` 可取 `default/alipay/unionpay/wechat/other`，旧数据缺少该字段时按 `default` 兼容。支付域名和提现说明使用现有独立键。该表为 MyISAM，批量保存必须先做原行快照、写后回读并在失败时显式恢复，不能依赖事务回滚。尚未初始化通道的资料字段统一返回和校验为空数组，避免整体保存首次创建默认通道时把等价的 `null` 与 `[]` 误判为回读失败；回读失败日志只记录不一致字段路径，不记录支付配置正文。
- 活动配置继续通过旧服务的 `获取_老板_配置数据`、`设置_老板_配置数据` 管理 `activity_on`、三套排行榜时间/奖励/领取/展示范围以及 `activity3_list_power`；活动文字继续使用 `usr_hash_info` 的三个“活动文本_”键。旧服务返回 769 表示配置键尚未设置，后台按空值处理。批量修改逐项回读，任何一步失败都尝试恢复已修改参数。
- 长期公告使用 `kbedm.usr_hash_info` 的“系统公告”键，并保持客户端 `btoa(encodeURIComponent(content))` 编码兼容。该表是 MyISAM，保存逻辑不能依赖事务回滚，必须在写入后回读校验并在失败时按原始行显式恢复。
- 即时通知和自动轮播只由后端调用服务器本机 `127.0.0.1:8890` 的 `通知_所有玩家_信息`；正文中的英文逗号会转换为中文逗号，再按旧客户端字段协议封装为 `,,,,<正文>`，不添加“系统广播”等显示前缀。轮播配置保存于 `mgr_notification_carousel_setting/item`，只有正式8891进程启用工作循环，本地和候选进程必须禁用。浏览器不能直接调用旧服务。
- 奖池金额读取和修改只由后端调用本机旧服务的 `异步_获取_奖池_数据`、`异步_设置_奖池_数据`。旧服务和 XuanManager 金额 API 使用整数“分”，运营页面统一以“元”输入和展示并允许两位小数，提交时精确换算为分。放奖控制通过大厅配置读取/设置 `reward_rate`、`reward_nopai_on`、`reward_nopai_dipi`、`reward_modify`；前三项按百分比，平台提留按整数元。修改接口要求提交完整目标值和页面基准值，发现并发变化或未知结构时拒绝写入；成功后必须回读一致才返回成功，部分写入失败则恢复四项原配置。
- MySQL 和旧管理接口 `127.0.0.1:8890` 均只允许 XuanManager 后端在服务器本机访问。
- 浏览器只访问 XuanManager 新后端，不能直连 MySQL 或旧管理接口。
- 数据库密码和初始管理员密码只通过运行环境传入，不得提交到仓库。

## 本地开发

1. 复制 `.env.example` 为不入库的 `.env`，填写本地或安全隧道后的数据库连接。
2. 在 `web/` 执行 `npm install`，然后执行 `npm run dev`。
3. 默认情况下 `/api` 会代理到 `127.0.0.1:8891`；需要只在本机运行前端、连接远程后端时，在不入库的 `web/.env.local` 中配置 `XUAN_DEV_API_TARGET` 和远程路径前缀 `XUAN_DEV_API_PREFIX`。
4. 浏览器访问 `http://127.0.0.1:7458/`。若未配置远程代理，则在 `server/` 执行 `go run ./cmd/xuanmanager` 启动本地后端。

后端启动时会自动执行 `server/migrations/` 中尚未执行的迁移。数据库中没有后台用户时，必须提供 `XUAN_BOOTSTRAP_ADMIN_USERNAME` 和 `XUAN_BOOTSTRAP_ADMIN_PASSWORD` 才会创建首个超级管理员。创建成功后应从运行环境移除初始密码。
