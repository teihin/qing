# XuanManager

XuanManager 是游戏运营团队自己的后台管理系统。后台账号与游戏玩家严格分离；系统设置管理后台自身账号和权限，游戏管理默认只读接入业务数据，仅对注册、公告、奖池、封号等已明确授权的流程开放最小写入能力。

## 当前功能

- 后台账号密码登录、单点会话、会话退出和登录失败锁定；同一后台账号只保留最近一次成功登录，新设备登录后旧设备会话立即失效。后台密码只要求至少 6 位，不强制字符组合，bcrypt 的 72 字节上限保持不变。
- 超级管理员拥有全部权限，不能被普通管理操作停用或降权；其后台账号及全部操作记录仅超级管理员本人可见。普通后台用户的用户列表、数量统计、审计列表、工作台和各业务页面的操作人/修改时间均由后端统一排除超级管理员信息，猜测超级管理员用户 ID 发起管理操作时也只返回“用户不存在”。
- 后台用户创建、编辑、启停、角色分配和密码重置。
- 角色创建、编辑和权限矩阵配置。
- 功能模块与操作权限管理。
- 菜单可见性和服务端接口权限双重校验。
- 管理操作审计，不记录明文密码。
- 工作台只展示当前能够准确计算的累计玩家、今日新增和今日登录，并统一按中国运营时间统计。经真实在线人数对照确认，`kbe_entitylog` 中的账号实体包含历史残留，不能代表当前在线；在游戏服务提供权威在线会话接口前，当前在线、今日峰值和小时在线对比均不展示，也不使用最后登录或账号实体数量推算。
- 系统配置包含“游戏公告设置”和“游戏通知发送”：长期公告支持编辑、玩家端预览、回读校验和清空；即时通知带发送范围确认、玩家端跑马灯预览、全服发送和最近记录。
- 系统配置中的“奖池设置”实时读取9个底皮档位的奖池金额和总额，支持逐项编辑、修改差额预览、刷新/恢复、完整基准冲突校验、二次确认、设置后循环回读和失败恢复。
- 游戏玩家查询支持玩家 ID、昵称、登录账号、代理 ID、代理名字、等级、房间、余额、客户端状态和注册日期等组合筛选；点击玩家可在“基本资料、资金情况、房间战绩”三个页签中继续查看完整金币流水、资金汇总、参与过的房间及每房输赢。玩家登录密码重置由独立角色权限控制，不读取旧密码；IP和GPS采用按需接口读取并固定只允许超级管理员查看，GPS可按WGS84原始坐标跳转高德地图定位。
- 玩家管理支持独立权限控制的客服加减分：选择增加或扣减、填写整数金币和维护原因、预览操作前后余额并二次确认；玩家处于房间中、余额已变化或扣减超过余额时拒绝提交，成功后回读最终余额并记录工单和审计。
- 封号管理支持按 6 位游戏玩家 ID 精确封号、填写玩家端提示、查看全部当前已封账号并解除封号；同一页面提供可分页筛选的封号历史，展示封号/解封、当时原因、操作人、时间和成功/失败结果。封号与解封均要求二次确认、服务端回读校验和操作审计，后台用户不受影响。
- 房间维护通过 `GET /api/admin/hall/rooms` 调用服务器本机 KB 命令 `查询_大厅_所有房间`，以紧凑卡片分页展示当前所有 `Custom` 活跃房间的房间号、房间名、状态、局数、玩家/观战/等待带入人数、创建时间和备注，不展示玩法、规则、房间类型、俱乐部或创建人。列表严格要求旧服务返回 `ret_code=512`、对象型 `ret_result` 和数组型 `result`；失败时不再回退使用可能残留的 `tbl_Account.sm_roomID`。指定房间及全部房间的友好/强制解散继续使用独立权限、二次确认和审计。
- 玩家优化只实现本游戏实际使用的“发牌优化”，不展示或修改优化2/胡牌优化字段；支持按玩家、状态、概率范围、后台设置账号和历史游戏设置人查询。列表优先显示实际执行操作的 XuanManager 后台账号，没有后台审计的旧数据才回退显示游戏历史设置人，不再把固定 BOSS ID 当作后台操作人。页面提供独立的“新增发牌优化”“调整参数”“删除优化”入口；三种操作均无需填写原因，并分别由 `game.player_optimization.create/update/delete` 角色权限控制，不再硬编码只限超级管理员。页面下方新增可分页筛选的历史记录，直观展示操作前后次数、概率、操作人、时间和成功/失败结果；普通后台账号的历史接口与页面会直接排除超级管理员执行的记录。写操作仍要求显式确认、事务基准校验和完整前后值审计，并由后端使用独立的服务器本机游戏库连接，在 InnoDB 事务中锁定玩家行并一次更新三个发牌优化字段，因此玩家离线时也能操作。
- 支付通道配置采用“通道总览 → 单通道分区编辑 → 全局支付与提现设置 → 保存摘要”的操作流程；可管理支付1～支付12、VIP充值、自助充值、提现等现有通道的启停、固定/自定义金额、玩家资料、提示文字、银行列表、支付地址和提现说明，并自动转换为客户端现有配置格式。
- 活动管理采用“活动总开关 → 三项活动卡片 → 时间、榜单奖励、玩家说明 → 手数倍率”的操作流程；支持玩家手数榜、玩家赢分榜和代理红利榜的发布/停止、时间区间、领取开关、展示名次、奖励规则与玩家说明。
- 代理管理只读查询，支持 BOSS、代理、盟主、合伙人和总裁分类，按条件筛选、逐级回溯 BOSS 授权链、检查断链/循环/双表冲突，以及查看直属或全部下级代理和玩家。
- 代理详情展示直属下级获授的盟主分红比例、合伙人比例，以及关系表中的小盟主、大盟主、合伙人和总裁层级槽位。
- 代理详情展示累计总红利、已提取红利和剩余红利，并提供可分页筛选的红利收入/提取流水；每笔收入明确显示来源玩家、来源房间、红利基数、计算比例和收益层级。
- 交易记录按玩家 ID 只读查询该玩家全部金币变化，支持游戏输赢、道具、消费、调整等分类，以及方向、业务类型、关键字和日期筛选；展示当前金币、流入、流出、净变化、游戏净输赢和道具支出。
- 交易列表和明细会按业务类型解释关联参数，明确显示房间、局数、累计带入、本次带入、操作后牌桌余额、消费项目和结算类型，不向运营人员展示无标签的原始数字。
- 交易黑名单用于限制指定游戏玩家赠送金币，支持名单总开关以及按6位玩家ID新增、替换和删除用户。查看、新增、修改、删除分别由角色权限控制；所有写操作要求二次确认、页面版本冲突校验、游戏服务写后回读和操作审计。该功能不会封禁账号，也不影响玩家登录或进入房间。
- 房间战绩采用“房间列表 → 房间详情”两级浏览：列表默认按最新战绩排序，支持按房间号、房间名、参与玩家和日期筛选、分页；列表和详情均不展示创建人，启用地九王时只显示“地九王”标签，未启用时留空。点击房间后展示开局和结束时间、参与玩家、累计带入、结算返还、最终输赢、全部局次，以及每局玩家身份、下注、芒果、输赢、两组牌面和操作时间线。
- 房间战绩的最终输赢优先按“结算返还－累计带入”计算；缺少结算流水时才回退到总战绩原始分数。两者不一致时页面会同时展示并标记数据异常，便于运营核查。
- 当前游戏只使用金币，玩家详情和交易记录均不展示钻石。

## 数据与部署约束

- XuanManager 自有数据使用游戏服务器本机 MySQL 实例中的 `webcm` 数据库。
- XuanManager 自有表全部以 `mgr_` 开头，不修改现有游戏业务表。
- `kbedm` 默认作为游戏业务数据的只读来源，与后台自身数据分库；只有公开注册写入 `third_marketing_info`、游戏公告写入 `usr_hash_info`、发牌优化事务更新 `tbl_Account.sm_optimize01_man/count/chance` 等已明确批准的流程可以使用独立的服务器本机写连接。
- 玩家管理通过后端跨库只读查询 `kbedm.tbl_Account`、`kbedm.kbe_accountinfos`，并关联直属代理昵称；不向浏览器暴露数据库连接。
- 代理管理通过后端只读查询 `kbedm.tbl_Account` 和 `kbedm.third_marketing_info`。直属关系以 `upper_guuid` 为主，并与账号表的 `sm_agentID` 交叉校验；不会直接修改代理授权或分红比例。
- 代理红利汇总以 `tbl_Account.sm_all_hongli`、`sm_use_hongli`、`sm_hongli` 为权威值，原始单位按百分之一红利展示；逐笔收入来源读取 `usr_income_info`，不与同内容的 `usr_activity_info_sub_hongli` 正向红利记录重复相加。提取明细只读取明确标记为提取或负数的记录，历史提取明细缺失时页面保留账户累计提取值并提示差额。
- 交易记录以 `kbedm.usr_cash_water` 为唯一完整流水来源，不合并中间表或辅助表，避免重复统计。实际金币变化统一按 `new_money - old_money` 计算；`add_money` 仅作为原始业务金额展示，不能直接当作钱包增减方向。
- 交易黑名单只由后端调用服务器本机旧服务的 `获取_副本_配置数据`、`设置_副本_配置数据`：`npc` 保存逗号分隔的6位游戏玩家ID，`disable_cash_exchange=True/False` 控制名单是否生效。浏览器不直接读写原始配置；修改时提交页面 `revision`，后端写入后循环回读，不一致则尝试恢复原值并记录审计。
- 房间战绩只读关联 `kbedm.usr_total_score`、`kbedm.usr_round_score`、`kbedm.usr_paipu_log` 和结算流水：总战绩提供房间与参与者元数据，逐局战绩提供输赢和牌面，牌谱日志提供下注动作时间线，结算流水用于校正最终输赢。历史房间是否启用地九王以 `usr_total_score.remark` 的第 11 个逗号字段为准：“地方”为是，“标准”为否；`remark2` 中的数值不是地九王开关。
- 玩家详情中的资金页复用 `game.transaction.view` 权限和主金币流水接口，房间页复用 `game.room_record.view` 权限；没有对应权限的后台角色不能通过玩家详情绕过交易或房间战绩权限。
- 玩家管理的基本资料只展示直属代理，不展示大代理、合伙人或总裁链路；发牌优化参数只在独立“玩家优化”模块按对应权限查看和操作，不在玩家基本资料或玩家列表接口中重复返回。
- 游戏账号封禁以 `tbl_Account.sm_client_status` 为权威状态：非空表示封号并作为玩家端提示，清空表示解封。XuanManager 只通过服务器本机旧服务的 `异步_设置_玩家_属性` 修改 `client_status`，不直接更新游戏玩家表；封号列表则从数据库只读查询全部非空状态，因此能包含历史或其他受控工具执行的封号。
- 玩家加减分只由后端调用服务器本机旧服务的 `/newmeng793afw/exchange`，签名密钥仅通过服务器运行环境 `XUAN_GAME_EXCHANGE_SIGN` 提供。浏览器和审计均不接触签名；当前游戏只操作整数金币，不操作钻石。玩家在房间内也允许增加或扣减账号金币，操作不会直接修改牌桌已经带入的积分，仍必须通过页面基准余额、余额不足校验、显式确认、服务回读和审计。
- 玩家登录密码重置只由后端调用服务器本机旧服务 `异步_设置_玩家_属性` 修改 `userPWD`，旧服务按游戏兼容规则保存MD5；成功后回读账号表并同步 `third_marketing_info.player_wxpwd`。密码明文和摘要均不进入接口响应、应用日志或审计。IP/GPS查询直接读取 `tbl_Account.sm_ip/sm_gps`，接口在后端强制校验超级管理员身份并设置禁止缓存；普通角色即使直接请求也返回403。
- 实时房间列表的唯一权威来源是本机旧服务 `查询_大厅_所有房间` 返回的 KB 大厅内存数据；`tbl_Account.sm_roomID` 不是房间实体状态，禁止用于当前房间列表或接口失败时的降级数据。列表接口只读且不返回玩家明细、手牌、牌堆、GPS、IP或发牌优化。解散仍通过独立的 `异步_执行_房间_命令` 转发现有房间命令，不直接修改玩家房间字段。
- 发牌优化查询读取 `tbl_Account.sm_optimize01_man/count/chance`，设置人名称通过账号表自关联展示；优化2字段在当前真实数据和客户端流程中均未使用。新增、调整和删除不调用旧8890在线属性接口，而是由后端通过独立的本机游戏库连接执行事务：`SELECT ... FOR UPDATE` 锁定玩家行、校验页面基准、一次更新设置人/次数/概率并在提交前回读。SQL 只允许操作这三个白名单字段，浏览器不接触游戏库凭据。
- 支付配置继续使用 `usr_hash_info`：`支付管理` 保存启用通道，`支付配置_<通道>` 保存兼容客户端 `btoa(encodeURIComponent(JSON))` 的结构化配置，支付域名和提现说明使用现有独立键。该表为 MyISAM，批量保存必须先做原行快照、写后回读并在失败时显式恢复，不能依赖事务回滚。
- 活动配置继续通过旧服务的 `获取_老板_配置数据`、`设置_老板_配置数据` 管理 `activity_on`、三套排行榜时间/奖励/领取/展示范围以及 `activity3_list_power`；活动文字继续使用 `usr_hash_info` 的三个“活动文本_”键。旧服务返回 769 表示配置键尚未设置，后台按空值处理。批量修改逐项回读，任何一步失败都尝试恢复已修改参数。
- 长期公告使用 `kbedm.usr_hash_info` 的“系统公告”键，并保持客户端 `btoa(encodeURIComponent(content))` 编码兼容。该表是 MyISAM，保存逻辑不能依赖事务回滚，必须在写入后回读校验并在失败时按原始行显式恢复。
- 即时通知只由后端调用服务器本机 `127.0.0.1:8890` 的 `通知_所有玩家_信息`；正文中的英文逗号会转换为中文逗号，再按旧客户端要求封装为 `,,,,####<正文>`。浏览器不能直接调用旧服务。
- 奖池读取和修改只由后端调用本机旧服务的 `异步_获取_奖池_数据`、`异步_设置_奖池_数据`。旧服务和 XuanManager HTTP API 使用整数“分”，运营页面统一以“元”输入和展示并允许两位小数，提交时精确换算为分。修改接口要求完整提交9个已知皮池和页面基准值，发现并发变化或未知新皮池时拒绝写入；成功后必须回读一致才返回成功。
- MySQL 和旧管理接口 `127.0.0.1:8890` 均只允许 XuanManager 后端在服务器本机访问。
- 浏览器只访问 XuanManager 新后端，不能直连 MySQL 或旧管理接口。
- 数据库密码和初始管理员密码只通过运行环境传入，不得提交到仓库。

## 本地开发

1. 复制 `.env.example` 为不入库的 `.env`，填写本地或安全隧道后的数据库连接。
2. 在 `web/` 执行 `npm install`，然后执行 `npm run dev`。
3. 默认情况下 `/api` 会代理到 `127.0.0.1:8891`；需要只在本机运行前端、连接远程后端时，在不入库的 `web/.env.local` 中配置 `XUAN_DEV_API_TARGET` 和远程路径前缀 `XUAN_DEV_API_PREFIX`。
4. 浏览器访问 `http://127.0.0.1:7458/`。若未配置远程代理，则在 `server/` 执行 `go run ./cmd/xuanmanager` 启动本地后端。

后端启动时会自动执行 `server/migrations/` 中尚未执行的迁移。数据库中没有后台用户时，必须提供 `XUAN_BOOTSTRAP_ADMIN_USERNAME` 和 `XUAN_BOOTSTRAP_ADMIN_PASSWORD` 才会创建首个超级管理员。创建成功后应从运行环境移除初始密码。
