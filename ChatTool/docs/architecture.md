# ChatTool 架构与关键流程

## 组件边界

```text
游戏客户端普通/VIP入口
  │ Tool.encrypt(玩家ID、昵称、通道、时间戳)
  ▼
手机浏览器 `?d=<AES密文>` ── HTTP / IP ──► Caddy `/chattool/`
                                              │
                                              ▼
                                      ChatTool `127.0.0.1:8893`
                                        ├─ webcm.chat_*（消息、会话、客服、审计）
                                        └─ 私有媒体目录（图片、视频、文件）
                                              ▲
                                              └──── HTTP / SSE ──── 多客服工作台
```

浏览器不连接 MySQL，也不调用游戏内部 8890。玩家资料由游戏客户端直接加密提供，ChatTool只校验密文格式、字段和有效时间，不经过KB授权。

公网链路按用户要求使用纯 HTTP。AES 密文避免玩家资料明文出现在入口URL中，但客户端内置口令可被逆向，因此不能把它描述成可靠防伪。建立会话后的 Cookie、权限和 CSRF 继续防止普通网页越权。

## 自动分配

1. 玩家提交有效期内的加密资料，复用其尚未结束的会话；否则创建新排队会话。
2. 普通入口使用 `general`，VIP充值入口使用 `vip_recharge`；同一玩家只复用同通道未结束会话。
3. 只在会话所属通道内，从“已启用、状态在线、心跳未超时、未达到接待上限”的客服中选择：
   - 当前活动会话数最少；
   - 活动数相同时，最久没有被分配的客服优先；
   - 仍相同时按客服 ID 稳定排序。
4. 分配和会话状态更新在同一个数据库事务中完成并写入 `chat_assignment_log`。
5. 客服主动离线、心跳超过阈值或账号被停用时，其活动会话重新进入原通道队列。
6. 单次派单循环最多处理 50 个会话；没有在线客服的通道不会阻塞其他通道派单。

客服身份、会话列表/详情、未读、媒体下载、输入状态、实时事件、主动接入和转接均在服务端再次校验 `channel_code`，不能依靠前端筛选实现隔离。主管的“全部会话”也只显示主管账号所属通道。

当前实时事件中心面向单个 ChatTool 实例。消息本身已经持久化，SSE 断线后前端会重连并重新读取消息；若未来部署多个 Go 实例，应把实时发布层换成 Redis/NATS，并继续让 MySQL 作为权威记录。

## 数据表

- `chat_channel`：可扩展客服通道；当前内置普通聊天和VIP充值。
- `chat_agent` / `chat_agent_session`：客服账号、角色、所属通道、接待量、在线状态和会话。
- `chat_player` / `chat_player_session`：客户端提供的玩家资料快照和浏览器会话。
- `chat_conversation`：队列、分配、已读、首响和结束状态。
- `chat_message` / `chat_media`：消息和媒体元数据。
- `chat_assignment_log`：自动分配、接入、转接、重排和结束。
- `chat_quick_reply`：快捷回复。
- `chat_satisfaction`：玩家服务评价。
- `chat_player_memo`：仅客服可见、跨会话保留的玩家备忘。
- `chat_audit_log`：关键安全和管理操作。

所有表不创建外键，兼容 `webcm` 当前账号没有 `REFERENCES` 权限的环境；合法性由事务和服务端查询校验。

## 内容保留与清空

- 后台每5分钟检查一次，永久清除创建满 `CHAT_MESSAGE_RETENTION`（默认48小时）的文字、系统消息、内部备注、图片、视频和文件。
- 媒体先在私有目录原子改名隔离，再在事务内删除消息和媒体记录；事务失败会恢复文件，提交成功后才删除磁盘文件。
- 客服手动清空要求显式二次确认，同样同时清除数据库和磁盘，并向玩家会话与本通道客服推送刷新事件。
- 会话、派单日志、评价、审计和玩家备忘不属于聊天内容保留范围。
